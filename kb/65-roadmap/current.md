Прямая работа Евы с клиентами через Telegram. Архитектура принята в [ADR-013](../90-decisions/ADR-013-eva-agent-architecture.md).

### Последовательность работ по Еве (крупными шагами)

> Согласованный с Максимом порядок. **Зафиксирован 2026-05-22** (восстановлен после того, как прошлая сессия не была закрыта по протоколу и план потерялся). Детальный чек-лист ниже разложен по этим шагам.

1. **Настроить основу Евы** — ✅ **сделано.** Архитектура (ADR-013), 4 слоя памяти, Postgres под Еву на VPS.
2. **Карточки клиентов и товаров под мультипроектность + работу Евы** — 🟡 **почти.** ADR-014 + К1–К3 задеплоены. Хвост: ретег товаров по проектам.
3. **Механизм завода нового клиента: Ева ↔ менеджер** — 🟢 **в работе.** Онбординг: менеджер заводит клиента ведённым диалогом с Евой (опрос «один вопрос = одно поле»), клиент активен сразу. Роль + процесс + сценарий Евы + должностная инструкция спроектированы 2026-05-22; дальше — реализация в коде.
4. **Взаимодействие Ева ↔ клиенты** — ⬜ **впереди.** Приём заявок, напоминания, баланс, эскалация. На этом этапе **определяем границы полномочий Евы** (ADR-013 п. 9) и донастраиваем, как она работает.

**Шаг 3 — механизм завода нового клиента: Ева ↔ менеджер** 🟢 в работе
- [x] **Спроектирован онбординг клиента** (2026-05-22, Обязательство 5 ADR-015): роль [sales-manager](../30-roles/to-be/sales-manager/README.md) + процесс [client-onboarding](../30-roles/to-be/sales-manager/processes/client-onboarding.md) + сценарий Евы [client-onboarding](../50-agents/eva/scenarios/client-onboarding.md) + должностная инструкция [for-team/sales-manager](../80-instructions/for-team/sales-manager.md). Механика: менеджер заводит клиента **диалогом с Евой** (ведённый опрос «один вопрос = одно поле», кнопки для полей-выбора, возможность прервать), два статуса `onbStatus` = **Активен / На паузе** (клиент активен сразу при заводе; привязка `tgChatId` через deep-link — опциональный бонус, у клиента может не быть Telegram). Поля: имя (уникальное), контактное лицо, проекты (мультивыбор, только активные), сегмент/уровень цены/тип продажи (по одному на клиента), менеджер (авто = спрашивающий), WhatsApp (обязат., межд. формат), Telegram/`tgChatId` (авто при активации), Яндекс-навигатор + фото места (Ева предлагает заполнить сразу).
- [ ] **Реализация онбординга в коде** (после уточнения сценария): инструмент Евы `create_client` (ведённый диалог), **новые поля карточки клиента `contactName`** (обязательное, имя контактного лица — Ева им обращается) **и `onbStatus`** (Активен/Пауза, миграция на чтении: существующие = Активен) — добавить в форму trade_app и хранение, проверка уникальности имени `n` (и в Еве, и в форме trade_app), генерация и показ deep-link в карточке, обработчик `/start onb_<token>` (привязка `tgChatId`+`tg`, активация), отчёт менеджеру. **Цель — дать менеджерам тестировать завод клиентов.**
- [ ] ⚠️ **Развязать `onbStatus` ↔ ADR-014 `onboarding` при кодировании.** Это **разные** поля: `onbStatus` (Активен/На паузе — жизненный цикл клиента, вводим сейчас на Шаге 3) ≠ `onboarding` ([ADR-014](../90-decisions/ADR-014-client-project-profile.md) стр. 62 — «статус знакомства с Евой», на этапе Ева↔клиент, Шаг 4). Не задублировать и не перепутать как «два статуса про онбординг». Заодно зафиксировать **финальные значения** `onbStatus` (русские лейблы «Активен»/«На паузе» vs англ. коды — старая запись changelog от 2026-05-22 ошибочно содержала `draft/active/paused`, отменено).
