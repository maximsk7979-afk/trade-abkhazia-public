# Боевой запуск розницы — дорожная карта

> **Что это.** Пошаговый план от текущего состояния (прототип дизайна без бэкенда +
> оптовое ядро) до **боевой розничной торговли**: клиент заказывает продукты в
> Telegram-приложении, мы закупаем утром на рынке, курьер развозит по Абхазии, деньги и
> товар учтены системой.
>
> Составлена 2026-08-30 после сплошного разбора кода ядра (`code/trade-api/*`,
> `trade_app_v3.jsx`, `code/mini-app`, `code/retail-app`) и базы знаний.

## 0. Рамка запуска (ответы владельца 2026-08-30)

| Параметр | Решение |
|---|---|
| Срок | **Жёсткого срока нет — делаем полно.** Запускаемся, когда контур закрыт целиком, включая отчётность и уведомления |
| Ассортимент | **Не ограничиваемся овощами/фруктами/зеленью.** Перечень товарных групп владелец даёт отдельно → отдельный пункт Фазы Р-0 |
| Исполнители | **Нанимаем отдельного курьера под розницу.** Закупка — существующий закупщик |
| География | **Вся Абхазия, Гагра–Очамчира.** Значит зоны, дни выезда по направлениям и маршрут — не опция, а часть запуска |

Следствия рамки: (1) «быстрый MVP с обрезанным учётом» отпадает — строим полный контур;
(2) маршрут доставки [GAP-051](../00-meta/gaps.md#gap-051) переходит из «позже» в
**обязательные** (Гагра–Очамчира — это ~160 км вдоль побережья); (3) ассортимент шире овощей
означает новых поставщиков, новые единицы измерения и, возможно, холодовую цепь — это
отдельная фаза мастер-данных, а не строка в справочнике.

## 1. Definition of Done — что считаем «боевым запуском»

Запуск состоялся, когда **все** пункты верны на проде, на реальных деньгах:

1. Незнакомый человек открывает бота, регистрируется сам, видит витрину с сегодняшними
   ценами и наличием, оформляет заказ с адресом и получает подтверждение.
2. Закупщик утром видит **сводный лист** (что купить, сколько, для кого), закупает на
   рынке, деньги списаны с его кошелька движком fin-ops.
3. Курьер видит маршрут по зоне, взвешивает на точке, фиксирует факт-сумму, принимает
   наличные — деньги падают в его кошелёк, долг клиента 0.
4. Клиент получает уведомления по этапам и видит в истории **факт**, а не заказанное.
5. Владелец видит **P&L проекта «Розница» отдельно от опта**, сходящийся с кассой и
   балансами; товарооборот розницы сверяется; усышка проведена.
6. Отмена любой операции даёт симметричное сторно (касса + баланс + P&L + FIFO).
7. Роли гейтятся fail-closed; клиент видит только своё; курьер — только свою доставку.
8. Есть письменные инструкции для курьера, закупщика, оператора; сценарии Евы наполнены.

Пока хоть один пункт открыт — это пилот, а не запуск.

## 2. Метод работы

Тот же, что дал результат на банане и финблоке ([[project_banana_golive_method]] в памяти,
Обязательства 5/6/7 ADR-015/022): **фаза за фазой, каждая — по четырём слоям**:

① TradeApp (веб, владелец/офис) · ② Ева · ③ мини-апп (клиент и сотрудники) · ④ база знаний
(роль → процесс → сценарий Евы → должностная инструкция).

Правила, не подлежащие обсуждению внутри фаз:
- **Матрица 4 плоскостей до кода** (касса × баланс × P&L × склад/COGS) + судьба товара +
  симметрия сторно — письменно, видимо владельцу.
- **Ролевая привязка** (кто инициирует / решает / исполняет / видит + поверхность),
  роли — только из [role-catalog](../35-security/role-catalog.md), гейт fail-closed.
- **Единый доменный слой**: витрина, Ева и TradeApp зовут один расчёт. Комментарий
  «зеркалит» в новом коде розницы — красный флаг, повод остановиться.
- Фаза закрыта только после **боевой приёмки на проде** со сторно и откатом.

## 3. Ревизия «что есть на самом деле» (сверено по коду 2026-08-30)

Карта функций [retail-app-feature-map.md](../40-system/retail-app-feature-map.md) писалась
до чтения кода и в трёх местах оптимистична. Ниже — факт.

### Есть и переиспользуется как есть

| Механика | Где в коде | Годность для розницы |
|---|---|---|
| Заказ-корзина с замороженной ценой | `order-service.buildMixedCartSale`, `order-model.js` | Полная. Модель строк (`miniOrder.lines`) годится под розницу |
| План закупки из заказов | `buyer-service.orderPlan` / `remainingPlan` | **Это и есть «закупочный лист»** — агрегация заявок дня по позициям |
| Закупка на рынке за нал | «Рынок (наличные)», `cashMarket`, `mpId`, `/api/mini/purchase` | Полная: каждая закупка отдельной записью, оплата 100% нал, баланс 0 |
| Товар «с колёс» сразу в развоз | `delivery-service.loadFromTrip` (партии `via:"field"`) | **Ключ к рознице:** товар не обязан лежать на складе |
| Отгрузка по точкам с факт-весом | `/api/mini/dlv/points`, `/dlv/ship`, `shipLineTotal` | Полная. Взвешивание на точке уже есть |
| Деньги | движок fin-ops ADR-027, мини-касса, сторно комплектом | Полная. Новых денежных механик розница не вводит |
| FIFO/COGS, усышка, сверка остатков | `fifo-batch`, `stock-service`, `shrinkage-service` | Полная |
| Изоляция клиента | `mini-auth.verifyInitData` + скоуп по `clientId` | Полная |

### Заявлено готовым, но по факту отсутствует

| Утверждение карты | Факт по коду | Последствие |
|---|---|---|
| «P&L / касса / баланс по рознице ✅ — сервисы работают по проекту» | **Оси проекта в отчётах нет.** `pnl-service`/`turnover-service` не знают слова `projectId`; `/api/pnl` и `/api/turnover` принимают только `from/to/office`. У продажи (`sales`) поля проекта нет вовсе | Розница и опт лягут в **один P&L**. Считать доходность розницы будет нечем → [GAP-085](../00-meta/gaps.md#gap-085) |
| «Розничный прайс — 🔶 достраиваем» | Прайс-механизмов **три и они несвязны**: банановая сетка (`banana-pricing`), ₽/кг весовых (`weighted-pricing`, плоская цена владельца), прайс opt/mid/ret (`PriceListMod` — **считается в браузере** из `buildCostMap(trips…)`, то есть **только из рейсов**). Себестоимости из местной закупки (ЗК) прайс не видит; `trade-pricelist-v1` на бою пуст | Розничной цены построить не из чего: закупка на рынке в базу цены не попадает. Плюс риск четвёртой копии → [GAP-086](../00-meta/gaps.md#gap-086) |
| «Авторизация ✅ Telegram initData» | Верно для **существующего** клиента. Незнакомец получает `role:'unknown'` → 403 на всех эндпоинтах. Само-регистрации нет нигде | Розница без самрегистрации **невозможна**: клиента заводит менеджер вручную → [GAP-087](../00-meta/gaps.md#gap-087) |
| «Заказ на день ✅» | Заказ **жёстко привязан к рейсу**: `isDayOpen` требует существующий `trip` на дату, иначе 409. Авто-создание дней сознательно отменено 2026-06-11 | Без рейса на дату витрина розницы закрыта. Нужен планировщик дней проекта |
| «Статусы заказа 🔶 есть» | Статусы **оптовые** (Новая → Отгружено), клиенту не показываются как лента этапов; в прототипе «доставлен» — таймер в браузере | Клиент не увидит, что происходит с заказом → [GAP-083](../00-meta/gaps.md#gap-083) |

Мелкий, но показательный дефект того же класса: `delivery-service` при приёмке возвратов
проставляет партиям `projectId: "PRJ-001"` **константой** (строки 347/373/388) — возврат
розничного товара уехал бы в проект опта.

### Принципиально новое (нет ни в каком виде)

Адрес клиента и зоны · слоты и стоимость доставки · маршрут объезда · самрегистрация ·
розничная ценовая политика · поиск/фильтры витрины · фото своего товара · черновик корзины
на сервере · клиентские уведомления по этапам · «сегодня на рынке» (наличие в модели
закупки-под-заказ).

## 4. Архитектурные решения (принимаю как архитектор, владелец подтверждает бизнес-цифры)

**Р-А1. Розница — отдельный проект `PRJ-005 «Розница»`** (ADR-009), не вторая система.
Справочники (товары, SKU, клиенты, кошельки, статьи) общие; разделение — по `projectId`.

**Р-А2. «День розницы» — это существующая сущность рейса (`trip`) проекта PRJ-005**, а не
новый документ. Обоснование: у рейса уже есть план из заявок, закупка у поставщика, приёмка,
выдача «с колёс», себестоимость, партии и `projectId`. Новая сущность = второй домен над тем
же смыслом (нарушение ADR-025). Что достраиваем: **расписание дней проекта** (день создаётся
сам, иначе витрина закрыта каждое утро) и **термины интерфейса** («День 30.08», не «Рейс Р-014»).

**Р-А3. Единый прайс-сервис** (`price-service` на сервере + ADR): градации `opt/mid/ret`,
база себестоимости — **последняя закупка позиции из любого источника** (рейс ИЛИ местная
закупка ЗК), политика наценки по группе товара, пол цены fail-closed (не ниже
себестоимости с доставкой). Витрина, Ева, TradeApp и мини-апп читают **один** канон.
Поглощает `weighted-pricing` и браузерный `PriceListMod`; банановая сетка остаётся частным
случаем градации. Закрывает [GAP-034](../00-meta/gaps.md#gap-034)/[GAP-040](../00-meta/gaps.md#gap-040)/[GAP-082](../00-meta/gaps.md#gap-082).

**Р-А4. Самрегистрация клиента розницы** — из `initData`: неизвестный `tgChatId` →
создаётся карточка клиента (проект PRJ-005, `priceLevel: ret`, статус «Новый»), телефон
обязателен, адрес — при первом заказе. Модерация **не блокирует** первый заказ (иначе
конверсия нулевая), но действуют ограничения новичка: лимит суммы первого заказа, только
нал/перевод при получении, стоп-лист. Ограничители — бизнес-цифры владельца.

**Р-А5. Курьер — роль `expeditor`** (в каталоге ролей это ровно «комплектация, отгрузка по
точкам, развоз клиентам»), при собственном авто дополнительно `driver`. **Новую роль
`courier` не заводим** — ADR-022 запрещает плодить роли вне `STAFF_ROLES`. Курьеру
заводится ₽-кошелёк; наличные сдаёт через мини-кассу, как менеджеры на развозе.

**Р-А6. Стоимость доставки — отдельная строка дохода**, а не скидка к товару: иначе
товарная маржа искажается и «бесплатная доставка от 3000 ₽» съедает её незаметно. Расход
на курьера/транспорт — opex B3. Полная матрица — в Фазе Р-7.

**Р-А7. Отмена после закупки** (правило на подтверждение владельцем): купленный товар
остаётся партией на складе розницы и перепродаётся следующим днём; испорченный — списание
B2 через усышку. Клиенту-рецидивисту — предоплата или стоп-лист.

## 5. Фазы

Порядок обязателен: каждая следующая опирается на предыдущую. Оценки — в сессиях работы
(1 сессия ≈ один рабочий заход), не в календарных днях.

---

### Р-0. Решения, мастер-данные, каркас проекта — *фундамент*

**Зачем.** Без справочников и параметров проекта любая витрина будет читать выдуманные
данные, как сейчас прототип.

**Бизнес-вход от владельца (блокирует фазу):**
1. **Перечень товарных групп розницы** — полный список того, чем торгуем (по требованию
   владельца отдельным пунктом). Для каждой группы: закупаем на рынке или у поставщика,
   весовой/штучный/тарный товар, нужна ли холодовая цепь, срок годности.
2. Стартовые параметры проекта: отсечка (04:00 согласована в прототипе), дни выезда по
   направлениям, стоимость доставки по зонам, порог бесплатной доставки (3000 ₽ в прототипе),
   лимит первого заказа новичка.
3. Кто курьер (человек в `trade-cat-staff`), какой у него кошелёк.

**Работы:**
- ① TradeApp: проект `PRJ-005`; **параметры проекта** — отсечка, слоты, зоны, тариф
  доставки, порог, расписание дней ([GAP-081](../00-meta/gaps.md#gap-081)); товарные группы
  и SKU по перечню; поля SKU **шаг заказа + группа + `approx` + тара**
  ([GAP-079](../00-meta/gaps.md#gap-079), исходные значения — `code/retail-app/step-grid.xlsx`);
  рыночные поставщики (`cashMarket`) по новым группам; кошелёк курьера.
- ② Ева: знает о проекте «Розница» и его параметрах (без клиентских диалогов пока).
- ③ Мини-апп: без изменений.
- ④ БЗ: `kb/20-domain/retail/` — модель розничной сделки; роль курьера (`expeditor`,
  розничный контур) в `30-roles/to-be/`; обновить `role-permissions`.

**Приёмка:** в вебе заведён проект с параметрами; SKU розницы имеют шаг/группу/`approx`/тару;
тестовая местная закупка (ЗК) по новой группе проходит и даёт партию с `projectId: PRJ-005`.

---

### Р-1. Единый прайс и розничная цена — *без этого витрина не имеет цен*

**Работы:**
- ① Сервер: `price-service` (Р-А3) — градации, база себестоимости из рейсов **и** ЗК,
  наценка политикой на группу, пол цены fail-closed, ₽/кг для весовых и ₽/место для тары
  («средний опт» — [GAP-082](../00-meta/gaps.md#gap-082)); `/api/price` как единственный
  источник; `PriceListMod` в вебе — делегат на сервер (снимаем браузерный расчёт).
- ② Ева: отвечает о цене по градации собеседника (розничный клиент — розница/средний опт,
  оптовая градация ему не видна ни при каких условиях).
- ③ Мини-аппы (оптовый и розничный) читают `/api/price`.
- ④ БЗ: ADR «Единый прайс»; `20-domain/pricing.md` переписать под три градации и источники
  себестоимости; правила наценки — в `accounting-rules`.

**Приёмка:** одна и та же позиция в вебе, Еве и витрине даёт **бит-в-бит одну цену**;
попытка задать «средний опт» ниже себестоимости с доставкой — отказ 400; товар без цены
на витрине не показывается (fail-closed, не «скидка без скидки»).

---

### Р-2. Личность розничного клиента — *без этого никто не сможет заказать*

**Работы:**
- ① TradeApp: карточка розничного клиента (телефон, адреса, зона, статус, лимит), очередь
  новых клиентов на просмотр, стоп-лист.
- ② Ева: сценарий знакомства с розничным клиентом (уже есть каркас для опта).
- ③ Мини-апп: **самрегистрация** ([GAP-087](../00-meta/gaps.md#gap-087)) — `initData` →
  создание клиента, обязательный телефон, адрес с картой; профиль (несколько адресов);
  всё состояние с сервера, `localStorage` только как кеш ([GAP-083](../00-meta/gaps.md#gap-083)).
- ④ БЗ: процесс «завод розничного клиента»; политика новичка; изоляция ([GAP-030](../00-meta/gaps.md#gap-030)).

**Приёмка:** с чистого Telegram-аккаунта: регистрация → профиль → адрес; второй аккаунт
не видит данные первого (проверка изоляции); клиент из стоп-листа получает отказ на заказ.

---

### Р-3. Витрина на реальных данных — *прототип превращается в приложение*

**Работы:**
- ③ Мини-апп розницы: каталог из справочника (группы, шаг, `approx`, тара — не из `app.js`);
  цены из `/api/price`; **фото своего товара** ([GAP-080](../00-meta/gaps.md#gap-080)) через
  фото-инфраструктуру ADR-016; поиск (перенести автоподбор на серверные группы); «сегодня на
  рынке» (что реально готовы закупить сегодня); черновик корзины на сервере.
- ① TradeApp: управление витриной — что показываем сегодня, стоп-позиции.
- ④ БЗ: `retail-mini-app.md` из «прототипа» в «боевой», описать состав экранов.

**Приёмка:** правка цены/шага/фото в вебе → изменение в витрине без деплоя; корзина
переживает перезапуск приложения и переход на другое устройство.

---

### Р-4. Заказ и день закупки — *ядро розничного потока*

**Матрица 4 плоскостей — пишем до кода** (розничная сделка разобрана в карте функций,
достроить: доставка как доход, отмена после закупки, новичок с лимитом).

**Работы:**
- ① TradeApp: «День розницы» (рейс PRJ-005) — расписание автосоздания, отсечка из параметров
  проекта, список заказов дня, ручное закрытие приёма.
- ③ Мини-апп клиента: оформление (день доставки, слот, адрес, комментарий, стоимость
  доставки по зоне, порог бесплатной), правка/отмена до отсечки, лента этапов заказа.
- ③ Мини-апп сотрудника: заказы дня у оператора.
- ② Ева: приём/правка заказа голосом-текстом для клиента, статус заказа.
- ④ БЗ: процесс «розничный заказ»; правило отмены после закупки (Р-А7).

**Приёмка:** заказ проходит с телефона клиента; после 04:00 день закрывается и заказ
уезжает на следующий; отмена до отсечки — чистая, после закупки — по правилу Р-А7.

---

### Р-5. Закупка под заказ — *утро на рынке*

**Работы:**
- ③ Мини-апп закупщика: **закупочный лист дня** (агрегат `orderPlan`: позиция → сколько →
  для скольких клиентов; тарный спрос — местами, не килограммами); факт-закупка с ценой и
  весом; недобор/замена позиции (что делать, если помидоров не оказалось) с уведомлением
  клиента; фото товара на рынке → в витрину ([GAP-080](../00-meta/gaps.md#gap-080)).
- ① TradeApp: контроль дня — план/факт/недобор, себестоимость дня.
- ④ БЗ: процесс закупщика для розницы (дополнение к `banana-procurement`).

**Приёмка:** деньги списаны из ₾/₽-кошелька закупщика движком fin-ops; партии созданы с
`projectId: PRJ-005`; недобор виден и клиенту, и оператору; отмена закупки — сторно комплектом.

---

### Р-6. Сборка, маршрут, доставка — *самая объёмная фаза при географии Гагра–Очамчира*

**Работы:**
- ① TradeApp: зоны и тарифы; формирование развоза по зоне/дню; назначение курьера.
- ③ Мини-апп курьера: маршрут с порядком точек ([GAP-051](../00-meta/gaps.md#gap-051), с
  географией всей Абхазии становится обязательным), навигация по `ynavUrl`, взвешивание на
  точке, факт-сумма, приём нала/перевода → кошелёк курьера, частичный отказ и возврат,
  статусы точки.
- ③ Мини-апп клиента: этапы «принят → закупаем → в пути → доставлен», факт-сумма после
  взвешивания.
- ④ БЗ: должностная инструкция курьера; процесс развоза розницы.

**Приёмка:** развоз из 5+ точек в двух зонах; факт-вес меняет сумму; нал у курьера сходится
до копейки; возврат непроданного оприходован в **розничный** проект (а не в PRJ-001 —
исправить константу в `delivery-service`).

---

### Р-7. Деньги и отчётность розницы — *без этого запуск слепой*

**Работы:**
- ① Сервер: **ось проекта** в отчётах ([GAP-085](../00-meta/gaps.md#gap-085)) — `projectId`
  у продажи (наследуется от дня/партии), фильтр `project` в `/api/pnl`, `/api/turnover`,
  кассе и балансах; P&L розницы отдельным разрезом; доставка отдельной строкой дохода (Р-А6);
  разрез по градации цены (розница vs тара «средний опт»).
- ① TradeApp: вкладка отчётов с переключателем проекта.
- ② Ева: `get_pnl`/`get_cash_all` понимают проект.
- ④ БЗ: правила учёта розницы в `accounting-rules`; сверка «три отчёта бьются» для розницы.

**Приёмка:** P&L «Розница» + P&L «Опт» = общий P&L до копейки; касса розничного дня сходится
с наличными курьера; товарооборот розницы даёт расхождение 0.

---

### Р-8. Уведомления и Ева — *связь с клиентом*

**Работы:** реализация [GAP-073](../00-meta/gaps.md#gap-073) / [ADR-026](../90-decisions/ADR-026-notifications-unified-layer.md)
в части розницы: `notify-core` (единый резолв, дедуп, ретрай, важность), клиентские
уведомления по этапам заказа, уведомления курьеру и закупщику, тихие часы. Ева — консультация
розничного клиента (наличие, цена, статус, повтор заказа).

**Приёмка:** клиент получает ровно по одному сообщению на этап; отмена/недобор доходят;
сотрудников не заваливает.

---

### Р-9. Пилот и боевой запуск

1. **Сквозной e2e-прогон** на синтетическом дне ([GAP-064](../00-meta/gaps.md#gap-064) —
   харнесс переиспользуем), вечером, с бэкапом и полной очисткой.
2. **Тестовый день с сотрудниками** — заказы от своих, реальная закупка, реальный развоз.
3. **Ограниченный пилот** — один город (Сухум), 5–10 заказов в день, 1–2 недели; ежедневная
   сверка касса/склад/P&L; сбор дефектов.
4. **Расширение на зоны** Гагра–Очамчира по дням выезда.
5. **Запуск**: инструкции выданы, обучение курьера и оператора проведено, метрики
   (заказы/день, средний чек, маржа, доля отмен, недобор) считаются в системе.

**Критерий выхода:** три дня подряд без ручных правок данных в БД.

## 7. Риски

| Риск | Почему опасен | Что делаем |
|---|---|---|
| **Смешение опта и розницы в отчётах** | Оси проекта нет; после запуска цифры уже не разделить задним числом | Ось проекта — **до** первого боевого заказа (Р-7 обязателен до Р-9) |
| **Четвёртая копия цены** | Уже три механизма; витрина легко получит свою | Р-1 сводит в один канон до того, как витрина пойдёт на реальные данные |
| **Скоропорт в рознице** | Закупка-под-заказ даёт 0 остатка только в идеале; недобор/отмены копят товар | Усышка B2 и ежедневная сверка уже есть — включить в ежедневный ритм розницы с первого дня |
| **География Гагра–Очамчира** | Стоимость доставки съест маржу, если возить по одному заказу | Дни выезда по направлениям + минимальная сумма по дальним зонам (решение 3) |
| **Клиент-новичок = риск неоплаты** | Заказ собран и куплен до оплаты | Лимит первого заказа + стоп-лист (Р-А4) |
| **Ева и мини-апп разъедутся с ядром** | Классическая ошибка, от которой защищает ADR-025 | Каждая фаза заканчивается проверкой «расчёт один, поверхностей много» |
