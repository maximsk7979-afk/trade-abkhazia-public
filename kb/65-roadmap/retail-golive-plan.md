# Боевой запуск розницы — дорожная карта

> **Что это.** Пошаговый план от текущего состояния (прототип дизайна без бэкенда +
> оптовое ядро) до **боевой розничной торговли**.
>
> Составлена 2026-08-30 после сплошного разбора кода ядра (`code/trade-api/*`,
> `trade_app_v3.jsx`, `code/mini-app`, `code/retail-app`) и базы знаний.
> **Редакция 2 (2026-08-30, вечер)** — операционная модель уточнена владельцем: расписание,
> зоны, однократное взвешивание, работа через рынок Сухума. Изменения затронули не цифры,
> а логику потока, поэтому переписаны §0, §4 и фазы Р-4…Р-6.

## 0. Идея и рамка запуска

**Идея.** Онлайн-магазин доставки **продуктов питания и товаров для дома** по Абхазии.
Клиент заказывает в Telegram-приложении, мы закупаем на рынке Сухума, курьер привозит.

**Пилотная товарная группа — овощи, фрукты, зелень.** С неё начинаем боевую торговлю.
Остальные группы (бытовые товары и прочее) добавляются после пилота, поэтому архитектура
проектируется под расширение, но мастер-данные и процессы запуска ограничены фрешем.

> Уточнение к прежней записи: «ассортимент шире овощей/фруктов/зелени» относится к
> **бизнесу в целом**, а не к первому запуску. Пилот — фреш; расширение — отдельный
> этап после Р-9. Для непортящихся товаров для дома складская модель уже работает в ядре
> (FIFO-партии, остаток, оприходование) — она проще фреша, а не сложнее.

| Параметр | Решение |
|---|---|
| Срок | Жёсткого нет — делаем полно, без урезанного MVP |
| Пилотный ассортимент | Овощи, фрукты, зелень |
| Исполнители | Нанимаем отдельного курьера; закупка — существующий закупщик |
| География | **Сухум + запад: Гудаута, Пицунда, Гагра и др.** Восток (Очамчира, Ткуарчал, Гал) **не обслуживаем** |
| Источник товара | Собственный склад на рынке Сухума + склады местных поставщиков на том же рынке |

## 0.1. Операционная модель (вводные владельца 2026-08-30)

**Приём заказов — круглосуточно.** Приложение никогда не «закрыто»; от времени заказа
зависит только **обещанное время доставки**.

| | **Сухум** | **Запад (Гудаута, Пицунда, Гагра…)** |
|---|---|---|
| Приём заказов | круглосуточно | круглосуточно |
| Окно доставки | 09:00–19:00 | один выезд в день, вторая половина дня |
| Обещание | заказ с **08:00 до 17:00** → доставка **в тот же день в течение 1,5 часов** | заказы, размещённые с **17:00 предыдущего дня до 05:00 текущего**, едут **сегодня** |
| Позже окна | ближайшее окно следующего дня *(правило на подтверждение — см. вопрос 1)* | следующий дневной выезд |
| Закупка | **рынок Сухума, 06:00–09:00** (общая для обеих зон) | |
| Взвешивание | **однократное**: закупщиком на рынке при закупке либо при сборке заказа на нашем складе | |
| Курьер | доставил → передал → получил оплату. **Весов у курьера нет** | |
| «С колёс» | **не используется** — весь товар проходит через рынок Сухума и наш склад | |

**Три следствия, которые меняют архитектуру** (разобраны в §4):

1. **Экспресс 1,5 часа возможен только из наличия.** Успеть за 90 минут «заказ → закупка →
   доставка» физически нельзя. Значит утренняя закупка покрывает не только подтверждённые
   заказы, но и **ожидаемый дневной спрос Сухума**. Модель — не чистая «закупка-под-заказ»,
   как считалось до сих пор, а **гибрид**: под заказ (запад) + из запаса (Сухум).
2. **Сумма заказа становится точной до выезда курьера.** Раз взвешивают один раз при
   сборке, клиент узнаёт финальную сумму **до** доставки, а не на пороге. Это снимает
   главную неловкость прототипа («≈» до последнего) и требует уведомления «заказ собран,
   к оплате столько-то».
3. **Выдача «с колёс» из плана уходит.** Готовый механизм ядра (`loadFromTrip`) не нужен —
   работает более простой путь «развоз со склада» (`loadFromWh`), который тоже готов.

## 1. Definition of Done — что считаем «боевым запуском»

Запуск состоялся, когда **все** пункты верны на проде, на реальных деньгах:

1. Незнакомый человек открывает бота, регистрируется сам, видит витрину с сегодняшними
   ценами и наличием, оформляет заказ с адресом и **видит обещание доставки по своей зоне**.
2. Закупщик утром видит **сводный лист** (заказы запада + запас под дневной Сухум),
   закупает на рынке, деньги списаны с его кошелька движком fin-ops.
3. Заказ **собирается и взвешивается один раз**, клиент получает точную сумму до выезда.
4. Курьер видит свою пачку заказов с адресами, доставляет, принимает наличные — деньги
   падают в его кошелёк, долг клиента 0.
5. Клиент получает уведомления по этапам и видит в истории факт.
6. Владелец видит **P&L проекта «Розница» отдельно от опта**, сходящийся с кассой и
   балансами; товарооборот розницы сверяется; усышка проведена.
7. Отмена любой операции даёт симметричное сторно (касса + баланс + P&L + FIFO).
8. Роли гейтятся fail-closed; клиент видит только своё; курьер — только свою доставку.
9. Есть письменные инструкции для курьера, сборщика, закупщика, оператора; сценарии Евы
   наполнены.

Пока хоть один пункт открыт — это пилот, а не запуск.

## 2. Метод работы

Тот же, что дал результат на банане и финблоке (Обязательства 5/6/7 ADR-015/022):
**фаза за фазой, каждая — по четырём слоям**: ① TradeApp · ② Ева · ③ мини-апп (клиент и
сотрудники) · ④ база знаний (роль → процесс → сценарий Евы → должностная инструкция).

Правила, не подлежащие обсуждению внутри фаз:
- **Матрица 4 плоскостей до кода** (касса × баланс × P&L × склад/COGS) + судьба товара +
  симметрия сторно — письменно, видимо владельцу.
- **Ролевая привязка** (кто инициирует / решает / исполняет / видит + поверхность),
  роли — только из [role-catalog](../35-security/role-catalog.md), гейт fail-closed.
- **Единый доменный слой**: витрина, Ева и TradeApp зовут один расчёт. Комментарий
  «зеркалит» в новом коде розницы — красный флаг, повод остановиться.
- Фаза закрыта только после **боевой приёмки на проде** со сторно и откатом.

## 3. Ревизия «что есть на самом деле» (сверено по коду 2026-08-30)

### Есть и переиспользуется как есть

| Механика | Где в коде | Годность для розницы |
|---|---|---|
| Заказ-корзина с замороженной ценой | `order-service.buildMixedCartSale`, `order-model.js` | Полная |
| План закупки из заказов | `buyer-service.orderPlan` / `remainingPlan` | **Это и есть «закупочный лист»**; для Сухума дополняется прогнозом запаса |
| Закупка на рынке за нал | «Рынок (наличные)», `cashMarket`, `mpId`, `/api/mini/purchase` | Полная: каждая закупка отдельной записью, оплата налом, баланс 0 |
| Развоз со склада | `delivery-service.loadFromWh` + FIFO-списание | Полная — **основной путь розницы** |
| Отгрузка по точкам | `/api/mini/dlv/points`, `/dlv/ship` | Годится, но **упрощается**: факт-вес фиксируется на сборке, курьер вес не вводит |
| Деньги | движок fin-ops ADR-027, мини-касса, сторно комплектом | Полная. Новых денежных механик розница не вводит |
| FIFO/COGS, усышка, сверка остатков | `fifo-batch`, `stock-service`, `shrinkage-service` | Полная; при работе из запаса становится **ежедневной необходимостью** |
| Изоляция клиента | `mini-auth.verifyInitData` + скоуп по `clientId` | Полная |

Выдача «с колёс» (`loadFromTrip`) в рознице **не используется** (решение владельца) —
механизм остаётся оптовым.

### Заявлено готовым, но по факту отсутствует

## 4. Архитектурные решения (принимаю как архитектор, владелец подтверждает бизнес-цифры)

**Р-А1. Розница — отдельный проект `PRJ-005 «Розница»`** (ADR-009), не вторая система.
Справочники (товары, SKU, клиенты, кошельки, статьи) общие; разделение — по `projectId`.

**Р-А2. Заказ принимается всегда; «день» — это не разрешение заказывать, а плановая
единица нашей работы.** Прежняя оптовая модель («есть рейс на дату → приём открыт, иначе
409») круглосуточному приёму противоречит и **отменяется для розницы**. Вместо неё:
- заказ создаётся в любой момент и сразу получает **обещание доставки**, вычисленное из
  зоны клиента, времени заказа и расписания (§0.1);
- работа дня оформляется двумя знакомыми ядру документами: **закупка на рынке** (местная
  закупка ЗК проекта PRJ-005 — приход на наш склад) и **развоз** (доставка Д-);
- по Сухуму развозов в день несколько (волны), по западу — один.

Новых сущностей не заводим: закупка, склад, партии, развоз и точки в ядре уже есть.

**Р-А3. Единый прайс-сервис** (`price-service` на сервере + ADR): градации `opt/mid/ret`,
база себестоимости — **последняя закупка позиции из любого источника** (рейс ИЛИ ЗК),
политика наценки по группе товара, пол цены fail-closed. Витрина, Ева, TradeApp и мини-апп
читают **один** канон. Поглощает `weighted-pricing` и браузерный `PriceListMod`.
Закрывает [GAP-034](../00-meta/gaps.md#gap-034)/[GAP-040](../00-meta/gaps.md#gap-040)/[GAP-082](../00-meta/gaps.md#gap-082).

**Р-А4. Самрегистрация клиента розницы** — из `initData`: неизвестный `tgChatId` →
карточка клиента (проект PRJ-005, `priceLevel: ret`, статус «Новый»), телефон обязателен,
адрес — при первом заказе. Модерация **не блокирует** первый заказ; действуют ограничители
новичка (лимит суммы, оплата при получении, стоп-лист). Цифры — за владельцем.

**Р-А5. Курьер — роль `expeditor`** (в каталоге это ровно «отгрузка по точкам, развоз
клиентам»), при своём авто дополнительно `driver`. Новую роль не заводим (ADR-022).
Курьеру — ₽-кошелёк; наличные сдаёт через мини-кассу.

**Р-А6. Стоимость доставки — отдельная строка дохода**, а не скидка к товару: иначе
товарная маржа искажается и порог бесплатной доставки съедает её незаметно. Расход на
курьера/транспорт — opex B3. Матрица — в фазе Р-7.

**Р-А7. Отмена после закупки** (на подтверждение владельцем): купленный товар остаётся
партией на складе и продаётся дальше — при работе из запаса это норма, а не исключение;
испорченный — списание B2 через усышку. Рецидивисту — предоплата или стоп-лист.

**Р-А8. Взвешивание однократное, на сборке. Курьер веса не вводит.** Появляется отдельный
шаг **«сборка заказа»** (роль `warehouse`, на рынке — возможно тот же закупщик): факт-вес
и факт-количество фиксируются один раз, сумма заказа становится окончательной, клиент
получает её уведомлением до выезда. Экран курьера сокращается до «доставил / передал /
принял оплату / не доставил (причина)». Технически это разделение существующей операции
`/dlv/ship` на два шага: **сборка** (веса и суммы) и **вручение** (статус и деньги).

**Р-А9. Наш склад на рынке Сухума — учётная локация** (офис/склад в справочнике). Весь
товар проходит через него; поставщики на рынке — источники закупки, а не точки отгрузки
клиенту. Отсюда же берётся остаток для витрины «сегодня в наличии».

**Р-А10. Зона — носитель расписания.** Отсечка, окно доставки, SLA, тариф и минимальная
сумма привязываются к **зоне**, а не к проекту целиком: у Сухума экспресс-режим, у запада —
один выезд с отсечкой 05:00. Это расширяет [GAP-081](../00-meta/gaps.md#gap-081) (там было
«параметр проекта» — теперь двухуровнево: проект → зоны).

**Р-А11. Дневной запас под экспресс — управляемая величина.** Раз 1,5 часа не позволяют
закупать под заказ, закупщик утром берёт запас под прогноз Сухума. Нужны: план запаса по
позициям (кто утверждает — решение владельца), ежедневная сверка остатка, правило уценки
и списания непроданного фреша. Без этого экспресс-обещание либо не выполняется, либо
незаметно съедает маржу.

## 5. Фазы

Порядок обязателен: каждая следующая опирается на предыдущую. Оценки — в сессиях работы,
не в календарных днях.

---

### Р-0. Решения, мастер-данные, каркас проекта — *фундамент*

**Бизнес-вход от владельца:**
1. Подтвердить пилотный ассортимент (овощи/фрукты/зелень) и список позиций — за основу
   берём 46 строк `code/retail-app/step-grid.xlsx`, вычитаем нефреш.
2. Зоны и их расписание (§0.1), тариф доставки и минимальная сумма по каждой зоне,
   порог бесплатной доставки.
3. Кто курьер и кто сборщик (люди в `trade-cat-staff`), их кошельки.
4. План дневного запаса: кто решает, сколько брать сверх заказов (Р-А11).

**Работы:**
- ① TradeApp: проект `PRJ-005`; **склад на рынке Сухума** как локация (Р-А9); **зоны**
  с расписанием и тарифами (Р-А10, [GAP-081](../00-meta/gaps.md#gap-081)); SKU пилота с
  полями **шаг заказа + группа + `approx` + тара** ([GAP-079](../00-meta/gaps.md#gap-079));
  рыночные поставщики (`cashMarket`); кошельки курьера и сборщика.
- ② Ева: знает проект, зоны и расписание.
- ③ Мини-апп: без изменений.
- ④ БЗ: `kb/20-domain/retail/` — модель розничной сделки и расписание; роли курьера и
  сборщика в `30-roles/to-be/`; обновить `role-permissions`.

**Приёмка:** проект и зоны заведены; SKU пилота имеют шаг/группу/`approx`/тару; тестовая
закупка ЗК даёт партию на складе рынка с `projectId: PRJ-005`.

### Р-1. Единый прайс и розничная цена

- ① Сервер: `price-service` (Р-А3) — градации, себестоимость из рейсов **и** ЗК, наценка
  по группе, пол цены fail-closed, ₽/кг для весовых и ₽/место для тары
  ([GAP-082](../00-meta/gaps.md#gap-082)); `/api/price` — единственный источник;
  `PriceListMod` → делегат.
- ② Ева: цена по градации собеседника; оптовая градация розничному клиенту не видна.
- ③ Оба мини-аппа читают `/api/price`.
- ④ БЗ: ADR «Единый прайс»; переписать `20-domain/pricing.md`; правила наценки в
  `accounting-rules`.

**Приёмка:** одна позиция в вебе, Еве и витрине — **бит-в-бит одна цена**; «средний опт»
ниже себестоимости с доставкой → отказ 400; товар без цены на витрине не показывается.

---

### Р-2. Личность розничного клиента

- ① TradeApp: карточка розничного клиента (телефон, адреса, **зона**, статус, лимит),
  очередь новых, стоп-лист.
- ② Ева: сценарий знакомства с розничным клиентом.
- ③ Мини-апп: **самрегистрация** ([GAP-087](../00-meta/gaps.md#gap-087)); обязательный
  телефон; адрес с картой и автоопределением зоны; профиль с несколькими адресами;
  состояние — с сервера ([GAP-083](../00-meta/gaps.md#gap-083)).
- ④ БЗ: процесс «завод розничного клиента»; политика новичка; изоляция
  ([GAP-030](../00-meta/gaps.md#gap-030)).

**Приёмка:** с чистого Telegram-аккаунта регистрация → адрес → определилась зона; второй
аккаунт не видит данные первого; адрес вне зоны обслуживания (восток) получает честный
отказ ещё до сборки корзины.

---

### Р-3. Витрина на реальных данных

- ③ Мини-апп розницы: каталог из справочника; цены из `/api/price`; **«сегодня в наличии»
  из остатка нашего склада** (Р-А9); свои фото ([GAP-080](../00-meta/gaps.md#gap-080));
  поиск на серверных группах; черновик корзины на сервере.
- ① TradeApp: управление витриной — что показываем, стоп-позиции.
- ④ БЗ: `retail-mini-app.md` из «прототипа» в «боевой».

**Приёмка:** правка цены/шага/фото в вебе → изменение в витрине без деплоя; корзина
переживает перезапуск и смену устройства; позиция с нулевым остатком в Сухуме не обещает
экспресс-доставку.

---

### Р-4. Заказ, обещание доставки и план дня — *ядро потока*

**Матрица 4 плоскостей — пишем до кода** (розничная сделка + доставка как доход + отмена
после закупки + новичок с лимитом).

- ① TradeApp: план дня — заказы запада к отсечке 05:00, заказы Сухума в реальном времени,
  сводка «что купить утром» (Р-5), ручные корректировки.
- ③ Мини-апп клиента: приём **круглосуточно**; расчёт обещания («доставим сегодня к
  15:30» / «сегодня во второй половине дня» / «завтра с 09:00») по зоне, времени и
  расписанию; стоимость доставки по зоне; правка и отмена до момента сборки;
  лента этапов.
- ③ Мини-апп сотрудника: очередь заказов, назначение на волну.
- ② Ева: приём и правка заказа, статус.
- ④ БЗ: процесс «розничный заказ»; правила расписания; правило отмены (Р-А7).

**Приёмка:** заказы в 03:00, в 12:00 и в 18:00 из Сухума и из Гагры дают **разные и
верные** обещания; после 05:00 западный заказ уезжает на следующий выезд; отмена до сборки
чистая, после закупки — по правилу Р-А7.

---

### Р-5. Утренняя закупка на рынке

- ③ Мини-апп закупщика: **лист закупки** = подтверждённые заказы запада + план запаса под
  Сухум (Р-А11), с разделением «под заказ / в запас»; факт-закупка с ценой и весом
  ([взвешивание №1](#р-а8)); недобор и замена с уведомлением клиента; фото товара → витрина.
- ① TradeApp: контроль — план/факт/недобор, себестоимость дня, остаток после закупки.
- ④ БЗ: процесс закупщика розницы; правило формирования запаса.

**Приёмка:** деньги списаны из кошелька закупщика движком fin-ops; партии на складе рынка
с `projectId: PRJ-005`; недобор виден клиенту и оператору; отмена закупки — сторно комплектом.

---

### Р-6. Сборка и доставка — *здесь модель изменилась сильнее всего*

**Сборка (новый шаг, Р-А8):**
- ③ Мини-апп сборщика: список заказов к сборке → по позициям факт-вес/количество →
  **сумма заказа окончательная** → уведомление клиенту «собран, к оплате X» → заказ
  в очередь на доставку. Списание FIFO происходит здесь.
- Расхождение с заказом (нет позиции, вес отличается) — по правилу недобора (вопрос 8).

**Доставка:**
- ① TradeApp: формирование волн — Сухум (несколько за день, по мере накопления и SLA
  1,5 ч), запад (один выезд, вторая половина дня); назначение курьера.
- ③ Мини-апп курьера: **пачка заказов с адресами и порядком** ([GAP-051](../00-meta/gaps.md#gap-051)
  — при экспресс-режиме это порядок внутри волны, а не оптимизация большого маршрута),
  навигация, статусы «доставил / не доставил (причина)», приём нала или перевода →
  кошелёк курьера. **Весов и пересчёта сумм у курьера нет.**
- ③ Мини-апп клиента: этапы «принят → собираем → в пути → доставлен» + точная сумма.
- ④ БЗ: инструкции курьера и сборщика; процессы сборки и развоза.

**Приёмка:** волна из 5+ заказов по Сухуму укладывается в обещанные 1,5 часа; западный
выезд закрывается одним развозом; нал у курьера сходится до копейки; недоставленный заказ
возвращается на склад **розничного** проекта (исправить константу PRJ-001,
[GAP-088](../00-meta/gaps.md#gap-088)).

---

### Р-7. Деньги и отчётность розницы

- ① Сервер: **ось проекта** в отчётах ([GAP-085](../00-meta/gaps.md#gap-085)) — `projectId`
  у продажи, фильтр `project` в `/api/pnl`, `/api/turnover`, кассе и балансах; доставка
  отдельной строкой дохода (Р-А6); разрезы **по зонам** и по градации цены.
- ① TradeApp: отчёты с переключателем проекта.
- ② Ева: `get_pnl`/`get_cash_all` понимают проект.
- ④ БЗ: правила учёта розницы в `accounting-rules`; ежедневный ритм сверки остатка и
  списания непроданного фреша (Р-А11).

**Приёмка:** P&L «Розница» + «Опт» = общий P&L до копейки; касса дня сходится с наличными
курьера; товарооборот розницы даёт расхождение 0; видно, сколько стоит доставка на запад
относительно выручки этой зоны.

---

### Р-8. Уведомления и Ева

Реализация [GAP-073](../00-meta/gaps.md#gap-073) / [ADR-026](../90-decisions/ADR-026-notifications-unified-layer.md)
в части розницы: `notify-core` (единый резолв, дедуп, ретрай, важность); клиентские
уведомления по этапам, **включая «собран, к оплате X»** и недобор; уведомления курьеру,
сборщику и закупщику; тихие часы (при круглосуточном приёме — обязательны, иначе ночные
заказы будят сотрудников). Ева — консультация розничного клиента.

**Приёмка:** по одному сообщению на этап; отмена и недобор доходят; ночью персонал не
будят, а утренняя сводка есть.

---

### Р-9. Пилот и боевой запуск

1. **Сквозной e2e-прогон** ([GAP-064](../00-meta/gaps.md#gap-064)) — вечером, с бэкапом и
   полной очисткой.
2. **Тестовый день с сотрудниками** — заказы от своих, реальная закупка, реальный развоз.
3. **Пилот по Сухуму** — 5–10 заказов в день, 1–2 недели; ежедневная сверка касса/склад/P&L;
   замер: укладываемся ли в 1,5 часа и сколько фреша списываем.
4. **Подключение западного направления** — один выезд в день с отсечкой 05:00.
5. **Запуск**: инструкции выданы, обучение проведено, метрики (заказы/день, средний чек,
   маржа, доля отмен, недобор, списания, доля доставок в SLA) считаются в системе.

**Критерий выхода:** три дня подряд без ручных правок данных в БД.

## 7. Риски

| Риск | Почему опасен | Что делаем |
|---|---|---|
| **Экспресс-обещание против скоропорта** | 1,5 часа требуют запаса, запас фреша к вечеру превращается в списание. Это главный экономический риск модели | Р-А11: план запаса, ежедневная сверка, правило уценки; замер списаний с первого дня пилота |
| **Смешение опта и розницы в отчётах** | Оси проекта нет; после запуска цифры не разделить задним числом | Ось проекта — **до** первого боевого заказа (Р-7 обязателен до Р-9) |
| **Четвёртая копия цены** | Уже три механизма; витрина легко получит свою | Р-1 сводит в один канон до выхода витрины на реальные данные |
| **Круглосуточный приём против оптовой модели «дня»** | `isDayOpen` вернёт 409 ночью — витрина будет отказывать клиенту | Р-А2: приём без привязки к дню, день — только наша плановая единица |
| **Стоимость доставки на запад** | Один выезд на 160 км окупается только при плотности заказов | Минимальная сумма по зоне (вопрос 4) + разрез P&L по зонам (Р-7) |
| **Клиент-новичок = риск неоплаты** | Заказ собран и куплен до оплаты | Лимит первого заказа + стоп-лист (Р-А4) |
| **Ева и мини-апп разъедутся с ядром** | Классическая ошибка, от которой защищает ADR-025 | Каждая фаза заканчивается проверкой «расчёт один, поверхностей много» |
