# Работать с ноутбука без рабочей станции

> Страховка на случай, если рабочий VPS недоступен — упал, потерян, нет денег на счету.
> Ноутбук в любой момент может стать полноценным рабочим местом: всё нужное лежит в GitHub.

## Правило одного писателя

После переезда на станцию **эталон — GitHub**, писать в него имеет право только одна
машина за раз. По умолчанию это рабочая станция. Ноутбук держит копию **для чтения** и
обновляет её `git pull`.

Если станция недоступна и ты переходишь на ноутбук — писателем становится ноутбук.
Когда станция вернётся, **сначала** подтянуть на ней изменения (`git pull --ff-only`), и
только потом продолжать там.

### Защита стоит в самом git, а не только на бумаге

На обеих машинах установлен хук `pre-commit` ([hooks/pre-commit-writer-guard.sh](../../../hooks/pre-commit-writer-guard.sh)):
он **блокирует коммит, если копия отстала от GitHub**. Значит на другой машине уже есть
работа, и коммит поверх создал бы расхождение.

```
❌ Коммит отклонён: эта копия отстала от GitHub на N коммит(ов).
   Сначала подтянуть чужую работу:  git pull --ff-only
```

Установка на новой машине (хуки в `.git/hooks/` не версионируются):

```bash
ln -sf ../../hooks/pre-commit-writer-guard.sh .git/hooks/pre-commit
```

Осознанно обойти (нет сети, а работу надо зафиксировать):
`SKIP_WRITER_GUARD=1 git commit ...`

### Чего хук НЕ ловит

Guard защищает от **расхождения веток** — когда копия отстала от GitHub. Он ничего не
знает о втором случае: **две активные сессии на одной машине** (или сессия на ноутбуке,
управляющая станцией). Тогда ветки не расходятся, правки ложатся в одну копию, а вторая
сессия продолжает действовать по прочитанному ранее — устаревшему — состоянию файла.

Реальный случай 2026-08-29: сессия станции читала `workstation-rebuild.md`, параллельно
он был исправлен, и правка «поверх» чуть не сломала подстановку путей в хуках. Поймала
не защита git, а проверка «файл изменён с момента чтения» в редакторе.

**Технической защиты не предлагаем** — блокировки уровня файлов создадут больше проблем,
чем решат. Правило организационное: **не держать одновременно активными сессию на
ноутбуке и на станции**. Если вторая сессия нужна для проверки — она работает строго на
чтение и об этом сказано первой.

### Что НЕ может случиться само

Выгрузка на GitHub происходит **только после коммита** — это локальный хук `post-commit`.
Ни cron, ни фоновой службы, ни расписания нет: включённый ноутбук сам по себе ничего не
отправляет. И затереть работу станции он не может — в хуке нет `--force`, а обычный push
GitHub отклоняет, если копия отстала.

## Разовая настройка ноутбука: хуки — симлинками, а не копиями

⚠️ **Требует выполнения на ноутбуке** (станция это сделать не может).

Хуки перенесли в репозиторий, чтобы они пережили потерю машины. На станции так и есть,
**на ноутбуке — нет**: там `~/Documents/trade_app/.claude/hooks/` содержит собственные
копии, а этот каталог не под git. Связи с `hooks/` в репозитории у них нет.

Последствие: правка `hooks/session-reminder.sh` на станции до ноутбука **не доходит**, и
ноутбук продолжает работать по старому протоколу, ничего не сообщив. Это тот же класс
тихого отказа, ради которого хуки и переносили в git. Копии уже разошлись — 2026-08-29
в `session-reminder.sh` добавлено предупреждение о расхождении памяти.

```bash
cd ~/Documents/trade_app/.claude/hooks
mv session-reminder.sh session-reminder.sh.bak
mv closing-check.sh    closing-check.sh.bak
ln -s ~/Documents/trade_app_repo/hooks/session-reminder.sh session-reminder.sh
ln -s ~/Documents/trade_app_repo/hooks/closing-check.sh    closing-check.sh

# проверка: хук отдаёт валидный JSON
bash session-reminder.sh | python3 -c "import sys,json;json.load(sys.stdin);print('хук работает через симлинк')"
```

После этого правки хуков на любой машине доезжают до ноутбука обычным `git pull`.

## Как начать работать с ноутбука

```bash
cd ~/Documents/trade_app_repo
git pull                              # подтянуть последнее из GitHub
./scripts/sync-memory.sh restore      # вернуть память агента из репозитория
claude                                # открыть сессию
```

Первой фразой скажи **«продолжаем работу»** — CC прочитает протокол и текущее состояние.

## Что при этом работает, а что нет

**Работает всё, кроме подключения с телефона:**

| | Ноутбук | Станция |
|---|---|---|
| Правка кода и базы знаний | да | да |
| Деплой на боевой (`deploy.sh`) | да | да |
| Приёмка headless-браузером | да (Chrome macOS) | да (Chrome Linux, `--no-sandbox`) |
| Работа с телефона | **нет** | да |
| Не зависит от включённого ноутбука | нет | да |

Деплой с ноутбука ходит на боевой по паролю из `credentials.md` (`sshpass`), со
станции — по ключу. Оба пути рабочие.

## Если ноутбука тоже нет

Всё, что нужно для восстановления, лежит в двух местах:

1. **GitHub** (`maximsk7979-afk/trade-abkhazia`, приватный) — код, база знаний,
   память агента в `agent-memory/`, хуки в `hooks/`, runbook восстановления.
2. **Менеджер паролей** — доступы: боевой VPS, БД, токены ботов, GitHub.
   Секретов в git нет и быть не должно ([GAP-006](../../00-meta/gaps.md#gap-006)).

С любой машины: поставить Claude Code, склонировать репозиторий, восстановить память,
взять секреты из менеджера — и работа продолжается. Боевой сервер при этом не
затрагивается: магазин, Ева и БД живут отдельно и переезда не замечают.

## Проверка страховки (учения)

Раз в пару месяцев стоит убедиться, что план рабочий, а не бумажный:

- [ ] `git pull` на ноутбуке проходит
- [ ] `./scripts/sync-memory.sh restore` возвращает 29+ файлов памяти
- [ ] сессия открывается, напоминание протокола появляется
- [ ] `./scripts/deploy.sh retail-app` проходит с ноутбука
