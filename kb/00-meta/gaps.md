# Белые пятна (gaps)

## Формат записи

```markdown
### GAP-NNN: <короткое описание>
**Обнаружено**: YYYY-MM-DD
**Где**: путь к коду / модулю / месту в системе
**Суть**: что именно не описано
**Приоритет**: high / medium / low
**Статус**: open / in-progress / closed (с датой и ссылкой на ADR/файл)
```

### GAP-009: Закупка вне рейса не описана и не реализована (CLOSED)
**Обнаружено**: 2026-04-28 (при наполнении глоссария)
**Где**: текущая модель закупок завязана на `trip.items[]`. Закупка вне рейса — отсутствует.
**Суть**: Местные и российские поставщики продают товар **не через рейс из Грузии**. Сейчас в системе нет flow "приход на склад от местного поставщика без рейса". Принято архитектурное решение: ввести **отдельную сущность `Purchase`** (закупка вне рейса) с префиксом `ЗК-` (см. [ADR-009](../90-decisions/ADR-009-multitenancy-projects.md), [ADR-010](../90-decisions/ADR-010-invoice-entity.md)).

**Приоритет**: high (нужно для PRJ-002 «Местные овощи» и PRJ-003 «Грузинские овощи» с июня 2026)
**Статус**: ✅ **closed 2026-05-21** — Слой Б Шага 1 реализован и задеплоен. Сущность `Purchase` (`ЗК-NNN`, ключ `trade-purchases-v1`), модуль «Местные закупки» под вкладкой «🛒 Закупки», себестоимость с распределением доставки по весу, создание партий FIFO при сохранении, долги в расчётах с поставщиком. Формат — [40-system/data-formats/purchase.md](../40-system/data-formats/purchase.md). Коммиты `5af1097`, `fded39e`, `9966e65`, `ad3927b`. Привязка `Invoice.linkedTo.type="purchase"` — в Слое В (Invoice).

**Реализованное правило себестоимости**: для местных закупок `costPU = закупочная цена` без долей `expShare` рейса. Доп. расходы (доставка от поставщика/с теплицы) — поле `deliveryCost`: при значении >0 распределяется по позициям пропорционально весу и входит в `costPU`; при 0/пусто — себестоимость = чистая цена закупки. **Остаётся (Шаг 3)**: различение валют в балансе поставщика при мультивалютных закупках.

### GAP-012: Стоимость списаний не учитывается как отдельная финансовая статья
**Обнаружено**: 2026-04-28 (при наполнении глоссария, карточка "Списание")
**Где**: `trade_app_v3.jsx`, обработка `whOp.opType === "writeoff"`. Списание уменьшает физический остаток в FIFO-партии, но **не порождает** запись в финансовом учёте о потерях.
**Суть**: Когда товар списывается на брак/порчу/утрату, **деньги, потраченные на его закупку, исчезают** из учёта без следа. То есть мы видим уменьшение остатка, но **не видим**:
- Сколько денег "сгорело" на списаниях за период
- Какие товары чаще списываются (частая порча → плохой поставщик / плохие условия хранения / неправильная закупка)
- Влияние списаний на общую прибыль

В коде каждая partia (`batch`) знает свою себестоимость единицы (`costPerUnit`), значит, в момент списания **можно вычислить стоимость списанного** = `qty × batch.costPerUnit`. Но эта величина никуда не сохраняется.

**Приоритет**: medium (нужно для финансовых отчётов, отчётов о потерях, P&L)
**Статус**: open. Что нужно:
- При создании whOp типа `writeoff` дополнительно сохранять рассчитанную стоимость списания (поле `writeoffCost` или подобное)
- Добавить в финансовые отчёты строку "Потери от списаний"
- Добавить отчёт "Списания за период" с детализацией по товарам/SKU
- Возможно — категории причин списания (испортилось / разбилось / утрачено / иное), для аналитики

### GAP-019: `trade-api` не валидирует payload POST `/api/storage/:key`
**Обнаружено**: 2026-05-27 (инцидент с потерей справочника клиентов из-за storage-api Евы)
**Где**: `/var/www/trade/server.js` на VPS (~50 строк, см. [40-system/api.md](../40-system/api.md))
**Суть**: `trade-api` принимает любой POST body со статусом 200 OK. Если в body **нет поля `value`** — сервер записывает в колонку `value` таблицы `app_storage` **null**, тем самым **молча стирая существующее значение ключа**. Не возвращает 400/422, не пишет в лог. Это превращает любой клиент-баг (опечатка в обёртке, забытое поле) в потерю данных без следа.

**Прецедент**: 2026-05-27 Ева писала без обёртки `{value}` → ~33 клиента из `trade-cat-clients` стёрты безвозвратно. См. CHANGELOG 2026-05-27, фикс на стороне Евы — коммит после инцидента; первопричина на стороне сервера остаётся.

**Приоритет**: medium (фикс на клиентах закрывает 99% случаев, но любой будущий клиент storage-api может наступить на ту же мину). Поднять до high, если KV ещё долго проживёт до миграции в Postgres (Шаг 2 ADR-009).

**Статус**: open. Что нужно:
- Добавить в `server.js` валидацию: если `req.body.value === undefined` → вернуть `400 { error: "missing 'value' field" }`, **не писать в БД**.
- Покрыть быстрым тестом (curl без `value` → ожидаем 400).
- Альтернатива (Шаг 2 ADR-009): когда KV уйдёт в Postgres с нормальными миграциями и schema-aware API, проблема исчезнет сама.

После фикса — обновить [40-system/api.md](../40-system/api.md) (удалить «не валидирует» из предупреждения).

### GAP-030: Изоляция данных клиента + доступ по роли + приватность памяти
**Обнаружено**: 2026-05-31 ([ADR-018](../90-decisions/ADR-018-eva-universal-assistant.md) §6, [ADR-017](../90-decisions/ADR-017-eva-memory-architecture.md))
**Где**: все клиент-facing инструменты Евы (`code/eva/src/tools/`); сборка контекста; ночной проход; будущий RBAC.
**Суть**: Гарантировать, что Ева **не раскрывает клиенту** данные других клиентов и внутреннюю экономику компании (см. список табу в [ADR-018](../90-decisions/ADR-018-eva-universal-assistant.md) §6 и [vision.md](../50-agents/eva/vision.md) принцип 6). Защита в глубину:
- **Архитектурно (главное):** ни один клиент-facing инструмент не возвращает cross-client/общефирменные данные; фильтр по id текущего клиента зашит в инструмент.
- **Контекст:** грузится только B и хвост A текущего клиента.
- **Гейт по роли собеседника:** клиент → строгий скоуп; менеджер/owner → внутренний доступ (связано с RBAC).
- **Промпт:** жёсткий принцип + отказ на попытки выманить.

Плюс приватность памяти: **фильтр для ночного прохода** (что не выносить в B — здоровье, семейные проблемы, политика, религия, личные финансы); **доступ к A/B по роли** (RBAC); **удаление памяти клиента по запросу**.
**Приоритет**: high (риск утечки коммерческих данных; критично до открытия Евы клиентам).
**Статус**: **in-progress** (2026-05-31). Архитектурный фундамент готов; остаток привязан к Шагу 4 / RBAC.
- [x] **Гейт инструментов по роли** (2026-05-31, коммит `f45da75`): двухслойный гейт в `code/eva/src/tools/index.js`. У каждого инструмента уровень `access` — `staff` (owner/manager) / `client` (обязан фильтровать выдачу по `ctx.clientId`) / `any` (нейтральный UI). `getSchemas(role)` прячет staff-инструменты от клиента (модель их не видит); `executeByName` делает hard-gate перед запуском. **Fail-closed:** нет объявленного `access` → `staff` → новый клиент-facing инструмент не заработает для клиента без явного `access:'client'`. `index.js` пробрасывает `role`+`clientId` в ctx (из `resolveIdentity`; при сбое — строгий клиент-скоуп). Проверено на VPS.
- [x] **Изоляция контекста** (2026-05-31): в диалоге грузится только B текущего клиента ([GAP-024](#gap-024), `resolveIdentity`→`getMemory` по его id); хвост A — будет в [GAP-025](#gap-025) тоже по его `client_id`.
- [x] **Приватный фильтр ночного прохода** (2026-05-31, [GAP-024](#gap-024) Фаза 2): системный промпт `memory-pass.js` явно запрещает выносить в B здоровье/семейные проблемы/политику/религию/личные финансы/сумму долга; тест «друг помнит ДР — приятно, ведёт базу болячек — жутковато». Проверено сквозным тестом.
- [x] **Промпт-слой** (2026-05-31, Ит.4 п.2): принцип «Конфиденциальность — клиент видит только своё» со списком табу в системном промпте.
- [ ] **Self-scope клиент-facing инструментов** — заработает в Шаге 4: каждый новый `access:'client'` инструмент (баланс, заказы, цены) отдаёт только данные `ctx.clientId`. Конструктивное правило закреплено fail-closed дефолтом.
- [ ] **Гейт по роли в самом промпте/сценариях клиента** — при открытии клиентских диалогов (Шаг 4): сейчас whitelist (`auth`) пускает только Максима, клиенты в свободный диалог ещё не выходят.
- [ ] **RBAC: доступ к A/B по роли** + **удаление памяти клиента по запросу** — связано с RBAC ([roadmap](../65-roadmap/current.md), Q3 2026) и CRM-модулем.

Конструктивное правило: **каждый новый инструмент объявляет `access`; клиент-facing — фильтрует выдачу по `ctx.clientId`.** Связано с RBAC ([roadmap](../65-roadmap/current.md), Q3 2026).
