# Словарь терминов (Glossary)

Единый источник терминологии проекта. Все термины — только в той форме, как зафиксированы здесь.

## 1. ID-префиксы и идентификаторы

### ПС (sale-direct)
Префикс ID для продажи со склада. Запись в `trade-sales-v1`, тип `sale-direct`. Создаётся через кнопку "+Со склада" в модуле "Продажи". Клиент сам забирает товар.

### ДС
**Устаревший префикс**. В коде и БД сейчас не используется. Вместо него ЗД-XXX или ПС-XXX в зависимости от способа отгрузки. См. [ADR-007](../90-decisions/ADR-007-sales-canonical-model.md).

### ЗД (order-stock)
Префикс ID для заявки на доставку с нашего склада. Запись в `trade-sales-v1`, тип `order-stock`. Создаётся через кнопку "+Доставка". После статуса "Отгружено" семантически становится продажей доставкой.

### ЗР (order-trip)
Префикс ID для заявки на товар, который привезём из Грузии. Запись в `trade-sales-v1`, тип `order-trip`. Создаётся через кнопку "+Под рейс". После статуса "Отгружено" — продажа доставкой.

### Р (рейс)
Префикс ID для рейса закупки `Р-XXX`. Запись в `trade-trips-v8`.

### Д (доставка)
Префикс ID для доставки `Д-XXX`. Запись в `trade-deliveries-v1`.

### B (партия)
Префикс ID для FIFO-партии `B-XXXX`. Запись в `trade-batches-v1`.

### К (клиент)
Префикс ID клиента `К-XXX`. Запись в `trade-cat-clients`.

### КА (контрагент)
Префикс ID контрагента `КА-XXX` (водители, таможня, грузчики, и т.д.). Запись в `trade-cat-contragents`.

### П (поставщик)
Префикс ID поставщика товара `П-XXX`. Запись в `trade-cat-suppliers`.

### С (сотрудник)
Префикс ID сотрудника `С-XXX`. Запись в `trade-cat-staff`.

### Т (товар)
Префикс ID товара `Т-XXX`. Запись в `trade-cat-products`.

### О (офис)
Префикс ID офиса/склада `О-XXX`. Запись в `trade-cat-offices`.

### SKU
Stock Keeping Unit — конкретный вариант товара (тара/вес). Префикс `SKU-XXX-XX`. Запись в `trade-cat-skus`.

## 2. Бизнес-сущности и роли по типу записи

### Заявка (request)
**Бизнес-имя** записи Sale на стадии до отгрузки. Это **не отдельная сущность** в БД, а семантический ярлык записи в зависимости от её статуса. См. [ADR-007](../90-decisions/ADR-007-sales-canonical-model.md). Когда `status !== "Отгружено"` — мы называем запись заявкой.

### Продажа (sale)
1. **Бизнес-имя** записи Sale в статусе "Отгружено" — факт состоявшейся продажи.
2. **Техническая сущность** в коде/БД — Sale, единая сущность для всех трёх типов (sale-direct, order-stock, order-trip).

### Продажа со склада (ПС)
Разовая операция: клиент сам пришёл, забрал товар, заплатил. Создаётся **сразу** со статусом "Отгружено". Тип в коде: `sale-direct`.

### Продажа доставкой (ДС, в речи)
Запись типа `order-stock` или `order-trip` в статусе "Отгружено". На уровне кода **отдельного типа `sale-delivery` нет** — это просто факт того, что заявка ЗД или ЗР дошла до конца жизненного цикла.

### Доставка
Сущность Delivery. Развоз товара по нескольким клиентам одной машиной. Имеет ID `Д-XXX`. Включает в себя несколько Sale (ЗД и/или ЗР).

### Рейс
Сущность Trip. Закупочная поездка из Грузии в Абхазию. ID `Р-XXX`. Содержит партнёров (например, Лия), расходы, закупленные товары.

> **Партия** и **Складская операция** — учётные сущности, описаны в [категории 5](#5-учётные-термины).

### Взаиморасчёт (settlement)
Ручная операция по платежам/начислениям сверх автоматического учёта. Хранится в `trade-settlements-v2`.

### Накладная (invoice)
Документ, фиксирующий состав отгрузки. В системе используется в двух сценариях.

**1. Входящая накладная** — от поставщика, фиксирует закупку.
- От грузинских поставщиков: фото на грузинском. Распознаётся ботом/Евой через OCR + словарь грузинских названий → попадает в `trip.items[]`. База знаний переводов — в обученном Claude у Максима, см. [GAP-003](gaps.md).
- От местных/российских поставщиков: формат пока не определён, см. [GAP-009](gaps.md).

**2. Исходящая накладная** — клиенту, по итогам отгрузки.
- Генерируется на лету функцией `downloadInvoice` (HTML).
- Основа — `shipment[]` в записи продажи (ЗД/ЗР).
- Содержит позиции с `qty`/`qtyTar`/`wBrutto`/`netto`, цены, итоговую сумму.
- Печатается или отправляется клиенту.

В коде **нет отдельной сущности "Накладная"** как сохранённого объекта: исходящая генерируется на лету из `shipment[]`, входящая распознаётся в `trip.items[]`.

Особый случай: строка **"Возврат / Брак"** в накладной — пометка в той же накладной, обрабатывается отдельно → запись в `settlements` как `defect_refund` (см. [Defect_refund](#defect_refund-возврат-за-брак)).

### Партнёр (по рейсу) — partner
Внешний участник, делящий с нами машину при рейсе из Грузии в Абхазию.

Хранится в `trip.partners[]` по имени строкой (`{"name": "Лия", "weight": "..."}`), **без ID контрагента** и **без отдельной записи в справочнике**. Сейчас в системе один партнёр — **Лия**.

Расходы рейса делятся пропорционально брутто-весу. Балансы по линии партнёра ведутся отдельно — модуль "🤝 Партнёр" в Взаиморасчётах, `acctType: "partner"`.

Партнёр — **отдельная сторона**: не клиент, не поставщик, не контрагент. Лия параллельно ещё и клиент (К-006), но это **независимые линии учёта** — балансы не пересекаются.

См. подробно: [20-domain/settlements/liya-partner.md](../20-domain/settlements/liya-partner.md).

⚠️ Архитектура `partners[]` поддерживает множество партнёров, но **справочника** партнёров и UI для управления нет — это [GAP-010](gaps.md).

### Контрагент (contragent)
Сторонняя сторона, с которой у нас есть деловые отношения и которая не подпадает под другие категории сторон ([Клиент](#клиент), [Поставщик](#поставщик-supplier), [Партнёр](#партнёр-по-рейсу--partner)). По сути — все прочие, с кем мы взаимодействуем по деньгам.

Текущие категории: водители, экспедитор, закупщик, грузчики, таможня, погранслужбы. В перспективе: арендодатели складов, налоговые органы, бухгалтерия, юристы, банки.

Хранится в `trade-cat-contragents`, ID `КА-XXX`. В `trip.expenses[]` и в ручных операциях `settlements` (`acctType: "expense"`) связывается через поле `contragentId`.

Полный перечень категорий и текущих контрагентов: см. [20-domain/contragents.md](../20-domain/contragents.md).

### Поставщик (supplier)
Сторонний продавец товара, у которого мы закупаем овощи и фрукты. Хранится в `trade-cat-suppliers`, ID `П-XXX`.

Бывает трёх географий:
- **Грузинский** — оптовые рынки в Грузии. Закупка через рейсы (`trip.items[]`). Расчёты в GEL, пересчёт в RUB по курсу рейса.
- **Местный (абхазский)** — теплицы и фермы на территории Абхазии. Закупка без рейса. Расчёты в RUB.
- **Российский** (в перспективе) — закупка без грузинского рейса. Расчёты в RUB.

Связь с рейсом не обязательна. Грузинский → товар приходит через рейс с прохождением таможни. Местный/российский → товар приходит на склад без рейса.

⚠️ Сейчас в коде формат поставщика не различает валюту и географию — это [GAP-008](gaps.md). Закупка вне рейса не реализована — это [GAP-009](gaps.md).

## 3. Типы продаж и товаров

### Тарный товар
Товар, продаваемый поштучно или ящиками без взвешивания. В SKU: `tp = 1`. Примеры: чеснок, бананы, конференция груша. В строке продажи: заполнено `qty`, пустые `qtyTar` и `wBrutto`.

### Весовой товар
Товар, продаваемый на вес. В SKU: `tp = 0`. Примеры: помидоры, огурцы, перец. В строке продажи: пустое `qty`, заполнены `qtyTar` (количество ящиков) и `wBrutto` (вес брутто).

### Брутто
Вес товара **с тарой**. Поле `wBrutto` в строках продажи. См. [20-domain/weight-calculation.md](../20-domain/weight-calculation.md).

### Нетто
Вес товара **без тары**. Вычисляется: `нетто = max(0, брутто − qtyTar × tw)`. См. [20-domain/weight-calculation.md](../20-domain/weight-calculation.md).

### Тара
Ящик/упаковка для весовых товаров. Имеет вес `tw` (определён в SKU).

### gw (gross weight)
Поле в SKU. Вес **одного ящика** брутто (для расчёта теоретического веса в рейсах).

### tw (tare weight)
Поле в SKU. Вес **одной тары** (одного пустого ящика).

### tp (товарный тип)
Поле в SKU. `0` — весовой товар, `1` — тарный товар.

### fw (fact weight)
Фактический вес из накладной (для строки закупки в рейсе). Если указан — используется вместо теоретического `thW = qty × gw`.

### thW (theoretical weight)
Теоретический вес: `qty × gw_per_box`. Используется в рейсе, если `fw` не задан.

### Заявка-позиция (item)
Строка `items[i]` в записи Sale (ЗД/ЗР). Описывает **что попросил** клиент.

### Отгрузка-позиция (shipment line)
Строка `shipment[i]` в записи Sale (ЗД/ЗР). Описывает **что фактически отгрузили**.

### Допродажа (на месте)
Позиция в доставке, которую клиент получает **дополнительно** — сверх заявленного — из [свободного объёма](#свободный-объём-доставки) машины. Сценарий: экспедитор приехал к клиенту, у него в машине ещё есть товар без привязки к заявке. Клиент видит и берёт.

В системе записывается как часть `shipment[]` существующей записи продажи (ЗД или ЗР), **не как отдельная сущность**. Аналитически отделить допродажу от выполнения заявки можно сравнением `shipment[]` с `items[]`: позиция, которой нет в `items[]`, — допродажа.

### Списание (writeoff)
Уменьшение количества товара на складе по причинам, не связанным с продажей: испортилось, разбилось, утрачено, утилизировано.

Записывается как [складская операция](#складская-операция-whop) с `opType="writeoff"`. Уменьшает остаток в FIFO-партиях (`batch.qtyRem`).

Списание — это **внутренняя операция склада**, не порождает финансовых обязательств перед клиентами или поставщиками. Стоимость списания — это **убыток владельца** (товар уже оплачен поставщику, но не будет продан).

**Не путать**:
- [Возврат с доставки](#возврат-с-доставки-return-to-warehouse) — товар, не проданный в доставке, физически возвращается на склад (увеличивает `qtyRem`, не уменьшает)
- [Возврат за брак](#возврат-за-брак-defect_refund) — денежный возврат клиенту за плохое качество, без физического движения товара

⚠️ Учёт стоимости списаний как отдельной финансовой статьи (отчёт о потерях) — отсутствует. См. [GAP-012](gaps.md).

### Возврат с доставки (return-to-warehouse)
Товар, **не проданный** во время доставки и возвращающийся на склад. Учёт в **единицах SKU** (ящиках, мешках, коробках) — та же единица, что у [свободного объёма](#свободный-объём-доставки) в машине.

Сценарии:
- Клиент отказался от части заявки на месте
- Свободный объём не был полностью распродан как допродажи
- Доставка отменена или прервана

Записывается как [складская операция](#складская-операция-whop) с `opType="return"`. Возвращает товар в FIFO-партии (увеличивает `batch.qtyRem`). Не связано с деньгами — это **исключительно учёт физического движения товара**.

См. также [Возврат за брак](#возврат-за-брак-defect_refund) — это другое.

### Свободный объём (доставки)
Часть товара в машине доставки, **не привязанная к конкретной заявке** клиента и доступная для допродаж на месте.

Учёт ведётся в **единицах SKU** (ящиках, мешках, коробках), не в кг. По каждому SKU в машине:
```
Загружено = Сумма заявок клиентов + Свободный объём    [всё в ед. SKU]
```

Экспедитор видит по каждой позиции: "под заявку клиента N ящиков, свободно M ящиков". После каждой допродажи свободный остаток уменьшается. Жёсткое правило: нельзя отгрузить клиенту больше, чем заявка + свободный остаток (по этому SKU).

Кг появляются позже — при отгрузке конкретному клиенту через взвешивание (для весовых). До взвешивания работа идёт только в количестве тары/упаковок.

Свободный объём — операционное понятие момента доставки. Нераспроданный остаток после завершения доставки возвращается на склад как [возврат](#возврат-return).

## 4. Финансовые термины

### Тип цены клиента
- `opt` — оптовая
- `mid` — средний опт
- `ret` — розница

Хранится в карточке клиента в поле `pt`. Используется в [Прайс-листе](#прайс-лист-price-list) для определения уровня цены.

### Округление вверх до кратных 5 ₽
Финансовая операция, применяемая при расчёте **оптовой** цены:

```
optPrice = ceil(optRaw / 5) × 5
```

Результат всегда округляется **вверх** до ближайшего числа, кратного 5.

Применяется **только к оптовой** цене. `mid` и `ret` формируются от уже округлённой `optPrice` **без дополнительного округления**.

В коде — функция `roundUp5(v) = Math.ceil(v / 5) * 5` (стр. 307).

**Цель** — получать "красивые" целые цифры в прайсе, удобные для устного озвучивания и быстрых расчётов клиента.

**Примеры**:
- `optRaw = 247.3` → `optPrice = 250`
- `optRaw = 250.0` → `optPrice = 250`
- `optRaw = 250.1` → `optPrice = 255`

### Маржа (margin)
Разница между ценой продажи и [себестоимостью](#себестоимость-costpu-cost-per-unit) единицы товара. Может выражаться:

- **В абсолютном виде**: `margin = price − costPU` (₽/кг или ₽/единица)
- **В процентном виде**: `margin% = (price − costPU) / price × 100`

⚠️ Не путать с [наценкой](#наценка-markup):
- **Наценка** считается **от себестоимости** (например, `mkOpt = +20 ₽/кг к costPU`)
- **Маржа** считается **от цены продажи** (показатель прибыльности)

Показатель "сколько мы зарабатываем с одного килограмма/коробки". В коде сейчас явно не вычисляется как отдельное поле, но все исходные данные есть (`costPU` и итоговые `opt`/`mid`/`ret`). Появится в отчётах прибыльности при разработке модуля "Финансы".

### ДДС (движение денежных средств) / Cashflow
Учёт фактических поступлений и выбытий денежных средств за период, **отдельно** от учёта [прибыли](#прибыль-profit--pl-profit--loss). Дополняет P&L, потому что прибыль и денежный поток могут расходиться: товар отгружен → прибыль есть, но клиент ещё не заплатил → денег нет.

**Поступления**:
- Оплата от клиентов: `saleData.paid` (для ПС), `shipmentPaid` (для ЗД/ЗР), ручные операции `settlements` с `opType="payment"`

**Выбытия**:
- Оплата [поставщикам](#поставщик-supplier): `trip.supplierPayments[]`, ручные `settlements` (acctType="supplier")
- Расходы рейса (`trip.expenses[]` где `paidBy="Мы"`): транспорт, закупщик, грузчик, экспедитор, таможня, погранслужбы, грузчик в Абхазии
- Расходы доставки: перевозчик доставки, грузчик
- Аренда склада, склад разное (когда появятся как [контрагенты](#контрагент-contragent))
- Отдельные платежи контрагентам через `settlements` (acctType="expense")

В **двух валютах**: GEL (закупка в Грузии) и RUB (всё остальное). Конвертация — по [курсу рейса](#курс-рейса-rate).

Отдельного отчёта ДДС в коде сейчас нет — будет реализован при разработке модуля "Финансы".

### Прибыль (profit) / P&L (Profit & Loss)
Финансовый результат деятельности за период.

```
Прибыль = Выручка − Себестоимость
```

Где:
- **Выручка** — сумма отгруженных продаж: `saleData.lines × price` для ПС, `shipmentTotal` для ЗД/ЗР
- **Себестоимость** — сумма (`costPU × количество`) по всем отгруженным позициям, плюс доли расходов рейса и доставки (пропорционально весу)

**P&L** (Profit & Loss) — отчёт о прибылях и убытках за период: выручка → минус себестоимость → минус прямые расходы → итоговый финансовый результат.

В коде сейчас P&L как готовый отчёт **не реализован**. Есть отдельные части (выручка по клиенту, себестоимость по партии), но единого отчёта по бизнесу нет. Описание появится в [20-domain/financial-reporting/](../20-domain/financial-reporting/) при разработке модуля "Финансы".

Перспектива: раздельный P&L **по офисам** — Фаза 3 архитектуры офисов (см. [20-domain/offices.md](../20-domain/offices.md)).

### Баланс (balance)
Сальдо взаиморасчётов с конкретной стороной (клиентом, поставщиком, контрагентом, партнёром) на текущий момент. Вычисляется на лету:

```
balance = charged − paid
```

**Знак баланса** зависит от типа стороны:

| Сторона | `balance > 0` | `balance < 0` |
|---|---|---|
| Клиент | клиент должен нам | предоплата / переплата клиента |
| Поставщик | мы должны поставщику | у нас переплата |
| Контрагент (водитель, таможня и т.д.) | мы должны | у нас переплата |
| Партнёр (Лия) | Лия должна нам | мы должны Лие |

Источники начислений (`charged`) и оплат (`paid`):
- Автоматически — из продаж, рейсов, доставок
- Вручную — операции в `trade-settlements-v2`. [Возврат за брак](#возврат-за-брак-defect_refund) учитывается через сторону `paid` (уменьшает баланс клиента в нашу пользу)

⚠️ **Баланс не хранится в БД** — всегда вычисляется в момент отображения. Это упрощает консистентность (один источник истины — операции), но может быть медленнее на больших объёмах.

См. реализацию: код `getClientSummary`, `getSupplierSummary`, `getExpenseSummary`, `getPartnerData`. См. также [20-domain/settlements/](../20-domain/settlements/).

### Курс рейса (rate)
Курс конвертации грузинских лари (**GEL**) в российские рубли (**RUB**) для конкретного рейса. Используется при пересчёте всех закупок и расходов рейса, выраженных в GEL, в рубли — для расчёта себестоимости и взаиморасчётов.

⚠️ В `trip.rate` хранится в формате **"сколько GEL за 1000 RUB"** (историческое решение). Реальный курс RUB/GEL вычисляется как `rate = 1000 / trip.rate`.

Например, `trip.rate = "34.2"` → 1 GEL = 1000 / 34.2 ≈ 29.24 ₽.

Курс задаётся при создании рейса (вводится на основе фактического обмена в Грузии). После фиксации **не меняется** — это исторический курс этой конкретной закупки.

См. формулы расчёта: [20-domain/settlements/liya-partner.md](../20-domain/settlements/liya-partner.md), раздел 5.

### Наценка (markup)
Добавочная сумма, прибавляемая к [себестоимости](#себестоимость-costpu-cost-per-unit) (для опта) или к оптовой цене (для mid/ret) для получения продажной цены соответствующего уровня.

В коде — поля `mkOpt`, `mkMid`, `mkRet` (markup для opt / mid / ret).

Дефолтные значения:
- `mkOpt = 20` (₽/кг для весовых, ₽/кг × tarW для тарных)
- `mkMid = 10` (поверх optPrice)
- `mkRet = 30` (поверх optPrice)

Особенность для **тарных товаров**: наценка указана в "₽/кг", но применяется к **весу одной тары** (`tarW = gw − tw`). То есть фактическая наценка к одной упаковке = `mk × tarW` ₽/единица.

Может быть переопределена для конкретной позиции через `plData.overrides[prodId|skuId].{mkOpt,mkMid,mkRet}`.

Подробно: [20-domain/pricing.md](../20-domain/pricing.md).

### Прайс-лист (price list)
Сущность с актуальными ценами на товары для трёх уровней клиентов ([opt / mid / ret](#тип-цены-клиента)). Хранится в `trade-pricelist-v1`.

Цены формируются от [себестоимости](#себестоимость-costpu-cost-per-unit) + [наценка](#наценка-markup) по правилам:
- **opt** = costPU + 20 ₽ → округление вверх до кратных 5 ₽
- **mid** = optPrice + 10 ₽ (без округления)
- **ret** = optPrice + 30 ₽ (без округления)

Структура `plData`:
- `defaults` — глобальные наценки `{mkOpt, mkMid, mkRet}`
- `overrides` — per-position переопределения наценок и **ручная фиксация opt** (`manualOpt`)
- `clients` — индивидуальные цены для конкретных клиентов (`plData.clients[clientId][prodId|skuId]`)

Полные правила и формулы: [20-domain/pricing.md](../20-domain/pricing.md).

### Себестоимость (costPU, cost per unit)
Полная стоимость единицы товара после прихода на склад. Включает:
- закупочную цену у поставщика (`purchRUB` после конвертации валюты)
- долю общих расходов рейса, распределённых **пропорционально брутто-весу** (`expShare`)

Хранится во внутренних расчётах как поле `_costPerUnit` в costItems рейса и как `costPerUnit` в [FIFO-партии](#партия-fifo-batch). Используется как база для [прайс-листа](#прайс-лист).

Берётся из **самого свежего рейса**, в котором был товар (статус ≥ "В пути"). Единицы:
- Весовой товар: **₽/кг** (по нетто-весу)
- Тарный товар: **₽/единица** (за ящик/мешок)

Подробно — [20-domain/pricing.md](../20-domain/pricing.md), раздел "Себестоимость единицы".

⚠️ Текущая модель подразумевает, что закупка идёт через рейс из Грузии. При появлении функции "закупка у местных/российских поставщиков" правило учёта себестоимости будет дорабатываться (без рейса → без `expShare` рейса). См. [GAP-009](gaps.md).

### Доля партнёра
Доля Лии в расходах рейса по весу: `pW / tW`, где `pW` — вес партнёра, `tW` — общий вес. См. [20-domain/settlements/liya-partner.md](../20-domain/settlements/liya-partner.md).

### Возврат за брак (defect_refund)
Денежная компенсация клиенту за товар, оказавшийся плохого качества после получения. **Не возврат товара физически на склад** — это уменьшение долга клиента (или возврат денег) на сумму бракованной части.

Распознаётся ботом/Евой из накладной по строке "Возврат" / "Брак". Записывается как ручная операция в `trade-settlements-v2`:
```
acctType: "client", opType: "defect_refund", amount: "положительное строкой"
```

Баланс клиента = Отгрузки − Оплаты − Defect_refund (система сама вычитает).

Сумма (`amount`) — что вернули в деньгах. Описание (`desc`) — за что (например, *"5 кг черри по 200 ₽"*).

См. [40-system/data-formats/settlement.md](../40-system/data-formats/settlement.md).

**Не путать** с [Возвратом с доставки](#возврат-с-доставки-return-to-warehouse) — это про физический товар, не про деньги.

## 5. Учётные термины

### Складская операция (WhOp / warehouse operation)
Запись в журнале склада, фиксирующая движение товара (приход, отгрузка, списание, возврат, начальный остаток). Хранится в `trade-whops-v1`. ID формата `WH-...`.

Дополняет [FIFO-партии](#партия-fifo-batch) — фиксирует фактические движения, тогда как партии содержат то, что пришло через рейс.

Полное описание полей и типов `opType` (initial, shipment, writeoff, return, income): [40-system/data-formats/whop.md](../40-system/data-formats/whop.md).

### Партия (FIFO batch)
Логическая единица учёта на складе — порция товара, поступившая одним рейсом от одного поставщика. Каждая партия имеет уникальную [себестоимость](#себестоимость-costpu-cost-per-unit), зафиксированную в момент создания. Списывается по правилу [FIFO](#fifo-first-in-first-out).

Хранится в `trade-batches-v1`, ID `B-XXXX`.

Полное описание формата и жизненного цикла: [40-system/data-formats/batch.md](../40-system/data-formats/batch.md).

### FIFO (First In First Out)
Первый пришёл — первый ушёл. Способ списания партий со склада: при отгрузке списываются первые поступления.

### paidBy
Поле в строке расхода рейса (`trip.expenses[i].paidBy`), указывающее, **кто фактически отдал деньги** контрагенту по этой статье. Принимает только **два значения**:
- `"Мы"` — заплатили мы из своих средств
- `"Партнёр"` — заплатил [партнёр](#партнёр-по-рейсу--partner) (Лия) из своих средств

Это ключевое поле для правильного расчёта взаиморасчётов:
- `paidBy="Партнёр"` → [контрагент](#контрагент-contragent) в "Расходах" автоматически считается **закрытым** (Лия заплатила сама), но **мы становимся должны Лие** нашу долю по весу.
- `paidBy="Мы"` → контрагент остаётся должником до ручного `payment` в модуле Расчёты, а **Лия становится должна нам** её долю.

Никаких других значений (`"Оба"`, `"50/50"` и т.д.) поле не принимает — плательщик всегда один.

См. формулы и каскад: [20-domain/settlements/liya-partner.md](../20-domain/settlements/liya-partner.md), раздел 5.

### Двухшаговая модель учёта (request → shipment)
Принцип учёта для [ЗД](#зд-order-stock) и [ЗР](#зр-order-trip): отдельно сохраняется **исходная заявка** (`items[]`) и **фактическая отгрузка** (`shipment[]`). Позволяет видеть расхождения между обещанным и доставленным. Не применяется для [ПС](#пс-sale-direct) — там одношаговая модель.

Полное описание: [ADR-007](../90-decisions/ADR-007-sales-canonical-model.md), раздел 5.

### Каскад статусов (status cascade)
Автоматическая смена статусов связанных записей при изменении статуса "родительской" сущности. В системе действуют два каскада: от рейса (через `tripId`) к ЗР-заявкам и от загрузки доставки (через `deliveryId`) к ЗД/ЗР.

Полное описание правил, переходов и свойств: [20-domain/sales-lifecycle.md](../20-domain/sales-lifecycle.md).

## 6. Роли

> Полные описания ролей (обязанности, функции, AS-IS / TO-BE) — в [`30-roles/`](../30-roles/). В глоссарии — только короткие определения для навигации.

### Владелец (owner)
Высший уровень роли в команде. Принимает стратегические решения, контролирует все области бизнеса, имеет полный доступ к данным системы.

Ведёт операционку компании: учёт продаж и доставок, координацию команды, контроль выполнения заявок. Один из главных пользователей системы и Евы.

Полное описание: [30-roles/<as-is|to-be>/ops-manager.md](../30-roles/) (заглушка).

### Закупщик (buyer)
Сотрудник или контрагент, проводящий закупки товара у поставщиков (преимущественно в Грузии). Может иметь двойную природу: как сотрудник в `trade-cat-staff` и как получатель платежей за услугу — [контрагент](#контрагент-contragent) в `trade-cat-contragents`.

### Менеджер продаж (sales_manager)
Ведёт клиентов, принимает заказы (заявки), контролирует расчёты с клиентами, формирует прайс под клиента. Каждый [клиент](#клиент) в системе привязан к конкретному менеджеру через `client.managerId`.

Полное описание: [30-roles/<as-is|to-be>/sales-manager.md](../30-roles/) (заглушка).

### Экспедитор (expeditor)
Загружает товар в машину, развозит клиентам, проводит взвешивание и фиксирует факт отгрузки (`completeClient`), фиксирует возвраты с доставки. См. [GAP-013](gaps.md) о статусе роли в команде.

Полное описание: [30-roles/<as-is|to-be>/expeditor.md](../30-roles/) (заглушка).

### Кладовщик (warehouse)
Сотрудник, ведущий учёт остатков на складе: принимает товар по приходу рейса (подтверждает фактические количества при переходе trip → "На складе"), формирует и списывает товар со склада для погрузки в машину при организации доставок, оприходует на склад непроданный товар (возвраты с доставки), оформляет списания (брак, порча), в конце каждого дня делает инвентаризацию товара на складе.

Полное описание: [30-roles/<as-is|to-be>/warehouse.md](../30-roles/) (заглушка).

### Бухгалтер (accountant)
Сотрудник, ведущий финансовый учёт: проверяет и фиксирует платежи (settlements), формирует отчётность (P&L, ДДС, акты сверки), контролирует балансы по контрагентам, поставщикам и клиентам.

Полное описание: [30-roles/<as-is|to-be>/accountant.md](../30-roles/) (заглушка).

### Грузчик (loader)
Внешний контрагент, выполняющий физическую погрузку/разгрузку товара. В системе учитываются как контрагенты категории `loader` с двумя статьями расходов рейса: `loader` (грузчики в Грузии, валюта GEL) и `loaderAbh` (грузчики в Абхазии, валюта RUB).

Полное описание: [30-roles/<as-is|to-be>/loader.md](../30-roles/) (заглушка).

### Водитель (driver)
Внешний контрагент, перевозящий груз. В системе учитываются как контрагенты категории `transport`. На каждый рейс из Грузии в Абхазию закрепляется конкретный водитель — статья расхода `transport` рейса.

Полное описание: [30-roles/<as-is|to-be>/driver.md](../30-roles/) (заглушка).

### Генеральный директор (gen_director)
Управленческая роль высшего звена. Оперативное управление компанией, координация всех функций, контроль ключевых процессов и команды.

Полное описание: [30-roles/<as-is|to-be>/gen-director.md](../30-roles/) (заглушка).

### Финансовый директор (fin_director)
Управленческая роль высшего звена в финансовом контуре. Управление финансами, бюджетирование, контроль P&L и денежных потоков, утверждение крупных платежей.

## 7. Технические термины

### app_storage
Единственная таблица в БД (PostgreSQL `trade_db`). KV-схема: `key` (varchar(255) primary key), `value` (text — JSON-строка), `updated_at` (timestamp). Универсальное хранилище для всех сущностей системы.

Полное описание: [40-system/database/overview.md](../40-system/database/overview.md).

### Storage-ключ
Имя в таблице [app_storage](#app_storage), под которым хранится JSON-блоб. Например, `trade-sales-v1`. Полный перечень: [40-system/database/storage-keys.md](../40-system/database/storage-keys.md).

### KV-store
Key-value хранилище. Текущая модель БД (одна таблица [app_storage](#app_storage) с колонками `key` / `value`).

### Бандл (bundle)
Собранный JavaScript-файл фронтенда после сборки [Vite](#vite), раздаётся браузеру через [Nginx](#nginx). Имеет хешированное имя вида `index-XXXXXX.js`, лежит в `/var/www/trade/public/assets/`. На каждый build генерируется новый бандл с новым хешем.

См. процесс сборки: [40-system/deployment.md](../40-system/deployment.md).

### Vite
Инструмент сборки фронтенда. Превращает исходный JSX (`trade_app_v3.jsx`) в оптимизированный JavaScript-бандл. Запускается командой `npx vite build` на VPS из директории `/var/www/trade/frontend/`. Текущая версия — Vite 5.4.

См. процесс деплоя: [70-operations/runbooks/deploy-frontend.md](../70-operations/runbooks/deploy-frontend.md).

### PM2
Менеджер процессов Node.js, используемый на VPS для запуска и контроля долгоживущих сервисов. Управляет процессами `trade-api` (Express API на порту 3001) и в перспективе процессом Евы. Сохраняет состояние через `pm2 save`, автоматически поднимает упавшие процессы.

См. инфраструктуру: [70-operations/infrastructure.md](../70-operations/infrastructure.md).

### Nginx
Веб-сервер на VPS. Раздаёт статический фронтенд (бандл из `/var/www/trade/public/`) и проксирует запросы `/api/*` на Node-процесс `trade-api` (порт 3001). Также обрабатывает HTTPS через Let's Encrypt сертификаты.

См. инфраструктуру: [70-operations/infrastructure.md](../70-operations/infrastructure.md).

### VPS (Virtual Private Server)
Виртуальный сервер, на котором развёрнута вся система: [Nginx](#nginx), PostgreSQL, Node-процессы `trade-api` и (в перспективе) Ева. IP 108.61.167.168, OS Ubuntu 22.04, доступ через SSH под пользователем root. Реальные доступы — в локальном `~/secrets-trade/credentials.md` (вне репо).

Полное описание: [70-operations/infrastructure.md](../70-operations/infrastructure.md).

### Express API (trade-api)
HTTP-сервер на Node.js (Express 5), работающий на VPS на порту 3001. Файл `/var/www/trade/server.js`, ~50 строк кода. Имеет 4 [эндпоинта](#эндпоинт-api-endpoint). Без бизнес-логики — прокси к [app_storage](#app_storage). Авторизации нет (см. [35-security](../35-security/)).

Полное описание: [40-system/api.md](../40-system/api.md).

### Эндпоинт API (endpoint)
URL + HTTP-метод, который обрабатывает [Express API](#express-api-trade-api). Сейчас 4 эндпоинта:
- `GET /api/storage/:key` — прочитать значение по ключу
- `POST /api/storage/:key` — записать значение (атомарно перезаписывает целиком)
- `DELETE /api/storage/:key` — удалить ключ
- `GET /api/health` — проверка живости

Полное описание: [40-system/api.md](../40-system/api.md).

### SSH-ключ (Ed25519)
Криптографическая пара ключей для беспарольного доступа Mac → GitHub. Приватный ключ — `~/.ssh/id_ed25519` (защищён passphrase, хранится в macOS Keychain), публичный — на GitHub. Создан 2026-04-28. Алгоритм Ed25519 (современный стандарт).

См. инфраструктуру и доступы: [70-operations/infrastructure.md](../70-operations/infrastructure.md).

### Seed-блок
Блок инициализации тестовых данных в коде `trade_app_v3.jsx`. Применяется один раз при старте, маркер записывается в БД (`trade-seed-vXX-full`). После канонизации seed-блоки данных продаж/рейсов **удалены** ([ADR-007](../90-decisions/ADR-007-sales-canonical-model.md)).

### Front matter
YAML-блок в начале каждого `.md`-файла в `kb/` с метаданными (title, status, references, и т.д.). См. [conventions.md](conventions.md).

### ADR
Architecture Decision Record. Файл `ADR-NNN-имя.md` в `kb/90-decisions/` с фиксацией архитектурного решения.

### Gap
"Белое пятно" — обнаруженный пробел в документации или коде. Записывается в [gaps.md](gaps.md).

### Runbook
Пошаговая инструкция повторяющейся операции. Лежит в `kb/70-operations/runbooks/`.

## 8. ИИ-термины

> Базовый набор. Полноценное наполнение — после проектирования архитектуры Евы (Q3 2026).

### ИИ-агент (AI agent)
Программа на основе LLM, способная вести диалог, использовать инструменты (вызывать API, читать и писать в БД), помнить контекст между сессиями. В нашем проекте — [Ева](#ева-eva) и в перспективе финансовый агент.

Полное описание архитектуры агентов: [50-agents/_shared/](../50-agents/_shared/) (заглушка).

### Ева (Eva)
Основной ИИ-агент проекта в Telegram. Замещает старого бота-экспедитора. Будет работать со всеми ролями (операционный менеджер, закупщик, экспедитор, менеджер продаж, кладовщик, бухгалтер, клиент, партнёр, владелец) с разными промптами и правами под каждую роль. Использует Claude Sonnet 4.6 через AWS Bedrock. На стадии проектирования.

Полное описание: [50-agents/eva/README.md](../50-agents/eva/README.md). Решение о замещении бота: [ADR-005](../90-decisions/ADR-005-eva-replaces-bot.md).

### Промпт (prompt)
Текстовая инструкция для LLM, определяющая её роль, поведение и доступные инструменты. В архитектуре Евы три уровня:
- **system-base** — общая часть, единая для всех ролей
- **role-prompt** — специфичный для роли (например, для оп-менеджера, для закупщика)
- **session** — динамический контекст текущего диалога

Полное описание: [50-agents/eva/prompts/](../50-agents/eva/) (заглушка).

### Инструмент (tool)
Функция, которую [агент](#ии-агент-ai-agent) может вызвать в процессе работы: чтение из БД, запись в БД, вызов внешнего API, отправка сообщения. У каждого инструмента есть описание параметров и поведения, которое агент видит в своём контексте.

Полное описание: [50-agents/eva/tools/](../50-agents/eva/) (заглушка).

### Сценарий (scenario)
Типовая бизнес-задача, которую агент решает по заранее описанным шагам. Например: распознать накладную, создать нового клиента, оформить возврат за брак. Каждый сценарий описан в [50-agents/eva/scenarios/](../50-agents/eva/) с шагами, инструментами и условиями.

Полное описание: [50-agents/eva/scenarios/](../50-agents/eva/) (заглушка).

### Активный сценарий (`activeScenario`)
Текущий выполняемый сценарий Евы для конкретного `chatId`. Хранится в сессии Евы (`Map<chatId, session>`, in-memory; миграция в Postgres — Ит.4). Используется, в частности, диспетчером контекста фото: если активный сценарий **ожидает фото** (поле `session.expectingPhoto = {base, entityId}`), пришедшее фото уходит в этот сценарий без уточняющего диалога.

См. [40-system/photo-infrastructure.md](../40-system/photo-infrastructure.md), слой (г).

## 9. Фото-инфраструктура

> Принципиальные термины из [ADR-016](../90-decisions/ADR-016-photo-infrastructure.md). Полное описание — [40-system/photo-infrastructure.md](../40-system/photo-infrastructure.md).

### Фото-инфраструктура
Единый пайплайн загрузки, хранения, привязки и просмотра фотографий: 5 слоёв (а→д) + 4 независимых базы фотографий ([GAP-018](gaps.md#gap-018), [GAP-020](gaps.md#gap-020), [GAP-021](gaps.md#gap-021), [GAP-022](gaps.md#gap-022)). Принципиальная архитектура — [ADR-016](../90-decisions/ADR-016-photo-infrastructure.md). Детали реализации — [40-system/photo-infrastructure.md](../40-system/photo-infrastructure.md).

### База фотографий
Логически независимая группа фотографий с одинаковой семантикой привязки. Сейчас четыре базы: `client-locations` (витрины клиентов), `shipments` (отгрузочные накладные), `skus` (фото товаров в каталоге), `purchase-offers` (фото с закупок для рассылок). Расширяемо — пункт 5 разбора 2026-05-30.

### `photoMeta`
Объект-запись о фотографии в массиве `photoField` на бизнес-сущности: `{url, uploadedBy, uploadedAt, caption, fileUniqueId, size, width, height}`. Формат **одинаков** для всех баз. Полная спецификация — в [client.md](../40-system/data-formats/client.md#объект-photometa-элемент-массива-locationphotos).

### `photoField`
Поле на бизнес-сущности, в котором лежит массив `photoMeta`. По базам: `client.locationPhotos[]`, `sale.shipmentPhotos[]`, `sku.photos[]`, `purchase.purchasePhotos[]` (или `trip.purchasePhotos[]`).

### `RawPhoto`
Промежуточная структура слоя (а) фото-инфраструктуры: нормализованное представление пришедшего из Telegram сообщения-фото (file_id, file_unique_id, локальный путь в `/tmp/eva/...`, sender, caption, mediaGroupId). Из неё диспетчер контекста собирает данные для endpoint `/api/photos`.

### Диспетчер контекста (фото)
Компонент сервиса Евы (слой «г» фото-инфраструктуры), решающий, к какой `base` и `entityId` привязать пришедший `RawPhoto`. Активный сценарий имеет приоритет, иначе — inline-кнопки выбора базы. Дальше передаёт работу handler'у базы.

### Handler базы (фото)
Per-base обработчик (`code/eva/src/photo/handlers/<base>.js`) — знает, как достать `entityId` для своей базы и что делать после загрузки (например, для `shipments` запускать распознавание накладной). Новая база = новый handler + строка в конфиге `PHOTO_BASES`.

### `PHOTO_BASES`
Конфиг trade-api (`server.js` или `photo-bases.js`), сопоставляющий имя базы с `{kvKey, photoField, findById, label}`. Точка расширения для новых баз фото без изменения общего пайплайна.

### `X-Photo-Token` *(не используется в Блоке 1)*
HTTP-заголовок с shared secret для авторизации `POST/DELETE /api/photos`. Был зарезервирован при дизайне 2026-05-30, но **снят при реализации Блока 1** — `/api/photos` пошёл без auth, симметрично `/api/storage`. Обоснование: бандл фронта публичен, токен в нём не защита, а театр. См. [ADR-016](../90-decisions/ADR-016-photo-infrastructure.md). После RBAC оба endpoint-а одинаково перейдут на JWT.

### `expectingPhoto`
Поле сессии Евы: `{base, entityId}`. Сценарий ставит его перед шагом, на котором ждёт фото; диспетчер контекста видит флаг и проводит пришедшее фото без уточняющего диалога. Сбрасывается после получения.

### `<PhotoGallery>` (UI-компонент)
Универсальный React-подобный компонент в trade_app для всех четырёх баз. Пропсы: `photos`, `editable`, `onUpload`, `onDelete`. Внутри — горизонтальная полоса миниатюр + lightbox при клике. Расширяемость на стороне UI — одна строка в любой секции карточки.
