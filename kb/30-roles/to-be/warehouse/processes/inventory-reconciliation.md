# Процесс: ежедневная сверка товарных остатков

> Бизнес-процесс роли [кладовщика](../README.md), закрывает [GAP-050](../../../../00-meta/gaps.md#gap-050). Техническая сторона Евы — в сценарии [eva/scenarios/inventory-reconciliation.md](../../../../50-agents/eva/scenarios/inventory-reconciliation.md). Единый калькулятор остатка/сверки — [ADR-025](../../../../90-decisions/ADR-025-single-domain-layer.md).

## Зачем

Каждый день в конце смены сверять **фактический** товар на складе с **книжным** остатком (FIFO-партии), чтобы ловить кражу, бой, пересорт, ошибки ввода и усышку — пока расхождение маленькое и понятно, что произошло. Без ежедневной сверки ошибки копятся и портят остаток, себестоимость и P&L.

## Два слоя сверки (важно для эргономики)

| Слой | Что | Частота | Единица |
|---|---|---|---|
| **A. Пересчёт мест** (ядро GAP-050) | книжный остаток ↔ факт. кол-во ящиков/мешков | **ежедневно** | штуки/места |
| **B. Взвешивание** ([GAP-054](../../../../00-meta/gaps.md#gap-054)) | нетто-кг партии ↔ факт. вес | по требованию (партия >7 дней / обнуление) | кг |

Ежедневная рутина = слой **A** (быстро). Вес кладовщик вводит, только когда система/процесс просит — это поток усышки.

## Действующие лица

- **Кладовщик** (`warehouse`) — пересчитывает товар, вводит факт в мини-апп.
- **Ева** — вечером напоминает кладовщику; утром шлёт сводку владельцу/ГД; по запросу показывает расхождения.
- **Владелец / ГД** — видят расхождения, решают по разбору/списанию.

## Шаги

| # | Кто | Действие | Правило |
|---|---|---|---|
| 1 | Ева | Вечером (≈19:00) напоминает кладовщику «пора сверить остатки» | CRM-крон по роли `warehouse` со своим складом |
| 2 | Кладовщик | Открывает мини-апп → вкладка **«📋 Сверка»** → «Новая сверка» | Книжный остаток уже подставлен (единый калькулятор) |
| 3 | Кладовщик | По каждой позиции вводит **факт. количество мест** | Δ и флаг (сходится/недостача/излишек) показываются вживую |
| 4 | Кладовщик | При необходимости — **факт. вес, кг** (если взвешивал) | Вес сверяется с допуском (по умолчанию 5%) |
| 5 | Кладовщик | Указывает **причину** по расхождениям (бой/пересорт/усышка) | Опционально, но желательно |
| 6 | Кладовщик | «Закрыть сверку» → запись `ИНВ-NNN` | Расхождения зафиксированы; остаток/склад **не правится автоматически** (v1) |
| 7 | Ева | Утром шлёт владельцу/ГД сводку за вчера | Была ли сверка, сколько расхождений; если не проведены — подсказка про кнопку |
| 8 | Владелец/ГД | Разбирают расхождения и **проводят** сверку | TradeApp «Склад → ✂️ Усышка» → кнопка «Провести» у `ИНВ-N` (фаза 2, [GAP-065](../../../../00-meta/gaps.md#gap-065) ✅ 2026-07-06): недостача → списание FIFO в B2; излишек мест → корр-партия по цене последней закупки (контра-B2); связь `СПИС↔ИНВ`; сторно комплектом. Fail-closed: если книга менялась после сверки — нужна новая сверка |

## Статусы расхождения

- **сходится (ok)** — факт = книга.
- **недостача (short)** — факт < книги (кража/бой/усышка).
- **излишек (surplus)** — факт > книги.
- **пересорт (phantom)** — посчитали то, чего в книге нет.

## Роли и доступ (Обязательство 7)

- **Инициирует/исполняет:** `warehouse` — только свой склад (`officeId` из карточки сотрудника), fail-closed гейт `requireInventory` (`owner`/`gen_director`/`warehouse`/`ops_manager`).
- **Видит/анализирует:** `owner`, `gen_director`, `fin_director` (отчёт в trade_app, сводка/ответы Евы).
- **Решает разбор/проводку:** `owner`/`gen_director` (фаза 2).
- Закупочные цены кладовщику не показываются.

## Границы (что НЕ делаем — осознанно)

- Не правим остаток **автоматически** по расхождению: проводка — всегда ручное решение владельца/ГД по кнопке (решение владельца 2026-07-06; кладовщик мог ошибиться в пересчёте).
- Кладовщик проводить не может — только фиксирует (fail-closed).
- Не требуем ежедневного взвешивания (вес — по требованию).
- Пересортицу не различаем: излишек всегда оприходуется как чистый излишек (корр-партия), недостача списывается отдельно.

## Реализация (ADR-025, один калькулятор)

Книжный остаток и сверка считаются **единым** `stock-service.cjs` (`stockSnapshot` + `reconcile`) — его зовут все поверхности: браузер (`/api/v2/stock`, `/api/v2/inventory`), мини-апп (`/api/mini/inventory`), Ева (топик `inventory`). Сущность-событие `inventory_counts` (`ИНВ-NNN`) хранит факт сверки для аудита, не дублируя расчёт.

**Фаза 2 (проводка, 2026-07-06):** `POST /api/v2/shrinkage {invId}` — сервер строит строки списания из зафлагованных строк сверки (канон `shrinkage-service`, ADR-025), гард `expectBook*` (книга не менялась после сверки), связь `СПИС.invId ↔ ИНВ.shrId`, дата проводки = дата сверки. Сторно — `POST /api/v2/shrinkage/cancel` (откат по `allocs[]`, документ `cancelled`, `shrId` снимается). Подробности учёта — [rulebook, статья shrinkage](../../../../20-domain/financial-reporting/accounting-rules/pay-categories-rulebook.md).
