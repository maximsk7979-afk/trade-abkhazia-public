## 7. ФОРМАТЫ ДАННЫХ (актуальные)

### Прямая продажа со склада (ПС)
```json
{
  "id": "ПС-087",
  "type": "sale-direct",
  "date": "2026-03-24",
  "clientId": "К-XXX",
  "officeId": "О-001",
  "managerId": "С-XXX",
  "status": "Отгружено",
  "deliveryId": "",
  "cm": "telegram",
  "history": [],
  "saleData": {
    "lines": [
      {
        "prodId": "Т-XXX",
        "skuId": "SKU-XXX-XX",
        "qty": "",
        "qtyTar": "5",
        "wBrutto": "32.5",
        "price": "260"
      }
    ],
    "paid": "5000"
  }
}
```

### Продажа доставки (ДС) — АКТУАЛЬНЫЙ ФОРМАТ
```json
{
  "id": "ДС-051",
  "type": "delivery-sale",
  "date": "2026-03-24",
  "clientId": "К-XXX",
  "status": "Отгружено",
  "deliveryId": "Д-011",
  "cm": "telegram",
  "history": [],
  "saleData": {
    "lines": [...],
    "paid": "0"
  }
}
```

> ⚠️ УСТАРЕВШИЙ ФОРМАТ — НЕ ИСПОЛЬЗОВАТЬ: `type: "order-stock"` + `shipment[]` + `shipmentTotal/shipmentPaid`
> Это формат старой системы. В коде, боте и ТЗ не упоминать и не использовать.

### Возврат за брак
```json
{
  "id": "S-REFUND-XXX",
  "acctType": "client",
  "clientId": "К-XXX",
  "opType": "defect_refund",
  "date": "2026-03-24",
  "amount": "1000",
  "desc": "Возмещение за брак: черри 5кг × 200₽"
}
```
- `amount` — всегда **положительное** число **строкой**
- Баланс клиента = Отгрузки − Оплаты − defect_refund (система сама вычитает)

### Сотрудник (trade-cat-staff)
```json
{
  "id": "С-001",
  "name": "Максим",
  "roles": ["owner"],
  "officeId": "О-001",
  "telegramChatId": "118206343",
  "telegramUsername": "",
  "whatsapp": "",
  "phone": "",
  "active": true
}
```
- `roles` — массив, возможные значения: `owner`, `gen_director`, `fin_director`, `ops_manager`, `expeditor`, `sales_manager`, `warehouse`, `buyer`, `accountant`, `loader`, `driver`
- `officeId` — ссылка на справочник офисов (О-001 Сухуми, О-002 Гагра, О-003 Гудаута)
- У одного сотрудника может быть несколько ролей

### Клиент (trade-cat-clients)
```json
{
  "id": "К-007",
  "n": "Аршак",
  "pt": "mid",
  "saleType": "ds",
  "wa": "+7...",
  "tg": "@username",
  "tgChatId": "123456789",
  "ynavUrl": "https://yandex.ru/maps/...",
  "managerId": "С-XXX"
}
```
- `pt` — тип цены: `opt` / `mid` / `ret`
- `saleType` — тип продажи: `ps` (со склада) / `ds` (доставка)
- `tgChatId` — для будущего бота-клиента
- `ynavUrl` — URL геолокации в Яндекс Навигаторе (для водителей)
- `managerId` — ссылка на сотрудника (С-XXX) с ролью `sales_manager`
- Клиент **не привязан** к складу — отгрузки могут быть с разных складов

### Офис / Склад (trade-cat-offices)
```json
{
  "id": "О-001",
  "n": "Сухуми",
  "active": true
}
```
- Офис = склад (единая сущность)
- ID-формат: О-001, О-002, О-003
- Текущие: О-001 Сухуми, О-002 Гагра, О-003 Гудаута

### Поля строки товара

| Поле | Весовой (tp=0) | Тарный (tp=1) |
|---|---|---|
| qty | "" (пусто) | кол-во штук строкой |
| qtyTar | кол-во ящиков строкой | "" (пусто) |
| wBrutto | расчётный брутто строкой | "" (пусто) |
| price | цена строкой | цена строкой |

## 8. ПРАВИЛА РАСЧЁТА ВЕСОВ

- `нетто = брутто − (qtyTar × tw)` — при вводе экспедитором
- `брутто = нетто + (qtyTar × tw)` — при фото-накладных
- **Тарные товары** (`tp=1`): чеснок, бананы, конференция груша — ТОЛЬКО `qty × price`, wBrutto = ""
- Разделитель дробей: запятая и точка равнозначны (5,8 = 5.8)

---

## 9. ПРАВИЛА ПРАЙС-ЛИСТА

- **Оптовая:** Себестоимость + 20 ₽/кг, округление вверх до кратных 5 ₽
- **Средний опт:** Оптовая + 10 ₽/кг (без дополнительного округления)
- **Розница:** Оптовая + 30 ₽/кг (без дополнительного округления)
- Себестоимость из последнего рейса, распределение расходов пропорционально весу брутто
- Тарные товары: наценка в ₽/кг × вес тары

### Правила:
1. ВСЕГДА брать свежий JSON-экспорт из UI перед написанием seed
2. Новый seed = все данные из экспорта + новые записи поверх
3. Новый блок вставляется ПОСЛЕ старого, ПЕРЕД `/* === END SEED V14 === */`
4. Старый блок (_SD3..._SD8) НЕ ТРОГАТЬ
5. Каждый seed — полный снимок всех массивов (не частичный)

## 11. АЛГОРИТМЫ БОТА (реализованы в v10)

Источник истины: `tz_prompt_v2.docx`

### Автоопределение типа ПС/ДС:
1. Есть `saleType` в карточке клиента → применить автоматически
2. Нет `saleType`, история ≥70% одного типа → применить + сохранить в карточку
3. История смешанная <70% → спросить кнопками → сохранить выбор в карточку
4. К-025 (разовый покупатель) → всегда ПС автоматически

### Возврат за брак:
- Распознавать строки "Возврат / Брак" в накладной
- Писать в `trade-settlements-v2` с `opType: "defect_refund"`

### Логика расхождения суммы:
- ≤50₽ — принять молча
- >50₽ — диалог: изменить вес / изменить цену / принять расчётную сумму

## 20. АРХИТЕКТУРА ОФИСОВ / СКЛАДОВ

**Принцип:** Офис = Склад (единая сущность `trade-cat-offices`).

### Утверждения (архитектурные):
1. Офис = склад. Нет разделения на офисы и склады
2. Каждый сотрудник привязан к конкретному складу/офису (`staff.officeId`)
3. Каждый покупатель привязан к конкретному менеджеру (`client.managerId`)
4. Покупатель **НЕ привязан** к складу — отгрузки могут быть с разных складов
5. Каждая продажа привязана к конкретному складу (`sale.officeId`)
6. Каждая продажа привязана к менеджеру через клиента (`sale.managerId` = `client.managerId`)

### Где используется officeId:
| Сущность | Поле | Назначение |
|---|---|---|
| Рейсы | `trip.officeId` | Целевой склад рейса |
| Партии FIFO | `batch.officeId` | На каком складе лежит |
| Продажи | `sale.officeId` | С какого склада отгружено |
| Складские операции | `whOp.officeId` | По какому складу |
| Доставки | `delivery.officeId` | С какого склада |
| Сотрудники | `staff.officeId` | Привязка к офису |

### Фазы реализации:
- **Фаза 1** ✅ Справочник офисов, миграция staff/client на officeId
- **Фаза 2** ✅ officeId во всех транзакционных сущностях + фильтрация в Складе
- **Фаза 3** (будущее): P&L по офисам, расходы по офисам

### По умолчанию:
- Все старые данные без officeId считаются как `О-001` (Сухуми)
- Новые записи получают officeId при создании
