# Eva — система памяти

> Как устроена память Евы и схема хранилища. Исходная модель — [ADR-013](../../90-decisions/ADR-013-eva-agent-architecture.md). **Финальные решения по слоям A–D (2026-05-31) — [ADR-017](../../90-decisions/ADR-017-eva-memory-architecture.md)**; объём помощника и изоляция данных клиента — [ADR-018](../../90-decisions/ADR-018-eva-universal-assistant.md). Общая архитектура — [architecture.md](architecture.md).

## Четыре слоя

| Слой | Что хранит | Где живёт | Когда грузится в контекст |
|---|---|---|---|
| **A. Сырые переписки** | каждое сообщение (вход/выход), клиент, канал, время; append-only | Postgres | последние N сообщений + извлечённые по необходимости |
| **B. Память клиента** | выжимка о клиенте + сжатое резюме отношений | Postgres | **целиком при каждом диалоге** с этим клиентом |
| **C. Общие знания** | бизнес-правила, товары, цены, правила продаж, база накладных | `kb/` → системный промпт | в системном промпте (кэш) |
| **D. Рабочая память** | текущая ветка диалога | контекст запроса | внутри одного разговора |

## Зачем разделение

Полная история клиента **никогда не помещается** в контекст целиком и удорожает каждый запрос. Поэтому:
- **A** — полный архив (источник истины, для людей и для извлечения), но в «голову» Евы идёт не весь.
- **B** — сжатая, постоянно обновляемая выжимка: именно она даёт ощущение «Ева меня помнит». Грузится целиком всегда.
- В контекст запроса = C (кэш) + B (клиент) + хвост A (+ извлечение из A при необходимости).

## Слой B — что в памяти клиента (финал, ADR-017)

B — сжатое «досье» клиента, **грузится в контекст целиком при каждом диалоге**. **Не дублирует карточку** `trade-cat-clients`: статику (сегмент, уровень цены, тип продажи, проекты, контакт) Ева читает из карточки. B хранит **поведение и отношения** — то, что менеджер держит «в голове». Два блока:

### Блок 1 — «О человеке» (Ева-друг)
| Поле | Что хранит | Источник |
|---|---|---|
| `address_form` | как обращаться: имя, «ты»/«вы» | переписка |
| `personal_facts` | семья, дети, родной город, значимые факты | переписка |
| `interests` | темы, на которые откликается (футбол, сад, рыбалка) | переписка |
| `comm_profile` | профиль общения — Ева ведёт сама по навыку-психологии (стиль + что ценит/избегать) | переписка + навык-психология |
| `life_context` | мягкие обстоятельства (открыл точку, переезжал) | переписка |
| `person_summary` | сжатый портрет личности | LLM из A |
| `important_dates` | **структурно**: ДР клиента и родственников, значимые даты — для проактивных поздравлений | переписка / знакомство |

### Блок 2 — «О работе с клиентом» (Ева-супер-менеджер)
| Поле | Что хранит | Источник |
|---|---|---|
| `assortment` | что обычно берёт (выжимка) | история продаж |
| `order_rhythm` | дни/частота заказов | даты заказов |
| `payment_behavior` | характер оплаты, отсрочки (**НЕ сумма долга** — она живьём) | расчёты + переписка |
| `delivery_prefs` | время, точка, кто принимает, въезд | переписка / онбординг |
| `price_sensitivity` | торгуется ли, цена vs качество | переписка + история |
| `quality_expectations` | проверяет ли товар, реакция на брак | переписка |
| `special_terms` | спец-договорённости, особые условия | переписка |
| `client_value` | масштаб/перспектива/тренд | история продаж |
| `business_summary` | краткая инструкция Еве «как с ним работать» | LLM из A + данные |

Правила: **долг — живьём** из расчётов; **ассортимент — выжимкой** в B. Набор полей **доучивается в процессе работы**.

### Приватность B («здравый фильтр»)
В B попадает только то, что **(а)** помогает работе/тёплому общению **И (б)** клиент был бы **рад**, что Ева это помнит. **Не кристаллизуем**: здоровье, семейные проблемы, политику, религию, личные финансы вне сделок, интимное. Чувствительное Ева слышит и реагирует **в моменте** (живёт в A), но в постоянный профиль не выносит. Доступ к A/B по роли, удаление по запросу клиента — [GAP-030](../../00-meta/gaps.md#gap-030).

## Контур обучения (как обновляется B)

**Ночной cron-проход** (`code/eva/src/memory-pass.js`, `30 3 * * *`; не после каждого диалога — дорого):
1. читает новые сообщения клиента из A + **детерминированную выжимку из истории продаж** (`code/eva/src/sales-history.js`: ассортимент, ритм, оборот/средний чек, тренд, характер оплаты — из отгруженных `trade-sales-v1`, без сумм долга);
2. извлекает новые факты, обновляет оба блока и резюме (с учётом фильтра приватности). Выжимка из продаж — **приоритетный источник** для `assortment`/`order_rhythm`/`client_value`/`payment_behavior`: переписка дополняет, но не перебивает цифры;
3. повторяющиеся паттерны у многих клиентов → очередь предложений к общей базе C (`eva_learning_queue`, подтверждение человеком — [ADR-012](../../90-decisions/ADR-012-eva-self-learning-plan.md)).

Кандидат прохода — клиент с **новыми сообщениями ИЛИ новыми отгрузками** с момента `B.updated_at` (watermark).

Память **по клиенту** (B) обновляется **Евой автоматически**, видна и правима сотрудником в CRM-модуле. **Общее знание (C) Ева сама НЕ пишет** — только предлагает, человек подтверждает (см. «Слой C» ниже).

## Слой C — общие знания (фиксированный, человеко-курируемый)

В системном промпте (кэш), собирается из `kb/`. **Ева C сама не переписывает** — только предлагает в `eva_learning_queue`. Состав: идентичность+характер ([vision.md](vision.md)), бизнес-правила, правила прайса, **справочник товаров (наизусть** — названия/синонимы для распознавания), **навыки «психология» и «продажи»** (начать легко, углублять), объём помощника ([ADR-018](../../90-decisions/ADR-018-eva-universal-assistant.md)), жёсткие принципы. **Цифры (цены/остатки/баланс/долг/рейсы) — никогда в C, только живым инструментом.**

## Слой D — рабочая память

Текущая нить диалога (RAM, ≤60 сообщений). При **пустой RAM** (рестарт/пауза) — читать **хвост A** (~20–30 последних сообщений чата) для непрерывности. Полное состояние сценария в Postgres (`eva_sessions`) — отложено; память о клиенте при этом обеспечивает B (грузится целиком). См. [GAP-025](../../00-meta/gaps.md#gap-025).

## Схема БД (черновик, Postgres)

> Имена/типы — ориентир для развёртывания Postgres под Еву. Финализируется при реализации.

```
eva_messages            -- слой A
  id            bigserial pk
  client_id     text            -- К-XXX (или tg-идентификатор до привязки)
  tg_chat_id    text
  direction     text            -- 'in' | 'out'
  author        text            -- 'client' | 'eva' | 'manager'
  body          text
  meta          jsonb           -- вложения, tool-вызовы, и т.п.
  created_at    timestamptz

eva_client_memory       -- слой B (одна строка на клиента); РЕАЛИЗОВАНО 2026-05-31 (GAP-024 Фаза 1)
  client_id     text pk
  person        jsonb           -- блок 1 «о человеке»: address_form, personal_facts, interests,
                                --   comm_profile, life_context, person_summary, important_dates[]
  business      jsonb           -- блок 2 «о работе»: assortment, order_rhythm, payment_behavior,
                                --   delivery_prefs, price_sensitivity, quality_expectations,
                                --   special_terms, client_value, business_summary
  updated_at    timestamptz
  -- Форма — два JSONB-блока (а не плоские колонки): набор полей доучивается без ALTER (ADR-017).
  -- Слой доступа: code/eva/src/client-memory.js (getMemory / upsertMemory / formatForPrompt).

eva_learning_queue      -- очередь предложений к общей базе C
  id            bigserial pk
  kind          text            -- 'term' | 'rule' | ...
  proposal      text
  evidence      jsonb           -- примеры из журнала
  status        text            -- 'pending' | 'accepted' | 'rejected'
  created_at    timestamptz

eva_escalations         -- эскалации менеджеру
  id            bigserial pk
  client_id     text
  manager_id    text
  reason        text
  status        text            -- 'open' | 'taken' | 'closed'
  created_at    timestamptz

eva_sessions            -- in-memory сейчас; в Postgres c Ит.4
  chat_id          text pk
  active_scenario  text            -- 'client-onboarding' | null
  expecting_photo  jsonb           -- {base, entityId} | null (фото-инфраструктура, ADR-016)
  state            jsonb           -- доп. контекст текущего сценария (slot-filling и т.п.)
  updated_at       timestamptz
```

> Поле `expecting_photo` используется [диспетчером контекста фото-инфраструктуры](../../40-system/photo-infrastructure.md#слой-г--диспетчер-контекста) ([ADR-016](../../90-decisions/ADR-016-photo-infrastructure.md)). Сценарий-владелец фото-ожидания ставит флаг перед шагом с фото; диспетчер видит и проводит пришедшее фото без уточняющего диалога. Сбрасывается после получения.

## Кэширование контекста

Системный промпт (принципы [vision.md](vision.md) + общие знания C) стабилен между запросами → кэшируется (prompt caching), чтобы каждый диалоговый ход был дешёвым и быстрым. Память клиента (B) и хвост A добавляются поверх кэша.

## Эволюция

На текущих объёмах память клиента (B) помещается в контекст целиком — векторный поиск избыточен (та же логика, что в [ADR-012](../../90-decisions/ADR-012-eva-self-learning-plan.md), альт. 5). При разрастании архива A — добавим извлечение релевантных фрагментов (retrieval) поверх B.
