# Eva — система памяти

> Как устроена память Евы и схема хранилища. Решение — [ADR-013](../../90-decisions/ADR-013-eva-agent-architecture.md). Общая архитектура — [architecture.md](architecture.md).

## Четыре слоя

| Слой | Что хранит | Где живёт | Когда грузится в контекст |
|---|---|---|---|
| **A. Сырые переписки** | каждое сообщение (вход/выход), клиент, канал, время; append-only | Postgres | последние N сообщений + извлечённые по необходимости |
| **B. Память клиента** | выжимка о клиенте + сжатое резюме отношений | Postgres | **целиком при каждом диалоге** с этим клиентом |
| **C. Общие знания** | бизнес-правила, товары, цены, правила продаж, база накладных | `kb/` → системный промпт | в системном промпте (кэш) |
| **D. Рабочая память** | текущая ветка диалога | контекст запроса | внутри одного разговора |

## Зачем разделение

Полная история клиента **никогда не помещается** в контекст целиком и удорожает каждый запрос. Поэтому:
- **A** — полный архив (источник истины, для людей и для извлечения), но в «голову» Евы идёт не весь.
- **B** — сжатая, постоянно обновляемая выжимка: именно она даёт ощущение «Ева меня помнит». Грузится целиком всегда.
- В контекст запроса = C (кэш) + B (клиент) + хвост A (+ извлечение из A при необходимости).

## Слой B — что в памяти клиента

Структурированная часть + свободное резюме:
- **Сегмент** (магазин / кафе / ресторан / перекупщик / рынок / частник) — *поля профиля уточняются отдельно перед онбордингом*.
- **Ассортимент** — что обычно покупает (для матчинга с рейсами).
- **Платёжное поведение** — как и когда платит, склонность к долгу.
- **Стиль/характер общения** — краткий/разговорчивый, на что реагирует.
- **Ключевые факты** — особые договорённости, предпочтения, важные даты.
- **Резюме отношений** — сжатый рассказ истории общения, обновляемый после разговоров.

Часть полей дублирует/расширяет карточку клиента из `trade-cat-clients` — связь профиля клиента и памяти Евы прорабатывается при проектировании онбординга.

## Контур обучения (как обновляется B)

После разговора (или по расписанию) фоновый проход:
1. читает новые сообщения из A;
2. извлекает новые факты и обновляет резюме отношений в B;
3. повторяющиеся паттерны у многих клиентов → очередь предложений к общей базе C (подтверждение человеком — как в [ADR-012](../../90-decisions/ADR-012-eva-self-learning-plan.md)).

Никакое **общее** знание (C) не попадает в базу без подтверждения человеком. Память **по клиенту** (B) обновляется автоматически, но всегда видна и правима сотрудником в CRM-модуле.

## Схема БД (черновик, Postgres)

> Имена/типы — ориентир для развёртывания Postgres под Еву. Финализируется при реализации.

```
eva_messages            -- слой A
  id            bigserial pk
  client_id     text            -- К-XXX (или tg-идентификатор до привязки)
  tg_chat_id    text
  direction     text            -- 'in' | 'out'
  author        text            -- 'client' | 'eva' | 'manager'
  body          text
  meta          jsonb           -- вложения, tool-вызовы, и т.п.
  created_at    timestamptz

eva_client_memory       -- слой B (одна строка на клиента)
  client_id     text pk
  segment       text
  assortment    jsonb           -- категории/товары/проекты (формат уточняется)
  payment_note  text
  style_note    text
  facts         jsonb           -- ключевые факты
  summary       text            -- сжатое резюме отношений
  updated_at    timestamptz

eva_learning_queue      -- очередь предложений к общей базе C
  id            bigserial pk
  kind          text            -- 'term' | 'rule' | ...
  proposal      text
  evidence      jsonb           -- примеры из журнала
  status        text            -- 'pending' | 'accepted' | 'rejected'
  created_at    timestamptz

eva_escalations         -- эскалации менеджеру
  id            bigserial pk
  client_id     text
  manager_id    text
  reason        text
  status        text            -- 'open' | 'taken' | 'closed'
  created_at    timestamptz

eva_sessions            -- in-memory сейчас; в Postgres c Ит.4
  chat_id          text pk
  active_scenario  text            -- 'client-onboarding' | null
  expecting_photo  jsonb           -- {base, entityId} | null (фото-инфраструктура, ADR-016)
  state            jsonb           -- доп. контекст текущего сценария (slot-filling и т.п.)
  updated_at       timestamptz
```

> Поле `expecting_photo` используется [диспетчером контекста фото-инфраструктуры](../../40-system/photo-infrastructure.md#слой-г--диспетчер-контекста) ([ADR-016](../../90-decisions/ADR-016-photo-infrastructure.md)). Сценарий-владелец фото-ожидания ставит флаг перед шагом с фото; диспетчер видит и проводит пришедшее фото без уточняющего диалога. Сбрасывается после получения.

## Кэширование контекста

Системный промпт (принципы [vision.md](vision.md) + общие знания C) стабилен между запросами → кэшируется (prompt caching), чтобы каждый диалоговый ход был дешёвым и быстрым. Память клиента (B) и хвост A добавляются поверх кэша.

## Эволюция

На текущих объёмах память клиента (B) помещается в контекст целиком — векторный поиск избыточен (та же логика, что в [ADR-012](../../90-decisions/ADR-012-eva-self-learning-plan.md), альт. 5). При разрастании архива A — добавим извлечение релевантных фрагментов (retrieval) поверх B.
