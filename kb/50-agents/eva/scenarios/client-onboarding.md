# Сценарий: онбординг клиента

> Первый из бизнес-сценариев Евы. Как новый клиент попадает «на связь» с Евой: от черновика, заведённого менеджером, до активного клиента, которому Ева принимает заявки и шлёт напоминания. Архитектура — [ADR-013](../../../90-decisions/ADR-013-eva-agent-architecture.md), профиль клиента — [ADR-014](../../../90-decisions/ADR-014-client-project-profile.md), характер и принципы — [vision.md](../vision.md).

## Зачем отдельный сценарий

Старый `bot_expeditor` **не связывал** Telegram-пользователя с клиентом: он определял клиента по имени из накладной (OCR) при каждом сообщении. Для Евы это не годится — память (слой B) и проактивные напоминания требуют **устойчивой связки `tgChatId ↔ клиент`**. Онбординг — это процесс установления этой связки и наполнения первичного профиля.

Поле `client.tgChatId` в карточке уже есть (форма редактирования клиента, `code/trade_app_v3.jsx`), но заполняется вручную и механизма привязки нет. Этот сценарий вводит механизм.

## Действующие лица

- **Менеджер продаж** (`staff.role = sales_manager`) — заводит черновик клиента, отдаёт клиенту ссылку-приглашение.
- **Клиент** — новый покупатель, ещё не писавший Еве.
- **Ева** — принимает первый контакт, знакомится, наполняет память, активирует клиента.

## Состояния клиента (вводится поле `onbStatus`)

| `onbStatus` | Что значит | Что делает Ева |
|---|---|---|
| `draft` | менеджер завёл черновик, клиент ещё не на связи | ничего проактивно; ждёт привязки по deep-link |
| `active` | `tgChatId` привязан, профиль наполнен | принимает заявки, отвечает, шлёт напоминания (CRM) |
| `paused` | временно отключён (по просьбе/решению менеджера) | не пишет проактивно, на входящее — вежливо или эскалация |

> Новое поле `onbStatus` (default `active` для существующих клиентов при миграции на чтении, как в ADR-014). Требует правки кода — см. «Что нужно в коде».

## Полный поток

```
МЕНЕДЖЕР                     ЕВА (сервис)                  КЛИЕНТ
   │                             │                            │
1. │ заводит черновик клиента    │                            │
   │  (имя, менеджер, проект,    │                            │
   │   сегмент, priceLevel,      │                            │
   │   saleType) → onbStatus=draft                            │
   │                             │                            │
2. │ копирует deep-link из       │                            │
   │  карточки и отправляет      │                            │
   │  клиенту (WhatsApp/лично) ──┼──────────────────────────► │
   │                             │                            │
3. │                             │   /start onb_<token> ◄──── │ нажал Start
   │                             │                            │
4. │                  резолвит token → клиент,                │
   │                  пишет msg.chat.id в client.tgChatId     │
   │                             │                            │
5. │                  знакомится, представляется ────────────►│
   │                  (прозрачность: «я Ева, ИИ-помощник»)    │
   │                             │                            │
6. │                  лёгкий разговор: что обычно             │
   │                  берёте / чем интересуетесь  ◄──────────►│
   │                  → пишет в память клиента (слой B)       │
   │                             │                            │
7. │                  onbStatus=active; уведомляет            │
   │  ◄── дайджест/алерт ────────┤  менеджера «клиент на связи»│
   │                             │                            │
   ▼                             ▼                            ▼
                          Дальше — обычный диалог (приём заявок и т.д.)
```

### Шаг 1. Менеджер заводит черновик

В модуле клиентов `trade_app` менеджер создаёт карточку:
- **Имя** (`n`) — обязательно.
- **Менеджер** (`managerId`) — обычно сам себя; от него зависит, кому пойдут эскалации/дайджесты.
- **Проектный блок** (ADR-014): `projectId`, `segment`, `priceLevel` (`opt`/`mid`/`ret`), `saleType` (`ps`/`ds`). Минимум один блок — иначе Ева не знает, по какому прайсу работать.
- Контакты по желанию (`tg`, `wa`), `ynavUrl`, фото места (`locationPhotos[]`).
- `tgChatId` **оставляет пустым** — его заполнит Ева автоматически.
- `onbStatus = draft` (по умолчанию для новых карточек, заведённых под онбординг).

> **priceLevel задаётся менеджером в черновике** — поэтому Ева потом называет цену по уровню клиента, не нарушая границу полномочий «цена новому клиенту → через менеджера»: уровень уже определил человек. Эскалация на цене остаётся для торга/отклонения от прайса (ADR-013 п. 9).

### Шаг 2. Deep-link приглашение

Карточка показывает менеджеру готовую ссылку вида:

```
https://t.me/<eva_bot>?start=onb_<token>
```

- `<eva_bot>` — бот Евы (наследует Telegram-токен старого `bot_expeditor`, ADR-005).
- `onb_<token>` — payload Telegram deep-link (≤64 символа, латиница/цифры/`_`/`-`). `token` — одноразовый код, сгенерированный при создании черновика и сохранённый (см. «Хранение токена»). **Не используем `client.id` напрямую** — он кириллический (`К-026`) и угадываемый.

Менеджер отправляет ссылку клиенту любым удобным каналом (WhatsApp, личный Telegram, лично). Клиент жмёт ссылку → Telegram открывает чат с Евой с кнопкой **Start**.

### Шаг 3–4. Первый контакт и привязка

Клиент жмёт **Start** → Telegram шлёт боту `/start onb_<token>`.

Ева (сервис):
1. Извлекает `token` из payload.
2. Резолвит `token → client_id` (lookup, см. «Хранение токена»).
3. **Проверки:**
   - токен найден и не погашен → продолжить;
   - токен не найден / погашен / истёк → см. «Краевые случаи»;
   - у клиента уже стоит другой `tgChatId` → см. «Краевые случаи».
4. Записывает `msg.chat.id` в `client.tgChatId` через data-API.
5. Гасит токен (одноразовый).
6. Заводит запись клиента в памяти Евы (слой B, `eva_client_memory`) — пока пустую выжимку; пишет первое сообщение в слой A (`eva_messages`).

### Шаг 5. Знакомство (прозрачность)

Ева здоровается тепло и **сразу честно представляется** (жёсткий принцип прозрачности, [vision.md](../vision.md) п. 2):

> «Здравствуйте, [Имя]! Меня зовут Ева, я ИИ-помощник [компании]. Буду на связи по заказам, ценам, рейсам и остаткам — пишите как удобно, без всяких меню. Подскажу, напомню о рейсе, приму заявку. Если понадобится живой человек — позову вашего менеджера.»

Тон — по [vision.md](../vision.md): тёпло, по делу, без канцелярита, без заваливания текстом.

### Шаг 6. Лёгкий сбор первичного профиля → память (слой B)

У нового клиента **нет истории**, поэтому ассортимент пока не вывести (ADR-014 У1 — ассортимент derived из истории). Ева в живом разговоре, не анкетой, узнаёт:
- **что обычно берёт / чем интересуется** — это первичный «ассортимент-намерение», пишется в память B (`assortment`), не в карточку клиента;
- **как удобнее** (самовывоз со склада / доставка) — если расходится с `saleType` черновика, уточняет и эскалирует менеджеру правку, **сама карточку по типу продажи не переписывает на онбординге**;
- любые **ключевые факты** (часы работы, выходной, особенности) → `facts` в слое B.

Сегмент/уровень цены **не выясняет у клиента** — это решение менеджера (в черновике). Если менеджер не проставил — Ева работает, но первый прайс/заявку с непрописанным уровнем эскалирует.

Сбор — необязательный и ненавязчивый: если клиент сразу хочет заказать, Ева не держит его анкетой, профиль наполнится по ходу общения (контур обучения B, [memory-system.md](../memory-system.md)).

### Шаг 7. Активация

После привязки `tgChatId`:
- `onbStatus = active`;
- Ева шлёт менеджеру (`client.managerId`) короткий алерт/строку в дайджест: «Клиент [Имя] (К-XXX) на связи».

Клиент активен: дальше работает [сценарий приёма заявки](order-intake.md) и CRM-напоминания.

## Хранение токена

Одноразовый токен онбординга. Два варианта (выбрать при реализации):

- **A. На карточке клиента (KV).** Поле `client.onbToken` (+ `onbTokenUsed`/`onbExpiresAt`). Резолв `/start` = поиск клиента с таким токеном через data-API. Плюс: ничего нового в схеме. Минус: скан клиентов на каждый `/start` (на текущих объёмах — приемлемо).
- **B. Отдельная таблица в Postgres Евы.** `eva_onboarding_tokens(token pk, client_id, created_at, expires_at, used_at)`. Плюс: чистый lookup, TTL, аудит. Минус: +1 таблица к схеме [memory-system.md](../memory-system.md).

**Рекомендация:** начать с **A** (меньше движущихся частей), перейти на B при росте. Срок жизни токена — например, 14 дней; повторная генерация по кнопке в карточке.

## Краевые случаи

| Ситуация | Поведение Евы |
|---|---|
| Токен не найден / погашен | Не привязывает. Вежливо: «Кажется, ссылка устарела — попрошу менеджера прислать новую». Алерт менеджеру. |
| Токен истёк по сроку | Как выше; менеджер перегенерирует ссылку в карточке. |
| У клиента уже привязан **другой** `tgChatId` | Не перезаписывает молча. Эскалация менеджеру (возможно, клиент сменил Telegram или это другой человек). |
| Этот `tgChatId` уже привязан к **другому** клиенту | Не привязывает. Эскалация: один Telegram-аккаунт = один клиент; разобраться вручную. |
| Клиент жмёт Start повторно (уже active) | Привязка не нужна; Ева просто продолжает обычный диалог. |
| **Холодный вход** — клиент пишет Еве сам, без deep-link, `tgChatId` неизвестен | Ева не выдумывает, кто это. Тепло здоровается, представляется, спрашивает, как зовут/от кого узнал, и **эскалирует менеджеру** завести черновик. Цены/заявки незнакомцу не оформляет (граница полномочий). См. также «разовый покупатель» ниже. |
| Клиент в `draft` пишет до нажатия Start (если как-то узнал бота) | Обрабатывается как холодный вход до момента привязки. |

> **Разовый покупатель** (`__walk_in__` / К-025, см. [business-rules-from-bot.md](../../../20-domain/business-rules-from-bot.md)) онбординга **не проходит** — это разовая продажа без карточки и без памяти. Если «холодный» собеседник — разовый, менеджер так и помечает; устойчивая связка с Telegram для него не заводится.

## Что нужно в коде (для реализации)

Сценарий описывает целевое поведение; для запуска нужно:

1. **Поле `onbStatus`** в карточке клиента (`draft`/`active`/`paused`), миграция на чтении: существующие клиенты = `active`. UI: бейдж статуса в списке, фильтр.
2. **Генерация и показ deep-link** в карточке: кнопка «Пригласить в Telegram» → токен + готовая ссылка для копирования; кнопка «Обновить ссылку».
3. **Хранение токена** (вариант A или B выше).
4. **Обработчик `/start onb_<token>`** в сервисе Евы: резолв, привязка `tgChatId`, гашение токена, активация, алерт менеджеру.
5. **Инструменты Евы** (контракты — `../tools/`, проектируются отдельно): `get_client_by_tgchat`, `bind_tgchat`, `update_client_memory`, `escalate_to_manager`, `notify_manager`.

## Открытые вопросы (на согласование с Максимом)

- **Имя бота Евы** для deep-link (`<eva_bot>`) — какой username у бота на унаследованном токене.
- **Название компании** в реплике-представлении (как Ева называет, от кого она).
- **Срок жизни** токена приглашения (предложено 14 дней).
- Нужна ли **лёгкая верификация** личности на первом контакте (например, переспросить имя) — или достаточно одноразового токена как доверия.
- Граница полномочий (ADR-013 п. 9) — финализация общей таблицы влияет на шаги 5–6 (что Ева говорит новому клиенту про цены).
