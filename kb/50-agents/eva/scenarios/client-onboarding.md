# Сценарий: онбординг клиента

> **Техническая сторона Евы** для процесса завода нового клиента. Бизнес-взгляд (что происходит, поля, правила) — в процессе роли [sales-manager/processes/client-onboarding.md](../../../30-roles/to-be/sales-manager/processes/client-onboarding.md). Архитектура — [ADR-013](../../../90-decisions/ADR-013-eva-agent-architecture.md), характер и принципы — [vision.md](../vision.md), структура связей — [ADR-015](../../../90-decisions/ADR-015-role-process-eva-structure.md).

## Суть

Менеджер заводит клиента **диалогом с Евой** (это взаимодействие «Ева ↔ менеджер», шаг 3 [roadmap](../../../65-roadmap/current.md)). Ева ведёт опрос, создаёт карточку через инструмент, выдаёт ссылку-приглашение. Клиент **активен сразу**; привязка к Telegram через deep-link — опциональный бонус (у клиента может не быть Telegram).

Зачем связка `tgChatId ↔ клиент`: чтобы Ева **помнила** клиента (память, слой B) и могла писать ему сама. Старый `bot_expeditor` этого не умел (определял клиента по имени из накладной).

## Поток (со стороны Евы)

```
МЕНЕДЖЕР                          ЕВА                              КЛИЕНТ
   │  «новый клиент» (любая фраза)  │                                 │
   ├───────────────────────────────►│ распознаёт намерение            │
   │                                 │ определяет менеджера по         │
   │                                 │ telegramChatId (staff)          │
   │  ◄── «Ок! Начинаем...» ─────────┤                                 │
   │                                 │                                 │
   │   ▲ опрос: 1 вопрос = 1 поле,   │                                 │
   │   │ проверка ответа, кнопки для │                                 │
   │   ▼ выбора, текст для остального│                                 │
   │                                 │                                 │
   │  всё заполнено →                │ create_client (onbStatus=Активен)│
   │  ◄── отчёт + deep-link ─────────┤ + генерация onbToken            │
   │                                 │                                 │
   │  пересылает ссылку в WhatsApp ──┼────────────────────────────────►│
   │                                 │   /start onb_<token> ◄──────────┤ (если есть TG)
   │                                 │ привязка tgChatId+tg,           │
   │                                 │ память клиента (B), знакомство ►│
```

## Шаги

### 1. Распознать намерение и менеджера
Менеджер пишет свободной фразой. Ева понимает намерение «завести клиента» (не по жёстким триггерам). Определяет, **кто пишет** — по `telegramChatId` в `trade-cat-staff`; если это не менеджер (`sales_manager`) — мягко отказывает/эскалирует. Подтверждает старт.

### 2. Ведённый опрос (slot-filling)
Поля и правила — в таблице процесса ([sales-manager/processes/client-onboarding.md](../../../30-roles/to-be/sales-manager/processes/client-onboarding.md#опрос-один-вопрос--одно-поле)). Технические требования к Еве:
- **Одно поле за раз**, следующий вопрос — после валидного ответа.
- **Поля-выбор** (проекты, сегмент, цена, тип продажи) — Telegram inline-кнопки. Проекты — мультивыбор (галочки ☐/☑ + «Готово»). Ева понимает и текстовый ответ, кнопки — удобство.
- **Проверки**: уникальность названия (`n`) через чтение клиентов; проект активен; сегмент входит в пересечение `applicableProjects` выбранных проектов; `wa` — международный формат `+<код>`.
- **Авто-поля**: `managerId` = текущий менеджер; `tg`/`tgChatId` — позже при активации; `onbStatus=Активен`.
- **Сегмент/цена/тип продажи** — один ответ, пишется во все проектные блоки клиента (ADR-014).
- **Прерывание**: «стоп»/«отмена» → свернуть без сохранения.

### 3. Создать карточку
Инструмент `create_client` пишет карточку в `trade-cat-clients` через data-API. Генерируется одноразовый `onbToken` для deep-link.

### 4. Отчёт + приглашение
Ева выдаёт сводку по карточке + готовую ссылку `https://t.me/<eva_bot>?start=onb_<token>` и текст для пересылки. Менеджер сам отправляет клиенту в WhatsApp.

### 5. Активация (опционально, если у клиента есть Telegram)
Клиент жмёт ссылку → `/start onb_<token>`:
1. резолв `token → client_id`;
2. запись `msg.chat.id` в `tgChatId`, `msg.from.username` в `tg` (если есть);
3. гашение токена;
4. заведение памяти клиента (слой B), запись первого сообщения (слой A);
5. **знакомство с прозрачностью** (vision.md п.2): «Здравствуйте, {contactName}! Я Ева, ИИ-помощник …» — обращение по **контактному лицу** (`contactName`).

Без Telegram шаг 5 не происходит — клиент остаётся активным без канала Евы.

## Краевые случаи

| Ситуация | Поведение Евы |
|---|---|
| Название клиента не уникально | Сообщает менеджеру, просит другое название (правило уникальности) |
| Пишет не менеджер (нет в staff / не sales_manager) | Завод не запускает; вежливо объясняет / эскалирует |
| Менеджер прервал опрос | Сворачивает без сохранения |
| У клиента нет Telegram | Карточка активна; deep-link не используется; канала Евы нет |
| Токен не найден/погашен/истёк | Не привязывает: «ссылка устарела — попрошу менеджера прислать новую» + алерт менеджеру |
| `tgChatId` уже привязан к другому клиенту | Не привязывает; эскалация (один TG = один клиент) |
| **Холодный вход** — клиент пишет без приглашения, `tgChatId` неизвестен | Не выдумывает, кто это; здоровается, представляется, спрашивает имя/от кого, **эскалирует менеджеру** завести через диалог; цены/заявки незнакомцу не оформляет (граница полномочий) |
| Разовый покупатель (`__walk_in__`/К-025) | Онбординг не проходит — разовая продажа без карточки и памяти |

## Инструменты Евы (контракты — в `../tools/`, проектируются)

- `whoami_staff` / идентификация менеджера по `telegramChatId`
- `check_client_name_unique`
- `list_active_projects`, `list_segments_for_projects`
- `create_client` (с проектными блоками, `onbStatus`)
- `gen_onboarding_link` (onbToken)
- при активации: `bind_tgchat`, `init_client_memory`
- `escalate_to_manager`, `notify_manager`

## Что нужно в коде (для реализации)

1. ✅ **Новые поля карточки клиента**: `contactName` («Контактное лицо», обязательное для новых) и `onbStatus` (`Активен`/`На паузе`; миграция на чтении: существующие = `Активен`). **Сделано 2026-05-23** в форме trade_app и хранении (коммит `2403e44`, [CHANGELOG](../../../95-changelog/2026-Q2.md)).
2. ✅ **Уникальность `n`** — case-insensitive trim. Проверяется в форме trade_app (коммит `2403e44`) И в Еве через инструмент `check_client_name_unique` (Ит.2, 2026-05-23).
3. ✅ **Инструменты в сервисе Евы** — `code/eva/src/tools/`, Ит.2 (коммит `b305041`): `check_client_name_unique`, `list_active_projects`, `list_segments_for_projects`, `create_client`. Плюс `ask_choice` / `ask_multi_choice` для inline-кнопок (Ит.2.5–2.6).
4. ⬜ **Генерация и хранение `onbToken`** (вариант A: поле на карточке + скан через data-API; TTL ~14 дней). — Ит.3.
5. ⬜ **Обработчик `/start onb_<token>`** в сервисе Евы (привязка `tgChatId`/`tg`, гашение токена, знакомство). — Ит.3.
6. ⬜ **Фото-инфраструктура** ([GAP-018](../../../00-meta/gaps.md)) — для поля «фото места доставки»; на первом прогоне Ева пропускает поле, к тесту менеджерами — настроить.
7. ✅ **Идентификация менеджера** по `telegramChatId` — Ит.1, инструмент `whoami_staff`.

### Полномочия

Расширены: рабочие сценарии (онбординг) запускают и `sales_manager`, и `owner` (для С-001 Максим — `owner`).

### UI-добавки в реализации (не было в исходном дизайне)

- **Inline-клавиатуры** для всех 4 полей-выбора (проекты — чекбоксы ☐/☑ + «Готово», сегмент/уровень цены/тип продажи — single-select). Реализованы инструментами `ask_choice` / `ask_multi_choice`. Callback от Telegram конвертируется в обычное user-сообщение в диалоге Евы, multi-select хранит состояние выбора в памяти на время диалога.
- **Команда `/reset`** — сброс in-memory сессии (для разработки + защита от застрявших состояний).
- **Self-heal**: если Anthropic возвращает 400 из-за порванной пары `tool_use`↔`tool_result` в истории — сессия автоматически сбрасывается, пользователь видит «начнём с чистого листа».

## Открытые вопросы (на согласование с Максимом)

- **Username бота Евы** для deep-link (`<eva_bot>`).
- **Название компании** в реплике-представлении.
- **Срок жизни** `onbToken` (предложено 14 дней).
- Нужна ли **лёгкая верификация** личности клиента при активации (или одноразового токена достаточно).
- Граница полномочий (ADR-013 п. 9) — финализация влияет на холодный вход и реплики про цены.
