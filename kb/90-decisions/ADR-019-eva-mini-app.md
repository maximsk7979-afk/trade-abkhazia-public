# ADR-019: Telegram Mini App как поверхность структурных действий Евы

## Контекст

Приступая к Шагу 4 ([roadmap](../65-roadmap/current.md)) — прямой работе Евы с клиентами (приём заявок, баланс, заказы) — встал вопрос **как именно** клиент и менеджер совершают структурные действия.

Базовый вариант — диалоговый сбор заявки через Еву (slot-filling, как онбординг). Максим обозначил его слабое место: **сбор заявки разговором имеет высокий риск ошибок из-за «человеческого фактора»** (свободный текст → Ева не так распознала товар/количество/цену → неверная заявка). Для денежных транзакций это неприемлемо.

Предложенное решение — по образцу мини-приложения **«Кошелёк» в Telegram**: внутри чата с Евой есть кнопка, открывающая **мини-приложение** с понятным интерфейсом, где совершаются основные действия. Наполнение и функционал интерфейса **зависят от роли** пользователя.

## Решение

Основной поверхностью для **структурных действий** Евы с клиентами и сотрудниками становится **Telegram Mini App** (мини-приложение в чате). Чат остаётся для **общения**, мини-апп берёт на себя **точные операции**.

### 1. Разделение труда: чат vs мини-апп

| Поверхность | Для чего |
|---|---|
| **Чат с Евой** | общение, вопросы, торг, фото, эскалация, тёплый контакт, проактив (поздравления, напоминания) |
| **Мини-апп** | структурные действия, где важна точность: оформление заявки, просмотр баланса/истории, (далее) другие операции |

Это снимает противоречие из [ADR-013](ADR-013-eva-agent-architecture.md) («избегаем ботского ощущения»): вместо фейково-диалоговых кнопок в чате — **настоящее приложение** для операций и **живой диалог** для общения.

### 2. Технический стек

- **Отдельный лёгкий мобильный фронт** под Telegram WebView (мобильный UX, тема Telegram, `MainButton`/`BackButton`). **Не** встраиваем админский `trade_app_v3.jsx` (десктоп-UX, ~6600 строк) — он остаётся инструментом сотрудников в браузере. Минимально необходимая бизнес-логика дублируется (как `seed.js`/`sales-history.js` зеркалят логику JSX), с прицелом на общий модуль в будущем.
- Бэкенд — существующий **`trade-api`** на VPS (расширяется ролевыми эндпоинтами). Хостинг — текущий HTTPS-домен `trade-abkhazia.com`.
- Бот Евы уже работает в Telegram (polling).

### 3. Идентификация и изоляция данных (критический путь)

При открытии Telegram передаёт подписанный **`initData`** (Telegram user id, имя и пр.).

- **Бэкенд обязан валидировать `initData`** алгоритмом Telegram (HMAC-SHA256 по токену бота) — это доказывает личность и не подделывается. **Личность никогда не берётся из клиентского кода.**
- По Telegram id резолвится роль (переиспользуем `resolveIdentity` рантайма Евы):
  - сотрудник (`trade-cat-staff.telegramChatId`) → **owner / manager**;
  - клиент (`trade-cat-clients.tgChatId`) → **client**;
  - неизвестный → доступа нет (эскалация / онбординг).
- Дальше бэкенд **фильтрует все данные по этой личности**. Это **архитектурная реализация изоляции** ([GAP-030](../00-meta/gaps.md#gap-030)): «клиент видит только своё» зашито на сервере, а не в промпте агента. Клиент-facing эндпоинты не возвращают cross-client/общефирменные данные (таб ‑у из [ADR-018](ADR-018-eva-universal-assistant.md) §6).

### 4. Ролевое наполнение

Один мини-апп — **разные экраны по роли**:

| Роль | Что видит/делает (MVP) |
|---|---|
| **client** | оформление заявки под рейс; свой баланс и история заказов/оплат |
| **manager** | оформление заявки за любого **своего** клиента; (далее) список своих клиентов, их заявки/баланс |
| **owner** | управление (напр. банановый прайс — [ADR-020](ADR-020-order-intake-banana-pricing.md)); полный доступ |

### 5. Точки входа

- **Постоянная menu-кнопка** бота (угол у поля ввода, как «Кошелёк») — через BotFather / `setChatMenuButton`, тип `web_app`.
- **Контекстные inline-кнопки** от Евы в диалоге («Оформить заказ») — `web_app`-кнопки по ходу разговора.

### 6. Граница (Telegram-only)

Мини-апп живёт **только в Telegram**. Клиенты **без Telegram** (онбординг это допускает — связь через WhatsApp) мини-аппом не пользуются — за них заявку оформляет **менеджер** (он в Telegram) через тот же апп. Мини-апп — **канал, не единственный путь**.

## Последствия

### Положительные
- Структурные операции — **точные** (форма вместо распознавания свободного текста), снят «человеческий фактор» из заявок.
- Изоляция данных решается **архитектурно** (валидация `initData` + серверная фильтрация), а не дисциплиной промпта — намного надёжнее.
- Единая поверхность для **всех** будущих структурных взаимодействий (заказы, баланс, каталог, оплаты), не только бананов.
- Прозрачность сохранена (это Telegram-апп компании), маскировки нет ([ADR-013](ADR-013-eva-agent-architecture.md)).

### Отрицательные / компромиссы
- **Два фронта** (админский trade_app + мини-апп) — больше поддержки; смягчаем общим API и логикой.
- Больше работы, чем чат-флоу; но окупается точностью и переиспользуемостью.
- Жёсткое требование: **валидация `initData` только на сервере** — иначе риск выдать себя за сотрудника/чужого клиента (критично для GAP-030).

## Альтернативы, которые отклонили

### Альтернатива 1: Диалоговый сбор заявки (slot-filling в чате)
**Почему отклонили:** высокий риск ошибок на свободном тексте в денежных операциях; ровно то «ботское» ощущение, от которого уходим.

### Альтернатива 2: Встроить админский `trade_app_v3.jsx` как мини-апп
**Почему отклонили:** десктоп-UX и объём не подходят мобильному клиентскому экрану; смешение ролей и рисков.

### Альтернатива 3: Внешний веб-портал (вне Telegram) с отдельным логином
**Почему отклонили:** отдельный логин/пароль — барьер для клиентов; Telegram даёт бесшовную идентификацию (`initData`) и единый канал с Евой.
