# ADR-026: Единый слой уведомлений

## Контекст

Аудит (2026-06-30, две разведки по коду) показал, что исходящие уведомления сотрудникам
разрослись стихийно — 40 типов, и в них накопился беспорядок:

1. **Два независимых отправителя.** Уведомления шлют (а) `trade-api` (`notify.js` + `server.js`)
   на бизнес-операции и (б) процесс Евы (`eva/src/…`) — кроны, инструменты, онбординг,
   оркестратор. Резолв «роль→chat_id» **скопирован** в `notify.js` и в `eva/message-log.js` —
   тот же запах «зеркалит», что в [ADR-025](ADR-025-single-domain-layer.md): дублированная
   логика разойдётся.
2. **Веб не уведомляет вообще.** `notify.*` висят только на роутах `/api/mini/*` (мини-апп).
   Все операции из веб-интерфейса (`/api/v2/*`, гейт `requireInternalToken`) — создание рейса,
   доставки, продажи, расчётов, закупки, партий, касса, прайс — **не порождают ни одного
   уведомления**. Та же операция из мини-аппа уведомляет, из веба — молчит.
3. **`active`-фильтр непоследователен.** Есть у `owner`/`warehouse`/`ops_manager`, **нет** у
   `buyer`/`sales_manager`/`supplier` → деактивированный сотрудник продолжает получать пинги.
4. **Нет дедупа** (кроме health-alert 1/час) и единого ретрая.
5. **Владельца заваливает** — `owner` адресат почти каждой строки; всё вперемешку.
6. **Нет реестра.** Нигде не видно «что, кому, когда»; расписание кронов — в crontab на VPS,
   тексты — в коде; нет привязки уведомлений к ролям по [ADR-022](ADR-022-role-model-rbac.md).

### Ограничения Telegram (зафиксировано, чтобы не строить на несуществующем)

- **Топиков в личном чате с ботом не бывает** — `message_thread_id` только в супергруппах.
- **Персональной фильтрации внутри общего топика нет** — все участники группы/темы видят все
  сообщения. «Каждому только своё» возможно лишь через отдельного получателя: ЛС с ботом
  (есть сейчас) или **наш собственный экран** (лента в мини-аппе, где рендер по роли — наш).

## Решение

### 1. Единый слой `notify-core` (под ADR-025)

Свести обоих отправителей в один модуль (`.cjs`, по примеру `trip-cost-core.cjs`/`stock-service.cjs`),
который импортируют и `trade-api`, и процесс Евы:

- **Реестр уведомлений** — декларативный: `{ kind, домен, важность, получатели(роли), шаблон, дедуп-ключ }`.
  Источник истины реестра — матрица [notifications-matrix.md](../50-agents/eva/notifications-matrix.md).
- **Единый резолв роль→chat_id** в одном месте (убирает копию из `notify.js` и `message-log.js`),
  с `active !== false`-фильтром **для всех** ролей.
- **Дедуп** по `(kind, refId)`; **ретрай** с backoff (как уже есть в `notify.js`).
- **Важность → маршрут:** `crit` (сразу в ЛС), `op` (роль-ЛС, кандидат в дайджест),
  `info` (дайджест).
- **Привязка к ролям (ADR-022, fail-closed):** уведомления без строки в матрице не отправляются.

### 2. Веб тоже уведомляет (через сервисный слой)

Перенести вызовы `notify.*` из роутов в **сервисный слой**, который зовут оба интерфейса
(`/api/v2/*` и `/api/mini/*`) → веб-операции уведомляют единообразно с мини-аппом. Предпосылка:
у `/api/v2/*` нет актора — **добавить выбор сотрудника в вебе** и прокидывать `staffId` (нужно
и для роль-биндинга, и для текста «кто сделал»).

### 3. Модель доставки (с учётом ограничений Telegram)

- **Базовая доставка — ЛС по роли** (уже даёт «каждому своё»).
- **Разгрузка владельца** — важностью + дайджестом, не каналами.
- **Тематические группы** (Продажи/Склад/Финансы/Закупки) — опционально, для общей
  осведомлённости; изоляция доступа за счёт *состава группы* (Финансы/Закупки чувствительны —
  только отдельные группы, не топики).
- **«Каждому своё + по темам»** в одном месте = **лента-вкладки в мини-аппе** (наш экран),
  отфильтрованная по роли. Это целевой ответ на запрос владельца, а не нативный Telegram.

### 4. Очерёдность: реализация — ПОСЛЕ финблока

**Спецификацию (эту ADR + матрицу) делаем сейчас; код-реализацию — после сборки финблока
(Ф-1…Ф-5, см. [roadmap](../65-roadmap/current.md)).** Причина: финблок вводит **кошельки**,
роль **`fin_director`** и денежные события («вторая нога» операций) — это переписывает D-блок
матрицы (деньги/расчёты) и часть A/C. Построить `notify-core` и развести 40 уведомлений до
финблока = гарантированный rework. Система «собирается» на **Ф-5 (Сведение)**: три отчёта
бьются между собой, проходит сквозной e2e ([GAP-064](../00-meta/gaps.md#gap-064)). На этот
момент матрица получателей стабильна.

## Последовательность шагов

**Сейчас (эта сессия / до финблока) — спецификация, без рисковой реализации:**
1. ✅ Матрица-аудит [notifications-matrix.md](../50-agents/eva/notifications-matrix.md) — 40 типов, текущее + цель.
2. ✅ ADR-026 (этот документ) — архитектура, ограничения, очерёдность.
3. ✅ [GAP-073](../00-meta/gaps.md#gap-073) — трекер; фиксация в roadmap.
4. ⏳ Сверка матрицы владельцем — открытые вопросы D/C/F/оркестратор закрываются по ходу финблока
   (когда роль `fin_director` и кошельки оформлены).

**После финблока (Ф-5) — реализация:**
5. `notify-core` (реестр + единый резолв + `active` + дедуп + ретрай + важность).
6. Перевод `trade-api` и Евы на `notify-core`; удаление копий резолва.
7. Веб уведомляет: notify в сервисный слой + выбор сотрудника в вебе (actor).
8. Тихие часы + утренний/вечерний дайджест (разгрузка владельца); inline-кнопки.
9. Лента-вкладки в мини-аппе по роли + журнал доставки.
10. Тесты, деплой (trade-api + Ева + фронт), прод-смоук (веб и мини).

## Последствия

- **+** Спецификация зафиксирована заранее → реализация после финблока будет быстрой и без догадок.
- **+** Матрица — единый источник для реестра и роль-биндинга (ADR-022/025).
- **+** Не делаем работу дважды (нет rework D-блока под финансы).
- **−** До реализации сохраняются текущие дефекты (веб молчит, `active`-баг, перегруз владельца).
  Латентный `active`-баг (деактивированный `buyer`/`sales_manager` получает пинги) — кандидат
  на ранний точечный фикс, если станет мешать; иначе закрывается вместе с `notify-core`.
- **Зависимость:** старт реализации привязан к Ф-5 финблока.

## Дополнение (2026-07-07, согласовано владельцем): триггер уведомлений = журнал изменений (transactional outbox)

Решение исходной ADR не меняется — уточняется **механизм захвата событий** для `notify-core`
с учётом появившегося [ADR-028](ADR-028-audit-log.md) (журнал всех изменений БД).

**Решение:** источник событий для уведомлений — **журнал `audit_log`**, а не вызовы отправки
внутри эндпоинтов. Это паттерн transactional outbox:

1. **Полнота по всем поверхностям гарантирована конструкцией.** Журнал снимает изменения на
   уровне сторов — единственного пути записи (ADR-024/025). Главная болезнь текущих
   уведомлений («веб молчит» — отправка вшита в отдельные эндпоинты, веб-пути забыты)
   становится невозможной по построению: новый эндпоинт/поверхность попадает в журнал
   автоматически. Требование владельца: «изменения фиксируются из всех источников ввода,
   единый движок» (2026-07-07).
2. **Транзакционная честность.** Журнальная строка коммитится вместе с операцией → нет
   уведомлений по откаченным операциям и нет потерь по совершённым (упавший отправщик
   догоняет журнал по курсору). Дедуп `(kind, refId)` и ретраи — тривиальны.
3. **Три слоя движка:** захват = `audit_log` (✅ есть, ADR-028) → **интерпретация** =
   декларативный реестр правил «сущность + переход поля → тип уведомления + кому (роль) +
   важность» (воркер читает журнал по курсору, диф против предыдущего состояния из цепочки
   журнала, матчит правила; правила = данные в одном реестре, а не код по эндпоинтам) →
   **доставка** = очередь notify-core (единый резолв роль→chat_id, `active`, дедуп, ретраи,
   тихие часы/дайджест, журнал доставки) — как в исходной ADR.

**Проектные ограничения (учесть при реализации):**
- **Батч-шум**: одна бизнес-операция (погрузка) = десятки журнальных строк; правила цепляются
  за смысловой переход (например, статус доставки), не за каждую строку.
- **`source='system'` не триггерит** уведомления по умолчанию (миграции/восстановления не
  должны рассылать шквал) — журнал уже различает источники.
- **Отправка строго асинхронна** (воркер с курсором, опрос ~секунды); никаких синхронных
  хуков в обёртке сторов — Telegram-таймауты не должны тормозить бизнес-операции.
- **Актор-детализация Евы**: журнал пишет источник «Ева» без менеджера — для уведомлений
  вида «менеджер X провёл Y через Еву» нужна передача актора Евой (обязательный
  пререквизит этапа реализации).

**Уже закрывшиеся пререквизиты:** веб-актор — даёт сессия [GAP-078](../00-meta/gaps.md#gap-078)
(лучше планировавшегося «выбора сотрудника в вебе»; п.7 последовательности упрощается);
слой захвата — ADR-028. **Очерёдность не меняется:** реализация — после Ф-5
(решение владельца 2026-06-30 в силе).
