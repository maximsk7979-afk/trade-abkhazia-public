# ADR-016: Фото-инфраструктура — единый пайплайн и независимые базы фотографий

## Контекст

Системе нужно работать с фотографиями в четырёх независимых сценариях:
1. Фото входов на склад/витрины клиентов — для экспедитора при доставке ([GAP-018](../00-meta/gaps.md#gap-018)).
2. Фото отгрузочных накладных — Ева распознаёт и создаёт запись Sale ([GAP-020](../00-meta/gaps.md#gap-020)).
3. Фото товаров в карточке SKU — Ева использует в диалогах с клиентами ([GAP-021](../00-meta/gaps.md#gap-021)).
4. Фото товаров с закупок — Ева рассылает клиентам для подтверждения заявки ([GAP-022](../00-meta/gaps.md#gap-022)).

В будущем (пункт 5 разбора 2026-05-30) появятся ещё базы — архитектура должна допускать добавление без переделки фундамента.

До этого ADR в `kb/` была одна заглушка `GAP-018 «Фото-инфраструктура»` без архитектурного дизайна. Реализация фото была заблокирована — это, в свою очередь, блокировало тест онбординга менеджерами.

## Решение

Архитектура фото-инфраструктуры строится из **пяти слоёв**, разделённых ответственностью:

| Слой | Что |
|---|---|
| (а) Приём фото из Telegram | Сервис Евы нормализует `RawPhoto`, скачивает в `/tmp/eva/...`, буферизует альбомы по `media_group_id` |
| (б) Хранение на VPS | Локально, `/var/www/trade/photos/<base>/<entityId>/<unixTs>_<fileUniqueId>.<ext>`, Nginx public с непредсказуемыми именами файлов |
| (в) Endpoint загрузки | `POST/DELETE /api/photos` на trade-api (multipart, `X-Photo-Token`); единая валидация и запись в KV |
| (г) Диспетчер контекста | Универсальный диспетчер выбирает `base` (активный сценарий → inline-кнопки); per-base **handlers** решают `entityId` и постобработку |
| (д) UI в trade_app | Универсальный компонент `<PhotoGallery>` в карточках; конвенция URL; кэш `Cache-Control: immutable` |

**Каждая база фото — независимая запись** на бизнес-сущности (массив объектов `photoMeta`), хранящая URL и метаданные `{uploadedBy, uploadedAt, caption, fileUniqueId, size, width, height}`. Не голые URL — для аудита и дедупа.

**Расширяемость (пункт 5)** обеспечена тем, что слои (а), (б Nginx), (в endpoint), (д компонент UI) — **общие**. Конкретика каждой базы — в одном файле handler (`code/eva/src/photo/handlers/<base>.js`) + строке в конфиге `PHOTO_BASES` на trade-api. Добавить новую базу = 4 шага (handler + конфиг + поле в сущности + секция в карточке).

**Детальная техническая спецификация** — [`kb/40-system/photo-infrastructure.md`](../40-system/photo-infrastructure.md). Этот ADR фиксирует решение; детальный документ — эталон для реализации и обновляется при изменениях.

## Последствия

### Положительные

- Закрывает блокер теста онбординга менеджерами (GAP-018 переходит в реализуемое состояние).
- Один пайплайн обслуживает 4 базы и масштабируется на новые без переделки фундамента (пункт 5).
- Закрывает урок [GAP-019](../00-meta/gaps.md#gap-019): новый endpoint валидирует payload и не молчит при отсутствии полей (в отличие от `POST /api/storage/:key`).
- UI и Ева пишут через один endpoint — единая точка валидации, единые ошибки.
- Метаданные на фото (`uploadedBy`, `uploadedAt`, `caption`) дают аудит «кто что когда загрузил» — полезно при работе с клиентами и при разборе инцидентов.
- Тонкий слой и no-deps реализация (без отдельных storage-SDK, без CDN) — на старте минимально.

### Отрицательные / компромиссы

- Файлы лежат локально на VPS — единственная точка отказа; бэкап нужен ([GAP-016](../00-meta/gaps.md#gap-016)) и архивация ([GAP-017](../00-meta/gaps.md#gap-017)).
- Доступ через Nginx public — «security through obscurity» (защита непредсказуемым именем файла). Для чувствительных кейсов в будущем потребуется signed URLs или auth-endpoint.
- Shared secret (`X-Photo-Token`) — слабая защита, до появления RBAC ([roadmap Q3 2026](../65-roadmap/current.md)).
- Состояние сессии Евы (включая `expectingPhoto`) — in-memory; при `pm2 restart eva` теряется. Переезд в Postgres — Ит.4 Евы.
- KV не транзакционен → теоретически возможна гонка при одновременной правке. Защиту вводим только если выстрелит.

## Альтернативы, которые отклонили

### Альтернатива 1: S3 / внешнее объектное хранилище

**Почему отклонили**: масштаб ~12 ГБ/год прогноз, на ближайший год — оверкилл. Биллинг, интеграция, отдельные креды. Локальный VPS + rsync для бэкапа проще и дешевле. Возврат к S3 — при росте объёма или регуляторных требованиях.

### Альтернатива 2: Прямая запись в файловую систему из сервиса Евы (без endpoint)

**Почему отклонили**: разрывает единую валидацию (Ева + потенциальная веб-форма пишут разными путями), дублирует доступ к KV (Ева сама бы обновляла массивы), не масштабируется на новые источники загрузки. Endpoint на trade-api — единая точка ответственности.

### Альтернатива 3: Одна универсальная сущность `Photo` в отдельной таблице, ссылки по ID

**Почему отклонили**: добавляет уровень индирекции (фото → ID → сущность), требует Postgres-таблицы и join'ы. Сейчас KV-store без таблиц; массивы объектов прямо на сущности работают и проще читаются. При миграции KV → Postgres ([roadmap Шаг 2](../65-roadmap/current.md)) — пересмотрим, но не блокер.

### Альтернатива 4: JSON-загрузка с base64-кодированием

**Почему отклонили**: 1.33× раздувает трафик; multipart — стандартный паттерн HTTP-загрузки, работает с любого клиента (Ева, веб-форма, curl).

### Альтернатива 5: Caption как первичный сигнал для выбора базы

**Почему отклонили**: ненадёжно (менеджер может ошибиться/опечататься), вводит NLP-классификацию там, где достаточно явных inline-кнопок. Caption сохраняем в `photoMeta.caption` как полезные данные, но не используем для маршрутизации.
