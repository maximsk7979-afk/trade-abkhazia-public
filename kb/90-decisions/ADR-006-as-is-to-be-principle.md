# ADR-006: Принцип AS-IS / TO-BE при описании трансформации

## Контекст

Проект Евы — это **трансформация бизнеса**, не просто разработка. Функции ролей переопределяются, часть передаётся Еве, появляются новые роли (например, экспедитор).

Это означает, что для каждой роли (а потенциально и для процессов и системы) есть **два состояния**:
- **AS-IS** — как работает сейчас, до Евы
- **TO-BE** — как будет работать с Евой

И эти состояния важно **не смешивать**:
- AS-IS нужен, чтобы помнить, откуда пришли, и сравнивать
- TO-BE нужен, чтобы понимать, куда идём
- Когда переход для конкретной роли завершён, AS-IS архивируется, TO-BE становится активным

## Решение

Принимаем принцип AS-IS / TO-BE для описания трансформации.

### Применяется к ролям обязательно

Слой `30-roles/` разделён на:
```
kb/30-roles/
├── README.md       Карта трансформации с таблицей состояний
├── as-is/          Состояние ДО Евы
└── to-be/          Целевое состояние С Евой
```

После завершения миграции конкретной роли:
- TO-BE становится `30-roles/<role>.md` (активное состояние)
- AS-IS переезжает в `99-archive/2026-roles-as-is/`

### Применяется к другим слоям только когда нужно

Принцип универсальный, но **не разворачиваем как-IS/TO-BE везде сразу**. Только там, где есть реальная разница состояний.

Возможные кандидаты на будущее:
- `20-domain/processes/as-is/` и `to-be/` — если будут переписывать процессы
- `40-system/` — если будем менять архитектуру под Еву

Бизнес-правила (FIFO, расчёт с Лиёй, прайс) — **не меняются** в трансформации. Для них AS-IS = TO-BE, разделение не нужно.

### Карта трансформации

В `30-roles/README.md` ведётся таблица:

| Роль | AS-IS | TO-BE | Миграция | Статус |
|---|---|---|---|---|
| ... | ... | ... | ... | ... |

CC обновляет её автоматически при изменениях.

### Алгоритм добавления новой роли

Поскольку появятся новые роли (экспедитор), нужен runbook. Создан: [70-operations/runbooks/add-new-role.md](../70-operations/runbooks/add-new-role.md). Восемь шагов с чек-листом.

## Последствия

### Положительные
- Не теряется память о текущем состоянии при проектировании будущего
- Легче принимать решения по миграции (что меняется, что остаётся)
- Чёткий жизненный цикл документа: AS-IS → TO-BE → активный → архив

### Отрицательные / компромиссы
- Двойная структура внутри `30-roles/` — кажется избыточной для маленьких ролей
- Требует дисциплины при переезде между состояниями (CC обязан это контролировать)

## Альтернативы, которые отклонили

### Только TO-BE, без AS-IS
**Почему отклонили**: теряется память о текущем состоянии. При сравнении и принятии решений нечего противопоставлять.

### Только AS-IS, без TO-BE (просто описать как есть)
**Почему отклонили**: тогда непонятно, **куда идём**. Проект Евы — про трансформацию, цель надо явно описать.

### Раздельные слои `30-roles-current/` и `30-roles-target/` на верхнем уровне
**Почему отклонили**: раздваивает ось ролей. Внутреннее `as-is/`/`to-be/` — концептуально чище.

### Оба состояния в одном файле, секциями
**Почему отклонили**: при росте описания ролей (TO-BE будет проектироваться долго) файлы становятся слишком большими. Разные состояния — разные файлы.
