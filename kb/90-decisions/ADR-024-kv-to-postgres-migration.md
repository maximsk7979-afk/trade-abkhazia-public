# ADR-024: Миграция KV → Postgres (поэтапная, по сущностям)

## Контекст

Все данные живут в `trade_db.app_storage` как **целые JSON-массивы на ключ** (`trade-sales-v1`,
`trade-cat-clients`, …). Каждая запись — read-modify-write всего массива. Пишут **три независимых
клиента**: trade_app (браузер), Ева, trade-api. Глубокий аудит 2026-06-11 признал это
**системным риском №1**:

- **Lost updates**: две одновременные записи — одна молча теряется (прецедент: потеря 33
  клиентов, 2026-05-27, INC у GAP-019). С боевым запуском (менеджеры + клиенты в мини-аппе +
  Ева) вероятность растёт с каждым пользователем.
- **Нет транзакций**: мультисущностные операции (погрузка доставки = партии+склад+заявки+
  доставка) сохраняются раздельно; обрыв посередине = рассогласование. Палиатив — `saveMultiple`
  с откатом (Фаза 3a), но это не атомарность.
- **Масштаб**: правка одной заявки переписывает весь массив заявок; объём растёт — растёт и
  окно гонки, и трафик.

«Шаг 2» roadmap планировал перенос «1:1 и потом нормализовать». Этот ADR уточняет КАК.

## Решение

### Принципы

1. **Поэтапно по сущностям, не big-bang.** Порядок — от самых горячих/опасных к холодным.
   Каждый этап самодостаточен: бэкап → теневая сверка → переключение → freeze KV-ключа.
2. **Таблица на сущность: индексируемые колонки + JSONB.** Не проектируем «идеальную
   реляционку» сразу: ключевые поля (id, status, даты, clientId/projectId/officeId) — колонками
   с индексами; вся остальная запись — колонка `doc JSONB` (полная обратная совместимость
   формата). Нормализация — потом, по мере надобности.
3. **Запись per-record + транзакции.** INSERT/UPDATE одной записи вместо массива; операции
   на несколько сущностей (погрузка) — одна SQL-транзакция в trade-api.
4. **Совместимость через trade-api.** Все клиенты и так ходят в trade-api. Для мигрированной
   сущности: `GET /api/storage/:key` продолжает отдавать массив (SELECT → сборка) — читатели
   не ломаются; **запись массива на мигрированный ключ запрещается (410)** — писатели
   переводятся на точечные ручки (`POST/PATCH /api/v2/<entity>`) по одному.
5. **Реестр миграции**: таблица `migration_registry(key, state: kv|shadow|migrated)` —
   маршрутизация в trade-api по состоянию ключа.

### Порядок этапов (инкременты)

| # | Сущность | Почему в этом месте очереди |
|---|---|---|
| M0 ✅ | Инфраструктура — **выполнено 2026-06-11** (код-реестр MIGRATED_KEYS вместо таблицы — проще, деплоится атомарно с кодом) | реестр, v2-роутер, шаблон таблицы |
| M1 ✅ | **sales** (заявки/продажи) — **выполнено 2026-06-11** | самый горячий ключ: пишут trade-api (мини-апп), trade_app; деньги |
| M2 | **trips** (+ циклы закупки Евы) | пишут Ева (оркестратор/инструменты), trade-api (ленивые рейсы), trade_app |
| M3 | **clients + справочники** | пишут Ева (create_client, цены) и trade_app; прецедент потери |
| M4 | **batches/whops/deliveries** | транзакция «погрузка» становится атомарной по-настоящему |
| M5 | settlements, остальное; `/api/storage` → read-only легаси | финал |

Каждый M: ~1–2 сессии. Между этапами система полностью рабочая (гибрид KV+таблицы).

### Что НЕ делаем

- Не меняем формат записей (JSONB хранит как есть) — фронт/Ева читают те же объекты.
- Не трогаем БД `eva` (память Евы) — она уже реляционная.
- Не вводим ORM — голый `pg`, как везде в проекте.

## Последствия

- (+) Снят системный риск №1 до масштабирования числа пользователей.
- (+) Точечные ручки = меньше трафика, быстрее UI, серверная валидация на запись.
- (+) Транзакции для мультисущностных операций (M4).
- (−) На время гибрида — две ветки кода чтения/записи в trade-api (маршрутизация по реестру).
- (−) Каждый этап требует аккуратного перевода всех писателей сущности (поиск по трём кодовым базам).

## Альтернативы, которые отклонили

- **Big-bang перенос всех ключей сразу** — недели фриза функционала, один гигантский рискованный
  деплой; поэтапность даёт ценность с M1.
- **Optimistic locking поверх KV (version-поле)** — лечит lost update, но не даёт ни транзакций,
  ни выборок, ни масштаба; столько же правок клиентов при худшем итоге.
- **Отдельная новая БД/сервис** — Postgres уже стоит и бэкапится (runbook), KV и так в нём.
