# ADR-014: Проектный профиль клиента, справочник сегментов, проектная привязка товара

## Контекст

Фокус смещён на мультипроектные продажи через Еву (см. [ADR-013](ADR-013-eva-agent-architecture.md)). Один клиент покупает в **нескольких проектах** (турецкие овощи, местные овощи, бананы; в будущем цемент, напитки, алкоголь) и в разных проектах ведёт себя по-разному: разный ассортимент, возможно разный уровень цены и тип продажи, разный сегмент.

Текущее состояние (`trade_app_v3.jsx`):
- **Карточка клиента — плоская**: `pt` (уровень цены), `saleType` (ПС/ДС), `managerId`, контакты, `ynavUrl`. Привязки к проекту нет.
- **Товар** (`{id, sn, fn, g}`) имеет категорию `g` («Помидоры», «Огурцы», «Овощи», «Фрукты», «Бананы»), но **привязки к проекту нет**.
- **Сегментов** (тип клиента: магазин/общепит/РБУ/…) в системе нет.

Для онбординга клиентов Евой и матчинга «клиент ↔ рейс/закупка по проекту» профиль клиента должен стать проектно-осознанным.

## Решение

### 1. Товар: единый справочник + `applicableProjects[]`

К товару добавляется `applicableProjects: ["PRJ-NNN", ...]` (мультивыбор). **Единый** справочник товаров, не отдельный под каждый проект.

Обоснование: один товар реально живёт в нескольких проектах (помидор Т-001 — и турецкие, и местные, и грузинские овощи); отдельные справочники заставили бы дублировать товар и раздробили бы единое пространство SKU/FIFO/прайса. Приём `applicableProjects[]` уже применён к поставщику (ADR-009) — единый стиль.

Категория для ассортимента = существующее поле `g`, отфильтрованное по проекту (показываются категории товаров, у которых проект в `applicableProjects`).

**Миграция существующих товаров:** Т-001..033 получают `applicableProjects: ["PRJ-001"]` (фолбэк по [ADR-009](ADR-009-multitenancy-projects.md) §8.2); ретег вручную по мере необходимости.

### 2. Новый справочник сегментов `trade-cat-segments`

Формат: `{ id: "СГ-NNN", name, applicableProjects: ["PRJ-NNN", ...] }`. Один сегмент может принадлежать нескольким проектам.

Стартовый seed:

| Сегмент | Проекты |
|---|---|
| Оптовый склад | PRJ-001/002/003 (овощи), PRJ-004 (бананы), PRJ-005 (напитки), PRJ-007 (цемент), PRJ-008 (снеки) |
| Магазин | PRJ-001/002/003/004/005/007/008 |
| Уличная точка | PRJ-001/002/003/004 |
| Общепит | PRJ-001/002/003/004/005 |
| Гостиницы | PRJ-005 |
| РБУ | PRJ-007 |
| Стройплощадка | PRJ-007 |

### 3. Клиент: блок по проекту

Карточка клиента:
- **Общие поля**: `id`, `n`, контакты (`wa`, `tg`, `tgChatId`), `ynavUrl`, `locationPhotos[]`, `managerId`.
  - `ynavUrl` — точка на Яндекс.Навигаторе.
  - `locationPhotos[]` — массив ссылок на фото места доставки (витрина, вход/разгрузка, ориентир) для водителей/экспедиторов. Хранилище фото — общая фото-инфраструктура (см. «Уточнения»). Forward-ready: поле заводится сейчас, загрузка через Еву — позже.
- **`projects[]`** — массив проектных блоков, по одному на проект, в котором клиент покупает:
  ```
  { projectId, segment, priceLevel, saleType }
  ```
  - `projectId` — из `trade-cat-projects`
  - `segment` — из `trade-cat-segments` (отфильтрованных по этому проекту)
  - `priceLevel` — opt / mid / ret (в этом проекте)
  - `saleType` — ПС / ЗД (в этом проекте)
- **`onboarding`** (статус знакомства с Евой) — добавляется на этапе Ева↔клиент, не сейчас.

**Ассортимент не хранится как поле** — выводится (см. «Уточнения»).

**Миграция существующих клиентов:** плоские `pt`/`saleType` → один блок `{ projectId:"PRJ-001", segment:"", priceLevel: pt, saleType: saleType }`. Нормализация **на чтении** (фолбэк), без деструктивной массовой миграции данных.

### 4. Граница с прайс-движком (стыковка со Шагом 3 ADR-009)

Данные клиента становятся проектными **сейчас** — в первую очередь для Евы (матчинг, напоминания, понимание клиента), CRM и онбординга. Полная проектная цена per-line завязана на Шаг 3 ADR-009 (когда продажи получат per-line `projectId`).

До Шага 3:
- вводится хелпер `getClientPriceLevel(client, projectId)` — возвращает `priceLevel` из соответствующего проектного блока, при отсутствии проекта-контекста — из **первичного блока** (мигрированный PRJ-001) ради обратной совместимости;
- существующая логика прайса (`calcPriceFor`) переводится на этот хелпер без изменения текущего поведения для овощей.

### 5. Алкоголь — позже

Отдельный проект «Алкоголь» не заводится сейчас (решение Максима 2026-05-22). Сегменты «напитки» пока ссылаются на PRJ-005 «Безалкогольные напитки».

## Уточнения (2026-05-22, до реализации К3)

### У1. Ассортимент клиента — вычисляемый, а не хранимое поле

Изначально проектный блок включал `assortment[]` (категории, которые берёт клиент). При обсуждении выяснилось: связки «клиент→проекты» и «товар→проекты» дают **полный каталог проектов клиента**, но не подмножество, которое клиент реально берёт. Это подмножество корректнее **выводить из истории продаж** (категории через `товар.g`), а не вести вручную (ручное поле устаревает).

Решение: `assortment[]` **убран** из карточки клиента. Ассортимент = вычисляется из истории продаж. Для нового клиента (истории нет) стартовый намёк собирает Ева при онбординге и хранит в своей **памяти клиента (слой B, [ADR-013](ADR-013-eva-agent-architecture.md))** — не в справочнике. На чтении из истории доступно уже сейчас на уровне категорий (`товар.g`); проектный разрез истории — со Шагом 3 ADR-009.

### У2. Поле `locationPhotos[]` и общая фото-инфраструктура

В карточку клиента добавляется `locationPhotos[]` — ссылки на фото места доставки для водителей/экспедиторов (дополняет `ynavUrl`). Менеджер при онбординге через Еву загружает фото; Ева сохраняет на сервере и вписывает ссылку.

Хранилище фото — **общая возможность** (загрузка → VPS → ссылка), а не частный случай: переиспользуется накладными ([ADR-010](ADR-010-invoice-entity.md), Слой В), фото точек клиентов и в будущем (фото товара, пруф доставки). На эти фото распространяется бэкап-проблема [GAP-016](../00-meta/gaps.md). Поле `locationPhotos[]` заводится в К3 как forward-ready (заполняется вручную ссылкой), механизм загрузки через Еву — при постройке фото-инфраструктуры. Связано с ролью водителя/экспедитора ([GAP-013](../00-meta/gaps.md)).

## Последствия

### Положительные
- Профиль клиента готов к мультипроектным продажам и к Еве (матчинг с рейсами по ассортименту проекта, проектные напоминания).
- Единый приём `applicableProjects[]` (поставщик/товар/сегмент) — предсказуемая архитектура.
- Сегменты как справочник (а не enum) — расширяемы без правки кода, переиспользуются между проектами.

### Отрицательные / компромиссы
- Карточка клиента усложняется (блоки по проектам) — больше UI и миграция данных.
- Полная проектная цена откладывается до Шага 3; до него прайс работает по первичному блоку — приемлемо, пока активны только овощные проекты с одним уровнем цены у клиента.
- Ретег существующих товаров по проектам — ручная работа (дефолт PRJ-001).

## Альтернативы, которые отклонили

### Альтернатива 1: Отдельный справочник товаров под каждый проект
**Почему отклонили:** дублирование товаров (помидор в 3 проектах = 3 записи), дробление SKU/FIFO/прайса, большой вредный рефактор.

### Альтернатива 2: Плоская карточка + только `projects[]` (мультивыбор проектов), уровень цены/тип продажи глобальные
**Почему отклонили:** не отражает, что клиент берёт овощи оптом, а напитки в розницу; ассортимент всё равно нужен per-project. Половинчатое решение пришлось бы переделывать.

### Альтернатива 3: Сегмент как enum в коде
**Почему отклонили:** словари сегментов растут и различаются по проектам; справочник с `applicableProjects[]` расширяется без правки кода и переиспользует общие сегменты.
