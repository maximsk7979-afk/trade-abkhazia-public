# ADR-011: Сегментация знаний Евы по поставщикам (двухуровневая база)

## Контекст

В мае 2026 Максим выгрузил из обученного Claude-чата накопленные знания по распознаванию грузинских накладных — словарь из 21 термина, правила определения сорта, эвристики неоднозначностей, особенности почерка. Эти 7 файлов (`invoice-01..07`) — стартовая база для будущей Евы (распознавание накладных по ADR-010, ADR-012).

При проектировании структуры базы знаний обнаружилось:

1. **Все 50+ распознанных накладных — от одного поставщика** (Заза, П-004, оптовый склад в Батуми). Это единственный поставщик в обучающем чате.
2. **У Зазы будут другие поставщики в том же проекте** (PRJ-001 «Турецкие овощи»). Максим закупает у Зазы как у основного, но есть и другие склады в Батуми и Грузии.
3. **Новые проекты приведут принципиально других поставщиков** (см. ADR-009): абхазские теплицы, российские поставщики на рынке Сухум, грузинские фермеры, поставщики цемента, мяса, напитков.
4. **Разные поставщики — разные правила распознавания.** Свой жаргон (один пишет `პომიდორი`, другой `ხონბუვი` для того же помидора), свой почерк или печатный формат, свой ассортимент, свои ценовые диапазоны, свои особенности оформления (зачёркивания, два покупателя на листе у Зазы).

Если оставить базу знаний единой («грузинский словарь»), произойдёт **перекрёстное загрязнение**:
- Жаргон Зазы попадёт в распознавание накладных другого поставщика → неверные SKU.
- Ценовые диапазоны Зазы (актуальные февраль-май 2026) применятся к ценам фермера в июне → ошибочное определение сорта по цене.
- Особенности почерка одного человека ничему не помогут при печатном бланке другого.
- При обновлении базы один поставщик «отравит» другого.

Нужна модель базы знаний, которая:
- разделяет знания о конкретном поставщике и знания общего характера (грузинский алфавит, универсальные структурные правила, арифметическая проверка)
- допускает добавление нового поставщика без переписывания общего слоя
- даёт Еве при распознавании конкретной накладной доступ только к **релевантной** базе
- сохраняет возможность кросс-поставщикового обучения (если общегрузинская графема `ვ` чаще читается так у троих поставщиков из четырёх — это попадает в общий слой)

## Решение

Введена **двухуровневая** база знаний Евы для распознавания накладных: общий слой + per-supplier слой. Полные локальные базы у каждого поставщика — без выноса общих терминов в канонический справочник.

### 1. Структура папок в `kb/20-domain/invoices/`

```
kb/20-domain/invoices/
├── README.md                          # карта папки
├── _common/                           # общий слой (общегрузинский, общий формат)
│   ├── georgian-alphabet.md           # буквы, типичные пары похожих графем
│   ├── invoice-structure.md           # универсальная структура строки
│   ├── arithmetic-verification.md     # правило кол-во × цена = сумма
│   ├── number-formats.md              # десятичные точки, тысячные, запятые
│   └── ocr-common-issues.md           # типичные технические проблемы фото
├── extraction-prompts.md              # инструмент выгрузки из обученных чатов
├── examples/                          # общий золотой датасет (регрессия)
│   └── README.md
└── suppliers/
    ├── README.md                      # как добавить нового поставщика
    ├── p-004-zaza/                    # Заза (текущий, см. ниже)
    │   ├── profile.md                 # карточка: имя, склад, ассортимент, контакт
    │   ├── dictionary.md              # его словарь (21 термин + расширения)
    │   ├── recognition-rules.md       # правила определения сорта, эвристики
    │   ├── format.md                  # его формат накладной (два покупателя на листе, и т.п.)
    │   ├── handwriting.md             # описание почерка
    │   ├── price-ranges.md            # типичные цены (с пометкой о сезонности)
    │   └── examples/                  # его эталонные накладные (10-15)
    │       ├── README.md
    │       ├── np-zaza-001.jpg
    │       └── np-zaza-001.md
    └── <next-supplier>/               # шаблон для следующего
```

**Принципы папок:**
- `_common/` — общегрузинские знания и универсальные правила. Применяются ко всем грузинским поставщикам.
- `suppliers/<id>/` — всё, что характеризует конкретного поставщика. **Полная локальная база**, см. п. 3.
- `examples/` (на верхнем уровне) — общий золотой датасет для регрессии, включает примеры разных поставщиков.
- Имя папки поставщика — `<supplier-id>-<short-name>`, латиницей (для путей в FS — `p-004-zaza`).

### 2. Связь с проектом и поставщиком

База знаний привязана к **поставщику**, не к проекту. Один поставщик может работать в нескольких проектах (см. `Supplier.applicableProjects` в ADR-009) — база у него одна, термины помечаются проектом при необходимости.

Связка с проектом — через метаданные `Project.knowledgeBasePath` в ADR-009 для **дополнительных** проектных настроек (правила распознавания, специфичные для категории — например, штрих-коды для напитков, серии заморозки для мяса/рыбы), но **базовые знания о поставщиках лежат в suppliers/**.

```
PRJ-001 (Турецкие овощи)
  └─ knowledgeBasePath: "kb/20-domain/invoices/_project-overrides/prj-001"  # опционально
       и дополнительно для каждого поставщика проекта:
       ├─ suppliers/p-004-zaza/
       ├─ suppliers/p-005-batumi-other/
       └─ ...
```

`_project-overrides/` создаётся только при появлении проектной специфики, не сразу.

### 3. «Полная локальная база» (вариант А) — а не канонический словарь (вариант Б)

При обсуждении возникло два варианта:

**Вариант А (выбран):** у каждого поставщика **полная** локальная база. Если оба поставщика пишут `პომიდორი` для классического помидора — это записано в обеих папках `suppliers/<id>/dictionary.md`. Дублирование 20-30 терминов на поставщика принимается.

**Вариант Б:** общий канонический словарь (`_common/georgian-canonical-dictionary.md`) + локальные базы только с отклонениями от него.

**Почему вариант А:**
- Меньшая когнитивная нагрузка при добавлении нового поставщика — открыл папку, заполнил по шаблону, не разбираясь, что «как у всех», а что «своё».
- Независимая эволюция: словарь одного поставщика обновляется без рисков для других.
- Прозрачность: чтобы понять, что Ева знает про этого поставщика, достаточно открыть одну папку.
- Дублирование 21 термина × 10 поставщиков = 210 строк — копеечная плата за независимость.

### 4. Стартовая база Зазы

Текущие 7 файлов выгрузки (`invoice-01..07-*.md` в `~/Desktop/trade-inbox/`) — это **знания о Зазе**, не «знания о грузинских накладных вообще». При интеграции в `kb/` они **распределяются**:

**В `_common/` идёт:**
- Грузинский алфавит и пары похожих графем (`ბ` vs `ვ`, `ხ` vs `ჯ`, `ი` vs `ო` и т.д.) — это общегрузинская специфика.
- Универсальная структура строки `(ЯЩИКИ) ТОВАР КОЛ-ВО × ЦЕНА = СУММА` — применима ко всем грузинским рукописным накладным.
- Принцип арифметической проверки (кол-во × цена = сумма, допуск 1-3 лари).
- Категории технических проблем фото (склейка букв, обрезка краёв, зачёркивания) — общие.

**В `suppliers/p-004-zaza/` идёт:**
- Профиль: «Заза, оптовый склад в Батуми, основной поставщик PRJ-001, рукописные накладные, типичный ассортимент 21 товар».
- Словарь жаргона: 21 термин с написаниями, транслитерациями, частотой.
- Правила определения сорта: 9 правил, привязанных к ценам Зазы.
- Эвристики неоднозначностей: 8 пар (ბარდა/ვარდა и т.д.) — это его конкретные пары.
- Особенности почерка: наклон, слипание, цвет ручки.
- Ценовые диапазоны: с пометкой «февраль-май 2026, сезонные».
- Особенности формата: «два покупателя на листе (Максим/Лия, MAKS/LIA)», «зачёркивания и исправления».
- Имена покупателей в его накладных: `მარნე`, `მაქი`, `MAKS`, `ლა`, `ლია`, `LIA`.

Реструктуризация — это Заход 3 общего плана (см. roadmap).

### 5. Как Ева выбирает базу при распознавании

Три механизма, по приоритету:

**Механизм 1: явный выбор сотрудником при загрузке Invoice.**
- В UI Евы при загрузке фото — поле «Поставщик», берётся из `trade-cat-suppliers`.
- Ева загружает в контекст: `_common/` + `suppliers/<выбранный-id>/`.
- Это основной механизм, доступен всегда, самый надёжный.

**Механизм 2: контекстная подсказка из рейса/закупки.**
- Если Invoice загружается в существующий Trip — у рейса есть `trip.items[].supplierId`. Список кандидатов сужается до этих поставщиков.
- Если в рейсе один поставщик — Ева выбирает автоматически, без вопроса.
- Если несколько — Ева предлагает выбор из нескольких.

**Механизм 3: автоопределение по «отпечатку».**
- Включается **только** когда у нескольких поставщиков набралось ≥10 эталонных накладных каждый.
- Признаки:
  - формат шапки (есть бланк / нет; имя покупателя в шапке / только дата)
  - набор товаров (если в накладной авокадо + конференция — это вряд ли цементный поставщик)
  - имена покупателей в шапке (MAKS/LIA — характерный признак Зазы)
  - почерк — слабый признак без отдельной ML-модели, на старте не используем
- Ева предлагает: «Похоже на Заза (П-004), верно?» — сотрудник подтверждает или меняет.

В Шаге 1 (MVP) — работают **только Механизмы 1 и 2**. Механизм 3 — в Этапе 2 самообучения (см. ADR-012).

### 6. Что попадает в `_common/` со временем

При накоплении знаний по 2+ поставщикам, если правило/наблюдение справедливо для всех — оно **переезжает** из локальной базы в `_common/`. Решение о переносе — ручное, по предложению Евы (Этап 2 ADR-012) или сотрудника. Антипаттерн — преждевременный перенос: «у Зазы помидор-классик это SKU-001-02, наверное у всех так» → перенос в общий слой → у другого поставщика проблемы.

**Правило:** общий слой растёт только при **наблюдённой одинаковости у ≥2 поставщиков**. Не наоборот (от теории к данным).

### 7. Шаблон карточки поставщика (`suppliers/<id>/profile.md`)

Минимальный набор полей для нового поставщика:

```yaml
---
title: "Профиль поставщика: <Имя>"
supplierId: П-NNN
applicableProjects: [PRJ-NNN, ...]
status: active | paused | archived
last_updated: YYYY-MM-DD
---

# Поставщик П-NNN: <Имя>

## Основное
- **Локация:** <город, страна, конкретный склад/рынок>
- **Тип:** <оптовая база / ферма / рынок / производитель>
- **Тип накладной:** <рукописная / печатный бланк / чек / отсутствует>
- **Язык накладной:** <грузинский / русский / турецкий / смешанный>
- **Валюта расчётов:** <GEL / RUB / USD / TRY>

## Ассортимент
<какие товары обычно — категории, не SKU>

## Особенности
<коротко: что отличает этого поставщика>

## Контакт
<имя продавца, телефон, мессенджер, если известны>
```

## Последствия

### Положительные

- **Изоляция знаний** — добавление нового поставщика не ломает распознавание других.
- **Прозрачность** — чтобы понять, что Ева знает про поставщика, достаточно открыть одну папку.
- **Минимальный порог входа** — добавить нового поставщика = заполнить папку по шаблону.
- **Независимая эволюция** — словарь Зазы обновляется отдельно от словаря фермера.
- **Готовность к не-грузинским поставщикам** — структура работает для абхазских теплиц (русский), турецких поставщиков напитков (турецкий), любого формата.
- **Прозрачное обучение** — журнал `Invoice.recognition.corrections` (см. ADR-010) ложится в `suppliers/<id>/` при автообучении.

### Отрицательные / компромиссы

- **Дублирование терминов** — 21 термин × N поставщиков. Для овощей это копейки, для проектов со штрих-кодами (напитки, снеки) — больше.
- **Принятие решения о переносе в `_common/`** — ручное. При большом числе поставщиков может накопиться долг «эти правила похожи, наверное надо обобщить, но руки не доходят».
- **Запутывание при смене поставщиком ассортимента** — если Заза вдруг начнёт поставлять напитки, его база разрастётся за счёт новой категории. Возможно стоит ввести `dictionary-<category>.md` внутри папки поставщика — отложено до появления реального кейса.
- **Сложнее cross-поставщиковая аналитика** — «какой термин знают N поставщиков из M?» требует обхода всех папок. На текущем масштабе не критично.

## Альтернативы, которые отклонили

### Альтернатива 1: Канонический грузинский словарь + локальные отклонения (вариант Б)
**Почему отклонили:** см. п. 3. При появлении поставщика сотрудник должен разбираться, что у него «как у всех», а что — своё. Дублирование 21 термина — несущественная плата за прозрачность.

### Альтернатива 2: База знаний по проектам, не по поставщикам
**Почему отклонили:** Один проект может включать множество поставщиков с разными форматами (PRJ-001 — Заза + другие склады Батуми). Привязка к проекту слишком грубая. Поставщик — естественная единица знаний о распознавании.

### Альтернатива 3: Единая «база грузинских накладных» без сегментации
**Почему отклонили:** Перекрёстное загрязнение (см. контекст). Жаргон Зазы испортит распознавание у другого поставщика.

### Альтернатива 4: База знаний в БД, а не в `kb/`
**Почему отклонили:**
1. Базу знаний удобно версионировать через git (история, откат, обзор).
2. Архитектор и Чат читают `kb/` через public-зеркало (ADR-008) — для проектирования им база нужна.
3. Для Евы в рантайме база читается как часть промпта — не требует БД-запросов.
В будущем (Q3) может появиться кэширование в БД для производительности, но источник истины — `kb/`.
