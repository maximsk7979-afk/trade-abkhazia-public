# ADR-010: Сущность Invoice (накладная поставщика) с трёхстатусной моделью

## Контекст

Сегодня в системе **нет** накладной как отдельной сущности. Когда закупщик привозит товар от поставщика, данные с рукописной накладной заносятся вручную сразу в `trip.items[]` (для рейсов) — позиции, веса, цены. Сам **документ** (фото накладной) нигде не сохраняется. Это создаёт несколько системных проблем:

1. **Невозможно проверить ввод задним числом.** Если Нелли через неделю заметила расхождение в `trip.items[]` — оригинал накладной не сохранён, сверять не с чем.
2. **Невозможно автоматизировать распознавание.** Ева (см. ADR-011, ADR-012) должна работать с фото, но фото не существует в БД.
3. **Нет журнала «нераспознанных».** Закупщик загрузил накладную утром на рынке, Нелли распознаёт вечером в офисе — нужен список «к обработке», которого нет.
4. **Нет защиты от потери данных.** Бумажная накладная теряется (порвалась, забыли) — данные восстанавливаются по памяти, с ошибками.
5. **Нет аудиторского следа.** Кто, когда, как распознал накладную — неизвестно.

Кроме того, в мае 2026 принято решение (ADR-009) о мультипроектной архитектуре. Один из новых проектов — **PRJ-002 «Местные овощи»** — закупается **без рейса** (Покупка на рынке Сухум у поставщиков, привозящих из России; покупка у абхазских теплиц). Это требует ещё одной новой сущности — `Purchase` (закупка вне рейса), для которой накладная тоже должна сохраняться.

Нужна модель Invoice, которая:
- сохраняет фото каждой накладной от момента загрузки
- даёт явный жизненный цикл «загружено → распознано» с возможностью отмены
- допускает несколько попыток (плохое фото → загрузить новое)
- работает и с рейсами (PRJ-001 / PRJ-003), и с закупками вне рейса (PRJ-002)
- сразу учитывает мультипроектную архитектуру
- даёт Нелли удобный список «к распознаванию»

## Решение

Введена новая сущность `Invoice` со своим storage-ключом, трёхстатусной моделью, ссылкой на фото и привязкой к проекту, поставщику и операции закупки (Trip или Purchase).

### 1. Префикс ID

**`НП-NNNNNN`** — Накладная Поставщика. Шесть цифр, авто-инкремент. Выбор:

- `Н-` отвергнут как недостаточно ясный (можно спутать с накладной клиенту, если такая когда-то появится).
- `НП-` явно отличает «накладная **поставщика**», оставляя пространство для `НК-` (накладная клиенту) в будущем.

### 2. Структура записи

Хранится в `trade-invoices-v1`. Поля:

```json
{
  "id": "НП-000001",
  "projectId": "PRJ-001",
  "supplierId": "П-004",
  "linkedTo": {
    "type": "trip",
    "id": "Р-NNN"
  },
  "invoiceDate": "2026-02-09",
  "uploadedAt": "2026-02-09T15:30:00+03:00",
  "uploadedBy": "С-NNN",
  "status": "recognized",
  "photos": [
    "p-004/2026/np-000001.jpg",
    "p-004/2026/np-000001-p2.jpg"
  ],
  "recognition": {
    "items": [
      {"prodId": "Т-NNN", "skuId": "SKU-...", "qty": "...", "qtyBoxes": "...", "price": "...", "amount": "...", "rawText": "...", "confidence": 0.94}
    ],
    "totals": {"sum": 9307, "currency": "GEL"},
    "recognizedAt": "2026-02-09T16:00:00+03:00",
    "recognizedBy": "С-NNN",
    "method": "ai+human" | "human-only" | "ai-only",
    "aiConfidence": 0.92,
    "corrections": [
      {"line": 3, "field": "skuId", "from": "SKU-001-02", "to": "SKU-001-03", "at": "..."}
    ]
  },
  "cancelReason": null,
  "replacedBy": null,
  "history": [
    {"at": "...", "by": "С-NNN", "action": "uploaded"},
    {"at": "...", "by": "С-NNN", "action": "status_changed", "from": "unrecognized", "to": "recognized"}
  ]
}
```

**Поля верхнего уровня:**

| Поле | Тип | Назначение |
|---|---|---|
| `id` | string | `НП-NNNNNN` |
| `projectId` | string | Проект из ADR-009. Обязательно. |
| `supplierId` | string | ID поставщика (`П-NNN`). Обязательно. |
| `linkedTo` | object \| null | Привязка к операции закупки — см. п. 3 |
| `invoiceDate` | string | Дата как в самом документе |
| `uploadedAt` | string (ISO) | Момент загрузки фото |
| `uploadedBy` | string | Кто загрузил (`С-NNN`) |
| `status` | enum | `unrecognized` / `recognized` / `cancelled` |
| `photos` | string[] | Относительные пути к файлам |
| `recognition` | object \| null | Данные распознавания, null до перехода в recognized |
| `cancelReason` | string \| null | Если cancelled — почему |
| `replacedBy` | string \| null | ID накладной-замены при перезаливе (см. п. 5) |
| `history` | object[] | Журнал действий |

### 3. Привязка к операции закупки (`linkedTo`)

Накладная может быть привязана к одной из двух сущностей — рейс или закупка вне рейса:

```json
"linkedTo": { "type": "trip", "id": "Р-NNN" }      // рейс
"linkedTo": { "type": "purchase", "id": "ЗК-NNN" } // закупка вне рейса (см. ADR-009 шаг 1, GAP-009)
"linkedTo": null                                    // ещё не привязано (редко)
```

Накладная **может существовать без привязки** (например, фото загружено, но ещё не понятно, к какому рейсу относится). Это допустимо в статусе `unrecognized`. При переходе в `recognized` привязка должна существовать.

### 4. Жизненный цикл статусов

```
        ┌─────────────────┐
        │   unrecognized  │ ◄── загрузка фото
        └─────────────────┘
             │       │
   распознавание    отмена
             │       │
             ▼       ▼
    ┌──────────────┐ ┌────────────┐
    │  recognized  │ │ cancelled  │
    └──────────────┘ └────────────┘
             │              ▲
        отмена (с откатом   │
        связанных данных) ──┘
```

| Переход | Условие | Побочные эффекты |
|---|---|---|
| `unrecognized → recognized` | Сотрудник подтвердил все позиции | Запись в `recognition`. Создание/обновление `trip.items` или `purchase.items` |
| `unrecognized → cancelled` | Сотрудник отметил «отменить» | Без побочных эффектов |
| `recognized → cancelled` | Сотрудник с подтверждением | **Каскадный откат:** связанные `trip.items` / `purchase.items` / Batch / WhOp пересчитываются. Требует двойного подтверждения в UI |
| Из `cancelled` обратно | **Нельзя** | Cancelled — финальное состояние |

### 5. Перезалив плохого фото — новая запись + `replacedBy`

Когда сотрудник видит, что фото плохого качества для распознавания, и закупщик прислал новое фото — создаётся **новая запись Invoice**, старая помечается `cancelled` с указанием на замену:

```json
// Старая запись:
{
  "id": "НП-000001",
  "status": "cancelled",
  "cancelReason": "Плохое качество фото, перезалив",
  "replacedBy": "НП-000002"
}

// Новая запись:
{
  "id": "НП-000002",
  "status": "unrecognized",
  ...
}
```

**Почему так (вариант 1, а не перезапись фото в существующей записи):**
- История версий сохраняется — видно все попытки
- Старое фото не теряется — может пригодиться через год
- Простая модель «1 Invoice = 1 фото + 1 распознавание»
- Аудит чище — без перезаписи данных

Альтернатива «та же запись, фото меняется» рассматривалась и отклонена (см. раздел «Альтернативы»).

### 6. Хранение фото на VPS

Физически — файловая система VPS, защищённая папка **вне** `dist/` (чтобы не отдавалась как статика):

```
/var/www/trade/invoices/
├── p-004/                       # ID поставщика латиницей
│   ├── 2026/
│   │   ├── np-000001.jpg
│   │   ├── np-000001-p2.jpg     # вторая страница
│   │   └── np-000002.jpg
│   └── 2025/
│       └── ...
```

**Доступ:** только через API-эндпоинт `GET /api/invoices/:id/photo/:n` с проверкой прав. Прямой URL к статике не работает.

**Бэкапы:** папка `/var/www/trade/invoices/` включается в регулярный бэкап вместе с БД. Это **открывает новый GAP** (см. ниже) — текущая процедура бэкапов файлов не описана.

**Будущая миграция:** при росте объёма (десятки тысяч фото) — переход на S3-совместимое хранилище (у Vultr есть Object Storage). Пока — файловая система.

### 7. Журнал для Нелли — вьюшка, не сущность

«Журнал нераспознанных» — это **фильтр** по Invoice, не отдельная таблица:

- `status === "unrecognized"`
- Сортировка: по `uploadedAt`, старые первыми
- Поля: дата, поставщик, проект, кто загрузил, давность («2 дня назад»)

**Telegram-уведомления для Нелли:**
- Каждое утро 9:00 МСК — сводка: «У тебя N нераспознанных накладных, самой старой M дней»
- При загрузке новой не-Нелли (закупщик, Максим) — мгновенное уведомление
- Реализация уведомлений может быть отложена — это не блокер MVP

### 8. UI

**Новый модуль «Накладные»** в навбаре:
- Главный экран Нелли — список всех Invoice с фильтрами по статусу, проекту, поставщику, периоду
- Карточка накладной: фото + распознанные позиции + статус + действия

**В существующих модулях:**
- В карточке Рейса (Trip) и Закупки (Purchase): кнопка `📷 Накладная` — если есть, открывает фото в попапе; если несколько накладных у одной операции — список
- В строках `trip.items` / `purchase.items` — маленькая иконка-ссылка на исходную накладную

**На главной:**
- Бейдж с количеством `unrecognized` — у Нелли и у Максима всегда на виду

### 9. Связь с распознаванием Евой (ADR-011, ADR-012)

В Шаге 1 (до июня 2026) — Invoice сохраняется и распознаётся **человеком вручную** через UI. Это уже даёт ценность (хранение фото, журнал, аудит).

В Q3 (когда заработает Ева — MVP по ADR-012):
- При загрузке фото Ева автоматически делает попытку распознавания
- Выдаёт черновик `recognition.items` с `confidence` по каждой позиции
- Сотрудник принимает / правит / отклоняет
- Метод фиксируется в `recognition.method` (`ai+human` / `human-only` / `ai-only`)
- Все исправления сохраняются в `recognition.corrections[]` — это **обучающие данные** для Этапа 2 самообучения (ADR-012)

### 10. Миграция существующих рейсов

Существующие записи `trip.items` остаются как есть — без обратной привязки к Invoice. Новые рейсы — обязательно с Invoice.

Альтернативу «дозалить накладные на старые рейсы задним числом» **не** реализуем — фото нет, ценности мало.

## Последствия

### Положительные

- **Документальная база восстанавливается** — каждая закупка имеет фото оригинала, доступное навсегда.
- **Журнал «к распознаванию» для Нелли** — нет потерянных накладных, нет «забыли занести».
- **Аудиторский след** — кто, когда, как распознал, что исправил. Готовая база для разбора инцидентов.
- **Готовность к Еве** — структура `recognition` рассчитана на AI и сохраняет данные для обучения.
- **Защита от ошибок** — расхождение в `trip.items` всегда можно проверить против оригинала.
- **Поддержка PRJ-002** — местные закупки на рынке тоже получают накладную (даже если она минимальная — чек, рукописная записка).
- **Версии перезаливов сохраняются** — `replacedBy` цепочкой даёт историю попыток.

### Отрицательные / компромиссы

- **Объём файлов будет расти** — несколько мегабайт на одну накладную × сотни накладных/месяц = десятки гигабайт за год. Нужен план миграции на S3 (когда — определим по факту).
- **Нелли получает новую обязанность** — распознавание. До Евы (Q3) это полностью ручной труд. Может быть необходима помощница или роль закупщика возьмёт часть.
- **Отмена `recognized → cancelled` сложна** — каскадный откат связанных данных требует аккуратной реализации и двойного подтверждения. Возможны баги в начале.
- **Хранение фото на VPS — пока без облачной репликации.** Падение диска = потеря фото. **Митигация:** включить папку фото в регулярные бэкапы (открытый новый GAP).
- **UI растёт** — новый модуль «Накладные», кнопки в существующих карточках, бейджи. Это значительный фронтенд-блок в Шаге 1.

## Открытые GAP, открытые этим ADR

- **GAP-016 (новый):** бэкап файлов накладных. Сейчас бэкапы только БД. Папка `/var/www/trade/invoices/` должна попадать в резервное копирование. Регулярность, ротация, восстановление — спроектировать перед запуском Шага 1.
- **GAP-017 (новый):** правила хранения и архивации старых фото. Через год — сколько хранить, что архивировать в холодное хранилище. Сейчас отложим, вернёмся через ~6 месяцев работы.

## Альтернативы, которые отклонили

### Альтернатива 1: Перезаливать фото в той же записи Invoice (вариант 2 из обсуждения)
**Почему отклонили:** История попыток размывается. Старое фото удаляется или хранится в `oldPhotos[]` — сложнее аудит. Решение «новая запись + replacedBy» проще и чище.

### Альтернатива 2: Хранить фото как base64 в БД
**Почему отклонили:** Раздувает БД в десятки раз, ухудшает производительность всех запросов, усложняет бэкап и репликацию.

### Альтернатива 3: Хранить только распознанные данные, фото не сохранять
**Почему отклонили:** Это текущее состояние, и именно оно — корень всех 5 проблем из «Контекста». Невозможен аудит, обучение Евы, восстановление ошибок.

### Альтернатива 4: Накладная как часть Trip (`trip.invoicePhoto`), не отдельная сущность
**Почему отклонили:**
1. PRJ-002 закупки без рейса — некуда положить.
2. Один рейс может иметь несколько накладных (несколько поставщиков).
3. Разные статусы (unrecognized / recognized) — внутри Trip это разводит логику.
4. Не масштабируется на будущие потоки документов (накладные клиентам, счета-фактуры).

### Альтернатива 5: S3-совместимое хранилище сразу
**Почему отклонили:** Лишний компонент инфраструктуры на старте. Файловая система VPS даёт ту же функциональность для текущих объёмов и проще в обслуживании. Миграция на S3 — простой шаг, когда объём вырастет.
