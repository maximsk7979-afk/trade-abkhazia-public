# ADR-012: Поэтапный план самообучения Евы для распознавания накладных

## Контекст

Максим уже три месяца (февраль-май 2026) распознаёт грузинские рукописные накладные через **обученный Claude-чат** в claude.ai — диалоговый чат с накопленным контекстом из 50+ примеров. Качество распознавания за это время выросло от грубых ошибок до «практически без ошибок» на последних накладных.

В беседе 2026-05-19 Максим поставил вопрос: можно ли реализовать аналогичный механизм в trade_app — чтобы Ева **постоянно самообучалась**, пополняла базу знаний при каждой совместной обработке накладной с сотрудником, и использовала накопленные знания на следующих накладных.

Ключевое уточнение: **«самообучение» здесь не означает fine-tuning модели.** Anthropic API не даёт обучать веса Claude. То, что произошло в обучающем чате — это не обучение модели, а **накопление контекста**. Все знания, которые применяет Claude в этом чате, либо явно в контексте, либо выведены логически. Мы можем воспроизвести и **улучшить** этот механизм через RAG (retrieval-augmented generation) и явное управление базой знаний.

Нужен поэтапный план, который:
- даёт ценность с первого этапа (MVP) без зависимости от полностью автоматического самообучения
- не размывает качество базы (не каждая ошибка сотрудника попадает в правила)
- защищён от регрессий (новое правило не должно ломать ранее работавшее распознавание)
- интегрирован с Invoice (ADR-010) и сегментацией по поставщикам (ADR-011)
- реалистичен по срокам — MVP к Q3 2026, далее эволюция

## Решение

Принят трёхэтапный план развития самообучения Евы. Каждый этап даёт ценность сам по себе и не требует завершения следующего. Переход между этапами — по факту накопления данных и пользовательской готовности.

### Этап 1 — MVP без автообучения (~2-3 недели работы, Q3 2026)

**Цель:** базовая инфраструктура распознавания. Все компоненты работают, кроме автоматического обновления базы знаний.

**Что делает Ева:**
1. Сотрудник загружает фото накладной → создаётся `Invoice` со статусом `unrecognized` (см. ADR-010).
2. Сотрудник указывает поставщика (или Ева определяет по контексту рейса — Механизм 2 из ADR-011).
3. Ева читает контекст: общий слой `_common/` + папка поставщика `suppliers/<id>/` (по ADR-011).
4. Ева делает **попытку распознавания** через Claude API: отправляет фото + системный промпт с базой знаний → получает черновик `recognition.items[]` с `confidence` по каждой позиции.
5. UI показывает сотруднику черновик: фото слева, разметка справа, позиции с низким `confidence` подсвечены.
6. Сотрудник принимает / правит / отклоняет каждую позицию. Все исправления сохраняются в `recognition.corrections[]` (см. ADR-010).
7. После подтверждения — Invoice переходит в `recognized`, создаются связанные `trip.items` / `purchase.items`.

**Что НЕ делает Ева в Этапе 1:**
- Не обновляет базу знаний автоматически — все знания берутся из текущего состояния `kb/`.
- Не предлагает новые правила или термины — даже если 5 раз подряд встретила незнакомое слово.
- Не определяет поставщика автоматически (Механизм 3) — только явный выбор или контекст рейса.

**База знаний пополняется вручную:**
- При появлении нового поставщика — Максим/Нелли заводят папку `suppliers/<id>/` по шаблону (ADR-011).
- При замеченном новом термине — добавляют в `dictionary.md` поставщика.
- Изменения в `kb/` — через CC (single writer per ADR-008).

**Журнал распознавания** копится автоматически: каждая Invoice со всеми правками сотрудника — обучающий материал для Этапа 2. Этап 1 нужен в том числе для сбора этого материала.

**Ценность Этапа 1 сама по себе:**
- Фото накладных сохраняются (закрытие 5 проблем из ADR-010 контекста)
- Журнал «к распознаванию» для Нелли
- Стартовая база знаний Зазы из выгрузки 2026-05 даёт качество ~70-80% «из коробки»
- Аудиторский след всех распознаваний

**Условие готовности перехода к Этапу 2:** накоплено ≥50 распознанных Invoice с правками, период работы ≥1 месяца.

### Этап 2 — Полуавтоматическое обучение (~2-3 недели работы)

**Цель:** Ева сама предлагает обновления базы знаний на основе накопленного журнала. Все предложения подтверждаются человеком.

**Новые возможности Евы:**

1. **Предложение новых терминов.** Если в журнале есть слово, которое 3+ раза было исправлено сотрудником одинаково (например, незнакомое грузинское слово → всегда «помидор розовый») — Ева предлагает: «Добавить термин X в словарь поставщика?»

2. **Предложение новых правил.** Если повторяющийся паттерн исправлений указывает на правило (например, цена в диапазоне 38 → всегда чеснок) — Ева формулирует правило и предлагает добавить в `recognition-rules.md`.

3. **Предложение пар неоднозначности.** Если два термина регулярно путаются — Ева добавляет в раздел эвристик.

4. **Предложение переноса в `_common/`.** Если у ≥2 поставщиков подтверждена одинаковость правила/термина — Ева предлагает вынести в общий слой (см. ADR-011 п. 6).

5. **Автоопределение поставщика (Механизм 3 из ADR-011).** Включается, когда у ≥2 поставщиков набралось ≥10 эталонных накладных. Ева предлагает «Похоже на Х, верно?» — сотрудник одним кликом подтверждает.

**Поток подтверждения:**
- Ева формирует **дайджест предложений** раз в неделю или по запросу.
- Максим/Нелли просматривают предложения в UI: текст предложения + примеры из журнала, на основе которых сформулировано.
- По каждому: «Принять» / «Отклонить» / «Изменить и принять».
- Принятые предложения → CC получает задание на обновление `kb/` → автокоммит → деплой.

**Регрессионный контроль:**
- Перед каждым добавлением Ева прогоняет золотой датасет (`examples/`) с обновлённой базой.
- Если качество распознавания эталонов падает — предложение **автоматически отклоняется** с пометкой «вызывает регрессию».
- Если не падает — отправляется на подтверждение человеком.

**Граница автоматизма в Этапе 2:** **никакое** новое знание не попадает в базу без подтверждения человеком. Это критично против размывания качества (см. альтернативы).

### Этап 3 — Автомодерация очевидных случаев (без жёсткого срока)

**Цель:** снижение нагрузки на подтверждение очевидных предложений; ручная модерация остаётся для правил и эвристик.

**Что становится автоматическим:**

1. **Новые термины с явной частотой.** Если незнакомое слово 5+ раз подряд распознано одинаково с подтверждением сотрудника, и регрессия не вызывается — попадает в словарь автоматически, с пометкой `auto-added` и ссылкой на источники.

2. **Уточнение ценовых диапазонов.** Если фактические цены вышли за зафиксированный диапазон — Ева расширяет границы автоматически (с порогом — например, цена в 2× от диапазона требует подтверждения).

3. **Обновление профиля поставщика.** Новые имена покупателей в шапке, обнаруженные сокращения — попадают в карточку.

**Что остаётся ручным:**
- Новые правила определения сорта.
- Новые пары неоднозначностей.
- Перенос знаний между поставщиками и в `_common/`.
- Изменения в формате накладной поставщика.
- Любое предложение, помеченное Евой как «низкая уверенность» или «контекст-зависимое».

**Откат:** журнал автодобавлений ведётся отдельно; любое автодобавление можно откатить одной командой за период.

### Связь этапов с проектами

Этапы 1-3 работают **в рамках одного поставщика** (изоляция знаний по ADR-011). То есть Этап 2 может быть включён для Зазы (когда у него накопится 50+ накладных), но для нового поставщика — снова Этап 1, потому что у него нет журнала.

Это **самоадаптация под зрелость базы**: у Зазы Ева агрессивнее предлагает, у нового поставщика — работает только на ручных правках. По мере накопления — переходит к более автоматическим этапам.

### Технические требования

**Для Этапа 1:**
- Claude API доступен в рантайме trade_app (через AWS Bedrock или прямой Anthropic — выбор в будущей задаче).
- Системный промпт собирается из `_common/` + `suppliers/<id>/` (общий размер 5-20K токенов — укладывается в контекст).
- Структура `Invoice.recognition` готова к этому (ADR-010).
- Логирование `recognition.corrections[]` — обязательно.

**Для Этапа 2:**
- Анализатор журнала: периодическое задание, читает Invoice за период, ищет паттерны.
- UI для дайджеста предложений.
- Хранение золотого датасета с поддержкой регрессионного прогона.

**Для Этапа 3:**
- Журнал автодобавлений с возможностью отката.
- Метрики качества для мониторинга (% попадания, % правок, средний `confidence`).

Бюджет Claude API при объёме ~30 накладных/неделя — на старте незначителен (см. INC-001, бюджетный мониторинг — ещё одна задача в roadmap).

## Последствия

### Положительные

- **Ева полезна с первого дня** — даже без автообучения MVP даёт скорость и точность лучше ручного ввода с нуля.
- **База знаний эволюционирует автоматически** при сохранении контроля человека.
- **Изоляция от размывания** — регрессионный прогон золотого датасета защищает от ухудшения качества.
- **Естественная адаптация на нового поставщика** — у каждого свой цикл созревания.
- **Накапливается ценный аудит** — журнал `recognition.corrections[]` сам по себе материал для бизнес-аналитики (какие ошибки чаще всего, у каких поставщиков, в каких товарах).

### Отрицательные / компромиссы

- **MVP требует ручной поддержки базы знаний** — пока Ева не дозреет до Этапа 2, новые термины добавляет CC по запросу.
- **Этап 2 требует UI для подтверждения предложений** — это новый блок работы, отложен от MVP.
- **Регрессионный прогон стоит токенов API** — каждое предложение → прогон 10-15 эталонов → расход. На малых объёмах не критично.
- **«Чёрный ящик» того, почему Claude распознал так, а не иначе** остаётся даже с RAG — мы видим, что было в контексте, но не интернальную логику модели. Митигация — журнал `confidence` и правок для статистики.
- **Не подходит для абсолютно нового языка/формата** — если появится новый поставщик с письменностью, которой нет в `_common/`, придётся вручную создавать общую базу для нового языка. Будет так с турецкими, армянскими, абхазскими накладными.

## Альтернативы, которые отклонили

### Альтернатива 1: Полностью автоматическое обучение с первого дня
**Почему отклонили:** Высокий риск размывания базы. Любая опечатка сотрудника или ситуативное решение мгновенно становятся «правилом». Через месяц база — мусор. Контроль человеком на старте критичен.

### Альтернатива 2: Fine-tuning модели на накопленных данных
**Почему отклонили:** Технически невозможно для Claude через Anthropic API. Для опенсорсных моделей возможно, но качество сильно ниже Claude — в нашем случае нерационально.

### Альтернатива 3: Никакого самообучения — только ручное ведение `kb/`
**Почему отклонили:** На малом числе поставщиков работает, но плохо масштабируется. Когда у Зазы 200 накладных и появилось 10 новых паттернов — заметить и зафиксировать вручную трудно. Полуавтоматическое обнаружение паттернов — естественное решение.

### Альтернатива 4: Сразу Этап 3 (автомодерация) без полуавтомата
**Почему отклонили:** Этап 2 нужен для **обучения людей** работе с предложениями. Сразу автомодерацию принять психологически тяжелее («Ева сама что-то добавила, что именно?»). Этап 2 — мост доверия.

### Альтернатива 5: Использовать другой подход к памяти агента — векторный поиск/RAG с самого старта
**Почему отклонили:** На текущем объёме базы (5-20K токенов на поставщика) всё помещается в промпт целиком — RAG избыточен. Когда база разрастётся (через год-два), переходим на векторный поиск. Сейчас «всё в промпт» проще и надёжнее.
