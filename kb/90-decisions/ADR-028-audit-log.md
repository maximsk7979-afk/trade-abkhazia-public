# ADR-028: Журнал изменений БД (audit_log)

## Контекст

Запрос владельца (2026-07-07): нужен журнал ВСЕХ изменений в базе — автор, время,
источник (TradeApp / мини-апп / Ева) и описание — для разбора спорных вопросов.
До этого существовали только частные следы: `fin_ops_log` (денежные операции движка
ADR-027, с актором), `history`-массивы статусов на продажах, `updated_at` на строках.
Глобального журнала не было.

## Решение

**Одна точка перехвата — слой сторов.** После миграции ADR-024 все записи в БД идут
через ~15 сторов с униформным API (`upsert`/`remove`/`batch`/`set`). `audit-log.js`
оборачивает мутирующие методы всех сторов (реестры `STORES`, `SINGLETONS`,
`app-web-auth`) — эндпоинты не правятся, новые эндпоинты покрываются автоматически,
пока пишут через сторы (Обязательство 8).

**Таблица `audit_log`** (append-only, ручки записи/удаления нет):
`ts` · `actor_id`/`actor_label` · `source` (web|mini|eva|internal|system) · `path` ·
`entity` (KV-ключ) · `op` (upsert|remove|set) · `entity_id` · `doc` (состояние ПОСЛЕ,
JSONB) · `summary`. Индексы по ts / (entity, entity_id) / actor_id.

**Ключевые свойства:**
1. **Актор из контекста запроса** — AsyncLocalStorage: middleware кладёт `req`; в момент
   записи стора извлекается `req.webUser` (веб-сессия GAP-078: staffId+имя) / `req.mini`
   (Telegram: staffId/clientId+роль) / internal-токен (заголовок `X-Source: eva` → «Ева»,
   иначе «internal-скрипт») / вне запроса → «system» (миграции, кроны).
   `X-Source` доверяется ТОЛЬКО вместе с валидным internal-токеном.
2. **Атомарность**: журнальная строка пишется тем же транзакционным клиентом, что и
   операция — откат операции откатывает журнал. Исключение — `batch()` сторов (своя
   внутренняя транзакция): журнал пишется после COMMIT, fail-open (сбой журнала логируется,
   но не роняет бизнес-операцию).
3. **«Состояние до» не дублируется**: цепочка записей той же `(entity, entity_id)` даёт
   историю — предыдущая запись и есть before (первая запись после внедрения — без before).
4. **Маскирование**: `app-web-auth` (учётки веб-входа) журналируется без тела (хэши
   паролей в журнал не попадают); документы >64КБ (прайс) — тоже только summary.
5. **Чтение**: `GET /api/audit` (фильтры entity/entityId/actor/source/from/to/limit≤1000) —
   сотрудники с полным веб-доступом и внутренние клиенты; `demo` → 403 (Обязательство 7).
   Веб-вкладка «🕓 Журнал» (скрыта у demo).

**Попутный фикс photos-router** (обнаружен инвентаризацией писателей): роутер фото читал
и писал `app_storage` НАПРЯМУЮ, тогда как его ключи (`trade-cat-clients`,
`trade-cat-contragents`, `trade-sales-v1`) с 2026-06-15 мигрированы в таблицы — фото
уходили бы в замороженную KV-копию (латентно: с миграции не было ни одной загрузки,
проверено по диску — данные целы). Переведён на `kvGet`/`kvUpsertOne` через сторы:
живые данные + автоматическое журналирование фото-правок.

## Границы (честно)

- Журнал покрывает **записи через приложение** (все три поверхности). Прямые SQL-правки
  (миграции CC через psql) в журнал не попадают — они фиксируются в CHANGELOG сессий;
  при необходимости следующий шаг — PG-триггеры.
- Ева журналируется как источник «Ева» без конкретного менеджера (актор-детализация
  Евы — кандидат на доработку; сами доки часто содержат `managerId`).
- `fin_ops_log` остаётся отдельным журналом операций движка (тип/params/сторно-связка);
  audit_log при этом видит и его следствия (settlements/movements) — двойное покрытие
  осознанное: разные оси.
