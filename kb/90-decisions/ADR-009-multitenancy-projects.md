# ADR-009: Мультипроектная архитектура (Project + projectId сквозной)

## Контекст

Система Trade Abkhazia изначально создавалась под **один бизнес** — закупку турецких овощей через грузинские оптовые склады (Заза в Батуми и др.) с продажей в Абхазии. Модель данных (Trip, Sale, WhOp, Batch, Settlement) не имеет понятия «проекта» или «направления бизнеса» — всё считается единой кассой и единым P&L.

В мае 2026 Максим расширяет деятельность на несколько параллельных направлений:

| Проект | Источник | Запуск |
|---|---|---|
| Турецкие овощи (текущий) | Турция → грузинские оптовые склады в Батуми (Заза и др.) | 2024 |
| Местные овощи | Абхазские теплицы + российский импорт через рынок в Сухуме | текущий |
| Грузинские овощи | Фермы и рынки Грузии | июнь 2026 |
| Бананы | Грузия (большие объёмы) | планируется |
| Безалкогольные напитки | Грузия, Турция, Армения | планируется |
| Замороженное мясо и рыба | Грузия | планируется |
| Цемент | Грузия | планируется |
| Снеки и кондитерские изделия | Грузия, Турция | планируется |

Если оставить единую модель — учёт по проектам будет невозможен, и масштабирование к 7+ проектам приведёт к смешению финансов, потере прозрачности P&L по направлениям, неконтролируемому переходу данных одного проекта в другой.

Нужна архитектура, которая:
- даёт **раздельный учёт и P&L** по каждому проекту
- разрешает **общие справочники** там, где сущности кросс-проектные (клиенты, склады, сотрудники)
- разрешает **смешанные операции** (один Sale-чек может включать товары из нескольких проектов)
- допускает **разную экономику** проектов (валюты, единицы измерения, способы хранения)
- мигрируется **обратно совместимо** — текущая работа PRJ-001 не прерывается
- готова к **запуску PRJ-003** к июню 2026 (срок жёсткий — старт сбора урожая грузинских фермеров)

## Решение

Введена сквозная мультипроектная архитектура с новой сущностью `Project`, полем `projectId` во всех транзакционных сущностях и гибким режимом для справочников.

### 1. Новый справочник `trade-cat-projects`

Хранится отдельным storage-ключом. Префикс ID — `PRJ-` (латиница, чтобы не путаться с `П-` поставщик, `ПР-` партнёр).

```json
{
  "id": "PRJ-001",
  "name": "Турецкие овощи",
  "shortName": "TURK-VEG",
  "status": "active",
  "startedAt": "2024-01-01",
  "category": "perishable-vegetables",
  "defaultCurrency": "GEL",
  "defaultOfficeId": "О-001",
  "ownerStaffId": "С-001",
  "knowledgeBasePath": "kb/20-domain/invoices/suppliers/p-004-zaza",
  "uiColor": "#5BA873",
  "description": "Закупка турецких овощей через грузинские оптовые склады (Заза в Батуми и др.), продажа в Абхазии"
}
```

| Поле | Назначение |
|---|---|
| `status` | `active` / `paused` / `archived` |
| `category` | техническая категория для UI и аналитики (см. таблицу ниже) |
| `defaultCurrency` | валюта по умолчанию для расчётов с поставщиками проекта |
| `defaultOfficeId` | основной склад проекта (можно несколько через `usedByProjects` в Office) |
| `ownerStaffId` | ответственный сотрудник |
| `knowledgeBasePath` | путь в `kb/` к спец-знаниям проекта (для Евы) |
| `uiColor` | цвет метки в интерфейсе для визуального различения |

### 2. Стартовые проекты

| ID | Имя | Категория | Валюта | Статус |
|---|---|---|---|---|
| `PRJ-001` | Турецкие овощи | `perishable-vegetables` | GEL | active |
| `PRJ-002` | Местные овощи | `perishable-vegetables` | RUB | active |
| `PRJ-003` | Грузинские овощи | `perishable-vegetables` | GEL | active (старт июнь 2026) |
| `PRJ-004` | Бананы | `perishable-vegetables` | GEL | paused (планируется) |
| `PRJ-005` | Безалкогольные напитки | `beverages` | mixed (GEL/TRY/AMD) | paused |
| `PRJ-006` | Замороженное мясо и рыба | `frozen` | GEL | paused |
| `PRJ-007` | Цемент | `construction` | GEL | paused |
| `PRJ-008` | Снеки и кондитерские | `snacks` | mixed (GEL/TRY) | paused |

`PRJ-004..008` заводятся в справочнике как `paused` — для резервирования ID и подготовки структуры. Перевод в `active` — когда проект реально стартует.

### 3. `projectId` сквозной во всех транзакционных сущностях

Поле обязательное, без default-значения на запись новых данных. Для существующих данных при миграции — default `PRJ-001`.

| Сущность | Поле | Комментарий |
|---|---|---|
| Trip | `projectId` | Рейс всегда внутри одного проекта |
| Purchase (новая, см. ADR-010 / GAP-009) | `projectId` | Закупка вне рейса — местные/локальные |
| Invoice (новая, см. ADR-010) | `projectId` | Накладная всегда внутри проекта |
| WhOp | `projectId` | Складская операция |
| Batch (партия FIFO) | `projectId` | Партия — товар проекта |
| Sale | **на уровне позиций** — `sale.items[].projectId` | Смешанные продажи (см. п. 5) |
| Settlement | `projectId` или `allocation` для cross-project (см. п. 7) | |

### 4. Справочники — три режима

**Режим А: общий, без поля `projectId`.**
- `Client` — клиент может покупать из любых проектов. Метаданные `boughtInProjects` — вычисляются из истории, не хранятся.
- `Contragent` — категории расходов (аренда, налоги, юрист) — обычно кросс-проектные.

**Режим Б: с массивом `applicableProjects` (или `worksInProjects` / `usedByProjects`).**
- `Supplier.applicableProjects: ["PRJ-001"]` — у поставщика основные проекты, но запись может появиться в любой. Жёсткой блокировки нет — поле для UI и подсказок.
- `Staff.worksInProjects: ["PRJ-001", "PRJ-002"]` — где работает сотрудник. Максим, Нелли — во всех; закупщик овощей у Зазы — только в PRJ-001.
- `Office.usedByProjects: ["PRJ-001", "PRJ-002"]` — кросс-проектные склады (О-001 Сухуми — для нескольких проектов).
- `Partner.applicableProjects: ["PRJ-001"]` — Лия пока в овощах.

**Режим В: с обязательным `projectId`.**
- `SKU / Product` — см. п. 5 (гибрид).

### 5. SKU — гибридная модель

При обсуждении возникло три варианта:
- А: SKU кросс-проектный, партии несут проект — клиент видит «Помидор» без различия
- Б: SKU per-project, всё дублируется — два разных SKU «Помидор турецкий» и «Помидор местный»
- **Гибрид (выбран)**: базовый SKU кросс-проектный + признак происхождения у партии + проект-зависимая цена

```json
SKU = {
  "id": "SKU-001-02",
  "name": "Помидор классический",
  "unit": "kg",
  "taraType": "box-14kg",
  "storageType": "ambient"
  // НЕТ поля projectId — SKU универсальный
}

Batch = {
  "id": "БТ-NNN",
  "skuId": "SKU-001-02",
  "projectId": "PRJ-001",      // обязательно
  "originLabel": "Турция / Заза", // для UI и поиска
  ...
}

PriceList entry = {
  "skuId": "SKU-001-02",
  "projectId": "PRJ-001",       // цена считается на паре (sku, project)
  "tier": "wholesale",
  "price": 80
}
```

Клиент в прайсе видит:
- «Помидор классический (турецкий) — 80 ₽»
- «Помидор классический (местный) — 60 ₽»

Это **один SKU** с разными ценами и origin-метками. При продаже выбирается партия из проекта, цена которого взята.

### 6. Sale смешанные — `projectId` на уровне позиции

Один Sale-чек может содержать товары из разных проектов:

```json
{
  "id": "ПС-001",
  "type": "sale-direct",
  "clientId": "К-XXX",
  "officeId": "О-001",
  "saleData": {
    "lines": [
      {"prodId": "Т-001", "skuId": "SKU-001-02", "projectId": "PRJ-001", "qty": "...", "price": "..."},
      {"prodId": "Т-001", "skuId": "SKU-001-02", "projectId": "PRJ-002", "qty": "...", "price": "..."}
    ]
  }
}
```

**Следствия:**
- FIFO выбирает партии **в рамках проекта позиции** (для строки с `projectId: PRJ-001` — только партии PRJ-001).
- Маржа и P&L считаются **per-line**, потом агрегируются по `projectId`.
- Возвраты, скидки, оплата — распределяются по позициям пропорционально.
- На `Sale` уровне поле `projectId` не вводится (становится derived: список уникальных проектов из позиций).

### 7. Cross-project расходы и распределение

Часть расходов общие для всех проектов: аренда офиса, зарплата Максима/Нелли, налоги, общая логистика, бухгалтер.

В `Settlement` с типом `expense` вводится поле `allocation`:

```json
{
  "type": "expense",
  "amount": 50000,
  "category": "rent",
  "allocation": {
    "method": "by-revenue",
    "splits": [
      {"projectId": "PRJ-001", "percent": 60},
      {"projectId": "PRJ-002", "percent": 40}
    ]
  }
}
```

Методы распределения:
- `by-revenue` — пропорционально обороту проекта за период
- `by-volume` — по объёму складирования (для аренды склада)
- `by-time` — учёт времени сотрудника (для зарплат)
- `manual` — ручное распределение для разовых

Альтернатива — `projectId` без allocation: для расходов, целиком относящихся к одному проекту (бензин для рейса PRJ-001).

### 8. Миграция существующих данных

Обратно совместимая, без перерывов в работе:

1. Создаётся `trade-cat-projects` с восемью PRJ-NNN (PRJ-001 — active, остальные — paused/active по статусу выше).
2. Все существующие транзакционные записи (Trip, Sale, WhOp, Batch, Settlement) получают `projectId = "PRJ-001"` на чтении (если поле отсутствует) и на записи (если поле не пришло — default PRJ-001).
3. Постепенно в коде убираем default-логику, когда подтверждаем чистоту данных.
4. UI получает переключатель проектов сверху (по умолчанию «Все проекты»).

### 9. Последовательность работ (поэтапная)

**Шаг 1 (срочно, до начала июня 2026, ~2 недели):**
- Завести `trade-cat-projects`, создать PRJ-001..PRJ-008.
- Добавить `projectId` во все транзакционные сущности **в текущем KV-store** с default PRJ-001.
- Реализовать сущность **Purchase** (закрытие GAP-009) — для местных закупок без рейса.
- Расширить `Supplier`: добавить `currency`, `country`, `applicableProjects` (закрытие GAP-008).
- Переключатель проектов в UI (фильтр сверху).
- К июню — можно оформлять закупки PRJ-002 (местные овощи) и PRJ-003 (грузинские фермеры).

**Шаг 2 (параллельно, без жёсткого срока, ~3 недели):**
- Миграция KV → Postgres (закрывает 2 пункта из «Отложено» в roadmap).
- Текущая структура переносится 1:1, потом постепенно нормализуется.

**Шаг 3 (после стабилизации Postgres):**
- Sale смешанные — `sale.items[].projectId`, переписывание FIFO и расчёта маржи на per-line.
- Cross-project расходы с `allocation` — корректная P&L по проекту.

**Шаг 4 (Q3 2026):**
- RBAC по проектам — закупщик овощей видит PRJ-001, бухгалтер видит финансы всех.
- Расширение Евы (см. ADR-010, ADR-011, ADR-012).

Подробности Шага 1 — в [roadmap/current.md](../65-roadmap/current.md).

## Последствия

### Положительные

- **Раздельный учёт и P&L по проектам** — каждое направление считается независимо.
- **Масштабируемость** — добавление нового проекта = создание PRJ-NNN + наполнение справочников SKU/поставщиков. Без архитектурной переделки.
- **Кросс-проектная аналитика** — сводный P&L по всем проектам, сравнение, общий cashflow.
- **Общие справочники сохраняются** — клиенты, склады, сотрудники работают на нескольких проектах без дублирования.
- **Smart-склады** — один физический склад (О-001 Сухуми) хранит товары нескольких проектов с прозрачным разделением партий.
- **RBAC на горизонте** — `projectId` уже встроен, ролевая модель ляжет поверх без миграции.
- **Обратно совместимая миграция** — текущий бизнес PRJ-001 не прерывается.

### Отрицательные / компромиссы

- **Каждый запрос к данным фильтруется по `projectId`** (или `IN (...)` для нескольких) — нагрузка чуть выше, но в текущих объёмах несущественно.
- **Sale смешанные требуют переделки FIFO и расчёта маржи** — это значительный код-рефакторинг, отложен на Шаг 3.
- **Cross-project расходы — концептуально сложны** для пользователей (требуется обучение, что аренда «общая, но 60/40»).
- **PRJ-004..008 — пустые карточки** в справочнике до запуска. Это сознательный компромисс ради резервирования ID и подготовки UI.
- **KV-store плохо подходит для мультипроектности** — но решение «миграция в Postgres сейчас» отложено в Шаг 2 ради соблюдения июньского дедлайна. Краткосрочно работаем на KV с фильтрацией в памяти.
- **Аналитика и отчёты переписываются** — все существующие P&L, cashflow, отчёты по клиентам становятся project-aware. Большой блок UI-работы в Шаге 3.

## Альтернативы, которые отклонили

### Альтернатива 1: Отдельные базы данных / схемы на каждый проект
**Почему отклонили:** Сводный P&L по всем проектам потребовал бы сложной агрегации через несколько БД. Один и тот же клиент в двух проектах = две записи (или сложная синхронизация). Общие справочники (склады, сотрудники) дублировались бы. При 7+ проектах — кошмар поддержки.

### Альтернатива 2: Микросервисы / отдельные приложения по типам товара
**Почему отклонили:** Не для текущего масштаба (один владелец, малая команда). Усложнение деплоя, дублирование кода, отсутствие сводной картины.

### Альтернатива 3: Один справочник без `projectId`, фильтрация только в UI
**Почему отклонили:** Не даёт раздельный P&L. Данные смешаны на уровне БД, RBAC по проектам невозможен. Это «иллюзия мультипроектности».

### Альтернатива 4: SKU per-project (вариант Б)
**Почему отклонили:** Полное дублирование справочника при пересечении товаров (помидор турецкий, помидор местный, помидор грузинский — три записи одного товара). Усложняет управление и аналитику. Гибрид с `originLabel` даёт ту же прозрачность для клиента без дублирования.

### Альтернатива 5: Sale = один проект (вариант А по Sale)
**Почему отклонили:** Реальный сценарий — клиент покупает помидоры (PRJ-001) и бананы (PRJ-004) одним чеком. Заставлять выписывать два чека = трение для продавца и недовольство клиента.

### Альтернатива 6: Миграция в Postgres перед добавлением `projectId`
**Почему отклонили:** Дедлайн PRJ-003 на июнь 2026. Полная миграция KV → Postgres за месяц с переписыванием всех CRUD = высокий риск сломать действующий PRJ-001. Поэтапный подход (projectId на KV сначала, Postgres потом) безопаснее.
