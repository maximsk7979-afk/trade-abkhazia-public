# ADR-017: Архитектура памяти Евы — финальные решения по слоям A–D

## Контекст

Четырёхслойная модель памяти Евы (A — сырые переписки, B — память клиента, C — общие знания, D — рабочая память) была намечена в [ADR-013](ADR-013-eva-agent-architecture.md) и описана в [memory-system.md](../50-agents/eva/memory-system.md) со статусом `design`. Слой A реализован 2026-05-30 (логирование в `eva_messages`). Остальные слои оставались на уровне эскиза: не было решено, **какие поля** в B, **кто и когда** их наполняет, что в C держим «наизусть» vs тянем инструментом, как обеспечить непрерывность диалога при рестарте.

На сессии 2026-05-31 (детальное обсуждение с Максимом) эти решения приняты. Этот ADR их фиксирует; живой спецификацией остаётся [memory-system.md](../50-agents/eva/memory-system.md), обновлённый под него.

## Решение

### Слой A — сырые переписки (реализован)
Append-only журнал `eva_messages`. Пишется каждое сообщение (вход/выход) на границе Telegram. Устраивает как есть. Нужен **веб-UI чтения** для Максима (фильтр по клиенту и периоду, для дообучения Евы) — [GAP-023](../00-meta/gaps.md#gap-023).

### Слой B — память клиента (`eva_client_memory`)
Сжатое «досье» клиента, **грузится в контекст целиком при каждом диалоге** с ним. Состоит из **двух блоков**:

**Блок 1 — «О человеке»** (чтобы Ева была тёплым собеседником, «другом»):
`address_form`, `personal_facts`, `interests`, `comm_profile` (профиль общения — Ева ведёт сама по навыку-психологии, объединяет стиль + что ценит/избегать), `life_context`, `person_summary`, `important_dates` (структурно: ДР клиента и родственников, значимые даты — для проактивных поздравлений).

**Блок 2 — «О работе с клиентом»** (чтобы Ева была сильным менеджером):
`assortment`, `order_rhythm`, `payment_behavior`, `delivery_prefs`, `price_sensitivity`, `quality_expectations`, `special_terms`, `client_value`, `business_summary`.

Правила данных:
- **B не дублирует карточку клиента** (`trade-cat-clients`). Статику (сегмент, уровень цены, тип продажи, проекты, контакт) Ева читает из карточки.
- **Долг — живьём** из расчётов (меняется ежедневно); в B только `payment_behavior` словами.
- **Ассортимент — выжимкой** в B (формулируется по-человечески, обновляется ночным проходом).
- Поля **доучиваются и донастраиваются в процессе работы** (набор не заморожен).

**Кто наполняет B:** Ева сама, **ночным cron-проходом** (не после каждого диалога — дорого и избыточно): читает новые сообщения из A + транзакции системы → извлекает факты, обновляет резюме. Человек может править B (CRM-модуль). Холодный старт: у нового клиента B почти пуст, растёт по мере общения и сделок.

### Слой C — общие знания (системный промпт, кэш)
**Фиксированный и человеко-курируемый. Ева сама C НЕ переписывает** — только предлагает в `eva_learning_queue`, человек подтверждает ([ADR-012](ADR-012-eva-self-learning-plan.md)). Причина: C — «правда компании» для всех клиентов; авто-правка из случайных разговоров = дрейф и ошибки.

Состав (модулями): идентичность + характер ([vision.md](../50-agents/eva/vision.md)), бизнес-правила, правила прайса, **справочник товаров (в промпт наизусть** — ~33 SKU стабильны, названия/синонимы/категории для распознавания «помидоры» → Т-XXX), **навык «психология общения»**, **навык «продажи»**, объём помощника ([ADR-018](ADR-018-eva-universal-assistant.md)), жёсткие принципы. Навыки-плейбуки: **начать легко, углублять итеративно**.

**Цифры — никогда в C.** Цены, остатки, баланс, долг, даты рейсов — **всегда живым инструментом** (иначе устареют → враньё, нарушение принципа «не выдумывать цифры»).

### Слой D — рабочая память (текущий диалог)
При пустой RAM-сессии (рестарт, давняя пауза) — **читать хвост слоя A** (~20–30 последних сообщений этого чата) для непрерывности нити. Полное состояние сценария в Postgres (`eva_sessions`) — **отложено**: рестарт посреди сценария редок, при необходимости — `/reset`. Память о клиенте при пустой RAM обеспечивает слой B (грузится целиком), поэтому D отвечает только за непрерывность конкретного разговора.

### Приватность памяти («здравый фильтр» для B)
В B попадает только то, что **(а)** помогает работе или тёплому общению **И (б)** клиент был бы **рад**, что Ева это помнит. Тест: «друг помнит твой ДР — приятно; друг ведёт базу твоих болячек — жутковато». **Не кристаллизуем** в B: здоровье, семейные проблемы, политику, религию, личные финансы вне наших сделок, интимное. Чувствительное Ева слышит и по-доброму реагирует **в моменте** (живёт в A-архиве), но в постоянный профиль не выносит. На будущее: доступ к A/B по роли (RBAC), удаление памяти по запросу клиента, инструкция-фильтр для ночного прохода ([GAP-030](../00-meta/gaps.md#gap-030)).

## Последствия

### Положительные
- B даёт ключевое ощущение «Ева меня помнит» дёшево (грузится сжатая выжимка, а не весь архив).
- Разделение «B авто / C курируется» защищает общие знания от дрейфа.
- Цифры всегда актуальны (живые инструменты) — нет риска устаревших цен в памяти.
- Слой D через чтение хвоста A не требует сложного переноса сессий в Postgres сейчас.

### Отрицательные / компромиссы
- Ночной проход = задержка до суток в обновлении B (приемлемо; ассортимент/ритм не меняются ежечасно).
- Рестарт посреди сценария теряет slot-filling (нужен `/reset`) — пока терпимо.
- Качество B зависит от качества извлечения LLM в ночном проходе — потребует отладки промпта прохода.

## Альтернативы, которые отклонили

### Хранить сумму долга в B
**Почему отклонили**: устаревает за день; долг считается живьём из расчётов.

### Обновлять B после каждого диалога
**Почему отклонили**: лишний LLM-проход на каждый разговор, дорого; ночной батч достаточен.

### Переносить `eva_sessions` в Postgres сразу
**Почему отклонили**: усложняет (чтение/запись состояния на каждое сообщение) при редких рестартах; чтение хвоста A решает непрерывность дешевле.

### Тянуть справочник товаров инструментом
**Почему отклонили**: ~33 SKU стабильны; в промпте — мгновенное распознавание без лишнего вызова. Цены при этом всё равно живые.

### Позволить Еве самой наполнять C
**Почему отклонили**: C — общая «правда компании»; авто-правка из разговоров ведёт к дрейфу. Только предложения + модерация человеком ([ADR-012](ADR-012-eva-self-learning-plan.md)).
