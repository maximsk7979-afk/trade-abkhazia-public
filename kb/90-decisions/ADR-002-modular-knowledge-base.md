# ADR-002: Модульная база знаний

## Контекст

До этого решения весь контекст проекта хранился в одном файле `CONTEXT.md` (~25 КБ, 547 строк). Файл смешивал:
- бизнес-описание
- инфраструктуру
- пароли и ключи API
- форматы данных
- бизнес-правила
- алгоритмы бота
- словарь грузинских названий
- статусы модулей и задач

Опыт работы с Архитектором за 20+ чатов показал: при передаче контекста через монолитный файл-сводку **теряется часть информации** — Архитектор "забывает" то, что обсуждалось 10 чатов назад. Каждый новый чат — частичная регрессия.

## Решение

Принимаем **модульную базу знаний** как способ организации документации.

### Принципы

1. **Дерево из множества небольших файлов** (целевая длина 200-400 строк), а не один монолит.
2. **Один файл = одна тема** (например, `liya-partner.md`, `pricing.md`).
3. **16 нумерованных слоёв** с промежутками (00, 10, 15, 20, 25, 30, 35, 40, 50, 65, 70, 75, 80, 90, 95, 99) — для расширяемости.
4. **Корневой `INDEX.md`** — карта/оглавление.
5. **`DECISIONS/` (ADR)** — журнал всех значимых решений.
6. **Принцип "один факт — одно место"** — везде ссылки, не дубликаты.
7. **Front matter** в каждом файле с метаданными о связях.
8. **Разделение логической и физической модели данных**: `20-domain/data-model/` (что такое сущность) vs `40-system/data-formats/` (как хранится в JSON).
9. **AS-IS / TO-BE** для ролей — фото текущего состояния и проектируемое целевое.
10. **Принцип Single Source of Truth для оперативных данных**: они в БД, не в `kb/` (см. ADR-004).

## Последствия

### Положительные
- Архитектор и CC грузят в контекст только релевантные файлы — меньше шума, точнее работа
- Расширение бесплатное (новый бизнес — новая папка `domains/<name>/`; новый агент — `50-agents/<name>/`)
- ADR не теряются — лекарство от "это уже обсуждали"
- Граф связей через front matter позволяет CC автоматически отслеживать консистентность

### Отрицательные / компромиссы
- Поначалу больше файлов и папок, чем один CONTEXT.md → ощущение сложности
- Требует дисциплины: каждый файл должен иметь шапку и ссылки. Это берёт на себя CC через [контракт](../00-meta/maintenance.md)
- Требует первоначального проектирования (≈2 длинные сессии — 27 и 28 апреля)

## Альтернативы, которые отклонили

### Оставить монолитный CONTEXT.md
**Почему отклонили**: проблема "потери контекста через 10 чатов" не решается. С ростом проекта станет хуже.

### Один файл на каждый аспект, без слоёв
**Почему отклонили**: без слоёв через 50 файлов теряется навигация. Слои дают предсказуемость структуры.

### Структура по типам контента (Diátaxis: tutorials/how-to/reference/explanation)
**Почему отклонили**: это для публичной документации продукта. У нас внутренний бизнес-проект — нужна структура по бизнес-доменам.

### Структура только по компонентам системы (frontend/backend/database)
**Почему отклонили**: половина знаний — про бизнес, не про код (учёт с Лиёй, словарь грузинских накладных). В чисто технической структуре они теряются.
