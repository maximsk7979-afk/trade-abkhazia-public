# ADR-023: Оркестратор закупки банана «из поля»

## Контекст

Фаза 1 Часть 2 (боевой запуск банана) требует автоматизировать **закупку «из поля» через
Telegram**: Ева перестаёт быть только реактивной и становится **проактивным оркестратором** —
по расписанию (груз. время, UTC+4) ведёт переписки с ГД, поставщиком, закупщиком и владельцем,
заводит рейс PRJ-004, контролирует лимит и дедлайны, эскалирует срывы. Полное видение — 13
шагов жизненного цикла, дословно в
[`banana-procurement-field-DRAFT.md`](../30-roles/to-be/buyer/processes/banana-procurement-field-DRAFT.md).

**Сверка с кодом (2026-06-10)** показала, что часть «нового» из видения уже есть:

- **`orderCapacity`** — лимит ящиков рейса уже реализован и enforced (`trade-api/order-service.js`:
  `tripRemaining`/`isOpen` фильтруют по остатку, витрина отдаёт `remaining`, частичный приём
  работает). Нужен лишь инструмент Евы **задать/изменить** лимит.
- **`orderCutoffAt`** — отсечка хранится **per-trip**; банановая отсечка 13:00 D4 ставится при
  заведении рейса как значение поля. Глобально `cutoffForDate` (МСК) для банана менять не нужно.
- **Исходящие сообщения** — транспорт готов (`trade-api/notify.js` `tgSend` тем же токеном).
- **Планировщик** — прецедент `eva/src/memory-pass.js` (standalone-скрипт по системному cron,
  `require.main`-гард). Тот же паттерн для тика закупки.
- **Роль `supplier`** — реализована ([ADR-022](ADR-022-role-model-rbac.md)); осталась конфигурация `tgChatId`.

## Решение

### 1. Центральная сущность — «Цикл закупки» (state machine в KV)

Один **цикл на день доставки D4** (= инициирование + 4). Хранение — **KV
`trade-banana-cycles`** (а не Postgres Евы): консистентно с архитектурой KV-first, видно в
trade-app, оба процесса Евы ходят через `storage-api`. Ключ — дата D4 (идемпотентно).

Форма записи и полный контракт переходов — в коде
[`eva/src/procurement/cycle-machine.js`](../../code/eva/src/procurement/cycle-machine.js)
(чистый модуль, без I/O) и тестах `eva/test/cycle-machine.test.js`. Состояния:
`INIT → ORDERING → TRIP_OPEN ⇄ LIMIT_REACHED → DRIVER_PENDING → INVOICE_PENDING →
PROEZD_PENDING → LOADING → PAID → DONE` (+ `CANCELLED`).

### 2. Два привода одного автомата

- **Проактивный** — `eva/src/procurement/procurement-tick.js` (системный cron, ~5 мин,
  паттерн `memory-pass.js`). Грузинское время = фикс. **UTC+4** (в Грузии нет DST). Делает:
  (а) kickoff цикла на D4; (б) по состоянию каждого активного цикла проверяет временные
  гарды (15:00/16:00 D0; 14:00/16:00 D3; 17:30/18:00 D3) и исполняет cron-переходы.
- **Реактивный** — обычный polling Евы. На входящем `resolveIdentity` ([ADR-022](ADR-022-role-model-rbac.md))
  даёт роли; если роль ∈ {`gen_director`, `supplier`, `buyer`} **и** есть цикл с `pending` на
  этого актора → в систем-промпт инжектится блок цикла + включается инструмент
  **`advance_cycle`**. Ева трактует ответ и двигает автомат.

Связь приводов — через флаг `pending` ("gd"|"supplier"|"buyer"|null) и `flags.*` (идемпотентность
эскалаций/напоминаний) в записи цикла.

### 3. Чистое ядро + семантические эффекты

`transition(cycle, event, payload, nowGe) → { cycle, effects, error }` — **чистая функция**,
не делает I/O. Эффекты семантичны (`{type:"message"|"createTrip"|"updateCapacity"|"escalate"}`)
и исполняются вызывающим (tick / `advance_cycle`). Это даёт полную тестируемость автомата
(46 unit-проверок по таблице переходов) без моков Telegram/KV.

### 4. Новые инструменты Евы

- `advance_cycle({cycleId, event, payload})` — реактивный драйвер.
- `create_banana_trip({d4, capacity, supplierId})` — рейс PRJ-004: `arrDate=d4`,
  `orderCapacity=capacity`, `orderCutoffAt = d4T13:00:00+04:00`, статус открыт (шаг 3).
- `set_trip_capacity({tripId, capacity})` — изменить лимит (шаг 6).

### 5. Границы (в этот проход — контракт, не реализация)

Полевые модули мини-аппа закупщика — **«Погрузка» (шаг 10), «Оплаты» (шаг 11), «Завершение
рейса» (шаг 12)** — и **накладная-PDF (перевод + сверка 4 полей, шаг 8)** заведены в автомате
как состояния-заглушки (`LOADING/PAID/DONE`, `invoiceState`). Их детальная проработка —
отдельными под-этапами ([ADR-010](ADR-010-invoice-entity.md)/[ADR-011](ADR-011-eva-supplier-segmentation.md)
для накладной).

## Роли и доступ (Обязательство 7 / ADR-022)

| Шаг | Инициирует/решает | Исполняет | Поверхность |
|---|---|---|---|
| 1 Объём+поставщик | ГД (`gen_director`), эск. владелец (`owner`) | Ева | Telegram (Ева→ГД) |
| 2 Заказ поставщику | Ева | поставщик (`supplier`, изолир.) | Telegram (Ева↔поставщик) |
| 3 Завести рейс | Ева | система | KV `trade-trips-v8` |
| 4 Приём заказов | клиент (`client`) | система | мини-апп (лимит рейса) |
| 5–6 Увеличение лимита | ГД | Ева | Telegram |
| 7 Назначение водителя | ГД, эск. владелец | Ева | Telegram |
| 8 Накладная | Ева | поставщик | Telegram (PDF) |
| 9 Согласование проезда | закупщик (`buyer`) | Ева (контроль дедлайна) | Telegram |
| 10–12 Погрузка/оплата/завершение | закупщик | система | мини-апп закупщика [заглушка] |

Водитель — **не роль**, контрагент `transport` (КА-007/008/009); фото ВУ/техпаспорта Ева берёт
из его карточки (шаг 8).

## Последствия

- **+** Автомат тестируется изолированно; добавление шага = строка в таблице + тест.
- **+** Состояние видно в trade-app (KV), переживает рестарт Евы.
- **+** Проактив и реактив разнесены, но работают над одной записью — нет рассинхрона.
- **−** Появляется системный cron-процесс (как `memory-pass`) — нужен мониторинг живости тика.
- **−** Реактивная сторона зависит от качества интерпретации ответов LLM → строгий гард
  `pending` + валидация payload в `advance_cycle` (fail-closed: не угадал — переспросить).
