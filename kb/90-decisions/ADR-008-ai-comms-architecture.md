# ADR-008: Архитектура коммуникации между AI-агентами через GitHub

## Контекст

В проекте **Trade Abkhazia** работают четыре участника:
- **Максим** — владелец, координатор, источник бизнес-знаний
- **CC** (Claude Code) — реализатор, единственный с git-доступом
- **Архитектор** (Claude.ai в браузере) — проектирует архитектуру и ТЗ
- **Чат** (ChatGPT) — помощник Максима в обсуждении (без прямого общения с CC)

Возникли две связанные проблемы:

1. **Потеря контекста между чатами Архитектора**. После 20+ чатов "сводки" Архитектора при передаче в новый чат теряли детали. Архитектор "забывал" решения 10 чатов назад.
2. **Защита от рассинхрона записей**. Если Архитектор и CC будут независимо править `kb/`, неизбежны конфликты, потери и несогласованные изменения.

Нужна архитектура, которая:
- Даёт Архитектору и Чату **актуальное** состояние без копипасты больших сводок
- Сохраняет принцип **single writer** (только CC пишет в `kb/`)
- Сохраняет **полную историю** коммуникации между AI-агентами
- Не требует прямого git-доступа от Архитектора и Чата (технически невозможно — они в браузере)

## Решение

Развёрнута трёхрепозиторная архитектура с локальной папкой-буфером.

### Три GitHub-репозитория

| Репозиторий | Видимость | Назначение | Кто пишет |
|---|---|---|---|
| `trade-abkhazia` | приватный | основной: `kb/` + код | только CC |
| `trade-abkhazia-public` | публичный | read-only зеркало `kb/` для Архитектора и Чата | только CC (синхронизация) |
| `trade-abkhazia-comms` | публичный | канал коммуникации (ТЗ от Архитектора, ответы CC) | только CC |

### Локальная папка-буфер

`~/Desktop/trade-inbox/` на Маке Максима — плоская папка, в которую Максим складывает файлы, полученные от Архитектора и Чата.

CC по команде "Проверь рабочую папку" читает все файлы, переносит в `comms/inbox/`, делает работу, отвечает в `comms/responses/`, обновляет `comms/INDEX.md`.

### Правила именования файлов

```
YYYY-MM-DD-HHMM_<источник>_<тип>_<краткое-описание>.md
```

Источник: `architect` / `chat` / `cc`.
Тип: `task` / `decision` / `question` / `note` / `update` / `roles` / `process` / `response`.

Дата-время до минут гарантирует уникальность имён.

### Поток работы

```
1. Ты ←→ Чат / Архитектор обсуждают задачу
2. Архитектор формирует ТЗ-файл по шаблону
3. Максим сохраняет файл в ~/Desktop/trade-inbox/
4. Команда CC: "Проверь рабочую папку"
5. CC:
   а) Копирует файл в comms/inbox/, удаляет из локальной папки
   б) Сверяет ТЗ с актуальным kb/ и кодом
   в) Делает работу (правки kb/ + код, если нужно)
   г) Пишет ответ в comms/responses/
   д) Обновляет comms/INDEX.md (карта активных задач)
   е) Делает коммиты и пуши в приватный + comms
   ж) Синхронизирует публичный зеркальный kb/
6. Архитектор в новом чате читает comms/INDEX.md, comms/inbox/,
   comms/responses/ и kb/INDEX.md через web fetch
```

### Архивирование завершённого

`comms/archive/inbox/` и `comms/archive/responses/` — для закрытых ТЗ. Перенос **только с явного согласия Максима** (защита от потери контекста при длительном отсутствии).

### Onboarding

`kb/00-meta/architect-onboarding.md` — текст, который Максим копирует в начале **каждого** нового чата с Архитектором. Содержит роль, обязательный порядок чтения файлов, правила, формат ТЗ, поведение при старте.

`kb/00-meta/chat-onboarding.md` — для Чата, отложен до уточнения роли (Чат — внутренний помощник между Максимом и Архитектором, с CC напрямую не общается).

### Шаблон ТЗ

`kb/00-meta/templates/architect-task.md` — полусвободный формат: секции `Контекст`, `Цель`, `Релевантные файлы`, `Требования`, `Что НЕ входит в задачу`, `Открытые вопросы`, `Приоритет`. С полным примером.

## Последствия

### Положительные

- Архитектор и Чат всегда видят **актуальное состояние** через публичные репо. Не нужны "сводки" с потерями.
- Полная история коммуникации сохранена в `comms/` (никакого удаления файлов).
- Single source of truth — CC единственный writer.
- При новом чате с Архитектором — **одна команда** "прочитай onboarding и ссылки", дальше он сам в контексте.
- Архивирование под контролем Максима — нет тихой потери задач.

### Отрицательные / компромиссы

- Тройной коммит (приватный + публичный + comms) — без автоматизации есть риск забыть синхронизацию. **Митигация**: GitHub Action для автосинхронизации публичного (после настройки PAT).
- Архитектор и Чат **не могут писать** в comms напрямую — всё через Максима как промежуточное звено. **Это компромисс**, не решаемый технически (они в браузере без git).
- Публичные репо доступны всем в интернете. **Митигация**: правило "ничего чувствительного в `kb/`" (зафиксировано в [conventions.md](../00-meta/conventions.md)). Секреты — в локальном `~/secrets-trade/credentials.md`.

## Альтернативы, которые отклонили

### Дать Архитектору и Чату прямой git-доступ
**Почему отклонили**: технически невозможно (они в браузере без git-клиента). Кроме того — нарушает принцип single writer.

### Использовать только приватный репо, копировать содержимое в чат
**Почему отклонили**: возвращает нас к проблеме "копипаста сводок" с потерей контекста. Не масштабируется.

### Чат как полноценный участник с прямым контактом с CC
**Почему отклонили**: Максим уточнил, что роль Чата — помощник в обсуждении между ним и Архитектором, не самостоятельный канал к CC.

### Хранить comms внутри приватного репо
**Почему отклонили**: тогда Архитектор не может читать через web fetch (требуется авторизация). Публичный comms решает это.
