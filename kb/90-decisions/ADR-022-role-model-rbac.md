# ADR-022: Ролевая модель и RBAC

## Контекст

При проектировании закупки банана «из поля» (Фаза 1, оркестрация Евы) выяснилось, что процесс
затрагивает множество акторов с разными правами: владелец, генеральный директор, закупщик,
поставщик, водитель, клиент. При этом **текущий резолв ролей и в Еве, и в мини-аппе
схлопывает всех в три грубых класса** `owner / manager / client`: любой сотрудник-не-owner
становится `manager` и получает **все** staff-инструменты (`code/eva/src/message-log.js`
`resolveIdentity`; `code/trade-api/mini-auth.js` `resolveIdentity`). Гранулярные роли из
`trade-cat-staff[].roles` (`gen_director`, `buyer`, `warehouse`, …) теряются на входе. Гейтинг
инструментов Евы тоже грубый — `staff | client | any`. Раздел `35-security` — заглушка, матрицы
прав нет.

Максим сформулировал: **роли — это фундамент; каждый бизнес-процесс в системе, Еве и
мини-аппе обязан иметь жёсткую привязку к ролям; это отдельный важный слой всей системы учёта.**

## Решение

### 1. Канонический словарь ролей

Источник истины ролей сотрудников — массив `roles` в `trade-cat-staff`. Внешние акторы —
вне staff. Полный каталог и назначения — в [`35-security/role-catalog.md`](../35-security/role-catalog.md).

- **Внутренние (staff, `trade-cat-staff[].roles`):** `owner`, `gen_director`, `fin_director`,
  `ops_manager`, `sales_manager`, `buyer`, `warehouse`.
- **Внешние:** `client` (в `trade-cat-clients`), **`supplier`** (новая; в `trade-cat-suppliers`,
  опознаётся по новому полю `tgChatId`; изолированный скоуп — только закупочная переписка).
- **Водитель — НЕ роль.** Сторонний наёмный перевозчик — это **контрагент** категории
  `transport` (`trade-cat-contragents`, КА-007/008/009). С системой не взаимодействует; Ева
  лишь читает из его карточки фото (ВУ, техпаспорт). Если водитель совмещает закупку — ему
  отдельно назначают роль `buyer`.

Один человек может иметь **несколько ролей**; одну роль — несколько человек. Роли назначаются
через систему (справочник сотрудников).

### 2. Механика RBAC

1. **Резолв возвращает полный набор ролей**, а не один класс:
   `{ roles: [...], staffId, clientId }` (внешние — `roles:["client"]` / `roles:["supplier"]` /
   `[]` для неизвестного). Зеркально в Еве (`message-log.resolveIdentity`) и мини-аппе
   (`mini-auth.resolveIdentity`).
2. **Гейтинг по списку ролей.** Каждый инструмент Евы и каждый эндпоинт мини-аппа объявляет,
   каким ролям он доступен. Доступ = непустое пересечение ролей пользователя с разрешёнными.
   - Ева: `tool.access` — список ролей (плюс спец-значения `"any"`, и внешние `"client"` /
     `"supplier"`).
   - Мини-апп: эндпоинт объявляет допустимые роли; middleware/handler проверяет пересечение.
3. **Fail-closed.** Нет объявления доступа → инструмент/эндпоинт доступен только `owner`.
   Новый клиент-/поставщик-facing инструмент не заработает для внешнего актора, пока явно не
   объявит это и не отфильтрует данные по `clientId`/контексту.
4. **Изоляция внешних акторов.** `client` видит только свои данные (фильтр по `clientId`);
   `supplier` не получает **ни одного** инструмента данных — только сценарий закупочной
   переписки. Поставщик никогда не видит цены, балансы, других поставщиков, клиентов.

### 3. Жёсткая привязка процессов к ролям (расширение ADR-015)

К четырём артефактам ADR-015 (роль / бизнес-процесс / сценарий Евы / должностная инструкция)
добавляется **обязательная секция «Роли и доступ»** в описании каждого бизнес-процесса:
для каждого шага указывается **кто инициирует, кто решает, кто исполняет, кто видит результат**
и через **какую поверхность** (Ева / мини-апп / trade_app). Без этой секции процесс не считается
готовым к реализации.

### 4. Инкрементальное наполнение прав

Scope ролей наполняется **по мере описания процессов и финансов**, а не весь сразу. Матрица
[`35-security/role-permissions.md`](../35-security/role-permissions.md) ведётся как живой
документ; неопределённые ячейки помечаются `⏳ уточняется`.

**Зафиксировано на 2026-06-09:**
- `gen_director`: **не видит** закупочные цены и маржу; видит **все продажи и расходы, кроме
  закупок товаров**; решает объём/поставщика закупки, назначение водителя, увеличение лимита.
- Принципы конфиденциальности (из `35-security`): закупочные цены и маржа не показываются
  никому, кроме `owner`/`fin_director` (по мере описания финансов); `sales_manager` видит
  только своих клиентов.

## Последствия

### Положительные
- Гранулярный доступ становится возможен; процессы гейтятся корректно по ролям.
- Единый словарь ролей для системы, Евы и мини-аппа — нет рассинхрона.
- Изоляция поставщика и клиента закрывает риск утечки коммерческих данных.
- Роль-биндинг как обязательная секция процесса не даёт «забыть» права при реализации.

### Отрицательные / компромиссы
- Переписывается резолв в двух слоях (Ева + мини-апп) и формат `access` инструментов — разовая
  миграция с регрессионной проверкой существующих гейтов (клиентские инструменты, онбординг).
- Матрица прав наполняется инкрементально → какое-то время часть ячеек `⏳ уточняется`.

## Альтернативы, которые отклонили

### Альтернатива 1: оставить грубые классы `owner/manager/client`
**Почему отклонили**: невозможно различить `gen_director`/`buyer`/`warehouse`/`supplier`,
а процесс закупки требует разных прав для каждого. Прямой блокер.

### Альтернатива 2: завести роль `driver` в системе
**Почему отклонили**: водитель — сторонний наёмный перевозчик, с системой не взаимодействует.
Он уже есть как контрагент `transport`. Роль создаётся только тем, кто реально работает в
Еве/мини-аппе.
