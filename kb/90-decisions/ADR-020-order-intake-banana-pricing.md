# ADR-020: Приём заявок под рейс + банановое ценообразование + границы полномочий Евы

## Контекст

Шаг 4 ([roadmap](../65-roadmap/current.md)) — приём заявок. Перед кодингом разбирали «6 развилок» приёма заявки и проектировали первый рабочий поток на **одной позиции — бананы** («оттестируем на ней, потом добавим позиции»). Поверхность действий — мини-апп ([ADR-019](ADR-019-eva-mini-app.md)). По ходу всплыли решения по процессу заказа, по **особому ценообразованию бананов** и по **границам полномочий Евы** (финализация [ADR-013](ADR-013-eva-agent-architecture.md) п. 9).

Решения приняты в сессии 2026-06-04 (диктовка Максима, по пунктам). Этот ADR их фиксирует.

## Решение

### Часть 1. Поток приёма заявки (под рейс)

**Бизнес-модель бананов:** банан — скоропорт, торгуем **преимущественно под заказ**. Регулярные рейсы Грузия→Абхазия; клиент через мини-апп размещает **заявку под конкретный рейс**; заявки аккумулируются → рейс закупается → в день доставки клиент **получает к себе** (доставка) **или забирает с нашего склада** (самовывоз). Параллельно — небольшой буфер на складе для разовых/постоянных (вне клиентского мини-аппа на MVP).

1. **Тип заявки — ЗР** (`order-trip`, [ADR-007](ADR-007-sales-canonical-model.md)), привязка к рейсу. Самовывоз/доставка — **отдельный атрибут** заявки (не отдельный тип).
2. **Рейс заводится вручную** (пока не вышли на регулярную работу; затем — расписание-константа с автогенерацией). Может быть **несколько открытых рейсов**; клиент **выбирает по дате доставки**.
3. **Отсечка приёма — два поля на рейс:** (а) **время** приёма; (б) **вместимость машины** в ящиках. Приём открыт, пока `сейчас < время` **И** `сумма заказов < вместимость` (что наступит раньше — закрывает приём; лимит заодно не даёт «перепродать» машину).
4. **На границе вместимости:** принимаем **сколько влезает** (частичное оформление) + сообщаем остаток; **клиент видит остаток** свободных ящиков; при **уменьшении** заявки ящики **возвращаются** в общий доступный остаток.
5. **Одна заявка на клиента на рейс**, **редактируемая** (увеличить/уменьшить) **и отменяемая** до отсечки; цена **пересчитывается автоматически**. После отсечки заявка фиксируется, объём передаётся закупщику.
6. **После оформления — авто-приём** (статус «Новая»): Ева **подтверждает клиенту в чате** и **уведомляет менеджера** клиента. Дополнительно — уведомление **владельцу** (см. Часть 3).
7. **Walk-in (разовый)** — без приложения; розничную продажу оформляет **менеджер** как ПС.

### Часть 2. Банановое ценообразование (особый режим)

Принципиально: **цена банана НЕ зависит от себестоимости закупки**, она ориентируется на рыночную цену (российский банан в Абхазии). Существующая модель системы (`calcPriceFor` = себестоимость + наценка, выбор по сегменту opt/mid/ret) для бананов **не применяется**.

1. **Отдельный режим цены** у товара (`pricingMode`: `cost-markup` по умолчанию / `volume-tier` для бананов). Расчёт ветвится по режиму — трёхуровневая модель остального ассортимента **не ломается**.
2. **Цена зависит от ОБЪЁМА заказа, а не от сегмента клиента.** Сегмент opt/mid/ret для бананов не читается.
3. **Структура цены (банан FP):**
   - **Розница** — для **разового** покупателя (walk-in, через менеджера): надбавка к рознице (исходно +500 к ориентиру).
   - **Постоянный клиент — по объёмным ступеням** (диапазоны количества → цена), начиная с **1 ящика**.
   - **Доставка: +100 ₽/коробка** к цене ступени (на любое количество, даже 1 ящик).
   - **Фикс-цена клиента** (договорная, ставит **менеджер**) — **перебивает** ступени и является **«всё включено»** (доставочная +100 не добавляется).
   - **Единая сетка** для всех источников (под рейс и из наличия — когда появится).
4. **Управление прайсом — через Еву, owner-only (интерим).** Пока систему обкатываем, **Максим задаёт сетку цен напрямую** (готовые цены ступеней + розница + доставочная надбавка), хранится как **таблица цен**. **Базовая цена Краснодара пока НЕ используется** в расчёте — она войдёт **позже** как основа автоматических правил (`база + наценки`), когда правила устоятся (связано с [GAP-002](../00-meta/gaps.md), [GAP-034](../00-meta/gaps.md#gap-034)). Право управления прайсом позже делегируется менеджеру / ген. директору.
5. **Заморозка цены:** цена фиксируется в момент оформления заявки; последующее изменение прайса на эту заявку **не влияет**. При сильном движении рынка **менеджер пересматривает** цену открытой заявки вручную.
6. **Себестоимость** заводится через **накладные** и нужна только для **маржи/P&L по отгрузкам** — на цену продажи не влияет.

**Сорт на MVP — только FP** (эконом, `Т-028`/`SKU-028-01`, коробка 20 кг). DOLE (премиум) не возим — в Абхазии не востребован.

### Часть 3. Уведомления владельцу

Ева шлёт владельцу (Максиму) уведомление в Telegram при: **новом клиенте**, **заявке клиента**, **заявке менеджера**. Менеджер клиента уведомляется о заявке отдельно. Получатели конфигурируемы (`NOTIFY_CHAT_IDS`, [telegram.md](../25-integrations/telegram.md)).

### Часть 4. Границы полномочий Евы (финализация ADR-013 п. 9)

Развилки приёма заявки, разобранные в сессии, переопределяют дефолт [ADR-013](ADR-013-eva-agent-architecture.md) п. 9:

| Развилка | Решение |
|---|---|
| **1. Кто инициирует заявку** | И клиент, и менеджер — через **один ролевой мини-апп** ([ADR-019](ADR-019-eva-mini-app.md)) |
| **2. Как определяется тип** | Формой, не диалогом: самовывоз/доставка — выбор; для бананов всё под рейс = **ЗР**. Снят риск распознавания |
| **3. Полномочия на ЗР** | Заявка оформляется **автоматически** по стандартной сетке/наличию вместимости; цена замораживается; менеджер пересматривает при скачке. Отклонение/торг — эскалация |
| **4. Порог расхождения суммы** | Для бананов (тарный товар, по коробкам) **не возникает** — количество точное. Порог нужен для **весового** товара на этапе **отгрузки/сверки** (отложено, см. развилку 6) |
| **5. Холодный/новый клиент** | Не резолвится по `initData` → **доступа нет** (эскалация/онбординг). Цены/заявки незнакомцу не оформляются. Изоляция архитектурная (GAP-030) |
| **6. Отгрузка (`shipment[]`)** | Отдельный процесс **экспедитора** ([GAP-013](../00-meta/gaps.md)); сейчас делаем **только приём заявки** |

## Последствия

### Положительные
- Чёткий, точный поток заявки на бананах, готовый к расширению на другие позиции.
- Банановое ценообразование изолировано отдельным режимом — не ломает существующую модель прайса.
- Двойная отсечка (время + вместимость) защищает от перепродажи рейса уже на приёме.
- Границы полномочий зафиксированы (закрыт открытый вопрос ADR-013 п. 9).

### Отрицательные / компромиссы
- Часть решений — **интерим** (ручной рейс, ручная сетка цен через Еву, ручной пересмотр цены при скачке). Кодифицируем в правила после обкатки — явно помечено, чтобы не забыть.
- Новая бизнес-логика (банановый прайс, лимиты рейса) требует диагностики влияния на Еву/Прайс/процессы ([ADR-015](ADR-015-role-process-eva-structure.md) Обязательство 6) — проведена при сведении в базу.
- Отложены фулфилмент-ситуации: нехватка на рейсе ([GAP-031](../00-meta/gaps.md#gap-031)), возврат/брак ([GAP-032](../00-meta/gaps.md#gap-032)), лимит долга ([GAP-033](../00-meta/gaps.md#gap-033)).

## Альтернативы, которые отклонили

### Банан в общей модели «себестоимость + наценка, 3 уровня»
**Почему отклонили:** цена банана рыночная (российский ориентир), не зависит от закупки; объёмная, а не сегментная. Впихивание в 3 уровня исказило бы и бананы, и общую модель. Отдельный режим цены — чище.

### Объёмная цена линейной формулой (а не ступенями)
**Почему отклонили:** даёт неудобные дробные цены, которые магазину тяжело запомнить и заложить в свою наценку. Ступени — круглые цены, наглядная сетка, пороги мотивируют добрать заказ. (Сессия 2026-06-04.)

### Агрегация нескольких заявок клиента на рейс
**Почему отклонили:** заменено **одной редактируемой заявкой** на клиента на рейс — проще и без неоднозначности, какой объём в какой ступени.
