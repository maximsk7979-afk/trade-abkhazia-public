# ADR-027: Финансовый операционный движок (fin-ops)

## Контекст: правило выполнено для чтения, нарушено для записи

ADR-025 требует единых серверных калькуляторов. Для **чтения** это выполнено (balance-service,
buyer-service, expense-service, cash-core, pnl-service, trip-cost-core…) — цифры едины. Для
**записи** знание «какой комплект записей создаёт операция X» продублировано в **четырёх местах**:

1. браузер «Расчёты» (`saveOp` + `payCashLeg`);
2. браузер «Касса» (`saveMov`: 5 веток по типу стороны + Модель Б);
3. серверные эндпоинты мини-аппа (`/api/mini/cash/*`, `recordClientPayment`, cashMarket…);
4. ручные бэкфиллы (SQL-комплекты).

**Следствие (хроника 2026-07-02…04):** серия багов одного класса — «полузаписи» (Инар,
Лия, поставщики из «Кассы»), несимметричные откаты (премия), потерянный contra-COGS
(возврат брака), дубли от двойного клика. Каждый чинился на ОДНОЙ поверхности; операции
как сущности в системе нет. Прецедент решения уже есть: sale-direct переведён на единый
серверный writer одной транзакцией (ADR-024 C2.3) — и там класс исчез (родственный GAP-072).

## Инвентаризация write-путей (проведена 2026-07-04, двойным проходом: вручную + независимый обход)

**15 серверных эндпоинтов** пишут финансовые сущности; **4 места** собирают пару
«settlement + кассовая нога»; Ева финансы **не пишет** (только читает — проверено);
мини-апп своих записей не делает (только серверные эндпоинты). Полная карта — в
[fin-ops-registry.md](../20-domain/financial-reporting/fin-ops-registry.md), раздел «As-is».

**Живые дыры, найденные при подготовке ADR** (ещё два кандидата в «очередной баг»):
- `POST /api/mini/buyer/supplier-op` (мини-«Расчёты» закупщика) — пишет оплату/возврат
  поставщику **без кассовой ноги** (источник 10 июньских безногих оплат);
- `POST /api/v2/purchase` (браузерная местная закупка) — оплата пишется в карточку
  `purchase.supplierPayments` **без ноги** (условие `byStaffId` истинно только для мини;
  источник кейса ЗК-006);
- мёртвый код: редакторы `supplierPayments` в формах рейса/ЗК (`addSP/rmSP/uSP`) определены,
  но не вызываются (вкладки в «просмотре» с шага 2 финблока) — удалить;
- **неровное сторно-покрытие**: у `pay-supplier` (мини), cashMarket-ноги, оплаты местной
  закупки нет выделенного пути отката — только ручное удаление из браузера.

## Решение

Ввести серверный **финансовый операционный движок** — реестр бизнес-операций с шаблонами
проводок (в бухгалтерских терминах: журнал операций / posting engine).

1. **Реестр операций** (`fin-ops-registry`): каждая операция = код + параметры + ролевые
   гейты + валидации (овердрафт, валюта, привязки) + **шаблон комплекта записей по четырём
   плоскостям** (касса × баланс × P&L × склад/COGS) + **шаблон сторно**. Реестр — данные+код
   в одном модуле `fin-ops-service.js`; правило четырёх плоскостей (память
   `feedback_four_planes_matrix`) применяется к каждой операции при заведении в реестр.
2. **Два эндпоинта на всё**: `POST /api/fin/op {type, params}` — провести;
   `POST /api/fin/cancel {opId}` — сторнировать комплект целиком. Обе — одной БД-транзакцией
   (`withTx`), полузапись невозможна по построению. Каждая проводка получает `opId`
   (журнал операций `fin_ops_log`: кто/когда/что/каким комплектом — аудиторский след).
3. **Все поверхности — тонкие**: формы TradeApp, мини-апп, Ева (будущие операции), бэкфиллы
   зовут только эти два эндпоинта. Фронт не знает состава комплекта. Гейты ролей — в движке
   (fail-closed, ADR-022); уведомления — единая точка (готова к notify-core ADR-026).
4. **Fail-closed**: операция без шаблона в реестре = отказ, а не полузапись.
5. **Границы движка** (что НЕ входит): товарные каноны остаются своими — sale-direct
   (продажи/FIFO), doPurchaseSave (партии ЗК), shrinkage (усышка), приёмка/погрузка.
   fin-ops ведёт деньги и обязательства и связывается с ними по `refId` (например,
   sale-direct вызывает операцию `client_payment` вместо собственной сборки пары).
6. **Диф-батчи `/api/v2/{settlements,cash-movements}/batch` остаются** для импорта/бэкапа,
   но фронтовые ФОРМЫ на них больше не пишут; в перспективе — internal-token.

## Миграция (без большого взрыва)

- **Этап 1**: движок + операции оплат (поставщик/контрагент/партнёр/сотрудник-премия,
  расход Модели Б, инкассация) + универсальное сторно; перевод «Кассы» и «Расчётов»;
  закрытие двух живых дыр (buyer/supplier-op, /api/v2/purchase) переводом на движок.
- **Этап 2**: возвраты за брак (3 схемы: деньгами/зачётом/заменой — по решению владельца),
  клиентские оплаты (вкл. sale-direct-интеграцию), обмен ₽→₾ как событие (**закрывает
  GAP-059**), капитал.
- **Этап 3**: мини-апп и Ева на те же операции (mini-эндпоинты становятся обёртками или
  удаляются), зарплатный модуль строится НА движке; e2e в GAP-064.
- **Приёмка каждого этапа**: автотест на каждую операцию «провести → сверить 4 плоскости →
  сторнировать → сверить откат до копейки» (регрессионный набор = таблица истинности
  реестра) + ручной прогон владельца. Старые пути живут до приёмки новых.

## Последствия

- (+) класс «полузапись» и «несимметричное сторно» умирает архитектурно; новая операция =
  одна запись в реестре + автотест, а не 4 правки по поверхностям;
- (+) журнал операций — аудит и фундамент отчёта Ф-5 (сведение);
- (+) GAP-059, GAP-072 (денежная часть), зарплатный модуль получают готовый каркас;
- (−) рефакторинг живых write-путей — риск; митигация: поэтапность, параллельная жизнь
  старых путей, двойной прогон тестов, откат на бэкап деплоя;
- (−) +1 слой абстракции: для сверхпростых движений (перемещение) шаблон тривиален — цена
  приемлема ради единообразия.

## Роли и доступ (Обязательство 7)

Гейтинг переезжает в реестр: каждая операция объявляет роли-инициаторы (fail-closed).
Матрица — колонка «Роли» в fin-ops-registry. Веб-RBAC (GAP-048) станет применим к операциям
автоматически (одна точка входа).
