# ADR-004: Source of Truth — БД vs kb/

## Контекст

При проектировании структуры `kb/` возникла потенциальная коллизия: где живут данные о сущностях системы (сотрудники, клиенты, контрагенты, продажи, рейсы, и т.д.)?

Если описывать каждого сотрудника / клиента / рейс в `kb/`, мы получим **две версии правды**:
- В БД — оперативные данные, обновляются через интерфейсы
- В `kb/` — текстовое описание, обновляется отдельно

Через месяц-два эти источники неизбежно разойдутся. Это в индустрии называется **drift**.

Дополнительно: финансовые цифры (выручка, оплаты, маржа) — это динамические данные, которые меняются каждый день. Хранить их в `kb/` и обновлять вручную невозможно.

## Решение

Принимаем строгое разделение:

### Оперативные данные → только БД

Источник истины — **БД** (`app_storage`, ключи `trade-cat-*`, `trade-sales-v1`, `trade-trips-v8` и т.д.). Управление через интерфейсы фронтенда. `kb/` **не дублирует**.

| Тип данных | Источник истины |
|---|---|
| Сотрудники (имя, ID, роли, контакты, офис) | БД, `trade-cat-staff` |
| Клиенты | БД, `trade-cat-clients` |
| Контрагенты | БД, `trade-cat-contragents` |
| Поставщики | БД, `trade-cat-suppliers` |
| Товары, SKU | БД, `trade-cat-products`, `trade-cat-skus` |
| Офисы | БД, `trade-cat-offices` |
| Продажи, рейсы, доставки, партии | БД, соответствующие ключи |
| Взаиморасчёты | БД, `trade-settlements-v2` |
| Реальные финансовые цифры (выручка, маржа, P&L) | БД (вычисляется) |

### Качественные характеристики → kb/

В `kb/` живут **только** те знания, которые в БД не помещаются:
- Описания **ролей** как абстракций (`30-roles/`)
- **Заметки о людях** — на чём специализируются, особенности (`15-team/`)
- **Бизнес-правила и формулы** (`20-domain/`)
- **Формы отчётов** (`20-domain/financial-reporting/`)
- **Описание системы и кода** (`40-system/`, `50-agents/`)
- **Решения и журналы** (`90-decisions/`, `75-incidents/`)

### Связь через front matter

В файлах `kb/`, относящихся к конкретной сущности, добавляется блок `data_source` в front matter:

```yaml
data_source:
  type: database
  storage_key: trade-cat-staff
  staff_id: С-002
```

Это указывает: *"Полные оперативные данные — там. Здесь — только заметки."*

## Последствия

### Положительные
- Невозможен drift между БД и `kb/` — нет дублирования
- Максим продолжает работать в "Справочнике сотрудников" как раньше, не через CC
- Финансовые цифры остаются защищёнными (в БД, через RBAC, не в репо)
- Реализуется требование Максима *"система безопасности по доступу к финансовым данным"* — финансовые цифры не в `kb/` означает, что доступ к репо ≠ доступ к деньгам

### Отрицательные / компромиссы
- При работе с конкретным человеком/клиентом нужно открывать **два места** (БД через UI + `kb/15-team/<имя>.md` для контекста). Решается через `data_source` в front matter.
- Запросы вида "покажи мне всех клиентов с балансом > X" — нельзя сделать через `kb/`, нужно через БД и интерфейсы. Это правильно.

## Применение к Лие

Лия — пограничный случай:
- Как **клиент К-006** — в БД (`trade-cat-clients`)
- Как **партнёр** — в БД (строкой в `trip.partners[]` каждого рейса)
- В `kb/` про неё — только **контекст двойной роли** ([15-team/liya.md](../15-team/liya.md)) и **бизнес-правила учёта** ([20-domain/settlements/liya-partner.md](../20-domain/settlements/liya-partner.md))

## Альтернативы, которые отклонили

### Дублировать всё в kb/ для удобства
**Почему отклонили**: drift гарантирован. Вред перевесит удобство через 2 месяца.

### Хранить всё только в kb/ (без БД)
**Почему отклонили**: невозможно для оперативного учёта. БД нужна как минимум для запросов и атомарных обновлений.

### Финансы в отдельный приватный репозиторий
**Почему отклонили**: финансовые **данные** в БД (там и должны быть). В `kb/` остаются только формы и правила — они не чувствительны.
