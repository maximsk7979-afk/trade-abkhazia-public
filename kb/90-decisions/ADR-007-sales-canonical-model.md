# ADR-007: Канонические форматы продаж и заявок

## Контекст

При первом серьёзном аудите кода и БД (28 апреля 2026) обнаружены множественные расхождения между:
- описаниями в `CONTEXT.md`
- кодом `trade_app_v3.jsx`
- реальными данными в БД
- "Правилами учёта движения товаров и движения денег v2.0" (документ февраля 2026)

Источники путаницы:
1. CONTEXT.md описывал ДС как формат `delivery-sale` (опечатка — в коде `sale-delivery`)
2. CONTEXT.md помечал `order-stock` как "устаревший", но в БД 49 действующих записей именно в этом типе
3. В коде есть мёртвый storage-ключ `SK_O = "trade-orders-v4"` с функцией `saveO`, не вызываемой нигде в логике
4. В коде есть 49 hardcoded seed-записей с типом `sale-delivery`, который не создаётся активной логикой
5. "Правила v2.0" описывают **заявки и продажи как две отдельные сущности** с миграцией, но в реализации это **одна сущность** с эволюцией статусов
6. Имена статусов в коде и в "Правилах v2.0" не совпадают
7. В коде используются параллельно два формата хранения отгрузки: `saleData.lines[]/paid` и `shipment[]/shipmentTotal/shipmentPaid`

Эти расхождения создавали серьёзный риск при проектировании Евы — без чёткой канонической модели Ева воспроизводила бы те же противоречия.

## Решение

Канонизируем модель продаж и заявок следующим образом.

### 1. Одна сущность Sale, три разновидности

В системе **одна сущность** — продажа (Sale). Хранится в `trade-sales-v1`. Имеет три разновидности (поле `type`):

| `type` | Префикс ID | UI-кнопка | Бизнес-смысл |
|---|---|---|---|
| `sale-direct` | ПС-XXX | "+Со склада" | Клиент сам пришёл и забрал товар со склада |
| `order-stock` | ЗД-XXX | "+Доставка" | Клиент попросил доставить с нашего склада |
| `order-trip` | ЗР-XXX | "+Под рейс" | Клиент попросил товар, который мы привезём из Грузии |

### 2. Бизнес-язык: "заявка" → "продажа"

Одна и та же запись на разных стадиях называется по-разному в зависимости от статуса:

- **"Заявка"** — пока `status !== "Отгружено"`. Это **обещание** клиенту.
- **"Продажа"** — когда `status === "Отгружено"`. Это **факт** отгрузки.

Тип записи (`sale-direct/order-stock/order-trip`) **не меняется** со сменой статуса. ID не меняется. Меняется только статус. Это одна запись в БД, которая семантически "превращается" из заявки в продажу.

### 3. Никаких отдельных "Заявок" как отдельной сущности

`trade-orders-v4` (storage-ключ `SK_O`), `setOrders`, `saveO`, `orders` props — **мёртвая ветка** ранней архитектуры. Удаляется из кода и БД. Заявок **как отдельной сущности нет**.

### 4. Жизненные циклы (имена остаются как в коде)

#### ПС (sale-direct)
- Создаётся **сразу** со статусом `"Отгружено"` (минуя "Новая")
- Возможные статусы: `Новая → Отгружено → Отменена`
- Это разовая операция: клиент пришёл, забрал, заплатил

#### ЗД (order-stock)
- Жизненный цикл: `Новая → В доставке → Отгружено / Отменена`
- Привязывается к доставке Д-XXX (через `deliveryId`)
- При создании доставки → статус "В доставке" (автоматически)
- При завершении доставки → статус "Отгружено" (автоматически)

#### ЗР (order-trip)
- Жизненный цикл: `Новая → В закупке → В пути → На складе → В доставке → Отгружено / Отменена`
- Привязывается к рейсу Р-XXX (через `tripId`) и к доставке (через `deliveryId`)
- Автокаскад от рейса по `tripId`:
  - Рейс "В закупке" → ЗР "В закупке" (если ЗР была "Новая")
  - Рейс "В пути" → ЗР "В пути" (если ЗР была "В закупке")
  - Рейс "На складе" → ЗР "На складе" (если ЗР была "В пути")
- При создании доставки → статус "В доставке"
- При завершении доставки → статус "Отгружено"

#### Рейс
- Жизненный цикл: `Планируется → В закупке → В пути → На складе → Закрыт`
- Из "Закрыт" возможен reopen → "На складе"

#### Доставка
- Жизненный цикл: `Формируется → В пути → Завершена`

### 5. Форматы данных по типу

#### ПС (sale-direct) — одношаговая модель
```json
{
  "id": "ПС-XXX",
  "type": "sale-direct",
  "date": "YYYY-MM-DD",
  "clientId": "К-XXX",
  "tripId": "",
  "officeId": "О-XXX",
  "managerId": "С-XXX",
  "status": "Отгружено",
  "cm": "комментарий",
  "history": [...],
  "saleData": {
    "lines": [{"prodId": "Т-XXX", "skuId": "SKU-XXX-XX", "qty": "...", "qtyTar": "...", "wBrutto": "...", "price": "..."}],
    "paid": "сумма оплаты",
    "clientName": "имя для разовых клиентов"
  }
}
```

Сумма продажи **не сохраняется** — вычисляется из `saleData.lines[]` на лету.

#### ЗД (order-stock) и ЗР (order-trip) — двухшаговая модель
```json
{
  "id": "ЗД-XXX или ЗР-XXX",
  "type": "order-stock или order-trip",
  "date": "YYYY-MM-DD",
  "clientId": "К-XXX",
  "tripId": "Р-XXX | пусто (для ЗД)",
  "deliveryId": "Д-XXX | пусто",
  "officeId": "О-XXX",
  "managerId": "С-XXX",
  "status": "статус из жизненного цикла",
  "cm": "комментарий",
  "history": [...],

  "items": [
    {"prodId": "Т-XXX", "skuId": "SKU-XXX-XX", "qtyReq": "запрошено", "itemSt": "ok|partial|none"}
  ],

  "shipment": [
    {"prodId": "...", "skuId": "...", "qty": "...", "qtyTar": "...", "wBrutto": "...", "price": "...", "netto": "..."}
  ],
  "shipmentTotal": число,
  "shipmentPaid": число
}
```

**Семантика двух наборов:**
- `items[]` — **что попросил** клиент при создании заявки
- `shipment[]` — **что фактически отгрузили** клиенту в момент доставки
- `shipmentTotal` — итоговая сумма отгрузки (фиксируется при статусе "Отгружено")
- `shipmentPaid` — сколько клиент **оплатил** в момент получения

Различение "запрошено vs отгружено" — **сознательная часть модели**: при доставке возможны расхождения (привезли меньше, чем заказали; добавили из свободного объёма). Эти два набора полей **оба нужны** и описаны как канонические.

### 6. Что удаляется из кода как мёртвая ветка

- `SK_O = "trade-orders-v4"` константа
- `setOrders`, `orders` state, `saveO` callback
- Загрузка `_get(SK_O)` при старте приложения
- Передача `orders={orders}` и `saveO={saveO}` во все модули
- Использование props `orders`, `saveO` внутри модулей
- Обращение к `orders.filter(... type === "stock" ...)` (стр. 10242 — древний слой)
- 49 hardcoded seed-записей с типом `sale-delivery`
- Упоминание `(orders || []).length` в подвале UI

### 7. Что переименовывается в UI

- Кнопка `📋 Заказы` в навбаре (модуль `OrdersAnalyticsMod`) → `📊 Закупки`. Модуль `OrdersAnalyticsMod` фактически отображает аналитику закупок в рейсах, не заявок. Имя кнопки приведено в соответствие со смыслом.

### 8. Что в БД

- Удалить ключ `trade-orders-v4` (мёртвый)
- Очистить транзакционные ключи (`trade-sales-v1`, `trade-trips-v8`, `trade-deliveries-v1`, `trade-batches-v1`, `trade-whops-v1`, `trade-settlements-v2`) — данные тестовые, не нужны
- Оставить справочники
- Оставить seed-маркеры (`trade-seed-v40-full`..`trade-seed-v45-full`) — чтобы старые seed-блоки (если в коде ещё остались) не загрузились повторно
- Удалить из кода **все** seed-блоки данных продаж/рейсов/доставок (оставить только seed справочников)

## Последствия

### Положительные
- **Одна модель** для Евы — без противоречий между документацией и кодом
- **Чистая база данных** — production стартует с нуля по правильной модели
- **Никаких параллельных систем** (как было бы при разделении заявок и продаж в две сущности по правилам v2.0)
- **Документация в kb/** становится единым источником истины — Ева, разработчики, Архитектор работают с одной моделью

### Отрицательные / компромиссы
- В коде остаётся два формата для отгрузки (`saleData.lines/paid` для ПС vs `shipment/shipmentTotal/shipmentPaid` для ЗД/ЗР). Это **сознательное** решение — формат отражает разный процесс. Унификация рассматривалась и отклонена на этапе аудита.
- "Правила учёта движения товаров и движения денег v2.0" частично устарели в части модели заявок и имён статусов. В `kb/` фиксируется текущая каноническая модель, документ архивируется как исторический.

## Альтернативы, которые отклонили

### Разделить заявки и продажи в две отдельные сущности (как в "Правилах v2.0")
**Почему отклонили**: ввело бы две параллельные базы с миграцией записей между ними. Усложнение без существенной выгоды. Решение — одна запись с эволюцией статусов и двумя бизнес-именами.

### Унифицировать `shipment` и `saleData` в один формат
**Почему отклонили**: для ЗД/ЗР семантически важно различать "что заказали" (`items`) и "что отгрузили" (`shipment`). Объединение потеряло бы это различие.

### Привести имена статусов к "Правилам v2.0" (Закуплена, Доставлена, и т.д.)
**Почему отклонили**: масштаб переработки кода и БД не оправдан. Текущие имена в коде понятны и работают. Документ "Правил" обновляется под код.

### Оставить SK_O как резерв "на будущее"
**Почему отклонили**: мёртвый код не оправдан. Если в будущем заявки понадобятся как отдельная сущность — добавим тогда чисто.
