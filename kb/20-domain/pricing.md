# Правила формирования прайс-листа

Описание формул расчёта цен по трём уровням (опт / средний опт / розница), источника себестоимости и механизмов переопределения.

> ⚠️ **Две разные модели ценообразования.** Этот документ описывает **cost-markup** модель (себестоимость + наценка `opt/mid/ret`) — она применяется к **овощам** (PRJ-001/002/003). **Бананы (PRJ-004) ценятся иначе — по сетке объёма (`volume-tier`)**, см. раздел [«Бананы — модель volume-tier»](#бананы--модель-volume-tier) ниже и [ADR-020](../90-decisions/ADR-020-order-intake-banana-pricing.md). Не путать.

## Базовые формулы

### Наценки по умолчанию

| Уровень | Код (`pt`) | Наценка | Округление |
|---|---|---|---|
| Оптовая | `opt` | **+20 ₽/кг** к себестоимости | вверх до кратных 5 ₽ |
| Средний опт | `mid` | **+10 ₽/кг** к оптовой | без округления |
| Розница | `ret` | **+30 ₽/кг** к оптовой | без округления |

### Формулы

```
optRaw  = costPU + 20         (для весовых)
        = costPU + 20 × tarW  (для тарных, tarW — вес товара в одной таре)
optPrice = ceil(optRaw / 5) × 5    // округление вверх до кратных 5 ₽

midPrice = optPrice + 10           (для весовых)
         = optPrice + 10 × tarW    (для тарных)

retPrice = optPrice + 30           (для весовых)
         = optPrice + 30 × tarW    (для тарных)
```

Где:
- `costPU` — себестоимость единицы (₽/кг для весовых, ₽/единица для тарных)
- `tarW` — вес товара в одной таре: `gw − tw` (брутто одной тары минус её собственный вес)

### Дефолтные значения наценок

Хранятся в `plData.defaults`:
```json
{ "mkOpt": 20, "mkMid": 10, "mkRet": 30 }
```

Дефолты можно поменять глобально (на все позиции) через UI прайс-листа.

## Источник себестоимости

**Себестоимость берётся из последнего рейса**, в котором был этот товар.

Алгоритм (`buildCostMap`):
1. Все рейсы сортируются по убыванию даты.
2. Из них берутся рейсы со статусом ≥ "В пути" (включая "В пути", "На складе", "Закрыт"). Рейсы "Планируется" и "В закупке" не используются.
3. Для каждой позиции — берётся **из самого свежего рейса**, где она встречалась.

Если позиция не была ни в одном подходящем рейсе — её **нет в прайсе** (calcPriceFor возвращает нули).

## Себестоимость единицы (`costPU`)

Рассчитывается в `calcItemG` (для каждой позиции `trip.items[i]`):

```
purchRUB = tot × rate              // закупочная стоимость в RUB
expShare = (w / iW) × ourExpRUB    // доля наших расходов рейса по брутто-весу
totalCost = purchRUB + expShare    // полная себестоимость позиции

costPU = isTara ? totalCost / qty       // ₽ за единицу для тарных
                : totalCost / nw        // ₽ за кг (по нетто) для весовых
```

Где:
- `tot` — сумма закупки (см. [weight-calculation.md](weight-calculation.md), формула рейса)
- `rate = 1000 / trip.rate` — курс RUB за GEL
- `w` — брутто-вес позиции
- `iW` — суммарный брутто-вес всех позиций рейса (наша часть)
- `ourExpRUB` — наша доля расходов рейса (после деления с партнёром Лиёй пропорционально весу)

**Распределение расходов** — пропорционально брутто-весу. Это правило подтверждается [Liya partner settlements](settlements/liya-partner.md).

## Применение цены к клиенту

```
По умолчанию: pt = "mid"
Разовый клиент (__walk_in__): pt = "ret"
Постоянный клиент: pt из карточки (opt / mid / ret)
```

Для конкретной продажи цена выбирается так:

```
basePrice = (pt === "opt") ? optPrice
          : (pt === "mid") ? midPrice
          :                  retPrice
```

## Механизмы переопределения цен

В коде есть **4 уровня** переопределения, **не упомянутые в исходном CONTEXT.md**, но важные для практики.

Хранятся в `plData` (ключ `trade-pricelist-v1`):

### 1. Глобальные дефолты наценок
`plData.defaults = { mkOpt, mkMid, mkRet }`. Меняет наценки **для всех позиций**.

### 2. Override наценок по позиции
`plData.overrides[<prodId|skuId>] = { mkOpt, mkMid, mkRet }`. Применяет другие наценки **только к этой позиции**.

### 3. Ручная фиксация оптовой цены
`plData.overrides[<prodId|skuId>].manualOpt = 250`. **Жёстко фиксирует** оптовую цену, игнорируя расчёт `costPU + mkOpt`. Средний опт и розница пересчитываются от этой ручной оптовой.

### 4. Индивидуальная цена для клиента
`plData.clients[<clientId>][<prodId|skuId>] = 245`. Назначает **итоговую цену** конкретному клиенту, игнорируя его `pt`-уровень.

## Тарные товары — особенность

Для тарных товаров (`tp = 1`):
- Себестоимость уже **в ₽ за единицу** (не за кг)
- Наценка **умножается на вес товара в одной таре** (`tarW = gw − tw`)
- То есть итоговая наценка к опту: `mkOpt × tarW` ₽ за единицу

Пример (иллюстрация cost-markup для тары вообще): товар в таре, вес товара в таре = 19 кг (gw=20, tw=1). Опт-наценка `20 × 19 = 380 ₽` за коробку. **⚠️ К банану эта формула НЕ применяется** — банан ценится по `volume-tier` (см. ниже), хотя физически тоже тарный (ящик 20 кг).

См. также [weight-calculation.md](weight-calculation.md) — формулы расчёта `gw`, `tw`, `tarW`.

## Бананы — модель volume-tier (якорь + надбавки)

Бананы (PRJ-004, SKU Банан FP `SKU-028-01`) ценятся **не** по cost-markup, а по модели **«якорь + надбавки»** (обновлено 2026-06-10). Полное обоснование — [ADR-020 Часть 2](../90-decisions/ADR-020-order-intake-banana-pricing.md). Реализация — `code/trade-api/banana-pricing.js` (зеркало для Евы — `code/eva/src/banana-pricing.js`, держать синхронно).

**Якорь (`anchor`)** — цена продажи российского банана в Сухуми (рыночный ориентир и **пол** сетки). Меняешь якорь → вся сетка пересчитывается. **Цена ступени = `anchor + offset`**; надбавки в рублях, фиксированные, убывают с объёмом (крупный опт offset 0 = якорь).

### Сетка цен (KV `trade-banana-pricing-v1`)

```json
{
  "skuId": "SKU-028-01",
  "anchor": 2400,                 // якорь — рос. банан в Сухуми (только владелец)
  "tiers": [                       // границы кол-ва ящиков + надбавка к якорю (owner+ГД)
    { "minQty": 1,  "maxQty": 9,    "offset": 200 },
    { "minQty": 10, "maxQty": 19,   "offset": 150 },
    { "minQty": 20, "maxQty": 29,   "offset": 100 },
    { "minQty": 30, "maxQty": null, "offset": 0   }
  ],
  "retailOffset": 300,            // надбавка к якорю для разового (owner+ГД)
  "deliverySurcharge": 100,       // доплата за доставку ₽/ящик, независимая (owner+ГД)
  "updatedAt": "...", "updatedBy": "..."
}
```

Боевые цены при якоре 2400: ступени **2600 / 2550 / 2500 / 2400**, розница **2700**, доставка **+100/ящик**. `materializeGrid` разворачивает сетку в абсолютные цены для мини-аппа; `normalizeGrid` поднимает старую схему (`tiers[].price`) в новую на чтении (деплой безопасен до миграции).

### Как считается цена (`priceForBanana`)

Приоритет источников (первый сработавший):

| Условие | Цена | `source` | Доставка |
|---|---|---|---|
| У клиента задан `bananaFixedPrice` > 0 | `max(bananaFixedPrice, anchor)` — **пол = якорь** | `fixed` | **не добавляется** |
| Разовый клиент (walk-in) | `anchor + retailOffset` | `retail` | не добавляется |
| Постоянный клиент | `anchor + tier.offset + (доставка ? deliverySurcharge : 0)` | `tier` | по тумблеру заявки |

- **Ступень** выбирается по **суммарному** числу банановых ящиков в заявке (не по строке).
- Цена **замораживается** в `miniOrder` при оформлении и тянется в отгрузку (редактируема экспедитором). Смена якоря/сетки на **оформленные** заявки не влияет.
- Если фикс-цена «устарела» (< нового якоря) — считается по якорю (`floored:true`), пока не переназначена (каскад).
- **`priceLevel` (opt/mid/ret) к банану не применяется.**

### Кто чем управляет (RBAC, ADR-022)

| Параметр | Кто меняет | Инструмент Евы |
|---|---|---|
| **Якорь** | только **владелец** | `manage_banana_pricing` (action update, `anchor`) |
| Надбавки / границы ступеней / розница / доставка | владелец + **ГД** | `manage_banana_pricing` |
| **Фикс-цена клиента** (сетка/фикс) | **менеджер** + ГД | `set_client_banana_price` |

Владелец — суперюзер. Визуальной таблицы в trade_app нет — управление через Еву (валидация: якорь > 0, ступени без разрывов с 1, последняя без верха, надбавки ≥ 0 и не растут с объёмом).

### Привязка цены у клиента (сетка / фикс)

У клиента банан считается **по сетке** (`bananaFixedPrice` пусто) **или по фикс-цене** (договорная, перебивает ступени, «всё включено», без доставочной надбавки). **При заводе клиента** Ева спрашивает менеджера: прайс-лист или фикс. Фикс-цену **нельзя ставить ниже якоря**; при назначении запоминается `bananaFixedAnchor` (якорь на тот момент) — для каскада переоценки.

**Каскад при смене якоря** (обязателен): Ева через диалог с каждым менеджером переназначает фикс-цены всех его фикс-клиентов; до переназначения цены ниже якоря считаются по якорю. *Интерактивный каскад — Фаза 2.* См. [client.md](../40-system/data-formats/client.md).
