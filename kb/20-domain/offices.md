# Архитектура офисов / складов

## Принцип

**Офис = склад** — единая сущность.

В системе нет разделения "офис" и "склад" как двух разных понятий. Один объект (`О-XXX`) представляет одновременно физическое место хранения товара и точку продажи/работы.

Это сознательное решение для упрощения: команда работает в формате "у нас три точки — Сухуми, Гагра, Гудаута", и каждая точка — это и склад, и офис.

См. JSON-формат: [40-system/data-formats/office.md](../40-system/data-formats/office.md).

## Текущие офисы

| ID | Название |
|---|---|
| О-001 | Сухуми |
| О-002 | Гагра |
| О-003 | Гудаута |

## Архитектурные утверждения

### 1. Сотрудник привязан к офису
`staff.officeId` обязателен. Один сотрудник — один офис.

### 2. Клиент НЕ привязан к офису
В `client` поля `officeId` **нет**. Клиент может покупать с любого склада.

Это сознательное решение: клиент в Гагре может приехать за товаром в Сухуми, или мы можем доставить ему с любого склада — система не должна это ограничивать.

### 3. Клиент привязан к менеджеру
`client.managerId` — ссылка на сотрудника с ролью `sales_manager`. Менеджер ведёт клиента независимо от того, с какого склада идут отгрузки.

### 4. Каждая транзакция привязана к офису
Любая транзакционная сущность имеет `officeId`:
- Рейс → целевой склад прихода
- Партия FIFO → склад хранения
- Продажа → склад отгрузки
- Доставка → склад, с которого формируется
- Складская операция → конкретный склад

### 5. Менеджер на продаже = менеджер клиента
При создании продажи `sale.managerId` копируется из `client.managerId`. Это автоматически (см. код модуля продаж).

## Где используется `officeId`

| Сущность | Поле | Назначение | Default при создании |
|---|---|---|---|
| Сотрудник | `staff.officeId` | Привязка сотрудника к офису | требуется явно |
| Клиент | — | (не привязан) | — |
| Рейс | `trip.officeId` | Целевой склад прихода | `О-001` |
| Партия FIFO | `batch.officeId` | Где лежит | из `trip.officeId` |
| Продажа | `sale.officeId` | С какого склада отгружено | из формы или `О-001` |
| Складская операция | `whOp.officeId` | По какому складу | `О-001` |
| Доставка | `delivery.officeId` | С какого склада | `О-001` |

**Default `О-001`** — все старые записи без явного `officeId` интерпретируются как Сухуми. Это унаследованное поведение от Фазы 1 миграции, осталось как fallback в коде (`x.officeId || "О-001"`).

## Фильтрация по офису

В модуле "Склад" работает фильтр `oFilter` — можно посмотреть остатки/движения только по одному офису.

В модулях "Продажи", "Рейсы", "Доставки" фильтра по офису сейчас **нет на уровне UI** — все операции видны всем. С точки зрения RBAC это будущая задача (см. [35-security/](../35-security/)).
