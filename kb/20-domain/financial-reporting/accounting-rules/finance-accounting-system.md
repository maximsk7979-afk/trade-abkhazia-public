## 0. Роль Claude Code в финблоке (важно)

CC работает как **финансовый аудитор**: **сам** ставит правила учёта по стандартам и обучает владельца;
у владельца спрашивает **только бизнес-факты**, не методологию. Согласованные планы CC ведёт до конца
сам, чекпоинт — только при критическом. Владелец (Максим) — не бухгалтер, ведёт разработку сам.

## 1. Три системы = интерфейсы к одному учёту (ADR-025)

**Один домен, три интерфейса:** **TradeApp** (веб, `trade_app_v3.jsx`), **Ева** (Telegram-ассистент),
**мини-приложение** (Telegram). Это НЕ три системы, а три поверхности к одному хранилищу и одному
набору расчётов. Правило: при любой доработке — **вызывать общий расчёт, а не копировать логику**.
Комментарии «зеркалит / mirrors» — красный флаг (параллельный стор).

**Порядок реализации финблока:** сначала настраиваем и выверяем в **TradeApp**, потом переносим в
Еву/мини-апп. По усышке владелец решил: ввод **только TradeApp**, Ева/мини-апп не участвуют.

## 2. Три проекции одного журнала (ключевой принцип)

Все деньги и обязательства — это **один операционный журнал**, на который смотрят под тремя углами:

| Проекция | Вопрос | Источник |
|---|---|---|
| **P&L / Ф-3** | сколько заработали | выручка (отгрузки) − COGS (FIFO) − усышка − opex + пр.доходы − финрасходы |
| **Cash Flow / Касса (Ф-1/Ф-2)** | сколько денег и где лежат | кассовые ноги `cash_movements` по кошелькам |
| **Балансы (Ф-4)** | кто кому должен | `settlements` по стороне (клиент/поставщик/контрагент/партнёр) |

Из этого следуют два фундаментальных правила:

### 2.1. Начисление ≠ оплата (метод начисления)
- **Обязательство** (начисление) фиксируется **без кошелька**; **оплата** — отдельное событие **с кошельком**.
- **Выручка** признаётся в момент **отгрузки** (`goods_revenue`), а не оплаты. Оплата клиента —
  это **поступление денег**, не доход.
- **Расход** признаётся: для accrual-статей — в момент **начисления** (зарплата/аренда за месяц =
  расход этого месяца); для cash-статей — в момент **оплаты**.

### 2.2. Двойная запись (две ноги)
Каждая денежная операция = **балансовая нога** (`settlements` — меняет долг стороны) + **кассовая
нога** (`cash_movements` — меняет остаток кошелька). Начисление — только балансовая нога. Оплата без
стороны (кассовый расход) — только кассовая нога. Усышка — только «складская» нога (ни денег, ни стороны).

## 6. P&L / Ф-3 — движок `pnl-service.js`

**Два уровня (решение владельца):** (1) маржа проекта (торговля); (2) бизнес после общих расходов.

```
                    Выручка (A1, отгрузки goods_revenue)
УРОВЕНЬ 1        −  Себестоимость проданного (B1 COGS, FIFO, с логистикой рейса)
(маржа проекта)  +  Возврат стоимости брака (contra-COGS, supplier_refund)
                 =  ВАЛОВАЯ ПРИБЫЛЬ  (grossMarginPct)
УРОВЕНЬ 2        −  Усышка / недостача / бой (B2)
(бизнес)         −  Операционные расходы (B3 opex)
                 =  Операционная прибыль
                 +  Прочие доходы (A2)
                 −  Финансовые расходы (B4)
                 =  ЧИСТАЯ ПРИБЫЛЬ  (netMarginPct)
```

### 6.1. Выручка A1
`= turnover.sales.total` — стоимость отгрузок «Отгружено» за период (тарный `qty×price`, весовой
`netto×price`). Признание — по отгрузке, не по оплате.

### 6.2. COGS проданного B1 (FIFO cost-of-sold) — критический механизм
COGS = **себестоимость именно проданного** (не процюремент). Себестоимость партии (₽/кг для весовых,
₽/место для тарных) уже **включает логистику рейса** (`trip-cost-core`), поэтому услуги рейса (`transport`,
`loader`, `customs` и т.п.) сидят в COGS и **из opex исключены** — иначе двойной счёт.

Два пути получения себестоимости проданного (оба переиспользуют `cogsOfBatchUnits`, GAP-060 «живая»
себестоимость из партии, а не снимок):
- **sale-direct** (прямая продажа): у продажи есть `_fifoAllocs` → `Σ cogsOfBatchUnits(batch, alloc.qty)`.
- **через доставку** (order-trip/order-stock): FIFO-аллокации на **доставке** (`dlv._fifoAllocs`) →
  `avgCostByPos` даёт себестоимость на позицию → умножаем на долю проданной строки (₽/кг × нетто для
  весовых, ₽/место × места для тарных). Та же формула оценивает возвраты в `completeDelivery` (симметрия).

**Сверка корректности:** COGS-проданного < процюремент (закупки) на стоимость остатка по FIFO; выручка
в P&L = `turnover.sales.total`.

### 6.3. Правило признания (без двойного счёта — каждая статья ровно из одного потока)
- **accrual-статьи** (`party:true`: зарплата/аренда/бонус/`supplier_refund`/проценты) → признаём по
  **начислению** = `settlements` charge (`opType != payment`). Оплаты (кассовые ноги) НЕ считаем.
- **cash-статьи** (`CASH_BASIS = {comms, meals, fuel, household, other_opex, bank_fees, vat_refund,
  interest_income, other_income}`) → признаём по **оплате** = `cash_movements` по `category`.
- Статья расхода контрагента берётся из **привязки контрагент→статья** (`payCategories[0]`, «один
  контрагент — одна статья»).
- `delivery.expenses` (развоз) → B3 opex, по дате доставки, ровно один раз.
- `trip.expenses` (услуги рейса) → НЕ opex (в COGS).

### 6.4. B2 усышка
`= Σ` проводок усышки (`inventory_counts kind:"shrinkage"`) за период, **нетто** (недостача − излишки).
Подробно — раздел 9.

### 6.5. Разрезы
`/api/pnl?from=&to=&office=`. Возвращает уровни + `breakdown` (B1contra/B2/B3/A2/B4) + `byProduct`
(COGS проданного по товарам). B2 breakdown — усышка по товарам.

## 7. Касса / Cash Flow (Ф-1/Ф-2)

- **Кошельки** держателей (сотрудник/владелец), валюта RUB/GEL. Остаток = сумма кассовых ног (`cash-core`).
- **Оплата = обязательный кошелёк.** Форма оплаты (Расчёты, все вкладки): фильтр кошельков **по валюте
  платежа** + только непустые + **гард овердрафта** (в минус нельзя).
- **Ноги:** `inflow` (C→W приход), `outflow` (W→… расход), `transfer`, `exchange` (обмен ₽↔₾).
- **Автоматические кассовые ноги:**
  - Отгрузка клиенту (TradeApp `completeClient` / мини-апп развоз): приход в ₽-кошелёк (обязателен при оплате>0).
  - **cashMarket «Рынок (наличные)»** (`cashMarket:true`): оплата 100% сразу при закупке → расходная
    нога из ₾-кошелька закупщика (`recordCashOutflow`, идемпотентно по `refId`). Баланс такого поставщика всегда 0.
  - Местная закупка (мини-апп): оплата поставщику при закупке → расходная нога из кошелька проводящего.
- **Курс:** дефолт нового рейса = последний курс; `rate = 1000/ri`. **Обмен ₽→₾ как событие** с фиксацией
  курса — **GAP-059 (open)**.

## 8. Балансы (Ф-4) — вычисляемые, не записи-начисления

Все балансы — **вычисляемые из источника** (как остаток = FIFO-партии), единым калькулятором:

| Сторона | Калькулятор | Модель |
|---|---|---|
| **Клиент** | `balance-service` | отгрузки (долг +) − оплаты (settlements payment) |
| **Поставщик** | `buyer-service.supplierLedger` | закупки − оплаты |
| **Контрагент** (услуги/аренда/транспорт) | `expense-service` | начислено − оплачено; `balance>0` = мы должны |
| **Партнёр (Лия)** | Лия-ветка (НЕ трогать) | распределение расходов рейса по нетто-долям веса |

**Контрагент — детали (`expense-service`):** источники — `trip.expenses` (услуги рейса; `Оплатил=Мы`
→ долг перед контрагентом; `Оплатил=Партнёр` → закрыт Лией, `charged=paid`, баланс 0), `delivery.expenses`
(`charged=paid`, оплачены при завершении), ручные `settlements` (acctType `expense`). Курс `rate=1000/ri`.

**Лия (совместные рейсы) — НЕ ТРОГАТЬ:** распределение расходов между нами и Лией **пропорционально
нетто-весу** нашего и её товара в рейсе, и обратно. `pCs balance = paidByPartner − partnerWeightShare`.
Многократно выверено с Лией — ветку не менять. `paidBy = Мы | Партнёр`.

## 9. Усышка / недостача / бой (B2) — `shrinkage-service.js`

**Вариант А (решение владельца 2026-06-14):** усышка — **отдельная видимая строка P&L (B2)**, НЕ в COGS
(спрятанная потеря не видна; отдельная строка мотивирует контроль).

- **Ввод — ТОЛЬКО TradeApp** (владелец/офис; решение 2026-07-01): «Склад → ✂️ Усышка». Мини-апп/Ева
  усышку **не проводят**. Кладовщик ведёт места-сверку в мини-аппе — это **другое** (GAP-050).
- **Показаны ВСЕ позиции с остатком** (решение 2026-07-02):
  - **весовые** — ввод факт-**веса** (кг): усышка → уменьшаем `nettoOrig` партий (FIFO, пропорц.
    нетто-остатку), стоимость = кг × `costPerUnit` (₽/кг);
  - **тарные/штучные** — ввод факт-**мест**: бой/порча → списание `qtyRem` по FIFO (`cogsOfBatchUnits`, ₽/место).
- **Излишек** (факт больше книги) = **контра к B2** (нетто ↑, стоимость отрицательна; итог B2 =
  недостача − излишки). Излишек мест — только в отчёт (себестоимость из воздуха не создаём).
- **Проводка** `POST /api/v2/shrinkage`: под `withSaleLock` списывает партии + пишет запись
  `inventory_counts kind:"shrinkage"` с `totalCost` и `lines[]`. `GET /api/v2/shrinkage` — история.
  `pnl-service` B2 = Σ этих записей за период.
- **Конверсация:** усохшие кг → B2, `nettoOrig` партии падает → будущий COGS считает меньше нетто →
  двойного счёта нет (себест.проданного + усышка = исходная стоимость партии).

## 13. Открытые вопросы / backlog финблока

- **Усышка — авто-триггер** `requires_inventory` (7 дней) + постфактум-распределение по доставкам —
  не делали (owner-driven ввод заменяет); вернёмся при необходимости. **Норма усышки % по SKU/периоду**

- **Ева / мини-апп P&L** — подключить к тому же `/api/pnl` (интерфейсы, не дублировать движок).
- **Мультивалютность opex** — `pnl-service` суммирует как ₽; при первых ₾-начислениях opex (аренда/зп)
  нормализовать по курсу (калибруем как бизнес-факт при первой операции).
- **GAP-059** — обмен ₽→₾ как событие с фиксацией курса (день перед закупкой); бэкфилл казны с 12.06.
- **GAP-073 / ADR-026** — порядок уведомлений (после финблока; финблок переписал D-блок матрицы).

## 14. Ключевые решения владельца (сжатый указатель, детали — decisions-log)

- Роль CC = финансовый аудитор (правила ставит сам, спрашивает бизнес-факты).
- Порядок: TradeApp → потом Ева/мини-апп.
- Выручка по отгрузке; оплата клиента вне P&L; оплата поставщику вне P&L (COGS по поступлению/продаже).
- COGS = себестоимость **проданного** (FIFO); логистика рейса — в COGS, не в opex.
- `supplier_refund` (брак) = contra-COGS (минус к B1), НЕ доход A2; штраф/пеня за брак → A2.
- P&L — **два уровня** (маржа проекта / бизнес); общие расходы не размазываем по сделкам.
- Баланс контрагента — **вычисляемый**; **один контрагент — одна статья**.
- Лия: распределение расходов рейса по нетто-долям — **выверено, не трогать**.
- Усышка (вариант А, отдельная строка B2); ввод **только TradeApp**; излишек = контра; показываем **все**
  позиции (весовые по весу, тарные по местам).
- Капитал: активны вклад/изъятие, дивиденды спящие. Займы (тело) — вне P&L, проценты — A2/B4.
