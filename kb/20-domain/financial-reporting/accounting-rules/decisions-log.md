# Журнал финансовых договорённостей

> Хронологический журнал решений по правилам финансового учёта. Каждая договорённость —
> датированная запись, чтобы **не терять контекст между сессиями и не повторять**. Новые записи
> добавляются сверху. Детали правил по статьям — в [pay-categories-rulebook.md](pay-categories-rulebook.md).

## 2026-07-03 — Мини-касса ГД: расширенный блок статей (состав согласован)

- **ГД/владелец в «Расходе» мини-кассы видят сверх менеджерских 8:** Таможня (Топсон/Тэнгиз), Погранслужбы, Грузчик в Абхазии, Услуги экспедитора, Аренда склада/дома/авто, **Оплата партнёру (Лия)**. Владелец исключил: Грузчик (Грузия), Спец.статус, Услуги закупщика. «Оплата поставщику ₽» — отдельная кнопка (уже была).
- **Механика party-статей обобщена:** двойная запись (settlement долг ↓ + нога), сторона из привязок карточек (`payCategories`), **автодефолт при единственной**; чужим ролям — 403 (transport разрешён всем кассовым ролям, остальное только ГД/owner). Лия — settlement `acctType:partner` (гасит её вычисляемый долг).
- **Не включено осознанно:** зарплата/премии (нет механики начислений staff — зарплатный контур позже), капитал/займы (только TradeApp, владелец).

## 2026-07-03 — Мини-касса: оплата «Транспорт рейса (Грузия)» менеджерами

- Менеджеры иногда платят водителям за транспорт рейса из своей кассы. Статья `transport` добавлена **в конец** списка расходов мини-кассы с выбором водителя (контрагенты с привязкой `transport`: Джамна/Тэриэл/Алико — список живой из справочника).
- **Механика — НЕ Модель Б:** двойная запись (settlement `expense/payment` — долг водителя ↓ + кассовая нога) — услуга уже в COGS рейса, это гашение кредиторки. Fail-closed без выбранного водителя. Уведомление: «оплата транспорта рейса → <водитель>, сумма, остаток».

## 2026-07-03 — Статья `loader_market` «Грузчики/тачкисты» + кладовщик в мини-кассе

- Обратная связь менеджеров: на складе/рынке Сухуми платят разовым грузчикам/тачкистам. Новая статья **B3 `loader_market`**, Модель Б (затрата в момент оплаты, без стороны); общий контрагент для случаев со стороной — КА-006 (вторая привязка). Статей 39.
- **Кладовщик (`warehouse`) добавлен в мини-кассу** (гейт вкладки и API) — он тоже платит на складе. Из списка расходов мини-кассы исключены `shrinkage` (неденежная) и `bank_fees` (спящая) — решения владельца этим же днём.

## 2026-07-03 — Касса в мини-аппе и Еве: роли и операции (Обязательство 7)

- **Мини-апп «💵 Касса»** — роли `sales_manager`, `expeditor`, `gen_director`, `owner`: видят ТОЛЬКО свои кошельки (fail-closed по holderId), выписка за период (канон cash-core), операции: **инкассация** (передача кассы, та же валюта) и **расход Модели Б** (статьи `party:false`); **овердрафт из мини-аппа запрещён** (в отличие от cashMarket «в поле»).
- **ГД/owner дополнительно из мини-аппа: оплата поставщикам в ₽** (двойная запись: settlement + нога). ₾-поставщики и контрагенты — только TradeApp.
- **ГД и ops — все кассы только через Еву** (`get_cash_all`, жёсткий ролевой гейт owner/gen_director/ops_manager). **Правило «закупочная сторона скрыта от ГД» для КАСС снято** (решение владельца: «ГД — по всем вопросам движения денег»).
- **Уведомления о каждой операции мини-кассы:** исполнителю — своё (без имени); owner+ГД+ops_manager — все кассы. Формат: чей кошелёк · операция · статья/куда · сумма · остаток.
- Ева-инструменты на канонах trade-api: `get_my_cash_period` (staff, свои), `get_cash_all` (гейт), `/api/cash/wallet-statement?labels=1` (ярлыки сторон резолвит сервер — зеркало фронтового legLabel).

## 2026-07-03 — Совместные рейсы с Лией: упрощённая модель «наша доля одной строкой»

- **Паттерн (решение владельца, подтверждён для Р-005/Р-006/Р-007):** когда наш товар едет **в машине Лии** и она оплачивает перевозку сама, в расходы рейса вносится **ОДНА строка «Транспортировка» = уже НАША доля** (договорная сумма), `Оплатил=Партнёр`; блок «Партнёры» и **вес Лии НЕ заполняются**.
- **Как это работает:** вес партнёра 0 → доля распределения 100% наша → вся строка идёт в наш COGS и полностью в долг Лие. Итог: долг Лие = ровно наша доля, себестоимость точная.
- **⚠️ Анти-правило:** в такие рейсы **НЕЛЬЗЯ** вносить вес Лии задним числом — система начнёт распределять по долям второй раз, долг Лие и COGS поедут. Вес партнёра заполняется ТОЛЬКО если в строках указана полная стоимость услуги (тогда система сама делит по нетто-долям — исходная Лия-ветка).
- Контрагент строки (Тэриэл) — аналитическая пометка, балансово нейтрален (самозакрыт `Оплатил=Партнёр`).
- Текущий долг Лие по рейсам: 30 000 (Р-005) + 26 400 (Р-006) + 34 440 (Р-007) = **90 840 ₽** — подтверждён владельцем.

## 2026-07-01 — B2 Усышка: проводка реализована (ввод только TradeApp)

- **Ввод усышки — ТОЛЬКО TradeApp** (владелец/офис). Мини-апп/Ева усышку не проводят (решение владельца). Кладовщик продолжает места-сверку в мини-аппе ([GAP-050]) — это отдельное.
- **Модель:** владелец вводит фактический остаток веса по товару (SKU) → система считает недостачу и списывает по FIFO: **вес** (усышка) уменьшает `nettoOrig` партий (пропорц. нетто-остатку, стоимость = кг × ₽/кг); **места** (бой/пропажа, опц.) списывают `qtyRem` (`cogsOfBatchUnits`). Расход → строка **B2** P&L (вариант А, отдельная строка, не в COGS).
- **Излишки (факт больше книги) — КОНТРА к B2** (решение владельца): нетто ↑, стоимость отрицательна; итог B2 = недостача − излишки. Излишек мест — только в отчёт (себестоимость не создаём из воздуха).
- **Реализация:** `shrinkage-service.js` (канон) + `POST/GET /api/v2/shrinkage` + `pnl-service` B2 из записей `inventory_counts kind:"shrinkage"` + вкладка «Склад → ✂️ Усышка». [GAP-054]/[GAP-055] closed. Бандл `index-C-ymlVtg.js`.
- **Роли:** проводит `owner`/офис (TradeApp); видят усышку в P&L `owner`/`gen_director`. Кладовщик места-сверку — мини-апп.

## 2026-07-01 — Шаг 5: P&L / Ф-3 (движок `pnl-service.js`, реализовано)

- **COGS = себестоимость проданного** (FIFO cost-of-sold), НЕ процюремент. **Почему:** метод начисления — расход товара признаётся в момент продажи, не закупки; иначе прибыль искажена на стоимость остатка.
- **Два уровня (решение владельца):** (1) **маржа проекта** = выручка − COGS (с логистикой рейса); (2) **бизнес** = − усышка − opex + прочие доходы − финрасходы = чистая прибыль. Общие расходы не размазываем по сделкам.
- **Привязка контрагент→статья** (один контрагент — одна статья, `payCategories[0]`) — классификатор расхода в P&L; если у контрагента несколько статей — решаем отдельно.
- **Правило признания (методология аудитора, без двойного счёта):** accrual-статьи (`party:true`) признаём по **начислению** (settlements charge); cash-статьи (`CASH_BASIS`: связь/бензин/питание/быт/прочий opex/банк.комиссии + доходы-по-факту НДС/проценты/прочий приход) — по **оплате** (cash_movements). `trip.expenses` не opex (уже в COGS через FIFO). `supplier_refund` (`dir:in` в B1) — контра-COGS (минус к себестоимости, не доход).
- **Усышка B2** = плейсхолдер 0 сейчас; настроим после инвентаризации со взвешиванием (бизнес-факт — накопленная недостача, выведем склад).
- **Проверено на бою:** валовая маржа **24.8%** (выручка 2.43M − COGS 1.83M = 603К). Детали реализации — в [pay-categories-rulebook.md](pay-categories-rulebook.md) «Реализация — шаг 5».

## 2026-07-01 — Метод работы над финучётом

- **Очерёдность платформ:** сначала настраиваем финансовый учёт в **TradeApp (веб)**; после того как
  всё настроено и выверено — переносим в **Еву и мини-приложение** (интерфейсы к одной системе, ADR-025).
- **Единица работы — статья справочника `trade-cat-paycategories`.** Идём по каждой статье и
  определяем: **правило заполнения**, **правило внесения** (кто/где/когда, одна нога или две),
  **правило учёта** (P&L / касса / баланс). Плюс определяем **порядок статей внутри групп**.
- **Цикл:** обсудили статью(и) → зафиксировали здесь и в рулбуке → реализовали в коде → внесли данные →
  вышли на реальные балансы с контрагентами и поставщиками.
- **Отдельный раздел базы:** все правила финучёта живут в
  `kb/20-domain/financial-reporting/accounting-rules/` — чтобы владелец не повторял договорённости.

## 2026-07-01 — Роль CC в финблоке
- CC работает как **финансовый аудитор**: сам ставит правила учёта по стандартам и обучает; вопросы владельцу — только по бизнес-фактам, не по методологии.

## 2026-07-01 — A1 `client_payment` (Оплата от клиента)
- Оплата = **поступление**, не доход. **Выручка признаётся по отгрузке** (`goods_revenue`), не по оплате → `client_payment` **вне P&L** (иначе двойной счёт). **Почему:** метод начисления; Cash Flow и P&L — разные проекции.
- Проводится **двумя ногами:** долг клиента ↓ (`settlements`) + приход в **₽-кошелёк** (`cash_movements`). **Как применять:** кошелёк — в мини-аппе автоматически кошелёк проводящего сотрудника; в TradeApp — **обязательное поле «в чей кошелёк»**.
- Оплата гасит **общий долг** клиента; привязка к отгрузке (`refId`) нужна для **сторно** (отмена отгрузки сторнирует и её платёж).
- **Переплата** → отрицательный баланс (аванс). Возврат переплаты — **новая статья `client_overpay_refund`** (dir out, client, вне P&L, две ноги: гасит отрицательный баланс + выбытие из кассы; в Cash Flow — «Возврат переплат покупателей»).
- **Бэклог реализации:** поле «кошелёк-получатель» в TradeApp; сверка связки платёж↔отгрузка для сторно; завести `client_overpay_refund`; поле `ord`.

## 2026-07-01 — A2 `supplier_bonus` (Бонус поставщика)
- Учитываем как **прочий доход A2**, НЕ как уменьшение COGS. **Почему:** приходит постфактум, не привязан к отгрузкам; чистая прибыль не меняется, а COGS не надо ретро-пересчитывать.
- **Две схемы (обе реализовать):** «деньгами» → приход в ₾-кошелёк + доход A2; «зачётом» → долг поставщику ↓ + доход A2 (без кассы). Валюта ₾.

## 2026-07-01 — Возвраты переплат = вне P&L (флаг `pnl:false`)
- **`supplier_overpay_refund`** (возврат переплаты от поставщика) — новая статья, симметрична `client_overpay_refund`. **Не влияет на прибыль**, только баланс + касса: Дт Касса — Кт Расчёты с поставщиком.
- **Принцип:** возвраты переплат и движения капитала/займов — **чисто балансово-кассовые**, в P&L не идут. Ввести у статьи явный флаг `pnl` (true/false); P&L строить по `pnl:true`, не только по `group`. **Почему:** иначе P&L посчитает поступления/возвраты как доход/расход (двойной счёт, искажение прибыли).

## 2026-07-01 — A2 `vat_refund` (Возврат НДС, Грузия)
- НДС отдельным счётом **не ведём** → возврат = **прочий доход A2** (₾), `pnl:true`. **Почему:** НДС сидит в себестоимости; возврат компенсирует завышенный COGS.
- Одна нога: приход в **₾-кошелёк Максима (КС-002)**; без стороны; не привязываем к рейсам/проектам. Признаём по поступлению. **Периодичность:** ежемесячно 15–25 числа за предыдущий месяц.

## 2026-07-01 — A2 `interest_income` (Проценты по выданным займам)
- Финансовый доход A2 (`pnl:true`), сторона — заёмщик; **тело займа отдельно в C3** `loan_given` (вне P&L). Признаём по получению. **Статус:** живых займов нет — на будущее.

## 2026-07-01 — B1 `supplier_payment` (Оплата поставщику)
- **Зеркало `client_payment`:** оплата поставщику — **не расход P&L**, а гашение долга + выбытие денег (`pnl:false`, 2 ноги: долг поставщику ↓ + касса ↓). **Почему:** COGS признаётся по поступлению/продаже товара, не по оплате.
- **Факты:** валюта ₾ и ₽; **несколько кошельков** → кошелёк-источник обязателен и выбирается явно (не авто); проводится через TradeApp и мини-апп. Поставщик обязателен, `refId` для сторно.
- **Предоплата:** сейчас нет, но **заложить** — платёж сверх долга → аванс (положительный баланс поставщика), возврат через `supplier_overpay_refund`.

## 2026-07-01 — РЕАЛИЗАЦИЯ Шаг 3: канонический баланс контрагентов (GAP-075 closed)
- **Решение владельца:** баланс с контрагентом — **вычисляемый** из источника (как Покупатели/Поставщики, ADR-025), НЕ записи-начисления. Всё в одном месте, без дублей.
- **`expense-service.js`** (сервер): `contragentLedger`/`contragentBalances` — логика фронтового `getExpenseSummary` 1-в-1. `Оплатил=Мы` → долг перед контрагентом; `Оплатил=Партнёр` → закрыт Лией (Лия-ветка не тронута — по нетто-долям, верна); delivery.expenses (charged=paid); ручные settlements. `rate=1000/ri`.
- Эндпоинты `/api/contragents/summary`, `/api/contragent/:id/summary`; «Расчёты → Расходы» делегирует на сервер; дубль-формулы удалены; +6 тестов (29 всего). Деплой `index-DROmshLv.js` + `expense-service.js`. Сверено на бою (Топсон 41000, Джамна 35000, Алико 12800).
- **Оплата контрагенту** — через единую форму (шаг 2): кошелёк + расходная нога, гасит вычисляемый долг.
- **Далее:** шаг 4 (delivery.expenses в P&L один раз, GAP-076 хвост) + шаг 5 (P&L Ф-3 по pnl:true).

## 2026-07-01 — РЕАЛИЗАЦИЯ Шаг 2: обязательный кошелёк при оплате + наличный рынок
- **Модель «начисление ≠ оплата»** (решение владельца): кошелёк нужен только при ОПЛАТЕ; при начислении обязательства — не нужен. Все оплаты — через единую форму «Расчёты» (Вариант 1); карточка рейса/ЗК = только начисление.
- **Выбор кошелька при оплате:** из всех кошельков, фильтр по валюте платежа + только непустые (баланс>0) + показ остатка; **гард овердрафта** (блок оплаты в минус). Мини-апп — авто-кошелёк проводящего; TradeApp — явный выбор. Оплата Лие — тоже с кошельком.
- **Часть A:** форма оплаты усилена (фильтр+гард); редактор `supplierPayments` на карточках рейса/ЗК → просмотр.
- **Часть B (cashMarket «Рынок наличные»):** оплата 100% сразу теперь пишет расходную ногу кассы из ₾-кошелька закупщика (`recordCashOutflow`).
