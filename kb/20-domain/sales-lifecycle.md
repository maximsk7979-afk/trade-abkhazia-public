# Жизненные циклы продаж — статусы и каскады

Описание статусов всех трёх типов продаж (ПС / ЗД / ЗР), статусов рейса и доставки, а также автоматических каскадов смены статусов.

> Справочник имён: см. [00-meta/glossary.md](../00-meta/glossary.md), категория "Учётные термины".
> Канонизация модели: [ADR-007](../90-decisions/ADR-007-sales-canonical-model.md).

## 1. Жизненные циклы

### ПС (sale-direct)
Создаётся **сразу** в статусе "Отгружено". Возможные статусы:

```
(Новая) → Отгружено → (Отменена)
```

ПС — разовая операция, без многостадийности.

### ЗД (order-stock)
```
Новая → В доставке → Отгружено
                 ↘ Отменена
```

### ЗР (order-trip)
```
Новая → В закупке → В пути → На складе → В доставке → Отгружено
                                                           ↘ Отменена
```

### Рейс (trip)
```
Планируется → В закупке → В пути → На складе → Закрыт
                                       ↑__________|  (reopen)
```

### Доставка (delivery)
```
Формируется → В пути → Завершена
```

## 2. Каскад от рейса (по `tripId`)

При смене статуса рейса все ЗР-заявки, привязанные к этому рейсу, автоматически переходят. Условие: `sale.tripId === trip.id`, `sale.type === "order-trip"`, и **текущий статус ЗР должен совпадать с ожидаемым предыдущим**.

| Trip → новый статус | ЗР: какой статус → новый |
|---|---|
| "В закупке" | "Новая" → "В закупке" |
| "В пути" | "В закупке" → "В пути" |
| "На складе" | "В пути" → "На складе" |

При переходе рейса в "На складе" дополнительно создаются [FIFO-партии](inventory-fifo.md) (`batch`) по фактическим количествам приёмки.

**Реализация в коде**: `changeSt` в TripsMod (`trade_app_v3.jsx`, ~стр. 1399-1469).

## 3. Каскад от загрузки доставки (по `deliveryId`)

При переходе доставки **"Формируется" → "В пути"** (момент физической загрузки машины товаром):

- Все `sales` из `dlv.saleIds` (любого типа: `order-stock` и `order-trip`) получают статус "В доставке"
- В каждую `sale` записывается `deliveryId`
- Создаются `WhOps` типа `shipment` (физическое списание со склада)
- FIFO-партии уменьшаются по факту погрузки

**Реализация в коде**: `doLoadDelivery` (`trade_app_v3.jsx`, ~стр. 642-650).

## 4. Без каскада — отгрузка клиенту в доставке

Когда экспедитор нажимает "✅ Отгружено" в карточке **конкретного** клиента в доставке, функция `completeClient`:
- **только эта одна** `sale` переходит в "Отгружено"
- ей записываются `shipmentTotal` и `shipmentPaid`

Это **per-client операция, не общий каскад**.

**Реализация**: `completeClient` (`trade_app_v3.jsx`, ~стр. 4188).

## 5. Без каскада — завершение доставки

При переходе доставки в "Завершена" (функция `completeDelivery`) статусы продаж **не меняются** — они уже были обновлены ранее через `completeClient` для каждого клиента отдельно. У завершения доставки другие задачи:
- сохранить `returns[]` (возвраты с доставки на склад)
- сохранить `expenses[]` доставки

**Реализация**: `completeDelivery` (`trade_app_v3.jsx`, ~стр. 4249).

## 6. Свойства каскада

- **Не обратимый**: если двинуть рейс назад в "В закупке", ЗР, уже бывшие в "На складе", **сами назад не уходят**. Это намеренно — обратное движение требует ручного управления.
- **Не принудительный**: заявка в "неподходящем" статусе пропускается. Например, если ЗР была в "Отменена", смена рейса её не вернёт в активный цикл.
- **Идемпотентный по факту**: повторный вызов с тем же статусом не порождает дублей в `history` (статус уже совпадает).

## 7. Связь с физическим товаром

Переход рейса в "На складе" создаёт партии — **физический товар появился у нас**.
Переход доставки в "В пути" списывает товар со склада — **товар поехал к клиентам**.
`completeClient` фиксирует факт получения клиентом и сумму.
`completeDelivery` финализирует возвраты на склад.
