# Сущности системы — концептуальная модель

Описание сущностей **на уровне домена**, без привязки к JSON-формату.

> Технические форматы (поля, имена, JSON) — в [40-system/data-formats/](../../40-system/data-formats/).

## Перечень сущностей

| Сущность | Описание | Storage |
|---|---|---|
| **Sale** (продажа) | Факт или обещание отгрузки товара клиенту | `trade-sales-v1` |
| **Trip** (рейс) | Закупочная поездка из Грузии в Абхазию | `trade-trips-v8` |
| **Delivery** (доставка) | Развоз товара клиентам | `trade-deliveries-v1` |
| **Batch** (партия) | FIFO-партия товара на складе | `trade-batches-v1` |
| **WhOp** (складская операция) | Приход/отгрузка/списание/возврат | `trade-whops-v1` |
| **Settlement** (запись взаиморасчёта) | Ручная операция платежа/начисления | `trade-settlements-v2` |
| **Client** (клиент) | Покупатель | `trade-cat-clients` |
| **Staff** (сотрудник) | Член команды | `trade-cat-staff` |
| **Office** (офис/склад) | Точка продаж/хранения | `trade-cat-offices` |
| **Supplier** (поставщик) | Поставщик товара в Грузии | `trade-cat-suppliers` |

| **PriceList** | Прайс-лист | `trade-pricelist-v1` |

## Sale (продажа) — главная сущность

### Одна сущность, три разновидности

В системе **одна** сущность Sale с тремя **типами** (`type`):

| Тип | Префикс | UI-кнопка | Когда применяется |
|---|---|---|---|
| `sale-direct` | ПС-XXX | "+Со склада" | Клиент сам пришёл и забрал |
| `order-stock` | ЗД-XXX | "+Доставка" | Клиент попросил доставить с нашего склада |
| `order-trip` | ЗР-XXX | "+Под рейс" | Клиент попросил товар, который мы привезём из Грузии |

См. [ADR-007](../../90-decisions/ADR-007-sales-canonical-model.md) — почему именно одна сущность, а не разделено на "Заявку" и "Продажу".

### "Заявка" vs "Продажа" — это **бизнес-имя**, не отдельная сущность

Запись Sale на разных стадиях называется по-разному:

- **"Заявка"** — пока статус не "Отгружено". Это обещание клиенту.
- **"Продажа"** — после статуса "Отгружено". Это факт отгрузки.

Тип записи (`sale-direct`/`order-stock`/`order-trip`) **не меняется** со сменой статуса. ID **не меняется**. Меняется только статус. Это **одна** запись в БД.

### Пополнение склада ("заявка на склад")

В [Правилах учёта v2.0](../../99-archive/old-context-md/) был третий тип заявки — **"На склад"** (пополнение для допродаж, без клиента). В реализации это **не отдельная заявка**, а обычная позиция в `trip.items[]` без привязки к продаже клиента. См. [trips.md](../trips.md).

### Атрибуты Sale

- ID (с префиксом)
- Тип (`type`)
- Дата
- Клиент (ссылка)
- Офис, с которого отгружено
- Менеджер продаж (берётся из карточки клиента)
- Статус (из жизненного цикла, см. [sales.md](../sales.md))
- История смены статусов
- Комментарий

Дополнительно по типу:
- ПС: `saleData.lines[]` (отгруженные позиции), `saleData.paid` (оплата)
- ЗД/ЗР: `items[]` (заявка), `shipment[]` (факт отгрузки), `shipmentTotal`, `shipmentPaid`

См. JSON-формат: [40-system/data-formats/sale.md](../../40-system/data-formats/sale.md).

## Связи между сущностями

### Sale → другие
- Каждая Sale → один Client
- Каждая Sale → один Office (с какого склада)
- Каждая Sale → один Staff (менеджер продаж)
- Каждая Sale ЗР → один Trip (через `tripId`)
- Каждая Sale ЗД/ЗР → одна Delivery (через `deliveryId`)
- Sale ПС не имеет ни Trip, ни Delivery

### Trip → другие
- Каждый Trip → один Office (целевой склад)
- Trip имеет массив `partners[]` (партнёры по рейсу, например, Лия)
- Trip имеет `expenses[]` (расходы)
- Trip имеет `items[]` (закупленные позиции — наша часть, не партнёрская)
- Trip имеет `supplierPayments[]` (наши платежи поставщикам)
- Связь с Sale: через `tripId` в Sale
- Связь с Batch: при статусе "На складе" создаются `Batch` записи

### Delivery → другие
- Каждая Delivery → один Office
- Delivery → может быть один или несколько Sale (ЗД/ЗР)
- При завершении Delivery → создаются WhOp записи отгрузки

### Batch (FIFO-партия)
- Создаётся при приходе Trip на склад
- Списывается FIFO при отгрузке (Sale, Delivery)
- Имеет `qtyOrig` (изначально) и `qtyRem` (остаток)
- Хранит `costPerUnit` (себестоимость единицы)
