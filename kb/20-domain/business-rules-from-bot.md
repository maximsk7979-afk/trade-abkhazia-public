# Бизнес-правила из старого бота (для использования при проектировании Евы)

Сводка алгоритмов, которые работали в старом `bot_expeditor_v10.js` и являются **бизнес-правилами**, не специфичными для конкретной реализации бота. Они должны быть учтены при проектировании Евы.

> **Источник истины**: оригинал — раздел 11 архивного [`CONTEXT-2026-04-26.md`](../99-archive/old-context-md/CONTEXT-2026-04-26.md). Старый бот отключён 2026-04-27 (см. [ADR-005](../90-decisions/ADR-005-eva-replaces-bot.md)). Алгоритмы извлекаются как референс, не как обязательная реализация — Ева может использовать улучшенные подходы.

## 1. Автоопределение типа продажи (ПС / ЗД)

При создании новой записи продажи с клиентом нужно определить тип:
- **ПС** (sale-direct) — клиент сам забирает со склада
- **ЗД** (order-stock) — клиент ждёт доставки

### Алгоритм

1. Если в карточке клиента есть `saleType` → применить автоматически
2. Если поле пустое, проверить историю продаж клиента: ≥ 70% одного типа → применить + сохранить выбор в карточку
3. Если история смешанная (< 70% любого типа) → спросить пользователя кнопками → сохранить выбор в карточку
4. Если клиент — разовый (`__walk_in__` или специально помеченный) → всегда **ПС** автоматически

### Семантика

- `saleType: "ps"` → ПС (`sale-direct`)
- `saleType: "ds"` → ЗД (`order-stock`)

Поле `saleType` — в `trade-cat-clients`, см. [40-system/data-formats/client.md](../40-system/data-formats/client.md).

## 2. Возврат за брак — распознавание из накладной

Бот распознавал в текстовых строках накладной слова **"Возврат"** или **"Брак"** и автоматически создавал запись в `trade-settlements-v2`:

```
acctType: "client"
opType: "defect_refund"
amount: <положительное число строкой>
desc: "<скопировать строку накладной>"
```

См. [40-system/data-formats/settlement.md](../40-system/data-formats/settlement.md).

## 3. Логика расхождения суммы

При оформлении продажи через бота возможно расхождение между **расчётной суммой** (по позициям и ценам) и **итоговой суммой по накладной**.

### Правило (актуально по последнему промпту v10 от 11.03.2026)

- **Расхождение ≤ 100 ₽** → принять автоматически (взять нетто из накладной как есть)
- **Расхождение > 100 ₽** → требуется решение

> ⚠️ **Расхождение между документами**: исходный CONTEXT.md (от 26.04) указывал порог **50 ₽**, но реальный промпт бота на VPS уже использует **100 ₽**. Канон — реализация. Зафиксировано при аудите 29.04.

> Порог **100 ₽** — эмпирический, от старого бота. При проектировании Евы можно пересмотреть (например, сделать % от суммы).

## 4. Уведомление при создании нового клиента

Когда в системе появляется **новый клиент** (через бота, через UI, через Еву) — отправить уведомление в Telegram-личку:

- Максиму (chat_id `118206343`)
- Нелли (chat_id `1719753990`, `@Nelli2023N`)

Список chat_id хранится в переменной окружения **`NOTIFY_CHAT_IDS`** в `.env` на VPS. См. [25-integrations/telegram.md](../25-integrations/telegram.md).

## 5. Разовый покупатель (К-025 / `__walk_in__`)

В текущей системе разовые покупатели обрабатываются двумя способами:
- В коде продажи — `clientId: "__walk_in__"`, имя в `saleData.clientName`
- В исторических данных встречается **К-025** как технический "разовый клиент" (этот ID существует в `trade-cat-clients`)

При проектировании Евы важно: разовый клиент = **всегда тип ПС**, не ЗД (он сам пришёл и забрал).
