# Changelog — 2026 Q2

## 2026-05-30 — Реализация Блока 1 фото-инфраструктуры: GAP-018 closed, шаг 3 онбординга 9/9

После архитектурного разбора (запись ниже) этим же днём — **реализован и задеплоен Блок 1**: фото витрин клиентов через Еву + UI в trade_app. Закрывает [GAP-018](../00-meta/gaps.md#gap-018), шаг 3 онбординга закрыт по 9 из 9 полей.

### Что Ева и trade_app умеют к концу дня

1. Менеджер в Telegram идёт в онбординг → после `create_client` Ева автоматически выставляет `session.expectingPhoto = {base: "client-locations", entityId: <новый clientId>}` и просит третьим абзацем: «Если есть фото места доставки — пришли сейчас, одно или несколько. Можно пропустить, написав "без фото"».
2. Менеджер шлёт одно или **несколько** фото (одиночные или альбом). Альбомы буферизуются 700мс по `media_group_id` и грузятся пакетом.
3. Поддерживаются `msg.photo` (сжатое JPEG) и `msg.document` с `image/*` mime (без сжатия, для накладных).
4. Дедуп по `file_unique_id` Telegram: повторное фото → «Это фото уже было — пропускаю».
5. После загрузки Ева подтверждает: «Принял ✅ Витрина / вход клиента — N фото».
6. В trade_app карточка клиента → секция «Фото места доставки» → `<PhotoGallery>` с миниатюрами + lightbox по клику + загрузка из формы (`+` плитка) + удаление (`×` крестик).
7. Endpoint `POST/DELETE /api/photos` на trade-api строго валидирует payload (фикс урока [GAP-019](../00-meta/gaps.md#gap-019) — на новом endpoint молчания при отсутствии полей нет).

### Архитектурное упрощение по ходу реализации

`X-Photo-Token` (зарезервированный при дизайне 2026-05-30) **снят при реализации Блока 1**. Обоснование: бандл фронта публичен, токен в нём — театр безопасности, а не защита; добавление endpoint для раздачи токена браузеру усложняет UX без выгоды. `/api/photos` идёт без auth, симметрично `/api/storage`. После RBAC оба endpoint-а перейдут на JWT.

Соответственно обновлены: ADR-016, photo-infrastructure.md, api.md, deployment.md, glossary.md.

### Совместимость legacy

`locationPhotos[]` ранее проектировался как массив URL-строк (до 2026-05-30). На практике поле было пустым во всех карточках — миграции не требуется. `<PhotoGallery>` нормализует legacy строки в объекты на чтении, поэтому даже если где-то остались URL-строки — они отображаются (без аудит-метаданных), удаление работает только на стороне фронта (на сервере таких записей нет).

## 2026-05-30 — Архитектура фото-инфраструктуры: ADR-016 + 4 базы + сплошной апдейт kb

Сессия разбора архитектуры фото-инфраструктуры под требование Максима: четыре независимых базы фотографий + общий пайплайн + расширяемость на будущие базы. По итогам — ADR + детальный технический документ + сплошная синхронизация смежных доков kb. **Кода в проде не появилось** — это дизайн-сессия; реализация (Блок 1) — в следующей сессии.

### Чем закончились предыдущие итерации

Перед сессией в roadmap (Шаг 3 онбординга) поле 9 «фото места доставки» было заблокировано «фото-инфраструктурой» — единственным **необработанным** требованием перед тестом онбординга менеджерами. GAP-018 в исходной формулировке смешивал «общий пайплайн» и «конкретную базу locationPhotos».

### Что сделано в сессии

**1. Разбито GAP-018 на 4 GAP-а** (по запросу Максима — отдельные GAP под каждую базу фото):
- **GAP-018** переоформлен → «Фото входов на склад/витрины клиентов» (`locationPhotos[]`). Грузит менеджер на онбординге через Еву, потребляет экспедитор при доставке. High prio.
- **GAP-020** новый: «Фото отгрузочных накладных» (привязка к Sale, Ева распознаёт и создаёт Sale).
- **GAP-021** новый: «Фото товаров в карточке SKU».
- **GAP-022** новый: «Фото товаров с закупок (для рассылок клиентам)».

Коммит `5c19c63`.

**2. Архитектура разобрана по 5 слоям** (с Максимом, по очереди):
- **(а) Приём фото из Telegram** — `msg.photo` + `msg.document image/*`, буферизация альбомов по `media_group_id` (700 мс), скачивание в `/tmp/eva/...` при приёме, дедуп по `file_unique_id`, лимит 20 МБ. Каждое фото → нормализованная структура `RawPhoto`. (Коммит `43b5772`.)
- **(б) Хранение на VPS** — `/var/www/trade/photos/<base>/<entityId>/<unixTs>_<fileUniqueId>.<ext>`, Nginx public с непредсказуемыми именами файлов. Запись о фото — массив объектов `photoMeta` (не голых URL) для аудита и дедупа. Удаление физическое (без soft-delete). HEIC и thumbnail — не сейчас. (Коммит `f5f8077`.)
- **(в) Endpoint `/api/photos`** — на trade-api, `POST/DELETE`, multipart, авторизация `X-Photo-Token` (shared secret). **Валидирует payload и не молчит при отсутствии полей** — прямой фикс урока [GAP-019](../00-meta/gaps.md#gap-019). Дедуп по `fileUniqueId` возвращает `200 {duplicate: true}`. Маппинг `PHOTO_BASES` — точка расширения для новых баз. (Коммит `5f2ba69`.)
- **(г) Диспетчер контекста** — общий диспетчер + per-base handlers (`code/eva/src/photo/handlers/<base>.js`). Активный сценарий имеет приоритет (флаг `session.expectingPhoto = {base, entityId}`), иначе — inline-кнопки выбора. Caption игнорируется как сигнал base, но сохраняется в `photoMeta`. (Принципы Р1-Р9.)
- **(д) UI в trade_app** — универсальный компонент `<PhotoGallery>` на все 4 базы (одна реализация — пять секций карточек). Lightbox без библиотек. Загрузка из веб-формы через тот же endpoint (`fileUniqueId` = UUID4 на фронте). `Cache-Control: immutable` 1 год. (Слои г и д — коммит `a2c884a`.)

**3. Финализирована архитектура**:
- Создан **[ADR-016](../90-decisions/ADR-016-photo-infrastructure.md)** «Фото-инфраструктура» с фиксацией решения и отклонёнными альтернативами (S3, прямая запись из Евы, отдельная таблица Photo, JSON+base64, caption-classifier).
- **[40-system/photo-infrastructure.md](../40-system/photo-infrastructure.md)** — детальная техническая спецификация по слоям, переведена в `status: active`.
- Обновлены [INDEX.md](../INDEX.md) и [roadmap](../65-roadmap/current.md).

## 2026-05-27 — Ит.3 Евы: deep-link приглашения + привязка `tgChatId` + notify менеджеру

После закрытия Ит.2 этим же днём — реализован и протестирован **Ит.3** Евы: завод клиента теперь завершается ссылкой-приглашением, клиент жмёт её → Ева привязывает его Telegram к карточке и сообщает менеджеру.

### Что Ева умеет к концу Ит.3

1. При создании клиента генерируется одноразовый `onbToken` (8 байт hex, 14 дней TTL) — хранится прямо на карточке клиента (вариант A из сценария).
2. Инструмент `create_client` возвращает менеджеру **готовую ссылку** `https://t.me/<bot>?start=onb_<token>` в поле `deepLink`. Системный промпт обязывает Еву включить её во второй абзац отчёта.
3. Обработчик `/start onb_<token>` в `index.js`:
   - **Идёт ДО whitelist-проверки** — клиент впервые пишет боту, его `chat_id` в `ALLOWED_CHAT_IDS` не входит. Пропуск разрешён ТОЛЬКО при валидном токене.
   - Ищет клиента по `onbToken`, проверяет срок (`onbTokenExpiresAt`).
   - Проверяет конфликт: один `tgChatId` = один клиент.
   - Записывает `tgChatId` + `tg` (username), гасит токен.
   - Приветствует клиента с прозрачностью ([vision.md](../50-agents/eva/vision.md) п.2): «Здравствуйте, {contactName}! Я Ева, ИИ-помощник Trade Abkhazia».
   - Отправляет notify менеджеру: «✅ {n} ({К-XXX}, контакт {contactName}) принял приглашение, привязан к Telegram».
4. Краевые случаи: токен не найден → «ссылка не действительна»; истёк → «ссылка устарела» + notify менеджеру; конфликт привязки → notify менеджеру с деталями.

## 2026-05-22 — Сценарий онбординга клиента для Евы

Спроектирован первый бизнес-сценарий Евы — [scenarios/client-onboarding.md](../50-agents/eva/scenarios/client-onboarding.md) (status: design). Только дизайн, реализация в коде — отдельная задача.

**Главное:** старый `bot_expeditor` не связывал Telegram-пользователя с клиентом (определял по имени из накладной OCR). Для памяти (слой B) и проактивных напоминаний Евы нужна устойчивая связка `tgChatId ↔ клиент`. Онбординг её устанавливает.

**Поток:** менеджер заводит черновик (`onbStatus=draft`, минимум один проектный блок с `priceLevel`/`saleType` по ADR-014) → копирует deep-link `https://t.me/<eva_bot>?start=onb_<token>` → клиент жмёт Start → Ева резолвит одноразовый токен, пишет `msg.chat.id` в `client.tgChatId`, гасит токен → знакомится с прозрачностью («я Ева, ИИ-помощник») → ненавязчиво наполняет память B (что обычно берёт, ключевые факты; ассортимент в карточку не пишется — derived, ADR-014 У1) → `onbStatus=active` + алерт менеджеру.

**Решения дизайна:**
- Введено поле `onbStatus` (`draft`/`active`/`paused`), миграция на чтении: существующие = `active`.
- `priceLevel` задаёт менеджер в черновике → Ева называет цену по уровню, не нарушая границу «цена новому клиенту → через менеджера» (эскалация остаётся для торга/отклонения от прайса).
- Сегмент/уровень у клиента не выясняются — это решение менеджера.
- Токен: вариант A (поле `onbToken` на карточке, скан через data-API — рекомендован на старте) vs B (таблица `eva_onboarding_tokens` в Postgres Евы). TTL ~14 дней.
- Краевые случаи: устаревший/погашенный токен, конфликт привязки (другой `tgChatId` / тот же chat у другого клиента), повторный Start, **холодный вход** (пишет без deep-link → эскалация менеджеру завести черновик, цены/заявки незнакомцу не оформляет), разовый покупатель онбординг не проходит.

**Что нужно в коде** (зафиксировано в сценарии): поле `onbStatus` + UI-бейдж/фильтр; генерация и показ deep-link в карточке (кнопки «Пригласить»/«Обновить ссылку»); хранение токена; обработчик `/start onb_<token>` в сервисе Евы; инструменты `get_client_by_tgchat`, `bind_tgchat`, `update_client_memory`, `escalate_to_manager`, `notify_manager`.

**Открытые вопросы к Максиму:** username бота Евы, название компании в реплике-представлении, срок жизни токена, нужна ли лёгкая верификация личности, финализация границы полномочий (ADR-013 п. 9).

Обновлены [eva/README.md](../50-agents/eva/README.md), [roadmap](../65-roadmap/current.md).

### Зафиксирована архитектура Евы — ADR-013 (accepted)

Принята общая агентная архитектура Евы как продавца, работающего с клиентом напрямую через Telegram (а не скриптовый бот). Компоненты:

- **Хранилище**: Postgres под данные Евы — поднимается отдельно и **раньше** общей миграции (Шаг 2 ADR-009). Бизнес-данные пока в KV через data-API.
- **Навыки (tools)**: чтение/запись клиентов и заявок (ПС/ЗД/ЗР), баланс, рейсы, остатки, коммуникация, эскалация, память. Принцип: цифры только из инструментов, без выдумок.
- **CRM-слой**: cron-напоминания (рейс/долг/реактивация), дайджест менеджеру, эскалация `escalate_to_manager` с перехватом диалога.
- **UI**: новый модуль «📨 CRM / Переписки» в trade_app (история диалогов + карточка памяти + перехват).
- **Принципы Евы**: живое общение, характер, прозрачность (не маскируется под человека), границы полномочий.

### Принято 4 архитектурных решения

После обсуждения с Максимом четырёх важных замечаний приняты ADR:

- **[ADR-009](../90-decisions/ADR-009-multitenancy-projects.md) — Мультипроектная архитектура.** Новый справочник `trade-cat-projects` с префиксом `PRJ-`. Восемь стартовых проектов (PRJ-001 «Турецкие овощи», PRJ-002 «Местные овощи», PRJ-003 «Грузинские овощи» (старт июнь), PRJ-004..008 — `paused`). `projectId` сквозной в транзакционных сущностях. Справочники в трёх режимах: общие (Client), с `applicableProjects` (Supplier, Staff, Office, Partner), обязательным проектом (через гибрид для SKU). Sale смешанные — `sale.items[].projectId`. Cross-project расходы через `allocation` (by-revenue, by-volume, by-time, manual). Миграция существующих данных → default `PRJ-001`.

- **[ADR-010](../90-decisions/ADR-010-invoice-entity.md) — Сущность Invoice (накладная поставщика).** Префикс `НП-NNNNNN`, storage-ключ `trade-invoices-v1`. Три статуса: `unrecognized` / `recognized` / `cancelled`. Перезалив плохого фото → новая запись + `replacedBy`. Каскадный откат `recognized → cancelled` с двойным подтверждением. `linkedTo` к Trip или Purchase (поддержка закупок вне рейса). Хранение фото в `/var/www/trade/invoices/<supplier>/<year>/`, доступ только через API. Модуль «Накладные» + кнопки в карточках закупок + бейдж нераспознанных. Структура `recognition.corrections[]` подготовлена под обучающие данные для Евы.

- **[ADR-011](../90-decisions/ADR-011-eva-supplier-segmentation.md) — Сегментация знаний Евы по поставщикам.** Двухуровневая база: общий слой `_common/` (грузинский алфавит, универсальные правила, арифметика, OCR-проблемы) + per-supplier `suppliers/<id>/` (профиль, словарь, правила, формат, почерк, цены, эталоны). **Вариант А** (полные локальные базы) — без канонического словаря, дублирование терминов допустимо. Три механизма выбора базы при распознавании: явный выбор → контекст рейса → автоопределение (Этап 2). Правило роста `_common/`: только при подтверждённой одинаковости у ≥2 поставщиков.

- **[ADR-012](../90-decisions/ADR-012-eva-self-learning-plan.md) — Поэтапный план самообучения Евы.** Три этапа: **Этап 1 MVP** (Q3 2026, ~2-3 недели) — Ева делает черновик, человек правит, ничего не идёт в базу автоматически; **Этап 2 полуавтомат** (после ~50 распознанных Invoice) — Ева формирует дайджест предложений на основе паттернов исправлений, человек подтверждает, регрессионный прогон золотого датасета; **Этап 3 автомодерация** — очевидные случаи (новые термины с явной частотой, ценовые диапазоны) автоматически, правила и эвристики остаются ручными.
