- **Дефект 2 — тарные строки.** Поле ввода тарных биндилось на `qtyTar`, а `calcLineTotal`/накладная/баланс используют `qty` → банан/тарные в смешанной корзине считались 0. Фикс: тарные — через `qty` (init + ввод).

## 2026-05-22 — Сценарий онбординга клиента для Евы

Спроектирован первый бизнес-сценарий Евы — [scenarios/client-onboarding.md](../50-agents/eva/scenarios/client-onboarding.md) (status: design). Только дизайн, реализация в коде — отдельная задача.

**Главное:** старый `bot_expeditor` не связывал Telegram-пользователя с клиентом (определял по имени из накладной OCR). Для памяти (слой B) и проактивных напоминаний Евы нужна устойчивая связка `tgChatId ↔ клиент`. Онбординг её устанавливает.

**Поток:** менеджер заводит черновик (`onbStatus=draft`, минимум один проектный блок с `priceLevel`/`saleType` по ADR-014) → копирует deep-link `https://t.me/<eva_bot>?start=onb_<token>` → клиент жмёт Start → Ева резолвит одноразовый токен, пишет `msg.chat.id` в `client.tgChatId`, гасит токен → знакомится с прозрачностью («я Ева, ИИ-помощник») → ненавязчиво наполняет память B (что обычно берёт, ключевые факты; ассортимент в карточку не пишется — derived, ADR-014 У1) → `onbStatus=active` + алерт менеджеру.

**Решения дизайна:**
- Введено поле `onbStatus` (`draft`/`active`/`paused`), миграция на чтении: существующие = `active`.
- `priceLevel` задаёт менеджер в черновике → Ева называет цену по уровню, не нарушая границу «цена новому клиенту → через менеджера» (эскалация остаётся для торга/отклонения от прайса).
- Сегмент/уровень у клиента не выясняются — это решение менеджера.
- Токен: вариант A (поле `onbToken` на карточке, скан через data-API — рекомендован на старте) vs B (таблица `eva_onboarding_tokens` в Postgres Евы). TTL ~14 дней.
- Краевые случаи: устаревший/погашенный токен, конфликт привязки (другой `tgChatId` / тот же chat у другого клиента), повторный Start, **холодный вход** (пишет без deep-link → эскалация менеджеру завести черновик, цены/заявки незнакомцу не оформляет), разовый покупатель онбординг не проходит.

**Что нужно в коде** (зафиксировано в сценарии): поле `onbStatus` + UI-бейдж/фильтр; генерация и показ deep-link в карточке (кнопки «Пригласить»/«Обновить ссылку»); хранение токена; обработчик `/start onb_<token>` в сервисе Евы; инструменты `get_client_by_tgchat`, `bind_tgchat`, `update_client_memory`, `escalate_to_manager`, `notify_manager`.

**Открытые вопросы к Максиму:** username бота Евы, название компании в реплике-представлении, срок жизни токена, нужна ли лёгкая верификация личности, финализация границы полномочий (ADR-013 п. 9).

Обновлены [eva/README.md](../50-agents/eva/README.md), [roadmap](../65-roadmap/current.md).

## 2026-05-22 — Смена фокуса на продажи + архитектура Евы (ADR-013)

Турецкие овощи свёрнуты, распознавание накладных Зазы (GAP-003) понижено в срочности. Фокус — доработка продаж и ИИ-агента Евы в части прямой работы с клиентами.

### Зафиксирована архитектура Евы — ADR-013 (accepted)

Принята общая агентная архитектура Евы как продавца, работающего с клиентом напрямую через Telegram (а не скриптовый бот). Компоненты:
- **Рантайм**: Node.js на VPS, замещает `bot_expeditor`; агентный цикл с инструментами (tool calling), Claude как «мозг».
- **Память — 4 слоя**: A сырые переписки, B память клиента (выжимка, грузится в контекст каждый раз), C общие знания (системный промпт + кэш), D рабочая память диалога.
- **Обучение — 2 контура**: по клиенту (автообновление B) + общее (очередь предложений к C с модерацией человеком, как ADR-012).
- **Хранилище**: Postgres под данные Евы — поднимается отдельно и **раньше** общей миграции (Шаг 2 ADR-009). Бизнес-данные пока в KV через data-API.
- **Навыки (tools)**: чтение/запись клиентов и заявок (ПС/ЗД/ЗР), баланс, рейсы, остатки, коммуникация, эскалация, память. Принцип: цифры только из инструментов, без выдумок.
- **CRM-слой**: cron-напоминания (рейс/долг/реактивация), дайджест менеджеру, эскалация `escalate_to_manager` с перехватом диалога.
- **UI**: новый модуль «📨 CRM / Переписки» в trade_app (история диалогов + карточка памяти + перехват).
- **Принципы Евы**: живое общение, характер, прозрачность (не маскируется под человека), границы полномочий.

### Принято 4 архитектурных решения

После обсуждения с Максимом четырёх важных замечаний приняты ADR:

- **[ADR-009](../90-decisions/ADR-009-multitenancy-projects.md) — Мультипроектная архитектура.** Новый справочник `trade-cat-projects` с префиксом `PRJ-`. Восемь стартовых проектов (PRJ-001 «Турецкие овощи», PRJ-002 «Местные овощи», PRJ-003 «Грузинские овощи» (старт июнь), PRJ-004..008 — `paused`). `projectId` сквозной в транзакционных сущностях. Справочники в трёх режимах: общие (Client), с `applicableProjects` (Supplier, Staff, Office, Partner), обязательным проектом (через гибрид для SKU). Sale смешанные — `sale.items[].projectId`. Cross-project расходы через `allocation` (by-revenue, by-volume, by-time, manual). Миграция существующих данных → default `PRJ-001`.

- **[ADR-010](../90-decisions/ADR-010-invoice-entity.md) — Сущность Invoice (накладная поставщика).** Префикс `НП-NNNNNN`, storage-ключ `trade-invoices-v1`. Три статуса: `unrecognized` / `recognized` / `cancelled`. Перезалив плохого фото → новая запись + `replacedBy`. Каскадный откат `recognized → cancelled` с двойным подтверждением. `linkedTo` к Trip или Purchase (поддержка закупок вне рейса). Хранение фото в `/var/www/trade/invoices/<supplier>/<year>/`, доступ только через API. Модуль «Накладные» + кнопки в карточках закупок + бейдж нераспознанных. Структура `recognition.corrections[]` подготовлена под обучающие данные для Евы.

- **[ADR-011](../90-decisions/ADR-011-eva-supplier-segmentation.md) — Сегментация знаний Евы по поставщикам.** Двухуровневая база: общий слой `_common/` (грузинский алфавит, универсальные правила, арифметика, OCR-проблемы) + per-supplier `suppliers/<id>/` (профиль, словарь, правила, формат, почерк, цены, эталоны). **Вариант А** (полные локальные базы) — без канонического словаря, дублирование терминов допустимо. Три механизма выбора базы при распознавании: явный выбор → контекст рейса → автоопределение (Этап 2). Правило роста `_common/`: только при подтверждённой одинаковости у ≥2 поставщиков.

- **[ADR-012](../90-decisions/ADR-012-eva-self-learning-plan.md) — Поэтапный план самообучения Евы.** Три этапа: **Этап 1 MVP** (Q3 2026, ~2-3 недели) — Ева делает черновик, человек правит, ничего не идёт в базу автоматически; **Этап 2 полуавтомат** (после ~50 распознанных Invoice) — Ева формирует дайджест предложений на основе паттернов исправлений, человек подтверждает, регрессионный прогон золотого датасета; **Этап 3 автомодерация** — очевидные случаи (новые термины с явной частотой, ценовые диапазоны) автоматически, правила и эвристики остаются ручными.
