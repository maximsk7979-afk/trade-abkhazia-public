## 2026-06-06 — fix: белый экран при «Завершить доставку» (CONTRAGENTS не объявлен в DeliveryMod)

Найдено при приёмочном тесте GAP-038 (Максим): нажатие «Завершить доставку» в Д-001 роняло trade_app в белый экран. Причина — **пред-существующий баг**: в `DeliveryMod` (`trade_app_v3.jsx`) при деструктуризации `cat` не была объявлена `CONTRAGENTS`, а модалка расходов доставки использует `CONTRAGENTS.map(...)` (выбор перевозчика/грузчика) → `ReferenceError: CONTRAGENTS is not defined` при открытии модалки. Всплыл сейчас, т.к. завершение доставки впервые реально прогнали на проде.

- **Фикс:** добавлено `CONTRAGENTS = cat.contragents || []` в деструктуризацию `DeliveryMod` (как уже сделано в `TripsMod`/`SettlementsMod`).
- **Развёрнуто** на VPS (бандл `index-BadKYNdi.js`). `esbuild` чист.
- **Приёмочный тест GAP-038 пройден:** ЗР-001 (смешанная корзина Светич) отгружена — `shipmentTotal` 8274 ₽ = помидор 7.7кг×120 + черри 6.2кг×250 + **банан 2×2900** (тарная строка считается, не 0); цены подставились **замороженные** из заявки, не из прайс-листа. GAP-038 подтверждён на проде.

## 2026-06-06 — GAP-038 closed: отгрузка весовых ЗР из мини-аппа (факт-вес + замороженная цена) + роль экспедитора

Замкнуто обещание «точная сумма после взвешивания» для заказов из мини-аппа. Диагностика: механизм факт-веса (взвешивания → нетто) и серверная связка (`shipment/:id` отдаёт `shipmentTotal` или ориентир) **уже были**; мешали два дефекта формы отгрузки `ClientShipmentEditor` (`trade_app_v3.jsx`).

- **Дефект 1 — цена (критичный).** Инициализация `shipment[]` из `items[]` брала цену из прайс-листа (`getDefPrice`), игнорируя **замороженную** согласованную цену `miniOrder.lines[].unitPrice`. У весовых SKU прайс-листовой цены нет → неверная/нулевая сумма. Фикс: `frozenUnitPrice(skuId)` (поддержка корзины v2 и легаси банан/весовой) подставляется приоритетно; поле **редактируемое** (экспедитор может изменить у машины); фолбэк на прайс-лист, если `miniOrder` нет.
- **Дефект 2 — тарные строки.** Поле ввода тарных биндилось на `qtyTar`, а `calcLineTotal`/накладная/баланс используют `qty` → банан/тарные в смешанной корзине считались 0. Фикс: тарные — через `qty` (init + ввод).
- **Решения Максима:** цена замороженная-**редактируемая**; объём — **весовые + банан/тарные**; брак/возврат/нехватка остаются отложенными ([GAP-031](../00-meta/gaps.md#gap-031)/[GAP-032](../00-meta/gaps.md#gap-032)).

- **Обязательство 5/6 (ADR-015) — роль экспедитора (GAP-013 → in-progress):** заведена отдельная **TO-BE роль** [expeditor](../30-roles/to-be/expeditor/README.md) + процесс [отгрузки и доставки](../30-roles/to-be/expeditor/processes/shipment.md) + [должностная инструкция](../80-instructions/for-team/expeditor.md); в [as-is](../30-roles/as-is/README.md) зафиксировано совмещение «менеджер+экспедитор» (по решению Максима — взвешивание **у клиента при выдаче**, работа в обоих интерфейсах: trade_app сейчас, Ева/фото накладной — перспектива). Обновлены [sale.md](../40-system/data-formats/sale.md), [mini-app.md](../40-system/mini-app.md), [order-intake](../30-roles/to-be/sales-manager/processes/order-intake.md), роль менеджера, INDEX, карта ролей.

- **Заказ на день:** экран «На какой день?» (4 кнопки: завтра/+2/+3/+4 с датами; прошедшая отсечка → неактивна). → **единый каталог**: активные SKU, у которых `applicableProjects ∩ проекты клиента ≠ ∅`, секциями **Овощи → Фрукты → Бананы → Прочее**. Клиент с одним проектом «Бананы» видит только бананы.
- **Смешанная корзина:** банан по ящикам (volume-tier по сумме банановых ящиков) + овощи по упаковкам (₽/кг) в одной заявке. `miniOrder.kind` = `mixed`/`weighted`/`banana`.
- **Учётный проект строки — при закупке, не при заказе:** один товар (помидор) бывает из Турции (PRJ-001) или Грузии (PRJ-003); `applicableProjects` — фильтр ассортимента, а не учётная привязка. Per-line `projectId`, FIFO, маржа и **распределение расходов смешанного рейса** отложены («Шаг 3» ADR-009) → [GAP-041](../00-meta/gaps.md#gap-041).
- **Код:** `order-service` (orderDays/cutoffForDate/isDayOpen МСК, `buildMixedCartSale`), `order-model.orderKind` → `mixed`; server `/order-days`, `/day-catalog`, `/order {date,delivery,lines}` (классификация по SKU + ленивый рейс); `notify` многострочный смешанный; мини-апп — экран дня + единый каталог секциями + смешанная корзина (заменил group-menu/banana/weighted потоки).

- `session-state.js` → `messagesFromTail(rows)` (маппинг `out`→assistant / иначе→user; склейка подряд идущих реплик одной роли; срез ведущих assistant, чтобы старт был с user — слой A только текст, пар tool_use/tool_result нет) + `hydrate(chatId, rows)` (наполняет только пустую сессию). `pushMessage` стал merge-aware — чинит границу с живой репликой, если хвост оканчивается на user (рестарт посреди хода), без двух user подряд.
- `index.js`: гидратация в `handleUserInput` **до** `logIncoming` (чтобы текущая реплика не задвоилась), только при пустой сессии и включённой БД. Сбой → старт с чистой сессии, поток не падает.
- Память о клиенте (B) по-прежнему обеспечивает долгую память; D — это краткосрочная непрерывность диалога. Полное состояние сценария (`eva_sessions`) осознанно отложено.
- **Проверки:** юнит-тест `code/eva/test/session-state.test.js` (`npm test`); **сквозная проверка на боевых `eva_messages`** — из чата owner'а (10 сообщений) восстановлена корректная чередующаяся история (старт с user, инварианты API соблюдены), +живая реплика не ломает чередование. ## 2026-06-04 — GAP-019 closed: trade-api валидирует payload POST /api/storage

Закрыта первопричина инцидента 2026-05-27 (Ева перетёрла 33 клиента, послав POST без обёртки `{value}`). До фикса `trade-api` принимал любой body со статусом 200 и при отсутствии `value` писал в колонку `NULL`, **молча стирая ключ**.

Гейт строгий: все легитимные клиенты (фронт, Ева) всегда шлют `value` строкой; для удаления есть `DELETE`.
- **Деплой:** scp + `pm2 restart trade-api` (бэкап `server.js.bak-2026-06-04-gap019`); `/api/health` зелёный.
- **Acceptance (curl, 8 проверок на одноразовом ключе):** валидный POST → 200, значение записано; POST без `value` / `value:null` / пустое тело → 400 и существующее значение **не стёрто** (ключевая проверка — раньше тут была тихая потеря); DELETE чистит ключ. Боевые данные не затронуты.
- [api.md](../40-system/api.md) обновлён: «не валидирует» → «валидирует», пример «неправильно» теперь → 400. Клиентский фикс Евы (`storage-api.js`) остаётся как defense-in-depth.

## 2026-06-04 — GAP-024: обогащение памяти клиента (слой B) из истории продаж

## 2026-05-31 — GAP-030: архитектурный гейт инструментов по роли (изоляция данных)

Заложен фундамент изоляции данных клиента ([ADR-018](../90-decisions/ADR-018-eva-universal-assistant.md) §6, коммит `f45da75`) — до открытия Евы клиентам (Шаг 4). Защита **по конструкции**, не «по инструкции».

- **Двухслойный гейт** в `code/eva/src/tools/index.js`. У каждого инструмента уровень `access`:
  - `staff` — только owner/manager (внутренние: онбординг, справочники);
  - `client` — доступен клиенту, **обязан фильтровать выдачу по `ctx.clientId`**;

## 2026-05-31 — Архитектура памяти и универсального помощника Евы: ADR-017, ADR-018, 8 GAP

Детальная проектная сессия с Максимом. Закрыты все открытые вопросы по архитектуре памяти Евы (поднятые 2026-05-30) и принято стратегическое решение об объёме Евы как помощника. Кода не трогали — наполнение базы знаний решениями, чтобы не потерять между сессиями.

### Приняты 2 ADR

- **[ADR-017](../90-decisions/ADR-017-eva-memory-architecture.md) — архитектура памяти (слои A–D, финал):**
  - **A** (сырые переписки) — устраивает; нужен веб-UI чтения ([GAP-023](../00-meta/gaps.md#gap-023)).
  - **B** (память клиента) — **два блока**: «О человеке» (`address_form`, `personal_facts`, `interests`, `comm_profile`, `life_context`, `person_summary`, `important_dates`) и «О работе» (`assortment`, `order_rhythm`, `payment_behavior`, `delivery_prefs`, `price_sensitivity`, `quality_expectations`, `special_terms`, `client_value`, `business_summary`). Наполняет **Ева ночным cron-проходом** из A + данных системы; грузится в контекст целиком; человек правит. Долг — живьём, ассортимент — выжимкой. Не дублирует карточку.
  - **C** (общие знания) — **фиксированный, человеко-курируемый** (Ева сама не пишет, только предлагает в `eva_learning_queue`). Товары — наизусть в промпт, цифры — всегда инструментом. + навыки «психология» и «продажи».

  - Ева — **полноценный помощник + интернет** (web-search). Граница off-topic — **характером** («занятый друг»: помогает коротко, крупные задачи мягко отклоняет) + **дешёвая модель** (Haiku — болтовня, Sonnet — торговля); техлимит — только аварийный бэкстоп. Чувствительные темы — с оговоркой. Обязателен алерт бюджета Bedrock ([INC-001](../75-incidents/INC-001-bot-anthropic-balance.md)).
  - **Изоляция данных клиента (критично):** клиент видит только своё; данные других клиентов и внутренняя экономика (закупки, маржа, обороты, поставщики) — **табу**. Защита архитектурная (инструменты отдают только данные текущего клиента) + гейт по роли собеседника + промпт. Стоимость: инфраструктура ~0 прироста, переменная ~$150–300/мес при текущем размере, управляемая.

Это фундамент под слой B (память клиента), CRM-модуль и обучение. Один из 5 пунктов Ит.4; остальные (характер из vision, краевые случаи, notify) — впереди.

### Что сделано

Два новых модуля в `code/eva/src/`:
- **`db.js`** — пул `pg` к БД `eva` (Postgres 14.22 на VPS, поднята 2026-05-22). Конфиг из `.env` (`EVA_PG_*`). **Мягкая деградация:** нет креды → пул не создаётся, `message-log` тихо отключает запись, бот работает без архива. `init` / `query` / `healthcheck` / `isEnabled` / `end`.
- **`message-log.js`** — `logIncoming` / `logOutgoing`, оба **fire-and-forget** (ошибки логируются, но не пробрасываются в поток бота — БД не на критическом пути ответа клиенту). Резолвер `resolveIdentity(chatId)` определяет автора с TTL-кешем 60с:
  - есть в `trade-cat-staff` → `owner` (если в roles) или `manager`, `client_id`=NULL;
  - есть в `trade-cat-clients` по `tgChatId` → `client` + его `К-XXX`;
  - иначе → `client` без id.
  - `invalidate(chatId)` сбрасывает кеш после привязки клиента (deep-link), чтобы приветствие логировалось уже как клиент.

Проводка в `index.js` — точки на границе Telegram:

| Событие | direction | author | примечание |
|---|---|---|---|
| Текст менеджера / выбор inline-кнопками | `in` | manager/owner | `meta.source` = text / button / multi-button |
| `/start onb_<token>` (активация клиента) | `in` | client | пре-whitelist, легитимный первый контакт |
| Входящее фото/документ-картинка | `in` | manager | `body`=«[фото]», детали в `meta` |
| `/reset`, `/start` | `in` | manager | `meta.command`=reset |
| Любой ответ Евы (`safeSend`) | `out` | eva | единый choke-point |
| Notify менеджеру | `out` | eva | `meta.aboutClient`=К-XXX |

**Защита от шума:** отказы неавторизованным/сканерам идут с `skipLog: true` и в архив не попадают; входящие логируются только для авторизованных (на текущих итерациях беседуют только менеджеры из whitelist, клиент — лишь разовая активация по deep-link).

### Что произошло

1. Максим прогнал онбординг «Импульс/Анна» (23.05 в 11:20 по логам pm2). Ева дошла до финала, инструмент `create_client` отчитался `ok:true`, сохранил К-034.

## 2026-05-23 — Поля `contactName`/`onbStatus` в карточке клиента + уникальность `n` (Шаг 3 онбординга)

## 2026-05-22 — Сценарий онбординга клиента для Евы

Спроектирован первый бизнес-сценарий Евы — [scenarios/client-onboarding.md](../50-agents/eva/scenarios/client-onboarding.md) (status: design). Только дизайн, реализация в коде — отдельная задача.

**Главное:** старый `bot_expeditor` не связывал Telegram-пользователя с клиентом (определял по имени из накладной OCR). Для памяти (слой B) и проактивных напоминаний Евы нужна устойчивая связка `tgChatId ↔ клиент`. Онбординг её устанавливает.

**Поток:** менеджер заводит черновик (`onbStatus=draft`, минимум один проектный блок с `priceLevel`/`saleType` по ADR-014) → копирует deep-link `https://t.me/<eva_bot>?start=onb_<token>` → клиент жмёт Start → Ева резолвит одноразовый токен, пишет `msg.chat.id` в `client.tgChatId`, гасит токен → знакомится с прозрачностью («я Ева, ИИ-помощник») → ненавязчиво наполняет память B (что обычно берёт, ключевые факты; ассортимент в карточку не пишется — derived, ADR-014 У1) → `onbStatus=active` + алерт менеджеру.

**Решения дизайна:**
- Введено поле `onbStatus` (`draft`/`active`/`paused`), миграция на чтении: существующие = `active`.
- `priceLevel` задаёт менеджер в черновике → Ева называет цену по уровню, не нарушая границу «цена новому клиенту → через менеджера» (эскалация остаётся для торга/отклонения от прайса).
- Сегмент/уровень у клиента не выясняются — это решение менеджера.
- Токен: вариант A (поле `onbToken` на карточке, скан через data-API — рекомендован на старте) vs B (таблица `eva_onboarding_tokens` в Postgres Евы). TTL ~14 дней.
- Краевые случаи: устаревший/погашенный токен, конфликт привязки (другой `tgChatId` / тот же chat у другого клиента), повторный Start, **холодный вход** (пишет без deep-link → эскалация менеджеру завести черновик, цены/заявки незнакомцу не оформляет), разовый покупатель онбординг не проходит.

**Что нужно в коде** (зафиксировано в сценарии): поле `onbStatus` + UI-бейдж/фильтр; генерация и показ deep-link в карточке (кнопки «Пригласить»/«Обновить ссылку»); хранение токена; обработчик `/start onb_<token>` в сервисе Евы; инструменты `get_client_by_tgchat`, `bind_tgchat`, `update_client_memory`, `escalate_to_manager`, `notify_manager`.

**Открытые вопросы к Максиму:** username бота Евы, название компании в реплике-представлении, срок жизни токена, нужна ли лёгкая верификация личности, финализация границы полномочий (ADR-013 п. 9).

Обновлены [eva/README.md](../50-agents/eva/README.md), [roadmap](../65-roadmap/current.md).

Принята общая агентная архитектура Евы как продавца, работающего с клиентом напрямую через Telegram (а не скриптовый бот). Компоненты:

- **Память — 4 слоя**: A сырые переписки, B память клиента (выжимка, грузится в контекст каждый раз), C общие знания (системный промпт + кэш), D рабочая память диалога.
- **Обучение — 2 контура**: по клиенту (автообновление B) + общее (очередь предложений к C с модерацией человеком, как ADR-012).
- **Хранилище**: Postgres под данные Евы — поднимается отдельно и **раньше** общей миграции (Шаг 2 ADR-009). Бизнес-данные пока в KV через data-API.
- **Навыки (tools)**: чтение/запись клиентов и заявок (ПС/ЗД/ЗР), баланс, рейсы, остатки, коммуникация, эскалация, память. Принцип: цифры только из инструментов, без выдумок.
- **CRM-слой**: cron-напоминания (рейс/долг/реактивация), дайджест менеджеру, эскалация `escalate_to_manager` с перехватом диалога.
- **UI**: новый модуль «📨 CRM / Переписки» в trade_app (история диалогов + карточка памяти + перехват).
- **Принципы Евы**: живое общение, характер, прозрачность (не маскируется под человека), границы полномочий.

### Принято 4 архитектурных решения

- **[ADR-009](../90-decisions/ADR-009-multitenancy-projects.md) — Мультипроектная архитектура.** Новый справочник `trade-cat-projects` с префиксом `PRJ-`.
