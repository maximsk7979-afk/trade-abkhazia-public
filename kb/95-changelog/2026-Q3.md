## 2026-07-04 (вечер) — ADR-027 Этап 1б: веб-формы «Касса» и «Расчёты» переведены на движок

Все ПЯТЬ поверхностей записи финопераций теперь идут через одну точку (/api/fin/op|cancel):
мини-касса (1а), мини-«Расчёты» закупщика (1а), веб-«Касса», веб-«Расчёты», бэкфиллы (обязаны
использовать движок). Изменения:

- **Веб-«Касса» (saveMov):** все ветки со сборкой комплектов на фронте УДАЛЕНЫ — форма
  выбирает операцию реестра (pay_supplier/pay_partner/client_payment/staff_bonus/
  expense_paygo/pay_contragent/expense_model_b/transfer/exchange), комплект строит сервер.
  Легаси-путь остался ТОЛЬКО для приходов без стороны и капитала (группы 3–4 реестра, Этап 2).
- **Веб-«Расчёты» (saveOp):** новые оплаты — через движок (статья контрагента — из привязки
  карточки); warehouse-оплаты и начисления/возмещения — старый путь до Этапа 2.
  **Операции движка неизменяемы**: правка = сторно комплектом + новая (форма подсказывает).
- **Сторно из обеих форм:** запись с finOpId удаляется КОМПЛЕКТОМ через /api/fin/cancel —
  независимо от того, с какой записи комплекта кликнули. Записи до движка — прежний
  каскад (refId + payGo-пара).
- **Фронт-хелперы finOp/finCancel:** применяют документы ответа сервера в state напрямую
  (batch-POST для них больше не выполняется — сервер уже записал транзакцией).
- **Приёмка (боевая, скрипты в scripts/accept/):** 7 кейсов с параметрами веб-форм, вкл.
  бэкдейтинг date — проведение → сторно → откат к базе бит-в-бит ✓; fail-closed капитала ✓;
  валидации движка отбили неверные ID (валюта поставщика, привязка payGo) ✓.
- Нюанс, найденный при самопроверке ДО деплоя: capital_withdrawal/dividend (out, без P&L)
  нельзя было слать в expense_model_b — оставлены на легаси-пути до операций капитала Этапа 2.

## 2026-07-04 — ADR-027: финансовый операционный движок (Этап 0 + Этап 1а) — конец «заплаток»

**Контекст (вопрос владельца):** серия багов-полузаписей показала — ADR-025 выполнен для чтения, но НЕ для записи: комплект «что создаёт операция» жил в 4 местах. Решение владельца: программа ADR-027, CC — постановщик/контролёр.

**Этап 0 (инвентаризация двойным проходом — вручную + независимый агент, списки сверены):** 15 write-эндпоинтов; 4 сборки пары «settlement+нога»; Ева не пишет (проверено); +2 живые дыры найдены сверкой (мини `buyer/supplier-op` без ноги — источник 10 июньских; браузерная ЗК без ноги — источник ЗК-006); мёртвый код addSP. [ADR-027](../90-decisions/ADR-027-fin-ops-engine.md) + [реестр операций v1](../20-domain/financial-reporting/fin-ops-registry.md) (21 операция × матрица 4 плоскостей × сторно × роли) — утверждены владельцем. Решения: брак от поставщика — деньгами и зачётом (замена товаром исключена); компенсация клиенту — зачётом без денег (P&L-плоскость — разбор в Этапе 2).

**Этап 1а (реализация):**
- **`fin-ops-service.js`** — реестр 9 операций (pay_supplier/contragent/partner, expense_paygo, expense_model_b, staff_bonus, client_payment, transfer, exchange): комплекты по 4 плоскостям, строгий овердрафт, fail-closed (нет операции/валидации → отказ, полузапись невозможна), каждый документ помечен `finOpId`. +10 юнит-тестов (таблица истинности).
- **Сервер:** `executeFinOp`/`cancelFinOp` — ОДНОЙ транзакцией; журнал **`fin_ops_log`** (кто/когда/что/каким комплектом — аудит + источник сторно); `POST /api/fin/op`, `POST /api/fin/cancel` (повторное сторно — идемпотентный 409). Ролевые гейты по реестру для мини-акторов.
- **Мини-касса → обёртки движка** (гейт «свой кошелёк» + notify; комплекты больше не дублируются). **Обе дыры закрыты:** supplier-op закупщика платит через движок (нога из его кошелька по валюте, fail-closed без кошелька); браузерная ЗК с оплатой — отказ с отсылкой в «Расчёты».
- **Боевая приёмка:** все 10 операций через `/api/fin/op` — проведение → сверка плоскостей (поставщики/контрагенты/кошельки/P&L) → сторно → повторное сторно (отказ) → **откат к базе бит-в-бит** ✓.
- Инцидент разработки: первая замена мини-обработчиков вырезала соседние эндпоинты (замечено git diff-контролем ДО деплоя, откат + точные границы) — процессный урок: diff-ревью обязательно после блочных правок.

**Дальше:** Этап 1б — перевод веб-форм «Касса»/«Расчёты» на `/api/fin/op|cancel` (delMov/delOp через `finOpId`); Этап 2 — возвраты за брак (по решениям), обмен-событие (GAP-059), капитал.

## 2026-07-02 — Ретро-усышка распроданных весовых (реклассификация COGS→B2) + проведён баклажан

**Запрос владельца:** списать усышку баклажана (+23 кг в сверке), но в «Усышке» его нет — остаток 0. Решение: модуль дополнен **ретро-усышкой** для распроданных весовых с кг-хвостом товарооборота.

**Бухгалтерская суть:** у распроданных партий стоимость уже целиком в COGS (весовые списываются по книжному весу партии) → списать хвост «сверху» = двойной счёт. Ретро-проводка — **отчётная реклассификация**: строка `retro:true` в СПИС-записи попадает в B2 (через totalCost) и **вычитается из COGS** той же суммой (`pnl-service` → `retroShrinkageReclass`, `shrinkage-service.retroReclass`). Конверсация тождественна по построению: **чистая прибыль не меняется**, валовая очищается, усышка видима строкой. Стоимость кг = средневзвешенный ₽/кг закрытых партий SKU. Излишек (dNetto<0) — контра. Признание — периодом проводки (стандартная коррекция текущим периодом).

**⚠️ Боевой урок (первая реализация откатана):** вариант «уменьшать `nettoOrig` закрытых партий → живой COGS пересчитается» на бою СЛОМАЛ конверсацию (COGS −971 вместо −2 780, чистая −1 809): живой COGS цепочек «погрузка→возврат→перепродажа» опирается на **снимки возвратных партий** — правка родителя доходит не до всех потребителей. Проводка откатана вручную (nettoOrig восстановлены из pre-audit снимка byte-exact, P&L вернулся до копейки), механика переделана на чистую отчётную контру **без мутации партий**. Вывод в копилку ADR-025: ретро-правки живого COGS через партии небезопасны при возвратных цепочках.

**Реализовано:** `computeRetroShrinkage` (без мутаций) + `retroReclass` в `shrinkage-service.js`; retro-строки в `POST /api/v2/shrinkage` (совместимо с обычными в одной проводке; whop `netto` со знаком закрывает кг-хвост сверки); `pnl-service` — `cogsNet −= retroReclass` + коррекция `byProduct`; фронт — секция **«📉 Распроданные весовые»** во вкладке «Склад → ✂️ Усышка» (кг-хвост из `/api/turnover`, предзаполнение). Тесты: shrinkage 7→11, pnl 9 — зелёные. Бандл `index-GQxxFizX.js`.

## 2026-07-01 — Фикс KPI «Продажи»: долг сведён с «Расчётами» (единый калькулятор)

**Симптом (аудит по двум снимкам владельца):** вкладка «Продажи» показывала долг **636 607,9 ₽**, вкладка «Расчёты → Клиенты» — **190 468,9 ₽**. Расхождение **446 139,0 ₽**.

**Аудит на боевых данных (свёл до рубля):** правильное число — **190 468,9** (канон `balance-service`, GAP-058). KPI-карточки «Продажи» (Выручка/Оплачено/Долг) — отдельный расчёт, разошедшийся с каноном (дрейф ADR-025). Две причины:
1. **394 955,0 ₽** — «Оплачено» считалось только по журналу `settlements` и НЕ включало `saleData.paid`. Оплаты разовых (`__walk_in__`) лежат именно там (settlement для walk-in не создаётся) → разовые выглядели неоплаченными.
2. **51 184,0 ₽** — в «Выручку» попадали **отменённые** продажи (5 шт: ПС-038/039/091/116/122), которые `balance-service` исключает.
394 955,0 + 51 184,0 = 446 139,0 (точно).

**Фикс** (`trade_app_v3.jsx`, SalesMod, KPI-блок): (а) отменённые исключены из выручки; (б) «Оплачено» = `salePaid` продажи (`saleData.paid` у sale-direct / `shipmentPaid` у заявок) + платежи/возмещения из `settlements` — как в `balance-service`. Проверка на боевых данных: Выручка 2 295 101,9 − Оплачено 2 104 633,0 = **Долг 190 468,9** = «Расчёты» ✓. Только отображение — продовые данные не менялись.

**Аудит Евы и мини-аппа (по запросу владельца):** подтверждено — баланс/долг везде через единый `balance-service` (Ева по HTTP `/api/client/:id/summary`; мини-апп `clientBalance`/`clientsRoster`; админка «Расчёты» — тоже). **Двойного учёта оплат нет**: walk-in → только `saleData.paid`, именованный → только settlement; поля не пересекаются, откат оплат синхронизирован. Единственный неканон — этот KPI «Продажи» — устранён.
