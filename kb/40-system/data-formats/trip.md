# Trip — JSON-формат рейса

Рейс (`Р-NNN`) — поставка товара из Грузии: контейнер закупки (позиции, поставщики, курс) + после прибытия — источник складских партий (FIFO). Документ описывает структуру; **жизненный цикл/переходы статусов** детально — частично [GAP-001](../../00-meta/gaps.md#gap-001).

## Storage

- Ключ: `trade-trips-v8`
- JS-константа: `SK_T`
- Содержимое: массив объектов

## Формат

```json
{
  "id": "Р-012",
  "date": "2026-06-08",
  "arrDate": "2026-06-10",
  "status": "Планируется",
  "projectId": "PRJ-004",
  "officeId": "О-001",
  "rate": "34.3",
  "ourWeight": "",
  "orderCutoffAt": "",
  "orderCapacity": "",
  "mixed": false,
  "partners": [{ "name": "Лия", "weight": "" }],
  "expenses": [{ "key": "transport", "amount": "", "cur": "RUB" }],
  "supplierPayments": [{ "supId": "П-005", "amount": "12000", "paidBy": "Мы" }],
  "items": [
    {
      "supId": "П-005",
      "prodId": "Т-028",
      "skuId": "SKU-028-01",
      "qty": "100",
      "price": "55",
      "pu": "тару",
      "fw": "",
      "tc": ""
    }
  ],
  "cm": "",
  "history": [{ "from": "—", "to": "Планируется", "at": "2026-06-08 10:00:00" }]
}
```

## Поля рейса

| Поле | Тип | Фаза | Описание |
|---|---|---|---|
| `id` | string | — | `Р-NNN` |
| `date` | string | 1 | Дата создания/закупки (YYYY-MM-DD) |
| `arrDate` | string | 1→2 | Дата прибытия/доставки. Для ADR-021-рейсов = день доставки клиенту |
| `status` | string | — | Статус: `Планируется` / `В закупке` / `В пути` / `На складе` / `Закрыт` (`T_ST`) |
| `projectId` | string | 1 | Проект ([ADR-009](../../90-decisions/ADR-009-multitenancy-projects.md)). Банан — `PRJ-004`. `""`+`mixed:true` — смешанный ADR-021 |
| `officeId` | string | 1 | Склад прибытия |
| `rate` | string | 1 | **Курс в формате «GEL за 1000 ₽»** (напр. `34.3`). В расчёте: `rateRUBperGEL = 1000 / rate`. Применяется к себестоимости в Фазе 2; долг поставщику остаётся в GEL |
| `ourWeight` | string | 2 | Наш вес в рейсе (для деления расходов с партнёром по весу) |
| `orderCutoffAt` | string | сейл | Отсечка приёма заявок (для рейсов-поверхностей заказа). **Для закупочного рейса PRJ-004 не нужен** |
| `orderCapacity` | string | сейл | Вместимость в ящиках (лимит заявок). Для банана-поставки не нужен |
| `mixed` | bool | — | Смешанный ежедневный рейс ([ADR-021](../../90-decisions/ADR-021-daily-mixed-trips-day-order.md)); может иметь `auto:true` (ленивое авто-создание) |
| `partners` | array | 1/2 | Доли партнёров `{name, weight}` (Лия). Банан — обычно **пусто** |
| `expenses` | array | 2 | Расходы рейса по типам (транспорт, растаможка…). Распределяются по весу в Фазе 2 |
| `supplierPayments` | array | 1 | Платежи поставщикам `{supId, amount (₾), paidBy}` |
| `items` | array | 1 | Позиции закупки (см. ниже) |
| `cm` | string | — | Комментарий |
| `history` | array | — | Переходы статусов `{from, to, at}` |

## Позиция закупки (`items[]`)

| Поле | Тип | Описание |
|---|---|---|
| `supId` | string | **Поставщик позиции** (`П-NNN`). Привязка per-position, не на рейс целиком — в одном рейсе допустимы разные поставщики. Банан → `П-005` (Рамаз) |
| `prodId` | string | Товар (`Т-NNN`). Банан FP → `Т-028` |
| `skuId` | string | Упаковка (`SKU-NNN-NN`). Банан FP → `SKU-028-01` |
| `qty` | string | Количество (ящиков для тарных, кг для весовых) |
| `price` | string | Закупочная цена **в лари (GEL)**: за ящик (если `pu="тару"`) или за кг (если `pu="кг"`) |
| `pu` | string | Единица цены: `"тару"` (за упаковку) или `"кг"` (за вес). Банан — `"тару"` |
| `fw` | string | Фактический вес (кг), если отличается от теоретического `qty × gw` |
| `tc` | string | Стоимость тары в лари (опционально) |
| `mpId` | string | **Только для «Рынок (наличные)» П-001** (`cashMarket`): id рыночной закупки (`MP-1`, `MP-2`…) — каждая закупка у отдельного рыночного продавца помечается своей группой, чтобы не сливались. У обычных поставщиков поля нет. |

Сумма позиции (в ₾): `pu="тару"` → `qty × price + qty × tc`; `pu="кг"` → `вес × price + qty × tc`.

## Расчёты с поставщиком (по рейсу)

`calcTrip` строит `supBal[supId] = { charged, paid }` (в GEL): `charged` = сумма позиций поставщика, `paid` = сумма его `supplierPayments`. Долг = `charged − paid`. Глобально агрегируется через канонический `buyer-service.supplierLedger` (рейсы + закупки `ЗК-` + ручные `settlements`; GAP-058). См. [pricing.md](../../20-domain/pricing.md) (себестоимость) и роль [закупщика](../../30-roles/to-be/buyer/README.md).

**«Рынок (наличные)» (П-001, флаг `cashMarket`) — разовый наличный поставщик** (по аналогии с разовым покупателем walk-in, 2026-06-19): закупки за наличные у РАЗНЫХ рыночных продавцов. Каждая закупка — отдельная самозакрывающаяся запись (группа `mpId`): позиции **добавляются** (не заменяют прошлые), оплата фиксируется **100% наличными сразу** в `supplierPayments[{supId, mpId, amount, cash:true}]` → начислено=оплачено, **баланс 0**. `supplierLedger` для `cashMarket`-поставщика отдаёт операции **по группам `mpId`** (товар/сумма/дата раздельно), а не одной суммой. Оплата вводится **внизу окна закупки** мини-аппа (как при продаже покупателю) — для обычных поставщиков это поле опционально (частичная/полная оплата при закупке → `supplierPayments`).

## Граница Фазы 1 / Фазы 2

- **Фаза 1 (закупка):** `items[]` с `supId`/`price`/`qty`, `rate`, `supplierPayments[]`.
- **Фаза 2 (доставка/оприходование):** на статусе **«На складе»** — диалог приёмки (факт-кол-во `qtyFact` в `item.acceptance`), распределение `expenses` по весу, расчёт себестоимости ящика, создание **FIFO-партий** ([batch.md](./batch.md)).
