# Sale — JSON-формат продажи в `app_storage`

> Логическая модель: см. [20-domain/data-model/entities.md](../../20-domain/data-model/entities.md).
> Бизнес-правила: см. [20-domain/sales.md](../../20-domain/sales.md).
> Канонизация модели: см. [ADR-007](../../90-decisions/ADR-007-sales-canonical-model.md).

## Storage

- Ключ: `trade-sales-v1`
- JS-константа: `SK_SALES`
- Содержимое: массив объектов
- Сохраняется через `POST /api/storage/trade-sales-v1` (атомарная замена всего массива)

## Одна сущность, три разновидности

Все продажи хранятся в **одном** массиве. Тип отличает поле `type`:

| `type` | Префикс ID | Что значит |
|---|---|---|
| `sale-direct` | ПС-XXX | Продажа со склада (клиент сам забрал) |
| `order-stock` | ЗД-XXX | Доставка с нашего склада |
| `order-trip` | ЗР-XXX | Под рейс (товар привезут из Грузии) |

На бизнес-языке: запись со `status !== "Отгружено"` называется **"заявкой"**, после `"Отгружено"` — **"продажей"**.

## Общие поля для всех типов

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| `id` | string | да | ID с префиксом ПС/ЗД/ЗР |
| `type` | string | да | `sale-direct` / `order-stock` / `order-trip` |
| `date` | string | да | Дата `YYYY-MM-DD` |
| `clientId` | string | да | Ссылка на клиента (К-XXX) или `__walk_in__` для разового |
| `tripId` | string | для ЗР | Ссылка на рейс Р-XXX (для ЗР) или `""` |
| `deliveryId` | string | для ЗД/ЗР | Ссылка на доставку Д-XXX или `""` |
| `officeId` | string | да | Офис/склад О-XXX (по умолчанию О-001) |
| `managerId` | string | нет | Менеджер продаж С-XXX (берётся из карточки клиента) |
| `status` | string | да | Статус из жизненного цикла |
| `cm` | string | нет | Свободный комментарий |
| `history` | array | да | История смен статуса: `[{from, to, at}]` |
| `shipmentPhotos` | array | нет | Массив объектов `photoMeta` — фото **отгрузочных** накладных (база `shipments` фото-инфраструктуры, [ADR-016](../../90-decisions/ADR-016-photo-infrastructure.md)). Загружает экспедитор/менеджер во время доставки через Еву; Ева распознаёт накладную и создаёт/обновляет эту запись Sale ([GAP-020](../../00-meta/gaps.md#gap-020)). Не путать с **входящими** накладными от поставщиков ([ADR-010](../../90-decisions/ADR-010-invoice-entity.md), Слой В) |

## ПС (sale-direct) — формат

Дополнительные поля **только** для `sale-direct`:

```json
{
  "id": "ПС-001",
  "type": "sale-direct",
  "date": "2026-04-28",
  "clientId": "К-007",
  "tripId": "",
  "deliveryId": "",
  "officeId": "О-001",
  "managerId": "С-XXX",
  "status": "Отгружено",
  "cm": "",
  "history": [
    {"from": "—", "to": "Новая", "at": "2026-04-28 10:15:00"},
    {"from": "Новая", "to": "Отгружено", "at": "2026-04-28 10:15:00"}
  ],
  "saleData": {
    "lines": [
      {"prodId": "Т-001", "skuId": "SKU-001-02", "qty": "", "qtyTar": "5", "wBrutto": "32.5", "price": "260"}
    ],
    "paid": "5000",
    "clientName": ""
  }
}
```

| Поле | Описание |
|---|---|
| `saleData.lines[]` | Отгруженные позиции |
| `saleData.paid` | Сумма оплаты от клиента (строкой) |
| `saleData.clientName` | Имя для разовых клиентов (когда `clientId === "__walk_in__"`) |

**Сумма продажи не хранится** — вычисляется на лету: `Σ qty × price` по строкам.

## ЗД (order-stock) и ЗР (order-trip) — формат

ЗД и ЗР используют **двухшаговую модель**: заявка `items[]` → отгрузка `shipment[]`.

```json
{
  "id": "ЗР-001",
  "type": "order-trip",
  "date": "2026-04-28",
  "clientId": "К-007",
  "tripId": "Р-001",
  "deliveryId": "Д-001",
  "officeId": "О-001",
  "managerId": "С-XXX",
  "status": "Отгружено",
  "cm": "",
  "history": [
    {"from": "—", "to": "Новая", "at": "..."},
    {"from": "Новая", "to": "В закупке", "at": "..."},
    {"from": "В закупке", "to": "В пути", "at": "..."},
    {"from": "В пути", "to": "На складе", "at": "..."},
    {"from": "На складе", "to": "В доставке", "at": "..."},
    {"from": "В доставке", "to": "Отгружено", "at": "..."}
  ],

  "items": [
    {"prodId": "Т-001", "skuId": "SKU-001-02", "qtyReq": "10", "itemSt": "ok"}
  ],

  "shipment": [
    {"prodId": "Т-001", "skuId": "SKU-001-02", "qty": "", "qtyTar": "10", "wBrutto": "70.0", "price": "260", "netto": "65.0"}
  ],
  "shipmentTotal": 18200,
  "shipmentPaid": 18200
}
```

### Поле `items[]` — заявка клиента (что попросил)

Заполняется при создании заявки.

| Поле | Описание |
|---|---|
| `prodId` | Товар (Т-XXX) |
| `skuId` | SKU |
| `qtyReq` | Запрошенное количество (строкой) |
| `itemSt` | Статус позиции: `ok` / `partial` / `none` (что доступно к закупке/отгрузке) |

### Поле `shipment[]` — фактическая отгрузка (что отдали)

Заполняется в момент доставки экспедитором.

| Поле | Описание |
|---|---|
| `prodId` | Товар |
| `skuId` | SKU |
| `qty` | Кол-во штук (для тарных товаров) |
| `qtyTar` | Кол-во ящиков (для весовых товаров) |
| `wBrutto` | Брутто-вес (для весовых) |
| `price` | Цена |
| `netto` | Нетто-вес (для весовых) |

### Финальные поля по факту отгрузки

| Поле | Описание |
|---|---|
| `shipmentTotal` | Итоговая сумма отгрузки (число, не строка) |
| `shipmentPaid` | Оплачено клиентом по факту получения (число, не строка) |

Заполняются автоматически при переходе статуса в "Отгружено" функцией `completeClient` (см. код `trade_app_v3.jsx`, ~стр. 12939).

## Различение "запрошено vs отгружено"

Это **сознательная часть модели** — для ЗД/ЗР важно сохранять оба набора:

- `items[]` — память о том, что клиент **изначально хотел**
- `shipment[]` — факт того, что **получил**

Часто они **отличаются**:
- Клиент попросил 10 ящиков, привезли 8 (товара меньше у поставщика)
- Клиент попросил помидоры, в свободном объёме оказались огурцы — добавили "допродажей"

Объединение этих наборов **отклонено** в [ADR-007](../../90-decisions/ADR-007-sales-canonical-model.md).

## Особенности сериализации

- **Числа хранятся строками**: `"qty":"5"`, `"price":"260"`. Парсятся через `parseFloat || 0` (хелпер `pN(s)`).
- **Исключение**: `shipmentTotal` и `shipmentPaid` хранятся как **числа**, не строки.
- **Даты**: `YYYY-MM-DD` (без времени).
- **Время в `history`**: `YYYY-MM-DD HH:MM:SS`.
- **Тарные товары** (tp=1): заполняется `qty`, `qtyTar=""`, `wBrutto=""`.
- **Весовые товары** (tp=0): `qty=""`, заполняется `qtyTar` и `wBrutto`.

## Атомарность и race conditions

⚠️ POST `/api/storage/trade-sales-v1` переписывает **весь массив** целиком. При параллельной записи двумя источниками (фронт + Ева) возможна race condition: поздний writer перезапишет промежуточный результат.

Это известное ограничение текущей KV-схемы. См. [40-system/database/overview.md](../database/overview.md).
